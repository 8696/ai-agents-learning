### `coach complete` 勾前必须先报

勾 ✅ 前按**顺序硬定**跑完 **过关检查 1 → 2 → 3**。任一不过 → **STOP**，不准勾 ✅，不跳过后面的过关检查假装过了。

**开跑前先报两句**（不算过关检查，但必须说）：① 该行当前状态（⬜/🔄；已 ✅ 就不重复勾）；② Demo 到 step 几、哪几步已锁定 ✅。

| 过关检查 | 查什么 | 谁查 | 状态词 | 不过怎么办 |
| -- | -- | -- | -- | -- |
| **1** | MD 知识覆盖（§7.2） | 教练自读 MD | 已覆盖 / 未覆盖 | STOP；先补 MD |
| **2** | Demo 完整度（§5.2） | 教练跑 check-demo | 过 / 不过 | STOP；先补 Demo / 锁定 |
| **3** | 目标↔代码（§5.4.A+B：抽清单 + 逐项核对） | 独立 subagent | 已实现 / 未实现 | STOP；补代码或拆成两条进度 |

**过关检查 3 固定约定（2026-09-05）**：

1. MD 进清单的项 → 代码必须**已实现**
2. **状态栏只许写「已实现」或「未实现」**——禁止 `⚠` / `❌` / `✅` /「警告但阻塞」/「单向缺口不阻塞」/「❌ 但不阻塞」/「注释算证据」。旧 MD §5.4 表若仍写「❌ · 不阻塞」，**按未实现计**，并在本次 complete 报告里改写成「未实现」（随后补代码或拆成两条进度）
3. 任一 **未实现 = 阻塞**（不准勾 ✅）。缺口只许 **补代码** 或 **拆成两条进度**；**禁止**问「接受缺口写进 MD」
4. **禁止**教练先自查一遍、再派 subagent「再查同一清单」——抽清单与核对都只在过关检查 3、由独立 subagent **一次做完**
5. **修复后不自动重跑过关检查 3**（2026-09-09 加）——过关检查 3 不过 → 教练推荐修复方案 → 学习者决定 1) 补这一步 / 2) 拆这一条 / 3) 停。**学习者选 1 后**：教练修代码 → **报告「之前过关检查 3 列出的 N 条缺口已实现 / 部分实现」** → **STOP 等学习者决定**：
   - **重跑过关检查 3**：派 subagent 跑「新的一次」（修复后新代码，不是「复扫同一清单」——清单因为修复变了）
   - **信任修复**：学习者/教练已看代码逻辑对，直接认为「已实现」，不重跑
   - **拆成两条进度 / 停**：拆走该项 / 暂停

   **禁止**：教练**自动**派 subagent 重跑过关检查 3（「我帮你重跑一下确认」是旧规则残留）。学习者拥有「重跑 vs 信任 vs 拆成两条进度」的最终决定权。

**证据规则**：找不到可观察实现 = **未实现**。仅注释 / README 文案 / MD 代码块 ≠ 已实现。后端一次跑完、前端只展示最终结果，但 MD 要求分步确认 / 分侧请求 → **未实现**（[§5.3.8 交互跟笔记走](./05-demo.md#538-http-demo-拆分多场景--多接口时强制)）。

**验证原则**（2026-09-08 沉淀 · 默认只查代码）：

- **默认只查代码 + 文件:行号证据** · 不跑 curl / 不起服务 / 不做运行时验证
- 代码看着通（handler 调用链对 + 字段透传 + 类型一致）即判「已实现」
- 需时补充运行时检查的**唯一场景**：
  1. 死代码嫌疑（写了但调用链有断点 · 找不到调用方）
  2. 字段写了但**未透传**（如 ExecResult 类型加了字段但 handler 没 return / 序列化没把字段写进 tool_result / 前端没渲染）
  3. 调用链有断点（registry → chat.ts → response 的中间某一环没接上）
- 这三类怀疑出现时再起服务 1 次 curl · 跑完立刻关（§5.3.15）· 不要把「端到端跑通」作为默认流程
