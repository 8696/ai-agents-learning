## 是什么

**一句话（进度表要能讲清的）**：检索增强生成（RAG）答错，不一定是模型笨，也不一定是改写没改好。有时是**检索单位和生成单位不是同一块**；有时是**切块离开全文后丢了「这段在讲谁」**；有时是**一条问句只打中一个语义邻域**。父子切块（Parent-Child Chunking）、情境检索（Contextual Retrieval）、多路查询（Multi-query）、查询扩展（Query Expansion）各补一类失败，不要混成「又一种改写」。

```text
用户原句
    │
    ├─ 查询改写 / 查询扩展 / 假想文档嵌入     ← 上一节（动问句，多半仍一次检索）
    ├─ 多路查询（Multi-query）               ← 本条：多条问句 × 多次检索 × 再合并
    │
    ▼
粗召回（向量 / BM25 / 混合）
    │  库里的切块可能已经不是「原文切一刀」：
    │  · 父子切块：入库的是小块，命中后取出父块
    │  · 情境检索：入库前给每块拼上定位句
    ▼
精排（Rerank）                             ← 第 2 条（改顺序，不换问句、不换库）
    ▼
生成  ← 提示词（Prompt）里仍应保留用户原句
```

| 手段 | 动哪一侧 | 补哪类失败 | 一句话 |
| -- | -- | -- | -- |
| 父子切块（Parent-Child Chunking） | 切块 | 小块搜得准、但生成时缺上下文；大块读得全、但检索被主题平均掉 | **检索单位 ≠ 生成单位** |
| 情境检索（Contextual Retrieval） | 切块（建库时） | 切块离开全文后，丢掉「这段在讲谁、属于哪一节」 | **入库前给切块补身份证** |
| 多路查询（Multi-query） | 查询 | 一条问句只打中一个语义邻域；或一句里几个角度，一次打分互相拖累 | **多条问句分别搜，再合成一份名单** |
| 查询扩展（Query Expansion） | 查询 | 用户词和库词对不上，但还想**留着原句里的锚点** | **原句保留，往同一条查询里补词，仍一次检索** |

进度表：四种都能说清「各解决什么」；**至少动手做过其中两种**；另外两种能讲适用场景即可。模块验收更具体：父子切块和情境检索里至少做一种；多路查询和查询扩展里至少做一种。

模块常见坑仍然成立：**一次只加一个变量，每次都跑评测集。** 四种可以叠，叠完变好却不知道是谁在起作用，等于没学。

不要叫「切片」——容易和数据集切分混在一起。切块（Chunk）是库里一段可单独打分、单独塞进提示词的正文。

## 为什么（Agent 开发要懂）

上一节看见的失败是：正确切块因为用词对不上，连候选窗都没进。本条再往两边拆：

1. **切块侧**：单层卡片被迫在「太大 / 太小」之间折中。折中失败时，改写再准也喂进去半句话，或喂进去一整章噪音。
2. **查询侧**：一条查询（哪怕已经改写或补过词）只打一次分，覆盖不了两个不相交的文档邻域。
3. **精排救不了这两类。** 精排只给已经进名单的切块改顺序。没进名单的父块上下文、没进名单的第二邻域，精排变不出来。
4. **每种手段都多花钱或多占词元预算（Token Budget）。** 父子切块让提示词变长；情境检索让**建库**变贵（每一块调一次模型）；多路查询让**每次提问**多一次模型调用和多次检索。没有评测集就全开，无法归因。

售后助手同一条业务线：用户问「杯子运输途中裂了怎么办」。库里「在途碎裂」小块搜得准，但 150 字里没有「必须填物流保单号」——那句在整节父块里。只喂小块，模型会答「找承运商」，漏掉保单号。这就是 Agent 不懂父子切块时的具体后果：检索看起来命中了，生成仍然缺关键约束。

## 核心对象

| 核心对象 | 管什么 |
| -- | -- |
| **父子切块（Parent-Child Chunking）** | 建库时两套粒度：子块进检索，父块进提示词 |
| **邻块扩展（Window Expansion）** | 不建父子，命中后按 `chunkIndex` 取上下邻居；便宜，邻块可能是另一主题 |
| **同父去重** | 多个子块命中同一父块时，父块只喂一次 |
| **情境检索（Contextual Retrieval）** | 建库时用模型给每块写定位句，拼到块前再嵌入、再建 BM25 |
| **情境嵌入 / 情境 BM25** | 同一份带定位句的文本既做向量也做关键词索引 |
| **标题继承（Header Inheritance）** | 程序拼章节路径，不调模型；标题里没有的实体补不了 |
| **多路查询（Multi-query）** | 一次生成多条问句，分别检索，再合并名单 |
| **倒数排名融合（Reciprocal Rank Fusion，RRF）** | 合并多路名单时，按名次倒数加分，被多路共同捞到的切块往上抬 |
| **查询扩展（Query Expansion）** | 原句 + 补丁，仍一条查询、一次检索（上一节主路径，本条放进对照表） |
| **失败归因** | 一次错误回答先问切分 / 检索 / 重排 / 生成，哪一环 |

## 每一种情况（变体）

### 1. 父子切块：检索用小卡片，生成念整段

模块 08 已经见过两头的坑：切太大，一整章压成一条向量，主题被平均掉；切太小，命中了「花生米下锅」，模型不知道这是哪道菜的哪一步。单层切块是在两头找折中。父子切块不折中：

> **搜的时候要短、要纯；读的时候要长、要全。这两件事不该由同一张卡片同时承担。**

数据怎么走：

```text
建库
  父块 = 一整节（例如 800 字「运输破损怎么处理」）
    ├─ 子块 1（开箱破损）→ 嵌入或打分，带上 parentId
    ├─ 子块 2（物流途中碎裂）→ 带上 parentId
    └─ 子块 3（拍照举证）→ 带上 parentId
  父块原文另存，通常不进「用来打分的那张表」

提问「杯子运输途中裂了怎么办」
  → 只和子块比分 → 命中子块 2（主题单一）
  → 用 parentId 取出父块
  → 塞进提示词的是父块全文，不是那 150 字
```

step-1 用售后手册把这一条做成可观察：默认问句会打中同一父块下多个子块；页面左栏是检索命中的子块，右栏是去重后的父块；生成只读父块。子块「运输途中碎裂」没有「物流保单号」，保单号写在父块整节里。

把父子切块当成「把块切大一点」：检索又回到主题被平均掉。

### 1b. 邻块扩展：不建父子时的便宜版

不存 `parentId` 也行：命中第 7 块，就把第 6、7、8 块一起喂给模型。靠的是 `chunkIndex`。

| | 父子切块 | 邻块扩展 |
| -- | -- | -- |
| 建库 | 两套粒度，子块记住父亲 | 一套粒度，只多数序号 |
| 命中后取什么 | 预先划好的那一节 | 上下邻居，碰运气 |
| 何时更稳 | 文档有清楚章节 | 切块顺序就是阅读顺序，且相邻块仍是同一主题 |
| 何时会翻车 | 父块本身还是一整章五个主题 | 固定长度硬切后，第 8 块已经是下一个政策 |

### 1c. 多个子块命中同一个父块：必须去重

问「破损怎么退」，子块 2 和子块 3 都进了前 K 条，父亲是同一节。按命中条数把父块塞两次，提示词里同一段政策出现两遍，浪费词元预算，模型还可能当成两条不同规定。

数据怎么走：命中列表先按 `parentId` 去重，再拼进提示词。要能看见：**检索命中了 3 条小块，实际只喂了 1 个父块。**

### 1d. 子块和父块在数据上有多悬殊（step-1 语料数字反例）

**子块 `child-damage-transit` 只有 50 字**：

> 「运输途中杯子裂了：属于物流破损。请先联系承运商。」

**只喂这一条给模型**，模型答：「请先联系承运商。」——**漏了关键约束**。

**父块 `par-damage` 整节 200+ 字**（关键约束全部在父块里）：

> 「运输破损怎么处理（整节）。开箱当时发现包装破损：当场拒收，并在签收单注明破损，不要先拆封使用。**运输途中杯子等易碎品裂了：属于物流破损，请先联系承运商，申报时必须填写物流保单号。举证：拍摄外箱、内衬、商品各一张，作为破损凭证；48 小时内提交，超时可能被拒。审核通过后由仓库安排补发或退款，处理时限 5 个工作日。**」

粗体那句是关键售后约束——「必须填物流保单号」「48 小时举证」「5 工作日处理」——**只在父块里有**。

| 只喂子块 | 喂父块 |
|---|---|
| 「请先联系承运商」 | 「① 联系承运商 ② 申报时**必须填物流保单号** ③ 拍照举证（外箱、内衬、商品） ④ **48 小时内**提交 ⑤ 审核后补发/退款，**5 个工作日**处理」 |

这就是为什么父块要在「生成」时出场——生成时要的就是这种「带约束的整段」，子块装不下。父块不进向量库是为了不污染检索信号；但**生成**要父块是因为整段上下文是不可替代的。

### 2. 情境检索：切块离开全文，先补身份证再入库

失败典型：「该季度营收增长了 3%。」原文上一页有公司名和年份；切出来单独嵌入后，向量里没有「哪家公司、哪一年」。用户问「Acme 2024 年 Q2 营收怎么变的」，这条切块可能排不进前 K 条。

模块 08 的标题继承已经补过一刀：把「《员工手册》> 第三章 假期」拼到块文本开头。那是**程序拼路径**，不调模型。它救得了「该期限自申请之日起算」不知道是年假还是病假——因为章节标题里就有「年假」。标题里没有的信息，标题继承补不了。公司名写在封面、数字写在第 12 页，章节标题只是「财务摘要」，这时需要情境检索。

Anthropic 的做法（2024-09 工程博客）：对每一个切块，把「整篇文档 + 这一块」送给模型，模型写 50～100 个词元的定位句，拼在切块前面，再用「定位句 + 原文」去做嵌入，并建 BM25 索引。拼上定位句之后的嵌入叫情境嵌入（Contextual Embeddings），同一份带定位句的文本再拿去建关键词索引叫情境 BM25（Contextual BM25）。

他们的评测数字（用来建立数量级，不是你库上的保证）：只做情境嵌入，前 20 条检索失败率大约降 35%；再加上情境 BM25，大约降 49%；再叠精排，大约降 67%。

情境检索**不改用户问句**。它改的是库里每一块在索引里长什么样。代价发生在建库：每一块都要调一次模型。同一篇文档的很多切块会反复把全文当作前缀，所以官方也提到可以用提示词缓存（Prompt Caching）把这篇文档的前缀费用摊薄——那是模块 19 的题，本条只要知道：**这是建库成本，不是每次提问成本。**

售后同样成立。切块原文：「该期限自签收之日起算，不含运输时间。」标题继承能拼上「保修」。若文档是「SKU-88 保温杯说明书」混在一个大 PDF 里、章节标题只是「注意事项」，定位句就要写出产品名。

本条进度表允许这一变体先讲场景；模块验收也允许「父子切块或情境检索做一种，另一种能讲清适用场景」。

### 2b / 2c. 情境嵌入还要进 BM25；标题继承 ≠ 情境检索

只做向量、专有名词仍然对不上，第 1 条混合检索的短板还在。定位句也要进 BM25。

| | 发生在 | 谁来写补丁 | 补什么 |
| -- | -- | -- | -- |
| 标题继承 | 建库 | 程序拼章节路径 | 块自己看不见的标题 |
| 情境检索 | 建库 | 模型读全文，写定位句 | 标题里也没有的实体（公司、季度、产品线） |
| 查询改写 | **提问时** | 模型改用户那句话 | 用户词和库词对不齐 |

把情境检索当成查询改写：提问时改问句，库里的切块还是匿名的。以为拼上 `metadata.filename` 就算情境检索：文件名常常是 `handbook-v3.pdf`，模型读全文写的定位句才带实体。

### 3. 多路查询：一条问句打不中两个邻域

上一节的扩展是：原句留着，往同一条查询里补词，仍然一次检索。有时一条再胖也不够。

两种具体死法：

1. **同一意图，一种说法只覆盖一个语义邻域。** 用户问「冬天杯子里的水隔夜还能喝吗」。库里一段写「保温杯隔夜水安全」，另一段写「密封圈发霉更换」。一条改写句容易偏向「能不能喝」，发霉那段进不了名单。
2. **一句里两个独立问题。** 「退货几天、保修几年？」上一节已经要求先拆成子问题。只把两个意图塞进一条更长的查询，BM25 会把「退货」和「保修」搅在一次打分里。

多路查询补的是：生成多条检索问句，每条单独粗召回，再把名单合成一份。

```text
用户原句
    │
    ▼
模型一次调用，产出 3～5 条检索问句
    ├─ 问句 A → 检索 → 名单 A
    ├─ 问句 B → 检索 → 名单 B
    └─ 问句 C → 检索 → 名单 C
    │
    ▼
合并：并集去重 + 倒数排名融合（RRF）
    │   （和第 1 条「向量一路、BM25 一路再融合」是同一类合并，
    │    这里合并的是「多条问句各自的名单」）
    ▼
一份检索名单 → 需要的话再精排 → 生成
生成和界面仍然对着用户原句
```

成本：生成多条问句通常是 **1 次模型调用**；后面 N 次检索是本地或向量库，比再调 N 次聊天模型便宜。合并后仍然 **1 次生成**。不要理解成「N 个 Agent 各答一遍」——那是模块 14。

本条动手之二，step-2 已写出。

### 3d. 一次调用返回 N 行 ≈ 同义改写，不是真不同角度

step-2 实际是**一次** chat completions 调用，发**一个**提示词，让模型返回 N 行。模型**不会真的**从 N 个独立视角思考——它大概率返回的是**同义改写**，不是**真正不同角度**。

```text
提示词示例（step-2 实际）：
  「请改写出 3 条不同说法的检索问句，覆盖同义词、政策名、相关概念；
   一行一条，只输出 3 行。」

默认问句「冬天杯子隔夜水还能喝吗」实际返回（近似）：
  1. 隔夜水是否安全
  2. 杯中水过夜是否能喝
  3. 隔夜的水是否健康
```

这 3 条**词不同但角度一样**——都是「能不能喝」的同义改写。

**为什么不是问题**：
1. 即使是同义改写，每条仍比原句多覆盖一些邻域
2. RRF 合并会去重 + 抬升被多路共同命中的切块
3. 重复不影响最终召回（同一子块在多路都命中 → RRF 分数高）

**什么时候会出问题**：库里用了**完全不同**的术语（「七天无理由」「SKU-88」），用户的口语怎么改写都打不中。

**更稳的提示词**（按角度明确）：
```text
你是售后检索改写助手。请把下面这句用户原句改写成 3 条检索问句：
- 第 1 条用「同义词 / 日常说法」（用户的本意）
- 第 2 条用「政策名 / 库内术语」（库里可能有的标准说法）
- 第 3 条用「相关概念 / 隐含信息」（用户没明说但想知道的东西）
一行一条，只输出 3 行。

用户原句：「冬天杯子隔夜水还能喝吗」
```

这样**1 次**调用返回的 N 行更可能真的不同角度。但本质上仍是模型 1 次调用的结果，**不完全独立**。

**真正的多角度需要**：N 次独立的 chat completions 调用，每次提示词强调不同角度——成本 N 倍，大多数场景**不划算**。Chain-of-Thought（先让模型列出 N 个角度再逐个生成）也是一种方案。

### 3b. 多路 ≠ 上一节拆子问题

| | 拆子问题（上一节） | 多路查询（本条） |
| -- | -- | -- |
| 为什么拆 | 一句里**两个意图**，搅在一起会互相拖分 | **同一个意图**，换几种说法分别覆盖邻域 |
| 产出 | 「退货时限」「保修年限」——内容不同 | 「未拆封超期退货」「七天无理由特例」——同一件事的不同说法 |
| 合并要解决什么 | 两份名单可能完全不相交，都要保留 | 多份名单大量重复，要去重，并用融合把「被好几路都捞到的切块」抬上去 |

生产里两者经常用同一套「多路检索 + 融合」代码。概念上不要并成一个词。

### 4. 查询扩展：原句留着，同一条查询里补词

上一节已经当主路径讲过，本条把它放进「各补哪类失败」的对照表，不当新算法。

```text
原句：「还能退吗」
扩展句：「还能退吗 七天无理由 未拆封 特例审核 SKU-88」
        └──────── 一次检索 ────────┘
```

和改写的差别：改写可以整句替换；扩展是「原句 + 补丁」。  
和多路查询的差别：扩展是 **1 条查询 × 1 次检索**；多路是 **N 条查询 × N 次检索 × 再合并**。

什么时候扩展就够：意图单一，缺的只是同义词 / 政策名 / 货号。什么时候不够：一句两个问题，或同一意图要覆盖两个不相交的文档邻域。

本条进度表允许讲场景。不可 import 上一节 Demo；本条 step-1 也不演示扩展。

### 5. 不该上

| 手段 | 不该上的信号 |
| -- | -- |
| 父子切块 | **每块自洽 = 检索单位和生成单位已经在同一块里** → 拆父子没意义。典型场景：FAQ 类（一问一答、每块独立完整）。再套父子只是把同一张卡片存两遍，还多一笔入库成本 |
| 情境检索 | 每块开头已经带齐产品名、章节、适用对象；再调模型写定位句，钱花在重复信息上 |
| 多路查询 | 问句已经是货号、条款编号、库标题原文。再扇出，可能把主键改丢（上一节「锚点不改写」同一条纪律） |
| 查询扩展 | 原句已经是库词；再补一堆同义词，BM25 被补丁稀释 |

### 6. 一次只加一个变量 + 失败归因

一次错误回答，先问是哪一环——切分 / 检索 / 重排 / 生成。本条要求能把「切块侧失败」和「查询侧失败」分开：正确小块能命中但模型读不懂 → 先看父子 / 情境；正确切块根本不进名单、且原句已经对齐库词 → 才看多路。

## 易混点

| 容易混成 | 其实 | 判错会怎样 |
| -- | -- | -- |
| 父子切块 = 把块切大 | 两套粒度：小块负责搜，父块负责读 | 检索又被主题平均掉 |
| 邻块扩展 = 父子切块 | 邻块靠序号碰运气；父子靠建库时划节 | 喂进去下一节政策 |
| 情境检索 = 标题继承 | 标题继承是程序拼路径；情境检索是模型读全文写定位句 | 封面里的公司名永远进不了向量 |
| 情境检索 = 查询改写 | 一个改库（建库时），一个改问句（提问时） | 库里的匿名切块永远漂 |
| 查询扩展 = 多路查询 | 一条变胖 vs 多条分搜再合并 | 两个邻域仍挤在一次打分里 |
| 多路查询 = 上一节拆子问题 | 换说法覆盖邻域 vs 切开两个意图 | 合并策略和评测都会对错失败类型 |
| 多路查询 = N 次生成 | 1 次生成问句 + N 次检索 + 1 次回答 | 成本和延迟按 Agent 扇出爆炸 |
| 多路查询 = 真独立 N 路 = 不同提示词调 N 次 | 1 次调用返回 N 行 ≈ 同义改写，不是真不同角度 | 成本 N 倍，但召回角度更多 |
| 精排能补这四种 | 精排只改已进名单的顺序 | 没进名单的父块、没进名单的第二邻域，精排变不出来 |
| 四种一起开就更好 | 一次一个变量 | 变好了不知道是谁起的作用 |

## 例子

**父子切块 · 生活**：你在书里夹了一张便利贴，只标了一句话。别人问起时，你靠便利贴定位到那一页，但念出来的是那一整段。定位用一句，回答用一段。  
**父子切块 · 前端**：站点内搜索命中的是某个 `<p>`，你不会只把这一个段落渲染成帮助页。你取出它的父级 `<section>`。检索命中的 DOM 节点，和最终渲染的容器，不是同一个。step-1 页面左栏 / 右栏就是这个对照。

**邻块扩展 · 生活**：便利贴那一页的上一页、下一页一起念。上一页可能已经是另一章。  
**邻块扩展 · 前端**：虚拟列表 overscan 多渲染上下几条；那几条不一定属于当前分组。

**情境检索 · 生活**：从相册抽出一张「蛋糕」特写。建索引之前先在背面写「2024 年小李 30 岁生日」。写背面发生在归档时，不是每次有人问才写。  
**情境检索 · 前端**：卡片列表如果只索引截断后的 `innerText`，「该季度增长 3%」搜不到公司名。写入索引前把面包屑和摘要拼进 `searchText`。情境检索用模型写那句摘要，而不是只用面包屑。

**多路查询 · 生活**：你跟图书管理员说「那本把宇宙讲成故事的薄书」。他同时查「霍金」「时间简史」「宇宙通俗读物」，三张检索单合并后再递给你。你看见的还是自己那句话。  
**多路查询 · 前端**：帮助中心同时打「退货政策」「七天无理由」「unopened return」，`Promise.all` 三条请求，再按 `id` 去重。地址栏里用户仍只打了一句。

**查询扩展 · 生活**：药店窗口你说「嗓子疼」，店员在同一张小票上加写「咽炎 布洛芬 含片」，还是开一次抽屉。  
**查询扩展 · 前端**：搜索中间件把 `q=退货` 扩成 `q=退货 七天无理由 未拆封`，仍然一次 `GET /search`。

## 需求清单

验收准绳，不是一次搭完整应用的施工单。后面写演示仍按知识一步步加，在进度表打钩时再逐条对。场景都挂在「售后助手」上。

1. **父子切块：命中小块、喂父块，两者能分开看见**  
   场景：运营把《运输破损》写成一节，下面有开箱、在途、举证三段。用户问「杯子运输途中裂了怎么办」。  
   目标：检索打中「在途碎裂」小块，实际喂给模型的是整节父块。  
   知识点：变体 1、1c。  
   验收：页面分开展示「检索命中的小块」和「将喂给模型的父块」，`id` 能对上父子；两个子块同父时父块只出现一次。

2. **情境检索：能讲清它补的是「切块离开全文丢实体」，并和标题继承划界**  
   场景：PDF 里封面是产品名，正文切块只剩「该期限自签收之日起算」。  
   目标：能说出建库时给切块补定位句、提问时不必改问句；能说出标题继承拼的是路径，情境检索写的是读完全文才知道的实体。  
   知识点：变体 2、2b、2c。  
   验收：口头能用售后例子走一遍数据流。进度表允许先讲场景；若后来动手，要看见「无定位句 / 有定位句」两套索引对照，且定位句全文可见。

3. **多路查询：多条问句分别检索，合并名单可见**  
   场景：用户问「冬天杯子隔夜水还能喝吗，密封圈发黑怎么办」或同一意图的多种说法。  
   目标：看见模型产出的每条检索问句、每条自己的名单、合并后的一份名单；某一正确切块只因其中一路才进名单。  
   知识点：变体 3、3c。  
   验收：每条问句自己的检索能逐步看见，禁止一个按钮打包成「内部跑完只给最终名单」；合并后有去重；界面仍显示用户原句。本条动手之二，step-1 尚未覆盖。

4. **查询扩展：能讲清它是一条查询补词，救不了多邻域**  
   场景：用户只说「还能退吗」，库词是「未拆封 / 特例」。  
   目标：能画出「原句 + 补丁 → 一次检索」，并能指出它和多路查询的差别。  
   知识点：变体 4。  
   验收：口头能对照上一节「一条查询补词」。进度表允许讲场景，不强制本条再写一套扩展演示。

5. **不该上能判断**  
   场景：问句是 `SKU-88`；库是一问一答 FAQ。  
   目标：货号走原句直搜、不上多路；FAQ 不上父子。  
   知识点：变体 5。  
   验收：能各举一例说明「开了会怎样」（主键被改丢 / 同一张卡片存两遍）。本条先讲场景。

6. **一次只加一个变量**  
   场景：已经有混合检索和精排。  
   目标：先只开父子或只开多路，再看命中变化。  
   知识点：变体 6。  
   验收：能说出「四种一起开」为什么无法归因。本条先讲场景。

## 我追问过的

| 问题 | 针对什么 | 回答 |
|------|---------|------|
| 既然父块不进向量库，那为什么还需要父块？ | 摸到父子切块的根——「检索单位 ≠ 生成单位」之间的具体差距，希望用 step-1 语料的具体数字看清楚 | 父块不进向量库是为了不污染检索信号（被多主题平均掉）；但**生成**要父块是因为整段上下文不可替代——子块 50 字装不下「物流保单号 / 48 小时 / 5 工作日」这些关键约束，只喂子块模型漏约束、喂父块模型答完整 5 步。详见「1d. 子块和父块在数据上有多悬殊（step-1 语料数字反例）」 |
| 「一条问句、N 条不同说法」指的是什么？ | 想知道 step-2 的核心机制——是多次独立调用，还是单次提示词生成多行 | step-2 是**1 次** chat completions 调用，发**1 个**提示词让模型返回 N 行。这 N 行大概率是**同义改写**而不是真不同角度。工程上接受这个限制（每条仍多覆盖邻域 + RRF 去重）；更稳的方案是按角度明确写提示词（详见「3d」） |
| 「让模型生成 N 条不同说法」会不会返回一样的？ | 摸到多路的隐藏限制——1 次调用返回的 N 行大概率是同义改写 | 你的质疑**完全对**。1 次调用 = 1 个提示词 = 模型一次性吐 N 行 = 大概率是同义改写。step-2 的 1 次 chat completions 调用里 temperature=0.3 仍可能近似；真要不同角度得 N 次调用（成本 N 倍）或 Chain-of-Thought（先列角度再生成）。当前接受这个限制 + 优化提示词按角度明确写 |

本轮其他对话主要是讲课、代码改动、调试修复（MiniMax 字段名 / 拆建库与检索两步），属学习节奏操作，按 §2.1 筛门不进本节。

## 取舍

| 做法 | 什么时候合理 | 代价 |
| -- | -- | -- |
| 父子切块 | 章节清楚，检索要准、生成要整节约束 | 库要存 parentId；提示词变长；父块太大则噪音又回来 |
| 邻块扩展 | 切块顺序即阅读顺序，暂不想建两套粒度 | 邻块可能是下一节政策 |
| 情境检索 | 切块正文缺实体，标题路径也补不上 | 建库时每块调模型；要用提示词缓存摊前缀 |
| 标题继承 | 章节路径里已经有关键实体 | 封面 / 文首里的实体补不了 |
| 多路查询 | 一条问句覆盖不了两个邻域，或一句多个角度 | 每次提问多一次模型调用 + N 次检索；合并要去重 |
| 查询扩展 | 意图单一，只缺同义词 / 政策名 / 货号 | 救不了多邻域；补丁过多会稀释 BM25 |
| 原句直搜、不上多路 | 问句已是货号 / 条款编号 / 库标题 | 用户用日常说法提问时会漏召回 |
| 一次只加一个变量 | 任何时候做进阶 RAG | 看起来「慢」，但能归因 |

本条推荐动手顺序：先父子切块（step-1 已写出），再多路查询；情境检索和查询扩展按进度表可先讲场景。不要第一步把四种手段全打开。

## 踩坑

1. **把父子切块做成「把块切大」。** 只把入库粒度调大，没有「子块打分 / 父块喂模型」两套单位，检索又被主题平均掉。
2. **命中多个子块却重复喂同一个父块。** 提示词里同一节出现两遍，词元浪费，模型可能当成两条规定。
3. **只展示最终答案，不展示命中小块 vs 喂父块。** 关上文件后会以为做了父子切块，其实只是块调大了。
4. **把情境检索当成查询改写。** 提问时改问句，库里的匿名切块永远漂。
5. **把标题继承当成情境检索。** 程序拼路径补不了封面里的公司名。
6. **情境检索只做向量、定位句不进 BM25。** 专有名词仍然对不上。
7. **把查询扩展当成多路查询。** 还是一次检索，两个邻域挤在一次打分里。
8. **把多路查询当成 N 次生成。** 账单和延迟按 Agent 扇出爆炸。
9. **问句已是货号还开多路。** 主键被改丢，BM25 的强项被拆掉。
10. **四种手段同一天全开。** 变好了不知道是谁起的作用。本模块验收写过：一次只加一个变量，每次都跑评测集。
11. **指望精排补这四种失败。** 没进名单的切块，精排变不出来。
