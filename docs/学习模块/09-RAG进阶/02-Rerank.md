## 是什么

**一句话（进度表要能讲清的）**：检索要拆成两阶段——**粗召回（Recall）**负责从全库把可能对的条目捞进候选；**精排（Rerank）**负责在候选里把真正相关的排到最前，再交给生成（Generate）。最终喂给大模型的那几条，**不是**第一阶段 Top-K 的原样截取。

模块 08 默认是：问句变成向量 → 余弦排出前 K 条 → 交给生成。上一节给第一阶段加了关键词通道（BM25）和融合。那份名单仍然只是**粗名单**。本条要加的是：

> **先用便宜的办法尽量把对的条目捞进候选，再用更贵的模型在候选内部重排。** 第一阶段第 12 名可以变成第 1 名；第 1 名也可以因为「字很像、事不对」被打下。硬边界：**没进候选的条目，精排永远看不见。**

搜索和推荐里把这叫 **两阶段检索（Two-stage Retrieval）**：

| 阶段 | 中文口头 | 英文 | 要什么 | 不怕什么 |
| -- | -- | -- | -- | -- |
| 第一阶段 | **粗召回（Recall）** | first-stage retrieval | 尽量把「可能对」的捞进候选集（Candidate Set），常见 20～100 条 | 里面夹着几条不太相关的 |
| 第二阶段 | **精排（Rerank）** | reranking | 在候选里把真正相关的排到最前，再截最终 Top-K（常见 3～8 条喂给生成） | 漏掉没进候选的（它救不了） |

```text
用户问句（这一步不改写问句）
        │
        ▼
第一阶段粗召回：向量 / BM25 / 混合（上一节）
        │
        │  候选 N 条（例如 50）——只求「对的在不在里面」
        ▼
第二阶段精排：交叉编码器 / 精排 API / 大模型给「问句+这篇」打相关分
        │
        │  按精排分重排，取最终 K 条（例如 5）——只求「这 5 条谁该在最前」
        ▼
生成（Generate）：只看见这 K 条
```

模块 08 的「余弦 Top-K」把两件事压成了一步：召回和最终名单是同一条榜。库只有几十条条目时够用。条目一多、问法和条目用词一拧，第一阶段排第一的常常是「用词很像、事不对」的总则；真正那条例外规定挤在第 8、第 15 名。生成只吃前 5 条 → **那条对的条目等于不存在。**

**重排序（Rerank / Re-ranking）** = 对已经召回来的一小撮文档，用更准、也更贵的相关性模型再打一遍分，按新分数重排，再取最终前 K 条。

「精排」是一个**大类概念**——目的就是「在候选内部把对的排到最前」。精排有多种实现方式：
- **神经精排（Neural Rerank）**：用神经网络模型打分（交叉编码器 / 专用精排 API / 大模型逐条打分）——本 step-1 演示的
- **业务加权（Business Re-ranking）**：按人写的规则加分（时间窗口 / 关键词 / 类目 / 店铺 / 客户等级）——本 step-2 演示的
- **混合精排**：把神经分和业务规则分按权重叠加
- **UI 置顶**：产品层硬顶，不进算法

**精排 vs 神经精排**：神经精排 ⊂ 精排——「神经精排」是精排的一种实现方式，不是精排的缩写。日常对话常混用是因为 90% 精排场景用神经精排，但概念上是「上位 vs 下位」关系，不是缩写。

## 为什么第一阶段和第二阶段必须是两种模型

### 双编码器（Bi-encoder）：第一阶段为什么能扫全库

**双编码器（Bi-encoder）**把问句和文档**分开**编码：

1. 离线：每一条过一遍嵌入模型（Embedding Model）→ 存成向量（可提前算、可建索引）。
2. 在线：只把**问句**编成一条向量。
3. 见面方式：余弦（或点积）。问句和文档在模型内部**从未一起出现过**。

好处：文档侧能预计算；百万张条目也能用近似近邻搜。代价：打分时看不见「这句话里的『碎了』到底对不对上那条条目里的『运输破损』」，只能看两个方向像不像。

上一节的 BM25 也是第一阶段：问句切词、文档切词，对上的词计分。同样是「各算各的，最后对一下」，不是「把问句和这篇正文当一段话一起读」。

### 交叉编码器（Cross-encoder）：第二阶段为什么准、为什么贵

**交叉编码器（Cross-encoder）**把 `问句 + 文档` **拼成一段**送进模型，让词和词互相做注意力（Attention），最后吐一个相关分（常见 0～1，或 logits）。

它真正在做的事：一边看着问句里的「杯子碎了」，一边看着正文里的「陶瓷运输破损可补发」，判断这是不是同一件事。

代价直白：

- 文档**不能**预先算好一个「和所有问句都通用」的向量——问句变了，每一对都要重新过模型。
- 对百万张条目逐对跑交叉编码器，延迟和钱都会炸。
- 所以它只配打**已经缩小的候选**，不配当全库扫描。

生产里还会碰到 **专用精排 API**（Cohere Rerank、Jina Reranker 这类）：一次请求带上问句和一组文档，返回每篇的相关分。思想仍是交叉编码器这一路——「对照着看」，不是再做一次双编码器。

「再 embed 一次问句+文档拼接」仍是双编码器思路，只是输入变长了，**没有**「问句词和文档词互相对齐打分」那种交互。那不是本条的第二阶段。

## 核心对象

| 核心对象 | 管什么 |
| -------- | ------ |
| **粗召回（Recall）** | 从全库尽快拿出候选 N 条；要的是「对的在不在里面」（召回率 Recall@N） |
| **精排（Rerank）** | 只在这 N 条内部重排；要的是「最终前 K 条是不是真相关」（**大类概念**，包含神经精排 / 业务加权 / 混合 / UI 置顶） |
| **双编码器（Bi-encoder）** | 问句、文档分开编码，余弦见面；能预计算、能扫大库 |
| **交叉编码器（Cross-encoder）** | 问句+文档一起过模型；准、贵、不能预计算 |
| **神经精排（Neural Rerank）** | 用神经网络模型打分——交叉编码器 / 专用精排 API（Cohere Rerank / Jina Reranker）/ 大模型逐条打分；**神经精排 ⊂ 精排**，是精排的一种实现方式 |
| **业务加权（Business Re-ranking）** | 按人写的规则给候选加分——时间窗口（如「近 N 天编辑过 +0.3」）/ 关键词命中 / 类目加权 / 店铺 / 客户等级；纯本地计算、不调模型；**业务加权 ⊂ 精排**，是精排的另一种实现方式 |
| **业务权重配置** | 业务加权三件套——开关 `on` / 窗口 `recentDays` / 加权值 `bonus`；任一项可独立调 |
| **候选集大小 N** | 精排的上限：N 之外的条目，第二阶段当它不存在 |
| **最终 Top-K** | 生成真正吃到的条数；K 通常远小于 N |
| **精排分数 vs 召回分数 vs 业务加权分** | 三把尺子，量纲不同，不能当同一种分直接加 |

## 各变体

贯穿同一条售后库：

| 条目 | 内容（人话） |
| -- | -- |
| A | 七天无理由退货总则 |
| B | 运输破损补发：陶瓷、杯类在途碎裂走补发，不走无理由 |
| C | `SKU-8821` 路由器保修 2 年 |
| D | 运费险怎么用 |
| E | 会员每年退货次数上限 |

### 变体 1 · 两阶段各干什么

粗召回问的是：**对的条目进没进这 50 条？** 精排问的是：**这 50 条里谁该排第一喂给生成？**

用户问：「杯子在路上碎了能退吗？」

第一阶段（向量或混合）可能是：A 总则第一（「退货」字最多），D、E 跟着，B 破损补发在第 8～12 名。若直接截 Top-5 给生成：模型只看见总则和运费险，一本正经讲七天无理由，**补发政策等于没入库。**

第二阶段对这批候选逐对打相关分后，B 升到第 1，A 落到后面——交叉编码器看见「碎了」对上「运输破损」，而总则从来没说杯子。

生活：急诊分诊先把你分到骨科候诊室（召回），医生问诊才决定是夹板还是手术（精排）。分错科，后面再认真也看错病。

前端：`Cmd+P` 先模糊捞 50 个文件名，再按「最近打开 + 路径匹配」把真要的那个顶到第一。第一阶段不是最终名单。

判错会怎样：把「生成只吃 5 条」误当成「库里只有 5 条」。检索失败常发生在截断，不在生成。

### 变体 2 · 双编码器为什么能扫全库

文档向量离线算一次。新问句只编码一次，和索引里所有向量比方向。百万条目也能做（近似近邻）。BM25 同理：倒排索引（Inverted Index）按词找帖，也不把问句和全文当一段话读。

生活：小区门卫有一份预先写好的住户特征条目。你报一句外貌，他按条目比对，不必每次把整栋人叫下来面试。

前端：商品标题预先建倒排；用户输入只查索引，不会当场对每个详情页跑一次 Transformer。

### 变体 3 · 交叉编码器为什么只能打候选

每一对 `(问句, 文档)` 都要完整过一遍模型。50 对 = 50 次量级的计算。全库 10 万张条目做不到在线精排。架构被逼成两阶段：便宜的扫全库，贵的只打短名单。

生活：你不会对全市所有房子做上门验房，只会验中介已经筛过的 8 套。

前端：列表页不会对每个商品请求一次「这个用户会不会买」的大模型；只会在已经召回的一页里跑排序模型。

判错会怎样：试图用交叉编码器替换第一阶段。Demo 库 20 条条目时看不出来；一上真实知识库，延迟先炸。

### 变体 4 · 精排救不了没进候选的文档

精排**重排的是名单内部**，不回头去库里再找。候选 N=8，真正那条条目在粗召回第 40 名 → 精排结果里永远没有它。

若第一阶段只取 Top-8，而 B 排在第 12，再贵的精排器也没用。这时该做的是：**加大 N，或修好第一阶段（混合检索、切块、后面的查询改写）**，不是换一个更强的精排模型自我安慰。

生活：相亲机构只给你 5 个人的资料。对的人在库存第 80 号、没被塞进这 5 份——你再怎么认真约会，也遇不到。

前端：无限滚动只加载了前 20 条。排在第 35 的那条，页面上的「智能排序」再怎么排都不会让它出现——它根本没进 DOM。

判错会怎样：线上事故只加精排，评测集召回率（Recall@N）没动，最终命中率也不动。

### 变体 5 · 候选太大的代价

N 不是越大越好。

- **钱和延迟**：交叉编码器 / 精排 API / 用对话模型逐条打分，都随 N 近似线性涨。
- **噪音**：第一阶段很靠后的往往已经是弱相关。精排器并非完美，偶发会把一篇「像那么回事」的噪音抬进最终 Top-K。
- **生成侧**：最终 K 通常仍只要 5 条；N 过大只增加第二阶段负担，不一定增加最终质量。

实务里常见起点：N=20～50，K=5。没有全世界通用的数，要用评测集看：继续加大 N，最终答案还没有变好，就停。

生活：验房从 8 套加到 80 套，周末不够用，人也看花眼。

前端：虚拟列表一次挂 2000 个节点去做「精细排序」，主线程条目死。先窗口再精排。

### 变体 6 · 排名会动：抬真相关、打假阳性

精排同时做两件事：

1. **抬**：用词不完全一样、但事对的条目（B：破损补发）从第 12 → 第 1。
2. **打**：用词很像、但答的不是这个问题的条目（A：七天无理由总则；D：运费险）往下放。

「假阳性」在双编码器里极常见：问「碎了能不能退」，总则里「退货」出现 20 次，余弦很高；真正写「在途碎裂走补发」的那条，用词是「破损 / 陶瓷」，余弦不一定最高。

关上文件还能讲出来要能讲的画面：**同一问句、同一批候选，两条榜并排，至少一篇的名次明显换了。** 名次完全不动，这一步就没教到「不是一次 Top-K 定生死」。

生活：简历关键词筛出来的第一名，面试发现是堆砌岗位名词；真正干过这事的人简历排第 7。面试会换名次。

前端：搜索「登录过期」命中一篇标题含「登录」的运营文案（假阳性），真正的 `401` 处理文档排后面。精排模型若读过正文，会把后者提前。

### 变体 7 · 精排不是混合融合

上一节的加权分数、倒数排名融合（Reciprocal Rank Fusion，RRF）发生在：**两份粗名单怎么合成一份粗名单。** 合成之后，你仍然只有第一阶段。

| | 混合融合 | 精排 |
| -- | -- | -- |
| 输入 | 两份（或多份）**召回榜** | **一份**已经召回的名单 |
| 看什么 | 分数或名次怎么合成 | 问句和这篇正文到底相关不相关 |
| 贵在哪 | 几乎只是算术 | 多一次模型（交叉编码器 / 精排 API / 大模型） |
| 救不了什么 | 某一侧完全没召回的 | 整份候选里都没有的 |

RRF 把向量第 3、BM25 第 1 合成「融合第 1」，**没有**重新读正文。精排会读。

判错会怎样：以为上一节做完 RRF 就已经「精排」了。模块验收要的「重排前后 Top-K 变化」对不上——融合前后变的是通道合成，不是交叉打分。

生活：两个朋友各推荐 10 家餐馆，你按名次合成一份 10 家（融合）；你自己再去吃过才重新排名（精排）。

前端：一个榜按相关度、一个榜按时间，RRF 合成粗名单；再用模型读标题+摘要重排，才是精排。

### 变体 8 · 精排不是查询改写（只对照到这一步）

**查询改写（Query Rewrite）** 发生在检索**之前**：改的是问句本身。下一节才整节讲。

本条精排发生在检索**之后**：问句字符串不变，只改名次。

同一句「杯子碎了能退吗」：

- 改写可能会变成「运输破损 补发 陶瓷」（那是第 3 条）。
- 精排仍用原句，和每篇候选正文对照打分。

两者可以叠：改写提高「对的条目进候选」的概率；精排提高「进了候选之后排到前面」的概率。本条 Demo 不要做成改写器，否则变量缠在一起，看不出是谁在动名次。

### 变体 9 · 点式打分（Pointwise）

**点式（Pointwise）**：每一对 `(问句, 文档)` 独立出一个相关分，然后按分排序。Cohere Rerank、Jina 这类 API 默认就是：一次请求里给 N 篇，回来每篇一个 `relevance_score`。

用对话大模型当精排器时，点式长这样：对每篇问「0 到 1，这段和问句有多相关，只回数字」。N 篇 = N 次调用量级。

优点：实现直、每篇有分、好看榜。缺点：模型没看见「这 10 篇之间谁更该排前面」，分数校准可能飘（0.82 和 0.79 未必真有稳定差距）。

生活：阅卷老师给每份卷单独打分，再按分排名。

前端：每个商品条目独立请求「推荐分」，再 `sort`。

### 变体 10 · 对式（Pairwise）和列表式（Listwise）

**对式（Pairwise）**：不给绝对分，问「A 和 B 谁更相关」。要排 N 篇，理论上要比很多对。更接近「排序」，也更贵。风险：循环偏好（A>B、B>C、C>A）。

**列表式（Listwise）**：把整份候选（或前 N 条的标题/摘要）一次塞给模型：「按相关性重排，返回 id 顺序」。对话模型做精排时很多人用这个，一次调用搞定。风险：长上下文里中间那些篇被冷落；乱序编造 id。

| | 点式 | 对式 | 列表式 |
| -- | -- | -- | -- |
| 模型看见什么 | 一篇 | 两篇 | 一串 |
| 输出 | 每篇一个分 | 谁赢 | 新顺序 |
| 贵 | N 次量级 | 对的数量 | 通常 1 次，但提示词很长 |
| 风险 | 分数不可比、校准差 | 循环偏好 | 中间篇被冷落；编造 id |

RAG 生产主力是**点式专用精排器**。列表式常见于「先用聊天模型顶上、还没接专用 API」。对式更多出现在训练排序模型，线上少直接两两比。

生活：点式是给每个选手打分；对式是淘汰赛两两比；列表式是评委看完整场名单一次性排座次。

前端：点式像每条评论一个情感分；列表式像把当前页 20 条一次性交给规则引擎返回新顺序。

### 变体 11 · 业务加权 vs 神经精排（两条不同的信号源）

产品常会再插一脚：新品加权、同店铺加权、最近 30 天编辑过的文档加权、「当前所选商品类目」加权。

这是**业务加权（Business Re-ranking / Rule-based Re-ranking）**，**不是神经精排**。它是精排大类下的另一种实现方式（神经精排用模型打分；业务加权用人写规则打分）。两者是**两条不同的信号源**，可以独立开关、独立调权重。

#### 业务加权的数据源

业务加权**不限于**向量库字段。按数据源分四类：

| 数据源 | 典型例子 | 是否存在向量库 |
|--------|---------|----------------|
| **向量库字段型** | `updatedAt` / `createdAt` / `tags` / `kind` / `on_promo` | 是（通常在 metadata 字段） |
| **用户上下文型** | `user.tier`（VIP/普通）/ `user.storeId`（本店）/ `user.region`（地区） | **否**——请求时附带 |
| **实时状态型** | 当前是否促销期 / 当前热点 / 当前时间 / 当前会话阶段 | **否**——实时算或查 Redis |
| **业务手工维护型** | 「双 11 主推品 pinned_ids 名单」/ 黑名单 / 优先级表 | **否**——单独的配置表 / 配置中心 |

step-2 demo 用的是「**向量库字段型**」（`updatedAt` 在 CORPUS 里）——教学简化，一个文件看完所有数据。生产里这个字段通常在向量库 metadata、外键表、或者实时服务里，关键不是「必须存在向量库」，而是「在业务加权那一跳能拿到这个信号」。

#### 业务加权的典型形态

| 业务语义 | 数据源 | 规则 |
|---------|--------|------|
| 新品加权 | 商品表 `createdAt` | 上架 ≤ 7 天 +bonus |
| 客户等级加权 | 请求时 `user.tier` | VIP 用户专属文档 +bonus |
| 同店加权 | 请求时 `user.storeId` | 本店商品 +bonus |
| 促销加权 | 商品表 `on_promo: bool` | 促销商品 +bonus |
| 法规更新加权 | 法规库 `updatedAt` | 近 N 天发布 / 修订的法规 +bonus |
| 紧急程度加权 | 工单 `priority: 'urgent'` | 标记「急」的工单 +bonus |
| 黑名单降权 | 黑名单表 | 命中黑名单 -bonus（甚至直接剔除） |
| 业务手工置顶 | pinned_ids 名单 | cardId ∈ pinned_ids → +bonus |

#### 业务加权 vs 神经精排（必须拆清）

| | 神经精排 | 业务加权 |
|--|---------|---------|
| **信号源** | 模型读问句和正文后给相关分 | 人写的规则（时间窗口 / 关键词 / 名单 / 上下文） |
| **计算位置** | 第二阶段核心（一般真发网络请求） | 精排后或精排前（**纯本地计算**，本 demo 不调模型） |
| **开销** | 高（每对一次模型） | 低（按字段查 + 算术） |
| **可解释** | 难（分数是模型内部状态） | 易（规则每条都能说清） |
| **可独立开关** | 可（`rerankOn: false`） | 可（`businessWeight.on: false`） |
| **数据源依赖** | 不需要外部数据 | 需要外部数据（向量库字段 / 上下文 / 名单） |
| **典型坑** | 写死分数冒充 | 数据源挂掉 → 静默失效 |

#### 怎么和神经精排叠用

- **可以叠**：神经分 + 业务加权分 = 综合分；按综合分排
- **不能混**：两把尺子，硬加需要校准（变体 13）
- **文案分清**：业务加权的 UI 必须标「**业务规则 / Rule**」，不能叫「智能排序」或「交叉编码器」
- **可以独立关**：业务加权关闭时，最终榜 = 神经精排榜（变体 12）

不要把「给含货号的条目 +0.3」叫做本条的 Rerank 教学——上一节已经用关键词通道解决编号。本条要看见的是**读了问句和正文之后**名次变了，**并且**神经分没动的情况下，业务规则能独立改名次。

#### 生活 / 前端例子

- **生活 · 医院分诊**：神经精排 = 医生判断谁更危重（读具体内容）；业务加权 = 「年满 65 岁优先叫号」「军人优先」（按身份调，不看病）；「急诊」标记也是业务加权。多个业务信号叠加在叫号顺序上，**不一定都存在分诊台的「向量库」里**——年龄在身份证，身份在户籍，急诊在挂号时填的字段。
- **前端 · 电商搜索**：神经精排 = 商品标题和搜索词的相关度模型；业务加权 = 「已上架 7 天内新品 +0.3」「品牌旗舰 +0.1」「促销标签 +0.2」。同一搜索词，开 / 关业务加权对照看：开的时候"最近上架的同款"靠前，关的时候按纯相关度排。

### 变体 12 · 何时可以不做精排

可以跳过第二阶段的典型情况：

- 库很小（教学用 20 条条目），第一阶段 Top-K 已经经常就是对的那一条。
- 延迟预算极紧（客服要 800ms 内出字），多一跳模型过不了关。
- 第一阶段已经是「精确编号命中 + 唯一一条条目」，再精排没有信息增益。
- 评测集显示：加上精排，最终答案正确率几乎不动，只是多花钱。

「可以不做」≠「两阶段思想没用」。库一长大、问法一拧，第一阶段假阳性会回来。本模块验收明确要**能展示重排前后 Top-K 的变化**——所以本条仍要会做、会关：关上时最终名单应等于粗召回截 K，用来对照。

### 变体 13 · 召回分和精排分不能混加

余弦 0.81、BM25 12.4、精排 0.37，三把尺子。上一节已经演过：余弦和 BM25 硬加会翻车。现在多了第三把。

常见错法：`最终分 = 0.5 * 融合分 + 0.5 * 精排分`，两边没拉齐。精排模型输出的 0～1 和融合后的 0～1 也未必同分布。

更干净的生产默认：

> 第一阶段只负责**谁进候选**（分数用来截 N，或给日志看）。  
> 第二阶段分数**单独**决定最终顺序。  
> 不要把精排当分融合的第三通道，除非你专门做了校准，并且评测证明它更好。

生活：初赛用「答题速度」排名取前 50，决赛用「正确率」重排。不会把「秒数」和「百分制」加起来宣布总冠军。

### 变体 14 · 失败在哪一环

模块验收：错误回答要能归因到切分 / 检索 / 重排 / 生成。本条至少要能分清后三环里「检索 vs 重排 vs 生成」（切分是模块 08 / 本模块第 4 条）。

| 你看见什么 | 坏在哪 | 不该先动什么 |
| -- | -- | -- |
| 对的条目连粗召回 N 条里都没有 | 第一阶段召回（或切块、或问句——后两条） | 换更贵的精排器 |
| 对的条目在候选里，但最终 Top-K 没有 | 精排（N 太小截掉、精排器打歪、业务规则挤掉） | 先怪生成「瞎说」 |
| 对的条目已经在最终 Top-K，回答仍错或乱编 | 生成（提示词、没要求引用、模型忽略材料） | 先怪检索 |

Agent 开发要懂这一步：否则会在错误的一层上烧钱。

## 为什么（Agent 开发要懂）

检索增强生成失败，很多时候不是大模型笨，是**喂进去的那几条就不对**。

模块 08 一次截 Top-K，等于让第一阶段同时当裁判。双编码器擅长「方向近」，也擅长把「退货」总则排到「在途碎裂补发」前面——字更像，事不对。生成只看见前 K 条，**没看见的条目等于不存在。** 模型不是「忽略了破损政策」，是你根本没把那条条目喂给它。

上一节混合解决的是另一类漏：编号、专名进不了向量名单。混合之后你仍可能把「很像的总则」排在真正例外规定前面。那是本条的假阳性问题。

不懂两阶段，线上常见三种烧钱方式：

1. 召回就漏了，却去买更贵的精排器。
2. 候选里有对的条目，却直接截第一阶段 Top-5 给生成，精排预算为 0。
3. 材料已经在最终 K 里，却回去调检索参数，其实该改提示词或强制引用。

不懂「业务加权 ≠ 神经精排」，还会多三种烧钱方式：

4. **业务规则改了，误以为模型升级了**：PM 加一条「双 11 主推 +0.5」加权，第二天命中率提升 5%——以为是模型升级，其实是规则加分。换模型厂商后规则没变，效果却掉了。
5. **业务加权静默失效**：业务加权的 `updatedAt` / `tags` / pinned 名单数据源挂了，没人告警，名次静默回到粗召回序，线上命中率悄悄下降。
6. **业务加权和神经精排绑死耦合**：把规则分和神经分揉成一个分数，规则改了想调一栏动两栏；想关业务加权调阈值发现没开关。

## 易混点

| 容易混成 | 其实是 | 判错会怎样 |
| -- | -- | -- |
| 精排 = 把 Top-K 取得更大 | 加大 K / 加大 N 仍是第一阶段窗口；精排是换打分器 | 延迟涨了，假阳性还在最前 |
| 精排 = 再 embed 一次 | 仍是双编码器；交叉编码器是问句和文档一起过 | 以为做了第二阶段，名次几乎不动 |
| 精排 = 混合 / RRF | 融合是合成粗名单；精排是对一份名单再读正文打分 | 上一节勾完就以为本条学完了 |
| 精排 = 查询改写 | 改写改问句（检索前）；精排改名次（检索后） | Demo 两个变量缠在一起 |
| 精排能把没召回的条目「找回来」 | 看不见候选外的条目 | 召回率没动，线上还是漏 |
| 交叉编码器可以替换第一阶段扫全库 | 算力和延迟不允许 | 一上量就超时 |
| 精排分、余弦分、BM25 分是同一种数 | 三把尺子 | 硬加之后「调权重」是在自欺 |
| 用大模型直接生成答案 = 已经精排 | 生成是吃材料写字；精排是决定喂哪几张 | 材料错了，生成越认真越错 |
| 标题含关键词置顶 = 神经精排 | 那是业务规则 | 规则一改，你以为模型变准了 |
| 精排 = 神经精排 | 「精排」是大类（神经精排 / 业务加权 / 混合 / UI 置顶），神经精排是其中一种实现方式；**不是缩写关系** | 90% 场景用神经精排所以常混用，但概念上混会搞错数据源 / 文案 / 开关 |
| 业务加权 = 向量库字段加权 | 业务加权**可以**引用向量库字段，但**也能**引用用户上下文 / 实时状态 / 业务手工名单 | 漏掉其他数据源，业务诉求接不上 |
| 业务加权 = 时间加权 | 时间加权是业务加权**最常见**的一种形态，不是唯一 | 误以为只能按时间 |
| 业务加权 = 神经分 + 0.3 那种简单加法 | 业务加权是**纯本地计算**，不调模型；和神经分是两把尺子叠加，需要校准才能相加 | 调权重调出幻觉 |
| 业务加权 = UI 置顶 | UI 置顶是产品层硬顶一条；业务加权是按规则逐条打分；两者可叠加 | UI 改不动，业务权重调错 |
| 业务加权 = metadata 过滤 | 过滤是召回前硬筛（不进就不进）；加权是召回后软调（在候选里改名次） | 该过滤的没过滤，该加权的没加权 |
| `updatedAt` 必须存在向量库里 | 可以在向量库 metadata / 外键表 / 实时算 | 误以为必须改向量库 schema 才能加业务加权 |
| 业务加权只能加分 | 也可以减分（黑名单降权）、或置零（废弃文档直接过滤） | 只考虑加分路径 |
| 专用精排 API 和聊天模型逐条打分是同一东西 | 前者为相关性训练、分数较稳、可批量；后者为对话训练、贵、分数飘 | 用聊天模型的 0.9 当真当成校准好的概率 |

和已学条目只对照到本步需要的那一层（不换条）：

- 模块 08 余弦 Top-K：那是「一次排序定最终名单」。本条把它拆成 N 和 K 两道截断。
- 上一节混合：解决「必须对上的字 / 口语同义」的**召回**问题，产出仍是粗名单。本条解决粗名单内部「像但不对」。
- 模块 08「库里没有要说不知道」：两边分数都低、精排分也低，仍然应该弃权。精排不是「总能排出一篇来答」。

## 需求清单

验收准绳，不是一次搭完整应用的施工单。每条对应一个变体（或变体组）。把演示写进 apps/ 按知识动态推进；`coach complete` 才按这里逐条对。

**需求 1 · 两阶段名单都看得见**  
业务场景：售后知识库，用户问「杯子在路上碎了能退吗」。  
目标：能说出粗召回和精排各干什么。  
知识点：变体 1、8（问句不变）。  
验收：同一问句、同一库；先出候选 N 条（粗召回），再出最终 Top-K（精排）；两条榜都在页上；精排前后问句字符串相同。粗召回和精排**分请求**，禁止一个接口打包两段轨迹。

**需求 2 · 第二阶段吃的是「问句+文档」成对**  
业务场景：值班同学以为「再 embed 一次」就是精排。  
目标：看见交叉 / 精排器的入参不是单独一篇文档向量。  
知识点：变体 2、3。  
验收：页面或响应里能看见每条送去第二阶段的是问句和该篇正文（或官方精排 API 的 `query` + `documents[]` 形状）；第一阶段仍是向量 / BM25 / 混合，不把交叉编码器拿去扫全库。

**需求 3 · 候选太小，对的条目进不了精排**  
业务场景：B「破损补发」在粗召回第 12 名，产品把 N 设成 8。  
目标：精排救不了召回漏。  
知识点：变体 4。  
验收：同一问句，N=8 时最终 Top-K **没有** B；页面能看见 B 在完整粗召回榜上的名次（在 N 之外）。

**需求 4 · 加大候选后，精排能把对的条目抬进最终 Top-K**  
业务场景：同上，N 改成 30。  
目标：N 是精排的上限，也是可调窗口。  
知识点：变体 4、5、6。  
验收：同一问句 N=30，B 出现在候选里，精排后进入最终 Top-K（最好 Top-1 或 Top-3）；能看见耗时或调用次数随 N 变。

**需求 5 · 假阳性被打下**  
业务场景：A「七天无理由总则」粗召回经常排第一，但没回答「在途碎裂」。  
目标：精排同时打假阳性。  
知识点：变体 6。  
验收：同一问句，A 在粗召回靠前、精排后名次下降（或至少不再压在 B 上面）；两条榜并排可对。

**需求 6 · 和混合融合对照**  
业务场景：上一节已经会 RRF / 加权，有人把融合后的榜直接当精排。  
目标：融合名次 ≠ 精排名次。  
知识点：变体 7。  
验收：同一问句先出融合粗名单，再出精排名单；至少一篇名次不同；不是把 RRF 分数标成 `rerankScore`。

**需求 7 · 点式相关分**  
业务场景：要接 Cohere / Jina 这类「问句 + 文档数组 → 每篇一个分」的 API，或用大模型逐条打分。  
目标：点式是默认线上形态。  
知识点：变体 9、13。  
验收：每篇候选有独立精排分；最终顺序按该分排；分数和余弦分、BM25 分并排展示且**不直接相加**。

**需求 8 · 列表式（或对式）和点式不是同一个输出形状**  
业务场景：有人用聊天模型一次「把这 10 条重排」当精排，和逐条打分混着讲。  
目标：三种打分方式至少再看见一种对照。  
知识点：变体 10。  
验收：同一批候选，点式返回每篇分；列表式返回新 id 顺序（或对式返回「A 比 B 更相关」）。形状能分开看。不要求三种都上专用 API。

**需求 9 · 业务加权和神经精排能拆开**  
业务场景：运营要求「近 30 天改过的制度置顶」；同时，VIP 客户 / 同店商品 / 法规更新等业务诉求要能独立加分，不绑死神经精排。  
目标：业务加权是精排之外的另一条信号源；神经精排打分不变时，名次因业务规则变化。  
知识点：变体 11。  
验收：
- 同一批神经精排结果，开关「新文档加权」或「业务加权开关」；开 / 关是两条**独立请求**（不是同一份数据硬加）。
- 神经分（`rerankScore`）那一栏没动，业务加权后名次换位——至少一条条目仅因业务规则改名次 ≥ 1 位。
- 业务加权榜每行能看见「神经分 + bonus = 综合分」+ 业务加权分（紫色徽标）。
- UI 文案必须把业务加权标成「业务规则 / 业务加权」，不能叫「智能排序」或「交叉编码器」。
- 业务加权这一跳**不调网络**（纯本地按 updatedAt 距离 + bonus 计算），日志里能看到「调用函数」而不是「调用模型」。
- 业务加权的数据源可来自向量库字段（如 `updatedAt`）/ 用户上下文（如 `user.tier`）/ 业务手工名单（如 `pinned_ids`）——本条 step-2 演示的是向量库字段型，其他类型同形。

**需求 10 · 精排可关，关闭后等于粗召回截 K**  
业务场景：延迟不够，或库很小。  
目标：知道何时可以不做。  
知识点：变体 12。  
验收：关闭精排，最终 Top-K 与粗召回前 K 条一致（同序）；打开后至少在本条设定的问句上名次有差异。

**需求 11 · 失败归因三态**  
业务场景：用户投诉「答错了」，值班不知道该加大 N、换精排器，还是改提示词。  
目标：检索漏 / 精排挤掉 / 生成无视材料 能分开。  
知识点：变体 14。  
验收：页面或预置三种情形能对上：① 对的条目不在候选；② 在候选但不在最终 K；③ 在最终 K 但生成没引用它（③ 若本步不调生成，可用「材料已在最终 K」标成生成侧前置条件，生成本身可留到有引用的后续步，但 ①② 必须可观察）。

## 取舍

| 场景 | 更稳的做法 | 不要选的 |
| -- | -- | -- |
| 库大、假阳性多、生成只吃 5 条 | 粗召回 N（20～50）+ 精排再截 K | 直接截第一阶段 Top-5 定生死 |
| 对的条目经常连候选都进不去 | 先修第一阶段（混合、加大 N、切块、后面的改写） | 只换更贵精排器 |
| 要接生产精排 | 专用精排 API（点式、批量、分数较稳） | 用聊天模型逐条闲聊式打分当长期方案 |
| 还没买精排 API、教学要看见名次动 | 用现有对话模型做点式打分（真调模型） | 写死假分数冒充精排 |
| 延迟极紧 / 库极小 / 评测无增益 | 关精排，最终 = 粗召回截 K | 为了「架构齐全」强制每请求打 50 次模型 |
| 运营要置顶新品 | 业务加权单独一列（独立端点、可独立开关） | 和神经精排揉成一个分数还说不清 |
| 业务信号是「该召回哪些」（如只在 VIP 库内搜） | 召回前 metadata 过滤（硬筛） | 走业务加权（业务加权是精排后的软调） |
| 业务信号是「候选里谁更靠前」（如新文档顶上去） | 召回后 / 精排前 / 精排后，三层任选 | 不分层，规则和神经分揉一起 |
| 业务加权的数据源在向量库 metadata | 业务加权那一跳直接读 metadata 字段（最简） | 复制到另一张表再加 |
| 业务加权的数据源是用户上下文（`user.tier`） | 请求时附带，业务加权那一跳读上下文 | 让用户写死在向量库里 |
| 业务加权的数据源是 pinned_ids 名单 | 业务加权那一跳读配置表 / 配置中心 | 改向量库 schema |
| 业务加权静默失效 | 必须有数据源告警（`updatedAt` 字段空 → 业务加权分自动归零 + 报警） | 假装看不见 |
| 业务加权和神经精排叠用 | 两者相加前校准过（两把尺子同分布）；UI 标「业务规则」 | 硬加 +0.3 写进神经精排输出 |

**业务加权的上线流程**（与神经精排独立）：

1. **线下评测**：开 vs 关业务加权，在评测集上对比命中率 / Top-K 变化
2. **看是否真有效**：业务加权经常有名次变化但最终答案没变好——要看到目标指标改善
3. **A/B 上线**：5% ~ 10% 流量开 vs 关对比
4. **监控**：业务规则数据源失效 / 命中率为 0 / 名次波动过大 → 报警

## 踩坑

- **把加大 K 当成精排**：窗口变大了，假阳性仍在最前。精排是换打分器，不是加长名单。
- **再 embed 一次冒充交叉编码器**：拼接后仍是双编码器，名次几乎不动，却以为做了第二阶段。
- **把 RRF / 加权融合标成 rerankScore**：融合没有读正文。对照必须是「融合榜 vs 精排榜」，不是换个字段名。
- **以为精排能找回没召回的卡**：N 之外等于不存在。召回率没动就先别买精排。
- **写死精排分**：本条要证明的是第二阶段读了问句和正文之后名次会变。本地写死的分数不算。
- **一个接口打包粗召回 + 精排**：对照看不出两阶段各自产出。必须分请求。
- **一次加上精排 + 查询改写**：效果变了不知道是谁的功劳。本模块验收写明：一次只加一个变量。
- **精排分和余弦 / BM25 硬加**：三把尺子。最终顺序默认只跟精排分。
- **用聊天模型的 0.9 当真概率**：对话模型不是为相关性校准训练的；专用精排 API 才是点式生产默认。
- **业务置顶和神经精排揉成一句「智能排序」**：规则一改，你以为模型变准了。
- **业务加权静默失效**：业务加权依赖的 `updatedAt` / `tags` / pinned 名单数据源挂了，没人告警，名次静默回到粗召回序，线上命中率悄悄下降。修复：数据源空值 / 异常 → 业务加权分自动归零 + 监控告警。
- **业务加权和神经精排绑死耦合**：把规则分和神经分揉成一个分数，规则改了想调一栏动两栏；想关业务加权调阈值发现没开关。修复：业务加权独立端点、独立开关、文案分清「业务规则」/「相关性」。
- **业务加权只在「开关=关」时看见对照就以为讲完了**：开关 off 时最终榜 = 神经精排榜，这只是「业务加权不影响」——还没看见业务加权**真起作用**的画面（神经分不变、规则改名次）。必须在开关 on 时看到至少一条条目名次因业务加权变化 ≥ 1 位。
- **业务加权的数据源假设**：以为 `updatedAt` 必须在向量库里 / 以为只能按时间加权 / 以为业务加权只能加分。修复：业务加权能引用任何数据源（向量库字段 / 用户上下文 / 实时状态 / 业务手工名单），加减分都行。
- **统一术语：知识库里的每一条记录业界标准叫 `chunk（文档片段）`**。本条教学界面统一用「知识库条目」或「一条记录 / 一条政策」，不再叫「卡片 / 一张卡 / 一张卡片」。踩坑：之前用「卡片」让学习者反复追问「一张卡到底是什么」（连问两轮才发现他指的就是知识库里的一条政策）。统一术语后学习者立刻明白——本 demo 的 `knowledge-base.ts` 里 25 条 `id` + `kind` + `text` 就是 25 个 chunk。

## 过关自检

关上文件还能讲出来，用售后的话说：

> **粗召回负责把可能对的条目捞进候选；精排负责在候选里决定谁喂给生成。** 两阶段用的不是同一种模型：双编码器能扫全库，交叉编码器准但只能打短名单。没进候选的条目，精排救不回来。精排也不是上一节的融合，更不是下一节的改写问句。看见同一问句两条榜、名次会跳，才算讲清「不是一次 Top-K 定生死」。

对着需求 1 的主对照：同一库、同一句「杯子在路上碎了能退吗」，粗召回和精排分两次请求，两条榜并排，B 升、A 降。

对着需求 9 的对照：同一句同一批神经精排结果，开关业务加权前后两条请求：
- **神经精排榜**（左）：每行只显示神经分；policy-B #2 / sku-K #10
- **业务加权榜**（右）：每行显示「神经分 + bonus = 综合分」+ 紫色「业务加权」徽标；policy-B #1 / sku-K #7（升 3 位）
- 神经分没动，名次变化完全来自业务规则——这才是「业务加权 ≠ 神经精排」的可讲画面。

> **粗召回负责把可能对的条目捞进候选；精排负责在候选里决定谁喂给生成；业务加权负责在已经排好的名次上按规则再调。** 三个动作不是同义词：粗召回看「对的在不在」，精排看「候选里谁该喂给生成」，业务加权看「按业务规则再顶一下」。每层用的不是同一种信号——召回是向量 / 关键词，精排是模型读问句+正文，业务加权是规则按数据源（向量库字段 / 用户上下文 / 实时状态 / 业务名单）加分。没进候选的条目，精排救不回来；进了候选但神经分低，业务加权能顶上去；业务加权数据源挂了，名次静默回到精排原序——三环都能坏，事故排查要分开看。
