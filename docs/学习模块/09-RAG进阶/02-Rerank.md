## 是什么

**一句话（进度表要能讲清的）**：粗召回（Retrieval / 第一阶段）从整库捞一批候选；精排 / 重排序（Rerank / 第二阶段）只给这批重新打「和**这一句问话**有多配」的分，再取新的前 K 条（Top-K）交给生成（Generate）。桌上没有的切块（Chunk），精排变不出来。不是一次粗召回的前 K 条定生死。

模块 08 默认：检索完直接取前 K 条就生成。上一节停在「两份粗名单怎么合成」。本条补中间这一步：**名单已经在了，顺序常常不对；不要把整份名单都喂给生成。**

**重排序（Rerank）** = 检索已经出了一份**比较宽的候选名单**之后，再用一个**更贵、但更会看「这句话和这一段配不配」**的模型，把名单重新打分、重新排队，最后只把新的前 K 条塞进提示词（Prompt）。

人话：粗召回是「先把可能有关的从仓库里搬到桌上」；精排是「趴在桌上，一对一对地看，哪几张真该给客服」。

```text
用户问句
    → 粗召回（Retrieval / 第一阶段）
         向量 / BM25 / 混合，从整库捞 N 条（例如 50）
    → 精排（Rerank / 第二阶段）
         只对这 N 条，把「问句 + 这一条切块」成对打分
    → 按精排分重新排队，取新的前 K 条（例如 5）
    → 这 5 条才进提示词，交给生成
```

| 阶段 | 看谁 | 干什么 | 快慢 |
| -- | -- | -- | -- |
| **粗召回** | 整座库（可能几万条） | 把「可能有关」的搬上来，宁宽勿漏 | 必须快：问句和切块**分开编码**，再比远近 |
| **精排** | 只看桌上这 N 条 | 判断「对这一句，哪几条真相关」，改顺序 | 可以慢：每次把问句和切块**拼在一起看** |

精排**不会**去库里再找一遍。

## 为什么（Agent 开发要懂）

检索增强生成失败，经常不是生成模型笨，是**正确切块没进提示词，或进了但排太靠后、被通用段落抢走注意力**。

客服问：「超过 7 天了，盒子没拆，还能退吗？」

库里同时有：

- 切块 A：七天无理由退货（「退」「7 天」都对得上，粗召回很容易第一）
- 切块 B：电子产品保修须知（意思近）
- 切块 C：未拆封、超期可申请特例审核（真正该引用的那条）

混合检索很可能把 C 捞进前 50，但排在第 15。生成如果只吃前 5 条，会按 A 回答「不行」。用户觉得机器人在念条款，工单升级。

你有两条路，都不免费：

- **把前 20 条全塞进提示词**：Token 预算（Token Budget）涨、噪音涨，模型仍可能抱着 A 不放。
- **先精排，再只塞 5 条**：多一次打分成本，但生成看见的材料干净。

Agent 要懂的后果就三句：

1. **生成只对你喂给它的前 K 条负责。** 排在 K 之外的切块，对它来说不存在。
2. **粗召回擅长「别漏」，不擅长「谁该第一」。** 混合检索解决「编号 / 口语两边都要进名单」；进了名单之后谁排前面，是这一小节的事。
3. **精排救不了「根本没被捞上来」。** 切块切坏了、召回 N 太小、混合也没覆盖——精排只是在错误名单里换座位。这时要回头查召回，不是再加一个更贵的精排模型。

## 核心对象

| 核心对象 | 管什么 |
| -- | -- |
| **粗召回（First-stage Retrieval）** | 从整库捞 N 条候选。上一节的向量 / BM25 / 混合都是这一阶段的实现 |
| **精排 / 重排序（Rerank）** | 只给这 N 条重新打「和这句问话有多配」的分，再取前 K 条 |
| **双塔编码器（Bi-encoder）** | 问句、切块**分开**变成向量，比余弦。快，能扫全库；从不在同一次计算里看见「这一对」 |
| **交叉编码器（Cross-encoder）** | 把问句和切块**拼成一段**再跑模型，直接出相关分。准，慢，不能扫全库 |
| **候选窗（Candidate Pool / Recall@N）** | 桌上有几条。精排的天花板 = 这扇窗 |
| **逐条打分（Pointwise）** | 每一对「问句 + 切块」独立出一个分 |
| **成对比较（Pairwise）** | 问「A 和 B 哪个更相关」 |
| **整份名单重排（Listwise）** | 一次把 N 条标题/摘要交给模型，让它给出新顺序 |
| **专用重排序接口** | 例如 Cohere Rerank、Jina Reranker：一次请求，问句 + 文档数组，回每条分数 |
| **用对话模型当重排序器（LLM-as-Reranker）** | 不另接重排序接口，让聊天模型给 0～1 分或直接重排 |

## 各变体

### 变体 1 · 两阶段流水线：粗召回捞、精排改顺序

粗召回回答：「整库里哪些可能有关？」精排回答：「对**这一句**，桌上谁该排前面？」

```text
问：超过 7 天了，盒子没拆，还能退吗？
  粗召回 Top-5（举例）：
    1. 七天无理由退货
    2. 电子产品保修须知
    3. 退货运费谁承担
    4. 质量问题 15 天包退
    5. 会员积分规则
  精排后 Top-5：
    1. 未拆封超期可申请特例审核   ← 原来可能在第 15
    2. 七天无理由退货
    3. 质量问题 15 天包退
    …
```

生活：派出所先按辖区拉 50 个可能相关的人（粗），再逐个对照片（精）。  
前端：全局搜索先用倒排索引捞 50 篇，再对这 50 篇算「和当前报错栈配不配」。

### 变体 2 · 双塔分开看 vs 交叉编码器成对看

双塔从不在同一次前向里看见「问句和切块这一对」。它只能说「两个方向近不近」。所以「7 天」和「退货」很容易把通用政策推到第一，即使问句里还有「没拆」「超过」。

交叉编码器（以及用对话模型拼在一起打分）看见的是**整对**：问句里的「没拆 + 超过 7 天」和切块里的「未拆封 + 超期特例」对得上。

生活：相亲软件先按标签筛 50 人（双塔），见面聊天才知道合不合（交叉）。标签近 ≠ 见面合适。  
前端：用商品标题向量做相似推荐（双塔）；用户点进详情后，用「搜索词 + 详情全文」再打一次相关分（交叉）。

数据怎么走：双塔像电商的「用户向量 × 商品向量」——商品向量可以离线算好，查询时只做近邻。交叉编码器像「每次把搜索词和这篇详情拼成一篇短文，重新读一遍」——所以只能处理桌上那几十条。

### 变体 3 · 候选窗：不在桌上，精排变不出来

精排的输入 = 粗召回的输出。正确切块若在第 80 名、你只召回 50，精排再贵也没有那一条。

```text
召回 N = 20，正确切块在第 37
  → 精排输入里没有它
  → 新的前 5 条无论怎么换，都是错的
  → 这时该加大 N、修切块、或回到混合检索，而不是换一个精排模型
```

生活：桌上就没有那本说明书，你再怎么翻桌上的书也找不到那一页。  
前端：接口 `limit=20`，目标记录是第 37 页——后面再 `sort` 也救不回。

### 变体 4 · 精排能救：已经在名单里，只是排太靠后

这是重排序最该被看见的一次成功：正确切块在召回名单里（比如第 15），精排后进入生成能看见的前 K 条（第 1）。

关上文件后要能说：我看见的不是「多搜到了一条」，是**同一条切块的名次被抬上来了**。

生活：50 份简历里本来就有对的那份，只是被关键词排序压到第 15；人工精读后提到第 1。  
前端：issue 搜索里标题含「7 天」的通用帖在最前；带「未拆封特例」的帖子在第二页；按「和当前问句的成对相关分」重排后它到第一页。

### 变体 5 · 精排救不了：窗里没有，或精排自己也排错

两种失败不要混：

| 失败 | 桌上有没有正确切块 | 你该查哪 |
| -- | -- | -- |
| 召回就没捞到 | 没有 | 切块、混合、N 够不够 |
| 捞到了，精排仍把通用政策排第一 | 有 | 精排模型 / 提示词、问句是否缺关键约束 |

精排模型也会错：它可能更喜欢「措辞完整的官方条款」，而不是那条短短的特例。看见「精排后还是错的」要能说出是哪一种失败，不能笼统说「重排序没用」。

生活：桌上有对的说明书，但你按封面漂亮程度重排，仍可能把通用手册放最前。  
前端：相关分模型被「标题更长、词更全」的文档骗了，短而准的那条仍排后面。

### 变体 6 · 多塞给生成 vs 先精排再少塞

「我不精排，把召回的 20 条全喂给大模型」看起来省事，代价是：

- Token 预算被 20 段政策占满
- 模型更容易引用反复出现的「七天无理由」
- 延迟和钱都涨，还不一定比「精排后 5 条」更准

精排的产品意义：用一次较贵的打分，换生成阶段更少、更干净的上下文（Context）。

生活：把整抽屉说明书扔给师傅，vs 先抽出那 3 页相关的。  
前端：把 20 个组件的源码塞进当前请求，vs 先按「和报错栈有多配」取出 5 个文件再问模型。

### 变体 7 · 三种分数不是同一把尺子

粗召回可能留下余弦相似度（Cosine Similarity）、BM25 分、混合分；精排再留下 0～1 或 logits。**不要把精排分和余弦分相加，也不要拿绝对值跨问句比「这个 0.9 一定比那个 0.8 更稳」。**

页面上必须能分开看：召回用的分、精排用的分、名次变化。混成一个「分数」列，关上文件会以为它们能比大小。

生活：期末百分制和面试 A/B/C 不能直接加。  
前端：`score` 字段来自两套模型，界面要写清「召回分」和「精排分」，不要只渲染一个数字。

### 变体 8 · 逐条打分（Pointwise）——这一小节的主路径

对桌上每一条问：「这句话和这一段有多相关？」得到一个独立分数，再排序。教学上最好懂，也最好观察：你能看见**每一对**的分。

用对话模型做，就是对每条候选发一次（或一批）「只打分、不要回答用户」的请求。N=20 就是大约 20 次模型调用，贵，但机制干净。

生活：老师给每份作业单独打 0～10 分，再按分排队。  
前端：对 20 条搜索结果各请求一次 `relevance: number`，再 `sort`。

### 变体 9 · 成对比较（Pairwise）

不问「A 是 0.8 分」，问「A 和 B，哪一段更该回答这句话？」适合难分伯仲的两条政策。代价：比较次数可以到 N×(N-1)/2，或你只比较前几名。分数不可直接当概率。

生活：两份简历放一起问「谁更适合这个岗位」。  
前端：对前两名争议结果做一次 A/B，而不是再出两个 0～1。

### 变体 10 · 整份名单一次重排（Listwise）

一次把 N 条的标题或摘要塞进上下文窗口（Context Window），让模型直接输出新顺序。调用次数少（常常 1 次），但：

- N 一大就撞上下文窗口
- 模型可能漏编号、发明名次
- 你必须校验：输出的 id 是不是桌上那批，有没有丢、有没有编

生活：把 20 份简历一次性摊开，请人排出前 5。  
前端：一个请求丢 20 个 `id + title`，回 `orderedIds`；回了桌上没有的 id，就当失败，不能静默采用。

### 变体 11 · 什么时候可以不做精排

精排不是默认必开。可以不做的典型情况：

- 库很小，粗召回前 5 条已经对
- 延迟预算吃不下（精排可能多几百毫秒到数秒）
- 钱不够：逐条打分 × 高峰每秒请求数（QPS）
- 你已经评过：加精排，检索命中率几乎不动

不做精排时，系统退化成模块 08 / 上一节：召回的前 K 条直接生成。这是明确的产品取舍，不是漏做。

生活：家里只有 3 本说明书，不必先「精排」。  
前端：配置项只有 8 条，直接列表，不必上相关分模型。

### 变体 12 · 精排叠在混合检索之后，不替代混合

上一节的混合检索解决「谁有资格上桌」：编号靠 BM25，口语靠向量。精排解决「上桌之后谁坐主位」。

常见错法：

- 只用精排、丢掉混合：编号切块可能根本不上桌
- 以为精排是「第三种检索」：它不扫全库
- 把混合分再和精排分硬加：尺子又混了

正确叠法：混合（或向量 / BM25）→ 得到 N 条 → 精排只看这 N 条 → 生成只看新的 K 条。

查询改写（下一节）发生在检索**之前**：先改问句，再去搜。精排发生在检索**之后**：问句已经搜过了，只改顺序。本条只划开，不整节讲改写。

生活：先用身份证 + 外貌各出一份名单并合并（混合），再对合并名单面试（精排）。面试不会把没进名单的人变出来。  
前端：搜索服务先 hybrid，再对这一页做 rerank 字段；改写搜索词是另一个中间件，挂在请求进检索之前。

### 变体 13 · 专用重排序接口 vs 用对话模型打分

| | 专用接口（Cohere / Jina 等） | 对话模型逐条或整份打分 |
| -- | -- | -- |
| 请求形状 | 一次：`query` + `documents[]` → 每条 `relevance` | 多次聊天，或一次很长的名单 |
| 延迟 / 钱 | 按设计就是打分，通常更稳 | 逐条会爆调用次数；整份吃上下文 |
| 教学 | 能看见业界真实字段 | 不另申请重排序密钥也能把机制跑出来 |
| 和生成模型 | 通常不是同一个模型 | 可以和回答用同一家，但任务不同：一个出分，一个出回答 |

两种都是第二阶段，不是两种「检索」。选哪一种是工程取舍，不是对错题。第一步演示可以用对话模型逐条打分，不必先申请 Cohere / Jina 密钥。

## 易混点

| 容易混成 | 差在哪 | 判错会怎样 |
| -- | -- | -- |
| 精排 = 又一次混合检索 | 混合是两边从整库出榜再融合；精排只给已有名单打分 | 你会以为精排能补回编号漏召回；补不回 |
| 精排 = 把前 K 条加大 | 加大 K 是让生成看见更多噪音；精排是改顺序后再截断 | Token 涨了，引用仍可能错 |
| 精排 = 查询改写 | 改写改的是进检索的那句话；精排改的是出来之后的顺序 | 你会在错的环节调参 |
| 精排分 = 余弦分 | 模型不同、量纲不同 | 硬加之后其实只听其中一把尺子 |
| 精排能「找全库」 | 交叉编码器不能扫全库 | 延迟爆炸，或你误以为漏召回能被精排修好 |
| 双塔已经「看见这一对了」 | 双塔只看见两个向量，没看见拼接后的句子 | 解释不清为什么通用政策总排第一 |
| 整份名单重排一定更省 | 省的是调用次数，花的是上下文；还可能编 id | 静默采用编造名次，生成引用鬼切块 |

## 例子

**核心对象各演一遍（生活 + 前端），数据怎么走：**

| 核心对象 | 生活 | 前端 |
| -- | -- | -- |
| 粗召回 | 先走到零食货架，不要翻全商场 | `filter` / 索引先出 50 条候选 |
| 精排 | 蹲下来看配料：儿童、无坚果、小包装 | 只对这 50 条跑贵的相关分，再 `sort` |
| 双塔 | 按标签筛 50 个相亲对象 | 标题向量近邻推荐 |
| 交叉编码器 | 见面聊天才知道合不合 | 「搜索词 + 详情全文」再打一次分 |
| 候选窗 | 桌上没有那本说明书 | `limit=20` 捞不到第 37 条 |
| 名次抬升 | 对的简历从第 15 提到第 1 | 同一 `id` 从召回第 15 到精排第 1 |
| 逐条打分 | 每份作业单独 0～10 | 每条 `relevance: number` |
| 成对比较 | 两份简历放一起比 | 只比 Top-2 谁赢 |
| 整份名单重排 | 20 份简历一次排出前 5 | 一次回 `orderedIds`，校验桌上有没有 |
| 可以关掉 | 家里只有 3 本说明书 | 配置项 8 条，直接列表 |
| 叠在混合后 | 先合并两份名单再面试 | hybrid 的文档数组 = 精排输入 |
| 专用接口 / 对话模型 | 请专业面试官 vs 请同事逐份打分 | `query + documents[]` vs 多次聊天打分 |

主场景（售后知识库）贯穿各变体：问句「超过 7 天了，盒子没拆，还能退吗？」；通用七天政策容易在粗召回排第一；「未拆封超期可申请特例」才是该引用的切块。

## 需求清单

每条对应一个变体。定位 = **验收准绳**，不是第一步就把整份应用搭完。step 仍按知识动态推进。

**需求 1 · 两阶段对照**  
业务场景：售后知识库，同一句「超过 7 天、盒子没拆，还能退吗」。  
目标：页面同时看见粗召回名单和精排后名单。  
知识点：变体 1。  
验收：一次操作后，能指出「第一阶段从整库捞 N 条，第二阶段只给这 N 条打分」；不是只显示最终前 K 条。

**需求 2 · 分开看 vs 成对看**  
业务场景：通用七天政策靠关键词 / 向量排第一，特例条款靠「问句 + 正文成对」才能翻盘。  
目标：能解释双塔为什么总推通用政策。  
知识点：变体 2。  
验收：能对照「召回分（分开编码）」和「精排分（成对）」两列，不是一个合并分数。

**需求 3 · 候选窗救不回**  
业务场景：特例切块故意放在召回窗之外（N 小于它的召回名次）。  
目标：证明精排不能创造切块。  
知识点：变体 3。  
验收：页面标明「正确切块不在候选里」；精排后前 K 条仍没有它。

**需求 4 · 名次被抬上来**  
业务场景：特例切块在召回名单里但在 K 之外（例如第 15）。  
目标：看见同一 `id` 从召回第 15 到精排第 1。  
知识点：变体 4。  
验收：名次变化表里是**同一条切块**，不是「精排新搜到一条」。

**需求 5 · 精排仍错，且能归因**  
业务场景：窗里有正确切块，但精排仍把通用政策排第一；另给一条「窗里没有」的对照。  
目标：两种失败能分开说。  
知识点：变体 5。  
验收：一种显示「在名单里仍排错」，一种显示「不在名单里」；禁止只显示一个红叉。

**需求 6 · 少塞 vs 多塞**  
业务场景：同一问句，一边把召回 20 条估计成即将塞进提示词的 Token，一边只统计精排后 5 条。  
目标：讲清为什么不把整份召回塞给生成。  
知识点：变体 6。  
验收：能看见条数和 Token 量级对比；不是一句文案「精排更准」。

**需求 7 · 分数分列**  
业务场景：同一条切块同时有召回分、精排分。  
目标：两把尺子不混加。  
知识点：变体 7。  
验收：界面分列；没有「综合分 = 余弦 + 精排」这种硬加（除非先写明经过归一且那是另一步实验）。

**需求 8 · 逐条打分主路径**  
业务场景：对候选每一条打 0～1（或模型返回的相关分）。  
目标：看懂逐条打分（Pointwise）。  
知识点：变体 8。  
验收：每一条候选都能看见自己的精排分；排序由这些分决定。

**需求 9 · 成对比较**  
业务场景：通用七天 vs 未拆封特例，只问谁更该回答当前问句。  
目标：看懂成对比较（Pairwise）。  
知识点：变体 9。  
验收：一次请求只比较两段，回谁赢；不是又出两个 0～1 冒充成对比较。

**需求 10 · 整份名单一次重排**  
业务场景：把候选 id + 标题一次交给模型，要新顺序。  
目标：看懂整份名单重排（Listwise）和它的校验。  
知识点：变体 10。  
验收：回了桌上没有的 id 或漏 id，页面当失败，不静默采用。

**需求 11 · 可以关掉精排**  
业务场景：库只有很少几条，或开关关闭精排。  
目标：系统退化成「召回前 K 条直接当生成材料」。  
知识点：变体 11。  
验收：关闭后名单等于粗召回截断，不再发精排请求。

**需求 12 · 叠在混合之后**  
业务场景：先得到混合（或本步的粗召回）名单，再精排。  
目标：精排不替代混合 / 不扫全库。  
知识点：变体 12。  
验收：能看见「进精排的那份名单来自召回」；精排请求的文档数组 = 召回结果，不是再扫全库。

**需求 13 · 专用接口 vs 对话模型打分**  
业务场景：同名单，一侧走「问句 + 文档数组」的重排序接口形状，一侧走对话模型打分（至少一侧真发请求）。  
目标：两种第二阶段实现能划界。  
知识点：变体 13。  
验收：请求形状能分开看；禁止一个接口打包跑两种实现还只回一个榜。

## 取舍

| 场景 | 更稳的做法 | 不要选的 |
| -- | -- | -- |
| 正确切块常在召回名单里但排在前 K 条之外 | 召回 N 条（N > K）再精排，生成只吃新的前 K 条 | 直接加大生成看见的 K，把 20 条政策全塞进提示词 |
| 编号 / 口语两种问句都要上桌 | 先混合检索凑名单，再精排 | 只用精排替代混合 |
| 教学要看见「每一对」的分 | 对话模型逐条打分（Pointwise） | 一上来接专用接口，分数从哪来看不见 |
| 生产要稳、QPS 高 | 专用重排序接口，或本地交叉编码器 | 对每条候选都打一次聊天补全 |
| 只要比两条谁更该回答 | 成对比较（Pairwise） | 再出两个 0～1 假装在比 |
| 想少调用次数、名单不长 | 整份名单一次重排，并校验 id | 不校验就采用模型吐出的顺序 |
| 库很小、召回前 5 条已经对、延迟吃紧 | 关掉精排，召回截断直接生成 | 默认必开精排 |
| 效果变了要归因 | 一次只加一个变量（本模块常见坑） | 同时加上精排 + 查询改写 + 换切块 |

---

## 踩坑

- **以为精排会再搜一遍全库**：交叉编码器不能扫全库。漏召回只能回头修召回。
- **正确切块在窗外还怪精排模型**：先看候选窗里有没有那条 `id`。
- **把召回 20 条全塞给生成当「不用精排」**：Token 和噪音一起涨，模型仍可能抱着通用政策。
- **余弦分 + 精排分硬加**：两把尺子，硬加等于乱听。
- **一个接口打包「召回轨迹 + 精排轨迹」**：对照看不出两阶段各干什么。召回和精排要能分开看见。
- **整份名单重排不校验 id**：模型漏编号或发明名次，生成会引用鬼切块。
- **一次加上混合 + 重排序 + 查询改写**：效果变了不知道是谁的功劳。本模块验收写明：一次只加一个变量。
- **用对话模型打分却让它「回答用户问题」**：第二阶段的任务是出分或出顺序，不是出最终答复。

## 过关自检

关上文件还能讲出来：

> **粗召回从整库捞一批候选；精排只给这批重新打「和这句问话配不配」的分，再交给生成。** 双塔分开编码，所以通用政策容易排第一；交叉编码器 / 成对打分才看见「没拆 + 超过 7 天」。桌上没有的，精排变不出来。看见同一条切块从第 15 到第 1，才叫精排救到了，不是又搜到一条。不要把 20 条全塞给生成，也不要把精排分和余弦分硬加。精排不替代混合，也不替代查询改写。

对着需求 1 + 4 的主对照：同一问句，召回名单和精排名单并排；特例切块是**同一 `id`** 被抬上来。
