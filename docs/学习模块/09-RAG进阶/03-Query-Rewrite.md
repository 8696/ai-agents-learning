## 是什么

**一句话（进度表要能讲清的）**：用户怎么说话 ≠ 知识库怎么写字。库里其实有那段该引用的正文，问的也是同一件事，只是两边用词（或问句形态）对不齐，检索对不上。查询改写（Query Rewrite）发生在检索（Retrieve）之前：先把用户那句话变成更像库里会写出来的检索词（或补上库里会出现的词），再去搜。查询扩展（Query Expansion）是旁边另一种动手方式——原句先留着，往**同一条**查询里补词。

检索单位叫 **切块（Chunk）**：库里一段可单独打分、单独塞进提示词（Prompt）的正文。多数是政策、说明、条款，写成陈述句，不是「切块里的问题」。要对上的是：

```text
用户这句话  ←→  能回答这句问话的那一段正文
```

不要叫「切片」——容易和数据集切分混在一起。也没有「向量切片」：向量只是检索通道之一，切块本身是文本。

人话：用户问「盒子没拆、超期了还能退吗」。库里那一段写「未拆封商品超过七日的特例审核」。两边说的是同一件事，**字对不上**。不改问句，BM25 对不上关键词；向量也可能漂到「七天无理由」那条通用政策上。改写不是让模型替你回答，是**先把送进检索器的那串字对齐**。

```text
用户原句（日常说法、指代、短、缺实体）
    │
    ▼
查询改写 / 查询扩展 / 假想文档嵌入（本条）
    │  产出：更好搜的问句（有时还多带几个词）
    ▼
粗召回（向量 / BM25 / 混合）
    │
    ▼
精排（上一节，改顺序，不改问句）
    │
    ▼
生成（Generate）← 提示词里仍应保留用户原句
```

**和上一节的分工**：精排问「已经捞上来的谁该第一」；改写问「这句话拿去搜，会不会把对的捞上来」。正确切块没进检索名单，精排再准也变不出来。

下一节才会把「一次生成多条问句、分别检索再合并（Multi-query）」和「一条查询补词（Query Expansion）」对照成两类失败补丁，并和切块策略放在一起。本条只要求：能说清**问句本身为什么要动、改写和扩展差在哪、假想文档嵌入（HyDE）又是另一条路**。

## 为什么（Agent 开发要懂）

检索增强生成（RAG）失败，上一节看见的是「正确切块在第 15 名，生成只吃前 5 条」。更前面还有一种失败：**正确切块连候选窗都没进。**

售后助手，用户说：

> 「盒子没拆，都八天了，还能退吗？」

库里真正该引用的切块写的是：

> 「未拆封商品超过七日可申请特例审核。」

| 只做这件事 | 常见结果 | 救得了吗 |
| -- | -- | -- |
| 只用向量 | 「退」的意思漂到「七天无理由」通用段，特例段不一定进前 N | 部分 |
| 只用 BM25 | 用户句里没有「未拆封 / 特例 / 七日」这些库词 | 经常救不了 |
| 上一节的精排 | 特例段没进检索名单，精排再准也变不出这条 | **救不了** |

Agent 要懂的后果三句：

1. **生成只对喂进去的切块负责。** 问句和库用词对不上 → 检索捞空或捞偏 → 后面精排、引用、评测全是在错误材料上演戏。
2. **上一节修顺序，这一节修入口。** 不是「有向量就不用改写」：向量已经在补「用词不同」；改写补的是更前面一层——把送进检索器的字符串，变得更像库里会写出来的那句话。
3. **改写会多花一次模型调用（或一张同义词表），也会改偏意图。** 问句已经是货号、条款编号、库里原词时，再改写可能把锚点改丢。不是默认永远开。

生活例子：你跟图书管理员说「那本把宇宙讲成故事的薄书」。目录里写的是《时间简史》。按原话搜书名会零命中；他先改成「霍金 时间简史 宇宙通俗」，才能找到。你看见的还是自己那句话，他内部已经换过检索词。

前端例子：搜索框用户打「退」。你不会把这三个字原样丢进 Elasticsearch。中间件先做同义词、纠错、补「七天无理由」。地址栏里用户仍看见自己打的字；索引吃到的是改过的查询。这和 Next.js 的 `rewrites` 是同一类分工：**对外仍是用户原路径，对内换成能打中资源的路径。**

## 核心对象

| 核心对象 | 管什么 |
| -- | -- |
| **词汇鸿沟（Lexical Gap）** | 用户用词和库用词不是同一套。这是本条的根因，不是模型「没读懂」 |
| **查询改写（Query Rewrite）** | 同一意图，把问句换成库里更可能出现的词；通常仍是**一条**查询 |
| **查询扩展（Query Expansion）** | 原句保留，往同一条查询里补同义词 / 政策名 / 货号 |
| **假想文档嵌入（HyDE，Hypothetical Document Embeddings）** | 不把问句改成关键词，而是让模型先写一段「如果库里有答案，那段大概长这样」，用这段去向量检索 |
| **多轮指代改写** | 「这个 / 那个 / 还能吗」要靠上一轮对话补成完整问句 |
| **检索用改写句 / 生成用原句** | 检索对齐库；生成和展示仍对着用户原话 |
| **意图漂移（Intent Drift）** | 改写把「能不能退」变成「怎么走退款流程」，搜到了另一类文档 |
| **流水线位置** | 改写在检索前；精排在检索后。两者不是替代关系 |
| **HyDE 不是补问句** | 把 HyDE 当成残句补全 | HyDE 产出是陈述段（陈述句 + 条款口吻 + 80~150 字），不是疑问句；残句补全（变体 5）才是补问句 |
| **HyDE 不是补真实切块** | 以为 HyDE 把库里没的切块"补"进来 | HyDE 产出是模型按知识编的，库里没有这条；只用作检索探针（不展示给用户）|
| **HyDE 不是字面匹配** | 拿假想段跑 BM25 | 假想段是模型编的、库是人工写的，字面不重合 → BM25 零命中；HyDE 用**余弦相似度**（向量匹配），靠「形态相同」（都是陈述段 + 条款口吻）在嵌入空间里近 |

## 每一种情况（变体）

### 1. 词汇鸿沟：同一件事，两套词

用户句进检索器，和切块比的是**字面或向量**，不是「意图说明书」。库写「未拆封 / 七日 / 特例审核」，用户写「盒子没拆 / 八天了 / 还能退吗」。BM25 要词重叠；向量要嵌入空间近。两套词既不重叠、嵌入也可能更靠近通用「退货」段。

生活：病人说「胸口闷得慌」，病历编码写「胸痛待查」。急诊分诊必须改词，否则检索指南会打到消化科。  
前端：站点内搜索用户打「怎么退」，`documents.title` 是「Return Policy · Unopened Exception」。不改写等于按原文模糊匹配标题。

判错会怎样：你以为是生成模型笨，其实正确切块从未进入提示词。

### 2. 同一意图换词（改写的主路径）

```text
原句：「盒子没拆，都八天了，还能退吗？」
    → 改写模型 / 规则
改写句：「未拆封 超过七日 退货 特例审核」
    → 用改写句做粗召回
特例切块进名单（甚至进前几名）
    → 需要的话再精排
    → 生成时提示词里仍放用户原句
```

生活：你对客服说「外壳都没撕」，客服在工单系统搜的是「未拆封」。  
前端：把用户输入规范化成搜索 API 的 `q`，响应里 `displayQuery` 仍是原句。

**和扩展的差别**：改写可以整句替换；扩展是「原句 + 补丁」，还是一条查询。

### 3. 一条查询补词（扩展）

原句不够胖，补上库里的词，仍一次检索。

```text
原句：「还能退吗」
扩展句：「还能退吗 七天无理由 未拆封 特例审核 SKU-88」
    → 一次 BM25 / 混合
```

生活：图书馆目录搜「宇宙」太吵；补上「霍金 通俗 物理」，还是一次搜索，不是连搜三次再人工合并。  
前端：搜索建议把「退」补成「退 七天无理由」，用户点补全后仍是一个请求。

下一节会讲：有时一条再胖也不够，要**同时生成多条问句分别检索再合并**。本条先分清：扩展 ≠ 多条查询。

### 4. 假想文档嵌入（HyDE）

问句太短、太口语、几乎没有实体时，改写成关键词也瘦。HyDE 换一条路：

```text
用户原句
    → 让模型写一段「若知识库有标准答案，那一节大概会怎么写」
假想段落（看起来像政策正文，不是搜索关键词）
    → 对假想段落做嵌入（Embedding）
    → 用这段向量去库里做向量检索
    → 真切块里「写得像这段」的会排前面
```

为什么有时比改写问句更灵：向量检索比的是「这段话和那段话像不像」。假想答案和库里的政策段，都是「陈述句、条款口吻」；用户原句是「疑问句、口语」，在嵌入空间里常常离政策段更远。

生活：你说「有没有那种把宇宙讲成故事的书」。管理员先在脑子里生成一段简介，拿简介去对目录摘要，而不是拿口头禅去对书名。  
前端：搜索框只有三个字。不拿三个字做嵌入，先让模型写 80 字 FAQ 风的假想回答，再拿这 80 字去打向量索引。

**坑**：假想段落写飞了（写成「如何在线提交退款工单」），检索会稳定打到流程页，而不是资格条款。假想文档不是事实，只是检索探针，不要展示成客服回复。

**HyDE 是补「假想的切块」—— 不是问句、不是真实切块（2026-09-14 补）**：

| 路径 | 产出形态 | 形态特征 |
| ---- | | | 
| 残句补全（变体 5）| 独立问句：「SKU-88 未拆封超过七天能否退货」| 疑问句、仍带意图 |
| 改写（变体 2）| 改写问句：「未拆封 超过七日 特例审核」| 库用语关键词 |
| **HyDE（变体 4）** | **假想政策段**：「未拆封商品超过七日的特例审核……审核通过后由质检决定收货……」| **陈述段 +条款口吻 + 80~150 字** |

**形态上是切块，身份上是假的**：HyDE 产出既不是用户问句（不是疑问句）、也不是库里已有的切块（是模型按知识编的）。**用途**只用于检索探针（不展示给用户、不当答案）。**核心机制**：把检索的输入从「问句形态」切换成「切块形态」，和库里切块形态对齐 → 嵌入 → cosine 高 → 命中。

**匹配的是向量，不是字面（2026-09-14 补）**：

```text
假想段 → 嵌入 → 假想段向量
                  ↓ 余弦相似度
8 个切块的预嵌入向量 → cosine 降序 → top-K
```

之所以用余弦而不是字面匹配（BM25 那种），是因为假想段是模型编的、库里切块是人工写的——**两者字面不重合、形态重合**（都是陈述段 + 条款口吻），嵌入空间里距离近。生活例子：图书管理员把口语问句「那本把宇宙讲成故事的薄书」先想成「如果是讲宇宙故事的书，目录大概怎么写」（假想段），拿这段去和真实目录摘要做匹配——找到《时间简史》。**易混点**：

- ❌ **HyDE = 补问句**：错。HyDE 产出是陈述段，不是疑问句（残句补全才是补问句）。
- ❌ **HyDE = 补真实切块**：错。HyDE 产出是模型按知识编的，库里没有这条。
- ❌ **HyDE = 字面匹配**：错。HyDE 用余弦相似度，不是 BM25 字面匹配。字面匹配会让假想段零命中（库里没有完全相同的句子）。

### 5. 多轮指代：残句不能直接搜

上一轮问「SKU-88 七天无理由怎么算」，这一轮只说「那没拆封超期呢？」「这个呢？」

若把「这个呢」原样送进检索，库里没有「这个」。必须先结合对话历史，改写成完整问句，例如「SKU-88 未拆封超过七日能否退货」。

生活：你跟导购说「那这件呢」，导购知道「这件」是刚才那件外套。检索系统不知道，除非你先写全。  
前端：多轮客服最后一条是残句；检索模块必须先产出独立问句（standalone query），再去搜。生成回答时，用户气泡仍显示「那这件呢」。

这和模块 06 的上下文（Context）有关，但本条只要求：指代消解是改写的一种输入，不是另一条 RAG 流水线。

**残句补全：你与模型的分工（2026-09-14 补）**：

| 你（开发者）做什么 | 模型做什么 |
| ----------------- | --------- |
| 拼接 history 进 prompt | 读议程 |
| 决定传几条 history（最近 3 轮？全部？）| 看到「这个」→找上一轮的最近实体 |
| 决定 history 格式（user/assistant 分行？）| 写 `{"standalone": "..."}` |
| 决定猜错了怎么办（兜底）| （你看着结果决定下一步）|

**「全不管」错的**——完全不传 history，模型没东西可猜，吐空 / 502。**「全管」也错的**——自己写指代消解算法写不过 LLM。**正确分工**：你负责输入准备（拼接 / 截断 / 格式 / 兜底），模型负责实际指代消解。这跟 §变体 10「规则 vs 模型」同一套思路——能规则先规则（你决定传几条），剩下的交给模型（消解指代）。

**猜的本质**：模型按「最近原则 + 句法角色 + 主题连贯」三条启发式**猜**「这个」指哪个实体——猜的依据是上一轮的实体 + 句法角色 + 主题连贯，**模型不知道，是猜的**。

**生产里 4 个减少猜错的手段**：

1. **history 截断**：只传最近 N 轮（通常 3~5 轮），不传全部
2. **多轮显式摘要**：让程序先把 history 总结成一段「上下文摘要」喂给模型（贵但准）
3. **多候选 + 置信度**：让模型返回多个候选 + 各自置信度，挑 confidence 最高的
4. **失败兜底**：模型吐空 / standalone 明显错 → catch + 回退原句检索（类似失败兜底 sub-page 的逻辑）

**demo 现状的 4 个代码缺口**：

- ❌ history 截断（demo 全传 history，没做 `slice(-N)`）
- ❌ 多轮摘要（demo 直接喂原文）
- ❌ 多候选（demo 只接一个 standalone）
- ❌ 失败兜底（demo `catch` 后抛 502，没回退原句检索）

按 §5.4 严格规则，这 4 条扩进 MD 后都属于「未实现」，`coach complete` 打钩前检查 4 时由独立 subagent 重新抽清单 + 逐项核对时按「未实现」算。

### 6. 一句里两个问题：先拆成可检索的子问题

「退货几天、保修几年？」这是两个检索意图。只改写成一条更长的查询，BM25 会把「退货」和「保修」搅在一次打分里。

本条要求看懂：先拆成「退货时限」「保修年限」两条可检索子问题。至于「两条分别检索完怎么合并名单」，下一节 Multi-query 再当失败补丁讲。本条不把合并算法当当前主课。

生活：你问医生「咳嗽吃什么、血压药能停吗」——分诊会拆成两个科，不会合成一个怪关键词。

**当前实现是 N 检索 + 1 生成（不是 N 次调模型解答 · 2026-09-14 补）**：拆 N 个子问题后，**N 次检索是本地词重叠**（不调模型，< 10ms × N）；合并后只调 **1 次生成模型**拿答复。拆3 个子问题只付 2 次 LLM 成本（拆 1 次 + 生成 1 次）。**检索 vs 生成的成本结构不一样**：检索几乎免费，生成几百 ms + 几分钱。"N 次调模型解答"是 Multi-agent fan-out 范式（[模块 14]），不是本节。**易混点**：误把"拆 N 次"等同于"调 N 次模型"——本节的拆只是**检索前改写**，生成阶段仍然 1 次。

### 7. 不该改写：问句已经是锚点

问句是 `SKU-88`、`条款 3.2`、库标题原文「七天无理由退货」。再交给改写模型，它可能扩成「电子产品退货政策」，**货号没了**，BM25 的强项被你亲手拆掉。

生活：你已经报了身份证号，窗口仍按「那个男的」去翻档案。  
前端：搜索框已经是精确 `id=`，中间件还跑一遍模型改写，等于把主键查询改成模糊查询。

**做法**：检测到货号 / 条款编号 / 与某切块标题高度重合 → 跳过改写，原句直搜。改写是开关，不是信仰。

**这是规则判定，不是模型判定**：判定由**三条本地正则**命中即跳过（demo 里是 SKU / 条款 / Section），不让模型判断。规则便宜、可解释、主键不会丢；模型判断会改偏、把锚点改没。

**生产里要看业务加主键模式**：demo 三条正则只覆盖电商 SKU + 中文条款 + 英文 Section 这一类组合。常见业务要再扩：

- 电商：订单号 `ORD-2024-001234`、物流单号 `SF1234567890`
- 金融：账号 16~19 位数字、合同号、流水号
- 医疗：病例号 `MRN-2024-000123`、处方号 `Rx20240115-001`
- 客服：工单号 `TKT#A2024-0115-001`
- 法律：案号 `(2024)京01民初123号`

**还要加一类：标题表查重**。问句里整段照搬库标题（如「七天无理由退货」原文），正则扫不到，但同样不该交给改写—— `detectAnchor` 里加一段：标题表较短时直接做精确包含判断（`query.includes(chunk.title)`），命中即跳过。

**所有规则集中在 `detectAnchor` 一个函数里**：业务加新主键模式就在这里加一行（或一项查表），其他地方不动。散到好几处 = 漏配风险翻倍。

### 8. 改写改偏：意图漂移

原句：「超过 7 天了，盒子没拆，还能退吗？」  
坏的改写：「如何申请退款、退款多久到账」

检索会稳定命中「退款流程 / 到账时间」，漏掉「未拆封超期特例」——资格没查，流程查了一堆。

页面上要同时看见原句、改写句、两份名单。改写句不能偷偷覆盖原句。改坏了要能回退到原句检索。

生活：你问「这瓶过期没，还能喝吗」，翻译成「如何购买新酒」。

**生产里怎么拦改偏（五个位置瀑布式防御 · 2026-09-14 补）**：

| # | 位置 | 谁介入 | 实时性 | 适用业务 |
| - | ---- | ------ | ------ | -------- |
| 1 | 离线评测 | QA | 每周 | 所有业务 |
| 2 | 改写时自动信号 | 程序 | 实时 | 量大、客服少 |
| 3 | **检索后客服自查** | **客服** | **实时** | **大多数客服场景** |
| 4 | 生成后用户反馈 | 用户 | 异步 | 所有业务 |
| 5 | 合规硬约束 | 程序 | 实时 | 金融 / 医疗 / 法律 |

**位置 3 是关键**——`drift.html` 的「用原句重搜」按钮就是这一关的镜像。客服工具页布局：原话 / top-K 列表（带 score）/ 改偏原因标注 / 「用原句重搜」按钮 / 「接受改写」按钮。客服看 top-K 没命中资格类 → 推断改写改偏 → 一键回退。

**程序不靠"理解改写语义"判定改偏**——靠对照（top-K 命中切块是不是目标类）、信号（实体保留率 / 字面相似度 / 意图词命中）、多模型投票、离线命中率差。语义漂没漂，程序判不出，是靠这些粗信号 + 人工 review。

### 9. 和精排的分工（流水线位置）

| | 查询改写 | 重排序 |
| -- | -- | -- |
| 改什么 | 问句 | 已经进检索名单的名单顺序 |
| 发生在 | 检索之前 | 检索之后 |
| 救什么 | 词对不上、残句、太瘦 | 对的在名单里但排太后 |
| 救不了 | 切块切坏、库里没有 | 正确切块没进检索名单 |

两者叠加时，本模块那条常见坑仍然成立：**一次只加一个变量。** 先只开改写看命中率，再决定要不要叠精排。不要同一天把混合 + 精排 + 改写全打开。

### 10. 规则改写 vs 模型改写

| | 规则（同义词表 / 正则货号 / 政策别名） | 模型改写 |
| -- | -- | -- |
| 优点 | 便宜、可解释、货号不会丢 | 能处理没见过的口语、指代、长句 |
| 缺点 | 覆盖不到新说法 | 贵、可能改偏、要兜底 |

生产里常见是**先规则后模型**：能抽到货号就把货号**作为锚点锁住**；剩下的口语再交给模型。教学上要能分开看见：规则产出 vs 模型产出，不要合成一个黑盒。

**RAG 三阶段分工（2026-09-14 补）**：RAG 不是一步，是三步——**召回宽 / 精排缩 / 生成准**：

| 阶段 | 目标 | 实现 | 多 / 少 |
| ---- | ---- | ---- | ------- |
| **召回** | 别漏掉该引用的 | BM25 / 向量 / 改写 / 拆子问题 / 补词 | **宽**（top-K 大一些）|
| **精排** | 把准的排前 | cross-encoder / Cohere Rerank（[第 2 条]）| **缩**（筛掉无关）|
| **生成** | 喂给 LLM 的最相关 | LLM 自己挑 + 引用 | **准**（喂少而精）|

**模型补词命中"非常多"是召回阶段的合理代价，不是浪费**——召回阶段"多"是为了给精排素材。如果召回阶段就"精准且少" → 漏掉该引用的 → 后面精排再准也变不出来。本节 step-1 只有召回、没有精排和生成，所以"多"看起来浪费——**这是 step-1 的简化，不是 RAG 的全貌**。完整 RAG 见 [模块 09 第 2 条 Rerank]（精排）和后续模块（生成）。

**dual-expansion sub-page 的目的是让你看清两边偏差，不是叠加用**。**先规则后模型是分层调用**，不要同时叠加（同时把规则 + 模型 addedTerms 都拼进扩展句 = "一次加两个变量"，违反笔记反复强调的「一次只加一个变量」原则）。正确做法：规则能命中就用规则；规则全 miss 时才让模型补。两侧对照看命中是不是同一类（跨类别 = 噪声大、稀释目标切块排名）。

### 11. 评测：改写前后要用同一份题

要有「原句检索」基线。同一份人工标注（哪条切块 `id` 该命中），只改「要不要改写」这一个开关，看命中率。HyDE、扩展、换词不要一次全开。

### 12. 检索用改写句，生成和界面用原句

改写句是内部探针。用户没说「特例审核」这四个字，界面上却回「根据你问的未拆封特例审核……」，用户会觉得机器人在改他的意思。

正确拼提示词：

```text
用户原话：盒子没拆，都八天了，还能退吗？
检索用的问句（仅内部）：未拆封 超过七日 特例审核
检索到的切块：……
请根据切块回答用户原话，不要把内部检索词当成用户说的话。
```

前端对照：URL rewrite 不改地址栏；搜索日志里 `raw_query` 和 `rewritten_query` 分列。

### 13. 改写失败要兜底

改写那一次模型 429、超时、吐空、吐了不像问句的散文 → **用原句检索继续走**，不要整条客服链路挂死。页面要标明「本次未改写，原因：……」。

生活：翻译耳机没电，你就用原话问柜台，总比站着空白好。

**本质：先尝试调改写，调失败才回退**。不是"提前不让它调"。生产触发原因：网络超时 / 429 速率限制 / 模型吐空 / 模型返回不是 JSON / 解析 JSON 失败 / 密钥 401 或配额耗尽。任何一条 → catch → 用原句检索继续走。

**两条路径对照**：
- 坏路径（总览页 `POST /api/rewrite-and-search`）：catch 没接住，抛 502，整页报死 = 客服链路挂死
- 好路径（失败兜底 sub-page `POST /api/fallback-and-search`）：catch 后回退原句，页面告诉用户"本次未改写 + reason"

**页面要标明什么**：`mode=rewritten|fallback` / `reason`（失败原因，改写成功时为空字符串）/ `queryUsed`（改写成功 = 改写句；fallback = 原句）/ 同一份检索名单。客服/用户必须能分辨"这次检索是不是回退的"。

**判错会怎样**：改写挂了整页 502，客服链路挂死。哪怕原句检索会受词汇鸿沟影响，也比空白 5xx 强太多——用户至少能看见通用政策段。

## 易混点

| 容易混成 | 差在哪 | 判错会怎样 |
| -- | -- | -- |
| 改写 = 精排 | 一个改问句，一个改顺序 | 正确切块没进检索名单，你还在调精排模型 |
| 改写 = 扩展 | 换词 vs 原句上补词；都还是一条查询 | 你以为开了「多路检索」，其实只是查询变长 |
| 扩展 = 下一节的多条问句分别检索 | 一条 vs 多条；合并名单是下一节的事 | 过早上 Multi-query，成本翻倍且本条验收对不上 |
| HyDE = 让模型直接答 | HyDE 的假想段落只拿去检索，不是最终答复 | 假想段写飞了你还当事实展示给用户 |
| 改写 = 微调（Fine-tuning）让模型懂口语 | 改写不改模型权重，只改送进检索器的字符串 | 知识一变你去重训，而不是改同义词表 / 提示词 |
| 改写后用改写句当用户原话 | 检索对齐库，对话应对齐人 | 用户觉得被改口；质检对不上录音 |
| 「扩展」就是把前 K 条（Top-K）加大 | 扩展改的是查询词；加大 K 是多塞切块 | Token 涨了，词汇鸿沟还在 |
| 永远改写 | 货号 / 条款号是锚点 | 改写把主键改丢，BM25 优势没了 |
| 拆 N 个子问题 = 调 N 次模型解答 | 误把检索当生成 | 拆只是**检索前改写**；N 次检索本地词重叠不调模型；生成阶段仍只 1 次。"N 次调模型解答"是 Multi-agent fan-out 范式（[模块 14]），不是本节 |
| 对应的是「切块里的问题」 | 切块多数是答案正文（陈述段），不是问题 | 你去库里找「问句对问句」，手册库会对空 |
| 「切片 / 向量切片」 | 检索单位是切块；向量只是通道 | 和数据集切片、和「只有向量会失败」缠在一起 |
| 有向量就能靠意思找到，不用改写 | 向量会补近义，但仍常找偏：短问句、口语、疑问句对条款口吻的陈述段不够近；更近的往往是通用主题段 | 你停在「已经上了向量」却看不到该引用的那一条 |
| HyDE = 补问句 | 把 HyDE 当成残句补全 | HyDE 产出是陈述段（不是疑问句）；残句补全（变体 5）才是补问句 |
| HyDE = 补真实切块 | 以为 HyDE 把库里没的切块"补"进来 | HyDE 产出是模型按知识编的；库里没有这条；只用作检索探针 |
| HyDE = 字面匹配（BM25）| 拿假想段跑 BM25 | 假想段是模型编的，库里没有完全相同的句子 → BM25 零命中；HyDE 用余弦相似度（向量匹配）才能命中 |

## 例子

客服知识库里同时有「七天无理由」和「未拆封超期特例」两段切块。

1. 用户打「盒子没拆，八天了还能退吗」→ 原句检索，特例段不在前几名或没进检索名单。  
2. 改写成「未拆封 超过七日 特例」→ 同一 `id` 进检索名单或名次抬升。  
3. 扩展：原句后面补政策名，仍一次检索。  
4. 用户只打「还能弄吗」且上一轮在聊某货号 → 先补成完整问句再搜。  
5. 用户直接贴货号 → 跳过改写。  
6. 改写模型把问题改成「退款到账时间」→ 两份名单对照能看出漂了，回退原句。  
7. 改写接口挂了 → 原句检索，页面标明未改写。  
8. 生成回复引用特例段，但用户气泡和提示词里的用户侧仍是原话。

关上文件后，若看不见「原句 / 改写句 / 两份名单」，「为什么要改写」只是口号。

| 失败兜底是不是"不让它调、用原句去检索"？ | 混淆"提前屏蔽"和"调失败才回退"——以为程序会自己判断不要调改写 | 不是提前不让它调。**先尝试改写**（`await rewriteAndRetrieve(query)`），失败（超时 / 429 / 吐空 / 解析炸 / 密钥挂）→ catch → **回退原句检索**（`retrieveByQuery(query)`）+ 标 reason。两条路径对照：总览页（`POST /api/rewrite-and-search`）= 坏路径 = 改写失败抛 502 整页报死；失败兜底 sub-page（`POST /api/fallback-and-search`）= 好路径 = catch 后回退，页面标 mode=fallback + reason + queryUsed=原句。生产里选好路径：哪怕原句检索受词汇鸿沟影响，也比 5xx 整页强太多。 |
| 生产里改偏可回退是人工回退吗？人工在哪一步介入？ | 以为程序会自动判定改偏 → 实际靠瀑布式防御 | 生产里**程序不靠理解语义判定改偏**——靠对照 / 信号 / 多模型投票 / 离线命中率。人工介入有**5 个位置（瀑布式）**：① 离线评测（QA 每周跑命中率对照，归因 prompt 改动）② 改写时自动信号（实体保留率 / 字面相似度 / 意图词命中 → 黄提示）③ **检索后客服自查**（最关键 = `drift.html` 「用原句重搜」按钮的直接镜像；客服工具页必须给 top-K 列表 + 「用原句重搜」按钮）④ 生成后用户反馈（用户说"跑题" → 工单 → 离线 review）⑤ 合规硬约束（金融/医疗/法律：改写前后 cos 相似度 < 阈值 → 强制回退原句）。**最少要有位置 3**——否则改偏只能眼睁睁发错。 |
| 残句补全里他怎么知道上下文？「这个 / 那个」指哪个问题？ | 以为模型"知道"上下文 → 实际模型在猜 | 模型按「最近原则 + 句法角色 + 主题连贯」三条启发式**猜**——猜的依据是上一轮的最近实体 / 主语宾语角色 / 主题连贯。**模型不知道，是猜的**。猜不准怎么办：① history 截断到最近 3~5 轮 ② 多轮显式摘要（程序先总结历史）③ 多候选 + 置信度 ④ 失败兜底（catch 后回退原句检索）。**demo 现状**：截断没做、摘要没做、多候选没做、失败兜底没做（catch 后 502）——这 4 条按 §5.4 严格规则算「未实现」，打钩前检查 4 由独立 subagent 重新抽清单 + 逐项核对时按「未实现」算。 |
| 调用大模型时什么都不用管吧？ | 以为传 query 就够 → 实际你负责输入准备、模型负责实际消解 | 不是「全不管」——你必须把 history 准备好送进去（拼接 / 截断 / 格式），模型才有得猜。也不是「全管」——自己写指代消解算法写不过 LLM。**正确分工**：你负责 4 件事（拼接 history / 决定传几条 / 决定格式 / 决定猜错兜底），模型负责实际指代消解。这跟 §变体 10「规则 vs 模型」同一套思路——能规则先规则（你决定传几条），剩下的交给模型（消解指代）。 |
| 一句拆成子问题后会调 N 次模型解答吗？ | 以为 N 次拆 = N 次模型成本 | **当前实现是 N 检索 + 1 生成**。N 次检索是本地词重叠（不调模型，< 10ms × N）；合并后只调 1 次生成模型。拆3 个子问题只付 2 次 LLM 成本（拆 1 次 + 生成 1 次）。**检索 vs 生成的成本结构不一样**：检索几乎免费，生成几百 ms + 几分钱。"N 次调模型解答"是 Multi-agent fan-out 范式（[模块 14]），不是本节——本节的拆只是检索前改写。 |
| HyDE 是补问题还是补切块？ | 以为 HyDE 补问句 / 补真实切块 | 都不是——**HyDE 补的是「假想的切块」**。形态是切块（陈述段 +条款口吻 + 80~150 字），身份是假的（模型按知识编的，库里没有这条），用途只作检索探针（不展示给用户、不当答案）。**和残句补全的对照**：残句补全（变体 5）产出独立问句（「SKU-88 未拆封超过七天能否退货」）；HyDE（变体 4）产出陈述段（「未拆封商品超过七日的特例审核……」）。**核心机制**：把检索输入从「问句形态」切换成「切块形态」，和库里切块形态对齐。 |
| HyDE 假想段和切块列表怎么匹配？字面还是向量？ | 以为字面匹配（BM25）| **匹配的是向量，不是字面**。流程：假想段 → 嵌入 → 假想段向量 → 余弦相似度 vs 8 个切块的预嵌入向量 → cosine 降序 → top-K。**之所以用余弦而不是字面匹配**：假想段是模型编的、库里切块是人工写的——两者字面不重合、形态重合（都是陈述段 +条款口吻），嵌入空间里距离近。**生活例子**：图书管理员把口语问句「那本把宇宙讲成故事的薄书」先想成「如果是讲宇宙故事的书，目录大概怎么写」（假想段），拿这段去和真实目录摘要做匹配——找到《时间简史》。 |
| 模型补词命中"非常多"是浪费吗？违背"精准且少"吗？ | 以为检索全程都要精准且少 | **不是浪费，是召回阶段的合理代价**——RAG 是三阶段分工（**召回宽 / 精排缩 / 生成准**）：召回阶段"多"是为了给精排素材；如果召回就"精准且少" → 漏掉该引用的 → 后面精排再准也变不出来。本节 step-1 只有召回没有精排，所以"多"看起来浪费——**这是 step-1 的简化，不是 RAG 的全貌**。完整 RAG 见 [模块 09 第 2 条 Rerank]（精排）。**dual-expansion 是分开看偏差，不是叠加用**——"先规则后模型"是分层调用（规则主用、模型补漏），不要同时叠加（违反笔记"一次只加一个变量"）。 |

## 需求清单（验收准绳，不是一次搭完整应用的施工单）

**需求 1 · 看见词汇鸿沟**  
业务场景：日常说法问退货，库标题是政策用语。  
目标：证明原句检索打不中或排很后。  
知识点：变体 1。  
验收：同一库、同一问句，原句检索结果里正确切块不在前 K 条（或没进检索名单），原因能看见（词重叠少 / 召回分低）。

**需求 2 · 同一意图换词**  
业务场景：把日常说法改成库用语后再搜。  
目标：改写后正确切块进检索名单或名次抬升。  
知识点：变体 2。  
验收：页面同时展示原句全文、改写句全文、两份名单；正确切块是同一 `id`，不是「又搜到一篇」。

**需求 3 · 一条查询补词**  
业务场景：原句太瘦，补政策名 / 同义词后再搜，仍一次检索。补进来的是「库用语 / 关键词 / 政策名」（不是另起整句话——整句换词是改写，不是扩展）。  
目标：分清扩展 ≠ 换掉原句，也 ≠ 多条查询。  
知识点：变体 3。  
验收：能看见扩展句 = 原句 + 补词；一次检索请求；名单相对原句有变化。补词方式分规则（同义词表）和模型（让 LLM 补词）两种，「规则 vs 模型分列」见需求 10。

**需求 4 · 假想文档当探针**  
业务场景：短口语问句走 HyDE：先生成假想政策段，再向量检索。  
目标：看懂假想段不是最终答案。  
知识点：变体 4。  
验收：页面能展开假想段落全文；检索入参是这段（或其向量），不是把假想段直接展示成客服回复。

**需求 5 · 残句先写全**  
业务场景：上一轮在聊某货号，这一轮「这个呢」。  
目标：检索吃完整问句。  
知识点：变体 5。  
验收：能看见送进检索的独立问句；用户侧仍显示残句。

**需求 6 · 一句拆成子问题**  
业务场景：「退货几天、保修几年」。  
目标：看见拆出来的可检索子问题。  
知识点：变体 6。  
验收：至少展示两条子问题原文。本步不要求把「多路合并」做成下一节那样的完整 Multi-query。

**需求 7 · 锚点问句不改写**  
业务场景：问句已含货号或条款编号。  
目标：跳过改写，避免丢锚点。  
知识点：变体 7。  
验收：该问句路径标明「未改写」及原因；检索用的就是原句。

**需求 8 · 改写改偏可回退**  
业务场景：故意用一条会改偏的改写（或模型真改偏）。  
目标：对照能看出意图漂了。  
知识点：变体 8。  
验收：原句名单 vs 改偏后名单分列；提供用原句重搜，禁止只留改偏结果。

**需求 9 · 和精排划界**  
业务场景：原句导致正确切块没进检索名单。  
目标：说明此时加精排救不回，要先改写。  
知识点：变体 9。  
验收：能看见「改写前候选窗里没有该 `id`」；文案写明精排看不见窗外切块。本条 Demo 不要求再实现上一节整套精排。

**需求 10 · 规则 vs 模型产出能分开看**  
业务场景：同义词表补词 vs 模型换词。  
目标：两种改写器不是一个黑盒。  
知识点：变体 10。  
验收：两侧请求能分开看（或分步点）；各自产出的查询字符串全文可见。

**需求 11 · 只加改写这一个变量**  
业务场景：同一份小评测集。  
目标：改写开 / 关对照命中。  
知识点：变体 11。  
验收：同一批问句、同一个库，只切换「是否改写」，命中数字分列。允许 step 较后才做；禁止和精排开关绑在同一个按钮里一次性跑完还只给一个总分。

**需求 12 · 生成侧保留原话**  
业务场景：改写后检索成功，再生成一句答复。  
目标：内部查询词不冒充用户原话。  
知识点：变体 12。  
验收：提示词或页面标注里，用户侧文本 = 原句；改写句标成内部检索词。

**需求 13 · 改写失败用原句兜底**  
业务场景：改写接口失败或吐空。  
目标：检索仍能走。  
知识点：变体 13。  
验收：该次结果标明「未改写」+ 原因；检索入参回退为原句；不是整页报死。

## 取舍

| 场景 | 更稳的做法 | 不要选的 |
| -- | -- | -- |
| 日常说法和库用语不是一套词，正确切块经常没进检索名单 | 检索前改写或补词，再召回 | 只加大生成看见的 K，或只加精排 |
| 问句已经是货号 / 条款编号 | 跳过改写，原句直搜 | 一律交给模型改写，把锚点改丢 |
| 问句太短、几乎没有实体 | 考虑 HyDE：假想政策段再向量检索 | 把假想段当最终答案展示给用户 |
| 原句还能用，只是偏瘦 | 扩展：原句 + 库词，一次检索 | 一上来就多条查询分别检索（那是下一节） |
| 效果变了要归因 | 一次只加改写这一个变量，对照原句检索基线 | 同时打开混合 + 精排 + 改写 |
| 改写模型挂了 / 吐空 | 用原句检索兜底，页面标明未改写 | 整条链路 500 |
| 能抽到货号 | 规则先**把货号锁住**，剩下的口语再交给模型 | 只用模型，货号经常被改没 |

| 残句补全 | history 截断到最近 3~5 轮 + 调模型做指代消解 + catch 后回退原句检索 | 全传 history 没截断 / 自己写指代消解 / catch 后整页 502 |
| 模型补词命中"非常多" | 召回阶段合理代价 + 后续精排 / 生成才能变准 | 单看 step-1 觉得多就是浪费 / 把规则和模型同时叠加用（违反"一次只加一个变量"）|

## 踩坑

- **以为精排能补词汇鸿沟**：正确切块没进检索名单，改顺序变不出新切块。先看候选窗里有没有那条 `id`。
- **以为上了向量就不用改写**：向量会补近义，但仍常找偏到通用主题段。短问句、口语、疑问句对条款口吻，嵌入空间里往往不够近。
- **把切块当成「里面的问题」**：手册库是陈述段。用户问句要对的是答案正文。
- **把切块叫成切片 / 向量切片**：单位是切块；向量只是通道。
- **改写句冒充用户原话**：检索用改写句，生成和界面用原句。内部探针不要念给用户听。
- **货号问句也改写**：主键被改成模糊主题，BM25 优势没了。
- **扩展和「一次出多条问句」当成一回事**：扩展还是一条查询；多路检索是下一节。
- **HyDE 的假想段落当事实**：它只是检索探针，写飞了会稳定打到错误类文档。
- **改写失败就整页报死**：回退原句检索，标明本次未改写。
- **一次加上混合 + 重排序 + 查询改写**：效果变了不知道是谁的功劳。本模块验收写明：一次只加一个变量。
- **漏主键模式**：只配了 SKU 这一条正则，没配订单号、物流单号——改写模型把订单号扩成「我的订单有什么问题」，BM25 拿不到主键。判错表现像词汇鸿沟（搜不到正确答案），但根因不一样：词汇鸿沟是用户和库用词不同；漏主键是改写把主键改丢了。生产里每加一类业务都要回 `detectAnchor` 加正则或查表，不能散到好几处。
- **把"先尝试改写再回退"写成"提前不让它调"**：本质区别是 catch 的位置。提前不让它调 = 不发网络请求；先尝试再回退 = 发了请求但失败时还能继续走。生产里大多数时候改写都能成功，提前屏蔽是浪费；只在 catch 后回退 = 性能不浪费 + 失败还能继续。
- **客服没有「用原句重搜」按钮**：改写改偏时客服工具页只能展示改偏后的 top-K，客服没有回退入口 → 只能眼睁睁发错回复 → 用户体验差。生产里客服工具页**必须**给两样东西：top-K 列表让客服自己判断 + 「用原句重搜」按钮让她能一键回退（`drift.html` 的镜像）。
- **「不用管」或「全管」残句补全**：「不用管」= 完全不传 history，模型没东西可猜，吐空 / 502；「全管」= 自己写指代消解算法（正则判断「这个」指哪个名词），写不过 LLM。正确做法：你负责拼接 history / 决定传几条 / 决定格式 / 决定猜错兜底；模型负责实际指代消解。
- **误把检索当生成**：以为拆 N 个子问题就要付 N 倍模型成本——其实拆 N 次只付**拆 1 次 + 检索 N 次本地 + 生成 1 次**。N 次检索是本地词重叠（< 10ms × N，几乎免费），不调模型；只有**拆 + 生成**两步调 LLM。判错会怎样：错估成本拒绝拆子问题；或以为已经调了 N 次模型实际只调了 1 次。
- **把召回阶段当精排阶段**：以为"检索命中多 = 浪费"——召回阶段就是"宽"，目的是给精排素材。本节 step-1 只有召回没有精排，所以"多"看起来浪费——这是 step-1 的简化。**完整 RAG 是召回宽 / 精排缩 / 生成准**三阶段分工。判错会怎样：错估召回阶段的合理代价；以为模型补词"命中多"就是错——其实是"召回阶段的代价"。

## 过关自检

关上文件还能讲出来：

> **用户要的答案在切块里；检索比的是「你送进去的那串字」和「切块里的字」。** 两边意思一样但字不一样（再加残句、太瘦、混了两个问题），关键词对不上，向量也容易漂到主题相近的通用段。查询改写发生在检索前，就是为了把这串字对齐。改写是同一意图换词；扩展是原句上补词（还是一条查询）；HyDE 是先写一段假想政策再拿去向量检索，假想段不是给用户看的答案。货号这类锚点不要改。改偏了要能对照、能回退。检索用改写句，生成和界面用原句。改写挂了就用原句继续搜。名单里没有的，上一节精排救不了。

对着需求 1 + 2 的主对照：同一问句，原句名单和改写后名单并排；特例切块是**同一 `id`** 被捞上来或抬上来。  
对着需求 3：扩展句能看见原句还在，只是后面多了库词，一次检索。  
对着需求 7：货号问句标明未改写。
