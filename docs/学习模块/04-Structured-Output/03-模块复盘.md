### 一句话讲完这个模块

让 LLM 从「**生成文字**」变成「**生成程序可以处理的数据**」——同一份 **Zod schema** 既是**入口协议**（派生 JSON Schema 喂给模型、走协议 A/B 哪一档），也是**出口卡尺**（`safeParse` 拿回 typed 对象、失败就 `issues` 回灌修复）。**所有结构化路径都靠这条单一事实来源**——没有这份 Zod，下游字段一漂全链炸。

### 这些条怎么连成一条线

按条 MD 各自看不到这一层，这是复盘的主要产出。

| 条 | 在链路里扮演 |
| --- | --- |
| **01 JSON Schema + Zod** | **工具层**：定义「数据形状」和「怎么校验」的**单一事实来源**——所有入口（喂模型）和出口（验回值）的源头。Zod 一份定义同时给三件事：运行时校验 + `z.infer` TS 类型 + `ZodError.issues` 报错模板（天然可喂给模型做 repair） |
| **02 JSON Mode vs Structured Output** | **协议层**：把 01 的 Zod schema **塞给模型时走哪条路、守约到什么程度**——A1/A2/A3 + B1/B2/B3 六档全景；协议 A `response_format.strict` 是 token-mask 物理闸；协议 B 没有 `response_format`，闸分散在 `tools[].input_schema` + `tool_choice` 两层软约束 |
| **本条 03 模块复盘** | **收口**：把上面两层用同一份 Zod 串起来——入口派生、协议选档、出口兜底——并标注「国内 provider 不真做 strict」的工程事实 |

**一句话串线**：「**01 拿到契约（Zod）→ 02 把契约塞给模型走哪档协议（A/B 哪一档）→ 客户端拿回结果再走 01 的 Zod 后置兜底**」。01 是工具，02 是用法；**两者不可拆开**——02 里的 `IntentZod` 之所以完全复用 01 的同一份契约，就是要把这个闭环演给读者看一遍。**国内 provider 上协议 B3 实测守约率反超协议 A strict**——这是 02 用 5 用例 × 双协议跑出来的工程事实，沉淀已写在本条 §5.2 Demo 判断块里。

### 模块验收对答

把本模块 README「验收」逐条抄进左列，右列用自己的话答一遍。有一条答不出就不准勾 ✅。

| 验收项（README 原话） | 我的回答 |
| --- | --- |
| Zod Schema → JSON Schema → 模型 → 解析 → 类型安全的 TS 对象，全链路打通 | 一份 `IntentZod` 起手 → `zodToJsonSchema` 派生协议 A 的 JSON Schema（白名单：禁 `anyOf` / 必 `additionalProperties:false` / `required` 列尽），协议 B 手写 `input_schema` 同形；模型吐回后用同一份 `IntentZod.safeParse()` 拿 typed 对象——`r.data` 在 `if (r.success)` 分支里 TS 自动 narrow，下游 `switch(r.data.action)` 不需要 any。**全链路靠"同一份 Zod"这条单一事实来源**——改了 schema 两端自动同步，不会漂。 |
| 解析失败时有自动重试（把错误信息回传给模型让它修） | 把 `ZodError.issues` 拼回 prompt：`error.issues.map(i => \`  - ${i.path.join(".")}: ${i.message}\`).join("\\n")` + 一句"请重新输出合法 JSON"——**只贴 issues + 上一轮输入，不贴整段对话**，避免 prompt 膨胀。02 条踩坑 #3 实证：让 `safeParseIntent` 和 `analyze` 共用同一个 `stripWrap()`，否则会出现"Zod ✓ + 缺 keys 同亮"自相矛盾的 bug。 |
| 能处理嵌套对象、数组、可选字段、枚举 | JSON Schema 用 `type: ["string","null"]` 表示可空，Zod 用 `.nullable()`；optional 默认极性两边相反——JSON Schema 全可选 + `required: [...]` 升格才必填，Zod 全必填 + `.optional()` 才允许缺。`enum` 两边写法一致（`enum: ["search","order","cancel"]`），但 OpenAI strict 不接受 `oneOf` / `nullable: true`，必须 `enum` + `type: [...],"null"`，这是协议 A 白名单最常踩的两个写法雷。 |
| 知道 JSON Mode 和 Structured Output（严格模式）的区别 | **JSON Mode**（协议 A `response_format: { type: "json_object" }`）只保**语法合法**——`JSON.parse` 不抛，但不保证字段名 / 必填 / 枚举。**Structured Output strict**（`type: "json_schema"` + `strict: true`）多保**符合 schema 白名单**——OpenAI 自己的实现是 token-mask 物理闸（采样每一 token 前 mask 掉"会让最终 schema 违例"的 token），模型**想错也错不了**。**但**：国内 provider（MiniMax-M3 实测）silent ignore 了 strict，行为退化成 JSON Mode。**所以 strict 是物理闸这层心智模型只对 OpenAI 自己成立**，跨 provider 必须实测 5 用例验证。 |
| 有「模型返回了不合法 JSON」的测试用例并能正确恢复 | **三段式恢复链**：先 `stripWrap(raw)` 三类剥离（`<think>` / ``` ``` fence ``` / 末尾省略号，每步后 `.trim()`）→ `JSON.parse` → `IntentZod.safeParse()`；任一阶段失败都把错误信息回传给模型做 repair（Zod 失败回灌 issues，strip 失败回灌原始 raw + 报错原因）。02 条 5 用例里"prompt 诱导违 enum"那一条就是这条验收的可观察对照：协议 A2 硬吐乱值、协议 A3 strict（MiniMax-M3）退化成 A2、协议 B3 模型拒调工具——三种失败行为都已经被测到。 |

**自测三问**（README 自测问题，对照上面的验收对答用自己的话答）：

| 自测问 | 我的回答 |
| --- | --- |
| **为什么要用 Structured Output？** | 让模型的输出从"自由文本"变成"程序能处理的数据"——避免字段漂移（`action` 漂成 `intent`/`cmd`/`op`，下游 `r.data.action × 100` 直接 `NaN`）、避免缺类型安全（手撸 `interface` 撑不到第二次改动）、避免复杂结构 prompt 写不动（嵌套 / 数组 / 枚举三段中文规则模型记不全，schema 一行 `enum` 就锁死）、避免跨语言接口对不齐（OpenAI / Anthropic / MCP 收的都是 JSON Schema；中间一定要会 Zod ↔ JSON Schema 转换）。一句话：**让模型"按契约吐"，下游就能"按契约验"，两端自动同步**。 |
| **如何保证类型安全？** | 用 Zod 做单一事实来源——一份 schema 同时给三件事：①运行时 `Schema.parse()` / `Schema.safeParse()` 真去校验；②编译期 `z.infer<typeof Schema>` 拿 TS 类型；③失败时 `error.issues[]` 自动生成路径化报错（天然是给模型吃的 repair prompt）。**关键**：Zod 改了 → TS 类型自动跟着改 → 服务端解析逻辑零改动；**不要**手撸 `interface Cat` 单独写一份 validator 库（joi / ajv / yup）——那是两份代码必然漂移。 |
| **模型输出的 JSON 不合法怎么办？** | **三步恢复链**：①`stripWrap()` 三类剥离（`<think>` / ``` ``` fence ``` / 末尾省略号），每步后 `.trim()`；②`JSON.parse`；③`Zod.safeParse` 拿 discriminated union，true 拿 `r.data`，false 拿 `r.error.issues`。**任一阶段失败都 repair**：把 `issues[].path + message` 拼回 prompt 让模型改，**只贴 issues 不贴整段对话**避免 prompt 膨胀；重试 ≤2 次仍失败就 fallback / 报警（**不要无限重试**——模型可能死锁在同样的错误上）。 |

### 最容易记错的三条

跨条易混——单条内的易混点留在 01/02 的「易混点」节里。

| 易混对 | 差在哪 | 判错代价 |
| --- | --- | --- |
| **JSON Schema 默认极性 vs Zod 默认极性** | JSON Schema 全可选 + `required: [...]` 升格才必填；Zod 全必填 + `.optional()` 才允许缺 | 抄反 → 一边过一边不过；以为是 JSON Schema 必填的字段到了 Zod 也必填、其实是 optional |
| **`strict: true` 不写 ≡ JSON Mode** | 协议 A `response_format: { type: "json_schema" }` 没写 `strict: true` → 回退 JSON Mode；A2 字段漂移上线才发现 | "我用了 structured output 但模型照样漂"——最常见 |
| **协议 A3 strict 失败行为 vs 协议 B3 tool_choice 强制失败行为** | A3 强制有结果（哪怕乱，模型硬吐）；B3 模型可以**拒调工具**——返回没有 `tool_use` block 的 content 数组 | 协议 B 路径 server 没处理"无 tool_use block"分支直接挂；把 A3 的"严"直接套到 B3 期望值上 |

### 踩过的坑（跨条）

跨条才记——单条内的踩坑留在 01/02 的「踩坑」节里。

- **国内 provider silent ignore 比 loud reject 危险 100 倍**。DeepSeek 协议 A strict 返 HTTP 400（好认，立刻降级）；MiniMax-M3 返 HTTP 200 + 模型自由发挥——schema 完全没校验，看上去"成功"实际没守。**生产里 MiniMax-M3 这种 silent ignore 是最危险的**——所以切 provider 前**实测 5 用例**别信文档、别假设"应该一样"。
- **`stripWrap()` 必须所有解析路径共用**。`safeParseIntent` 与 `analyze` 各写一份独立 strip 链会出现"Zod ✓ + 缺 keys 同亮"自相矛盾的 bug（02 条踩坑 #3 实证）。**修法**：抽 helper，所有解析路径共用同一清洗链，每步后强制 `.trim()`。
- **协议 B 模型可以拒调工具**。`tool_choice: { type: "tool", name: "Intent" }` 强制调工具，但模型可以**拒绝调**——返回没有 `tool_use` block 的 content 数组。协议 A strict 不会发生这种行为（协议 A 永远返回字符串、即便混乱）。**协议 B 的 server 代码必须兜底"模型没调工具"分支**：默认空 input / repair prompt 重试 / 降级到 B2 `tool_choice: { type: "any" }`。
- **推理模型夹 `<think>`**。o 系 / DeepSeek-reasoner / minimax 这类思考模型会先吐 `` `<think>...</think>` ``，再吐 JSON。`JSON.parse` 直接挂。**生产必须先 strip 再 parse**——这就是为什么 `stripWrap()` 不只是 fence 剥除，必须把 `<think>` 也列进去。
- **协议 B 没有"JSON Mode"等价字段**。协议 A 的 `json_object` 在 B 上没有对位字段——协议 B 唯一进入结构化路径的方法是 `tools + tool_choice`。**`tools` 是协议 B 的"闸的容器"**，不是一个开关。**`max_tokens` 是协议 B 必填**——忘填直接 400。
- **`response_format` 名字相同 ≠ 行为相同**。OpenAI / MiniMax / Zhipu 都标"structured outputs"，但 MiniMax silently ignored strict——**别假设"应该一样"**，切 provider 必实测。
- **协议 A3 strict 与协议 B3 tool_choice 强制与推理模式物理冲突**。OpenAI o 系 / DeepSeek-Reasoner / Anthropic extended thinking 等 reasoning 模型在 thinking 路径下，B3 强制 tool_choice 会被 HTTP 400 拒绝（`Thinking mode does not support this tool_choice`），A3 strict 同理受 token-mask 限制，reasoning 模型一般拿不到 A3。**修法**：协议 B 显式 `thinking: { type: "disabled" }`；协议 A 没法关，只能换非 reasoning 模型。
