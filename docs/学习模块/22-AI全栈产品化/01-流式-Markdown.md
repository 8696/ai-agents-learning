### 是什么

**流式 Markdown渲染**是把 LLM **边到边输出**的 Markdown 文本**实时渲染成 HTML 显示**给用户——技术本身简单，但有一个核心问题：**不完整 Markdown 语法会导致解析抖动**。

#### 朴素实现的「闪烁」

LLM 流式输出 `# 你好`，分三个 chunk 到：

```
chunk 1: "#"        → 渲染成普通文本 "#"
chunk 2: "# 你"     → 渲染成普通文本 "# 你"
chunk 3: "# 你好"   → 渲染成 H1 标题 "<h1>你好</h1>"
```

**用户看到**：第一秒看到 `#`，第三秒突然变成大字「你好」——**标题「跳」出来了**。同样的抖动发生在：

- **列表**：`- 项1` 拆成 `- ` → `- 项 1`（列表从无到有）
- **加粗**：`**重要**` 拆成 `**` → `**重` → `**重要**`（加粗闪一下又消失）
- **代码块**：`` ```python\nprint(1)\n``` `` 拆成多 chunk（代码块没闭合时 = 普通文本）
- **链接**：`[文](url)` 拆成 `[文]` → `[文](url)`（链接半成品闪烁）

#### 性能问题

**朴素重渲染**——每次 chunk 都全量重新解析 Markdown → 重新渲染整个 DOM：

- 1000 字 Markdown 流式输出 → 100+ 次 re-render
- 每次 re-render 都重新解析 + diff DOM → CPU 飙升
- 长内容时滚动条跳来跳去

**优化方向**：

| 优化 | 思路 |
|------|------|
| **增量 diff** | 只 render 新增部分（React diff 算法 / Svelte fine-grained） |
| **占位符** | 不完整语法用 placeholder（`# ?` / `- ?`）不渲染 |
| **缓冲** | 攒 N 个字符再渲染（牺牲实时性换稳定） |
| **\n 触发** | 只在换行符到达时重新解析块（标题 / 列表 / 代码块 都是块级） |

一句话：**流式 Markdown 不是「把流式文本渲染出来」那么简单，是「边到边 + 不闪 + 不卡」的平衡艺术**。

### 为什么（Agent 开发要懂）

Agent 的所有输出几乎都是**Markdown**——LLM 默认输出格式：

- **Chat Agent**：回答含标题 /列表 / 加粗 / 链接
- **代码 Agent**：输出含代码块（ ``` 等语法）
- **多 Agent 协作**：每段输出都要 Markdown 化

具体后果（举四个最常见的）：

1. **标题闪烁**：用户问「解释一下 HTTPS」→看到 `# ` 然后突然变成大字 → 用户觉得 UI 卡顿。
2. **列表跳位**：Agent 输出 `- 第一项\n- 第二项` → 流式过程中列表项反复增删 → 用户看着「列表在跳舞」。
3. **代码块闪烁**：Agent 输出 ```python\nprint(1)\n``` → 没闭合前是普通文本 → 闭合后变成灰色代码块 → 用户看到「突然变了」。
4. **CPU 飙升**：长回答 + 朴素重渲染 → 浏览器卡顿（特别是低端机）。

流式 Markdown 做不好 = **UI 抖动 + 性能崩**。

### 易混点

流式 Markdown 常被和它的「邻居机制」混淆。**判错任何一个会让 UI 闪烁 + 卡顿**——必须分清。

#### 流式 Markdown vs 流式纯文本

| | 流式 Markdown | 流式纯文本 |
|---|---|---|
| **闪烁** | **有**（语法解析抖动） | 无（直接显示） |
| **性能** | 解析 + render 两步 | 直接 append |
| **适合** | LLM 默认输出格式 | 简单日志流 |

**判错会怎样**：以为流式渲染就是「加 chunk 到 DOM」→ 没考虑 Markdown 语法抖动 → 上线后满屏闪。

#### 流式渲染 vs 完整渲染

| | 流式渲染 | 完整渲染 |
|---|---|---|
| **用户看到** | **边到边**（一个字一个字出） | 一次性全部出现 |
| **首字延迟** | 低（1~3 秒） | 高（全部生成才显示） |
| **适合** | 用户想看「AI 在想什么」 | 用户只想看结果 |

**判错会怎样**：用完整渲染做 LLM 输出 → 用户等 30 秒看到整段 → 体验比非流式还差。

#### 朴素重渲染 vs 增量 diff

| | 朴素重渲染 | 增量 diff |
|---|---|---|
| **每次 chunk** | 全量重新解析 + 全量重新 render | 只 render 新增部分 |
| **性能** | **差**（O(n²)） | **好**（O(n)） |
| **闪烁** | **严重**（每次 re-render 抖） | 轻（只 diff 新增） |

**判错会怎样**：用朴素重渲染做长内容 → CPU 飙升 + 滚动卡。

#### Markdown 解析器 vs HTML 解析器

| | Markdown 解析器 | HTML 解析器 |
|---|---|---|
| **上下文敏感** | **是**（`# ` 后跟空格才是标题） | 否（标签式） |
| **不完整容错** | 难（不闭合就乱解析） | 易（自动闭合） |
| **适合流式** | **难**（需特殊处理） | 易 |

**判错会怎样**：把 HTML 解析的思路搬到 Markdown → 没处理「不闭合」问题 → 满屏乱跳。

#### 流式 Markdown vs 流式 JSON

| | 流式 Markdown | 流式 JSON |
|---|---|---|
| **渐进合法** | **是**（不完整语法暂时当文本） | 否（`{}` 必须成对） |
| **适合流式** | **友好** | 不友好（要 partial JSON parser） |
| **例子** | `# 你好` 拆 chunk 仍能 render | `{a:1,b:` 不能 render |

**判错会怎样**：以为流式 JSON 也容易 → JSON 必须完整才合法 → 流式 JSON 要 partial parser（Vercel AI SDK 的 `streamText` 工具）。

### 核心概念（变体 / 分支全扫）

流式 Markdown 有 10 个变体。

#### 1. 流式渲染的根本问题

**核心**：**不完整 Markdown 语法 → 解析抖动**。LLM 一个字一个字吐，每次来都可能改变 Markdown 的语义：

```
chunk 1: "#"        → 文本 "#"
chunk 2: "# "        → 文本 "# "（还是文本，# 后必须有空格才是标题）
chunk 3: "# 你"      → 文本 "# 你"
chunk 4: "# 你好"    → <h1>你好</h1>（突然变成标题）
```

**例子**：打字稿（流式）边打边看，字随时变；印刷品（一次性）全部写完才看。

**需求 1（根本问题演示）**：实现一个朴素流式 Markdown 渲染器；观察标题 / 列表 / 加粗的闪烁时刻。

#### 2. 朴素重渲染的代价

每次 chunk 都全量重新解析 + 重新 render：

```
chunk 1 → parse → render (DOM)
chunk 2 → parse 整段 → render 整段 (DOM 全替)
chunk 3 → parse 整段 → render 整段
...
```

**性能**：1000 字 Markdown → 100+ 次 re-render → **O(n²)** 复杂度 → CPU 飙升。

**需求 2（朴素 vs 增量对比）**：实现朴素版 + 增量 diff 版；对比 1000 字流式渲染的 CPU 占用。

#### 3. 常见闪烁场景（标题 / 列表 / 加粗 / 代码块 / 链接）

| 场景 | 朴素实现的问题 | 流式 chunk 序列 |
|------|---------------|----------------|
| **标题** | `# `还没出现时是普通文本 | `#` → `# ` → `# 你好` |
| **列表** | `- ` 后项还没出现时是普通文本 | `-` → `- ` → `- 项1` |
| **加粗** | `**` 没闭合时是普通文本 | `**` → `**重` → `**重要**` |
| **代码块** | ``` 没闭合时是普通文本 | ```` → ````p → ```python\n...``` |
| **链接** | `[文字](url)` 半成品 | `[` → `[文` → `[文](` → `[文](url)` |

**例子**：直播字幕（流式）字幕边出边显示，可能闪烁；新闻稿（一次性）排好版再看。

**需求 3（闪烁场景覆盖）**：对 5 种语法各构造 1 个流式输入；记录朴素实现的闪烁次数。

#### 4. 不完整语法占位符

**思路**：解析时跳过不完整语法，用占位符防止闪烁：

```
"# 你" → "# ?" (占位，不渲染为标题)
"# 你好" → <h1>你好</h1> (完整后才渲染)
```

**实现**：解析器扫描到 `# ` 但没有内容 → 输出占位符（不渲染）；扫描到 `# xxx\n` 才输出 `<h1>`。

**需求 4（占位符）**：实现「不完整语法不渲染」逻辑；验证5 种语法都不闪。

#### 5. 缓冲 N 字符再渲染

**思路**：牺牲实时性换稳定——攒 N 个字符再渲染：

```
chunk 1: "#" → 缓冲（不渲染）
chunk 2: "# 你" → 缓冲（不渲染）
chunk 3: "# 你好\n" → 攒够换行 → 渲染 <h1>你好</h1>
```

**代价**：首字延迟变高（典型从1s → 2~3s）；闪烁消失。

**Trade-off**：实时性 ↔ 稳定性。

**需求 5（缓冲渲染）**：实现「攒 N 字符再渲染」；对比首字延迟和稳定性。

#### 6. \n 触发块渲染

**思路**：Markdown 块级语法（标题 / 列表 / 代码块）都是按行解析的——**只在 `\n` 到达时重新解析块**：

```
chunk 1: "#" → 文本（不解析）
chunk 2: "# 你" → 文本（不解析）
chunk 3: "# 你好\n" → 触发解析 → <h1>你好</h1>
```

**优点**：行内的字符不影响块渲染；只在换行时抖一次。

**需求 6（\n 触发）**：实现「只在 \n 到达时解析块级语法」；验证行内字符（`**` 中间过程）不闪。

#### 7. 库选型

| 库 | 特点 | 流式友好度 |
|----|------|------------|
| **react-markdown** | React 生态主流 | 中（要自己处理流式） |
| **marked** | 速度快 / 老牌 | 中（不内置流式） |
| **markdown-it** | 插件丰富 | 中（不内置流式） |
| **Streamdown** | **专门为流式设计** | **高**（Vercel 出品） |
| **react-markdown + remark-gfm** | 完整 GFM 支持 | 中（要自己处理流式） |

**例子**：流式库（Streamdown）专门为 LLM 流式设计 → 默认不闪；通用库（marked / markdown-it）→ 要自己包装。

**需求 7（库选型）**：对比 Streamdown / react-markdown / marked 的流式闪烁率。

#### 8. 增量 diff 渲染

**思路**：用 React diff / Svelte fine-grained / Solid.js signals，只 render 新增部分：

```
chunk 1 → 渲染 chunk 1
chunk 2 → diff(chunk 1 + chunk 2) → 只渲染 chunk 2 的新 DOM
chunk 3 → diff → 只渲染 chunk 3 的新 DOM
```

**性能**：O(n)（不是 O(n²)）。

**需求 8（增量 diff）**：用 React 增量渲染 vs朴素全量重渲染；对比 1000 字流式的帧率。

#### 9. virtual scroll 长内容

**思路**：长内容（几千字）不要全渲染在 DOM 里——只渲染**可视窗口**：

```
[前1000 字 offscreen]
[当前可视区 500 字渲染]
[后 1000 字 offscreen]
```

**库**：react-virtuoso / react-window / @tanstack/virtual。

**适合**：Agent 长输出（几千字）；聊天历史很长。

**需求 9（virtual scroll）**：用 react-virtuoso渲染 5000 字流式内容；对比 DOM 节点数 + 帧率。

#### 10. 性能指标

**流式 Markdown 必须有指标**：

| 指标 | 怎么算 |
|------|--------|
| **首字延迟** | 用户发起 → 第一个字显示 |
| **首屏渲染** | 用户发起 → 第一个块（标题 / 段落）渲染完 |
| **闪烁次数** | 标题 / 列表跳动的次数 |
| **帧率** | 渲染过程中 FPS（应 ≥ 50） |
| **CPU占用** | 渲染过程中的 CPU 平均占用 |

**告警**：闪烁 > 5 次 / 帧率 < 30 FPS / CPU > 50%。

**需求 10（性能指标）**：实现 5 类指标采集；命中时告警。

### 例子

#### 打字稿 vs 印刷品

打字稿（流式）边打边看，字随时变 → 印刷品（一次性）全部写完才看。

对应：**流式 Markdown 像打字稿，每次有新 chunk 都要 re-render**。

#### 直播字幕 vs 新闻稿

直播字幕（流式）字幕边出边显示，可能闪烁 → 新闻稿（一次性）排好版再看。

对应：**流式 Markdown = 直播字幕；必须处理字幕抖动**。

#### 拼图 vs 看完整图

拼图（流式）边到边拼，每次抖动 → 看完整图（一次性）一次到位。

对应：**朴素流式渲染 = 拼图；每块位置都在抖**。

#### 标题闪烁

用户问「HTTPS」→ 看到 `# ` 突然变成大字 → UI 抖。

对应：**朴素实现的常见问题**。

#### 代码块切换

Agent 输出 ```python\nprint(1)\n``` → 没闭合前是普通文本 → 闭合后变成灰色块。

对应：**代码块的「突变」**。

#### CPU 飙升（低端机）

低端机 + 长回答 + 朴素重渲染 → 浏览器卡顿（特别是手机）。

对应：**优化流式渲染性能**。
