# **Node ≥22**：最低 22，不锁死小版本；换机器怎么对齐

> 对应模块：[模块 00 · 环境准备](./README.md) · 小节进度第 2 条
> 本条在「一小节一文件」改版前已勾 ✅。按当时约束对话和模块级笔记补全到 9 节模板。

- **来源**：本对话（陪跑 Coach）；无外部 URL
- **状态**：已沉淀

### 是什么

本仓库运行时：**最低 Node 22，不设上限**。

- `package.json` 里 `engines: { "node": ">=22" }`：安装 / 启动时拦住 **低于 22** 的版本。
- `apps/.nvmrc` 写的是**推荐**版本 22，方便换机器对齐；不是「只能用 22.x.y 某一个 patch」。
- 对齐方式：进入 `apps/` 再执行 `nvm use`（它读的是 `apps/.nvmrc`）。

TypeScript 侧配套：`@types/node` ^22；子项目 `tsconfig.json` `extends` `apps/tsconfig.base.json`。类型检查要够用（`strict: true`、外部数据 Zod 校验），但不是把所有 TS 插件规则开到最严。

### 为什么（Agent 开发要懂）

后面五个 app 都是 **TypeScript 5 + Node ≥22 + yarn**。版本飘了会出现两类事故：

1. 本机 Node 17/18/20 → `yarn dev` 被 `engines` 直接拦住，误以为是模型 Key 或 SDK 的问题。
2. 锁死某一个小版本（例如必须 22.14.0）→ 换电脑、CI、同事环境全部卡死，学习摩擦远大于收益。

「最低 22、推荐 22、22/24 都能跑」是为了：**学习环境可预期，又不把更高 LTS 卡死。**

### 易混点

| 容易当成 | 其实是 |
|----------|--------|
| `engines: ">=22"` 只允许 22 | 只拦 **低于** 22；22、23、24 都能过。 |
| 在仓库根执行 `nvm use` | `.nvmrc` 在 `apps/`，根目录读不到。 |
| `.nvmrc` 的 22 = 唯一合法版本 | 那是推荐值；`engines` 才是硬门槛。 |
| 「约束 Node 22」= 写成 `"22.x"` 或 `"22.14.0"` | 当时明确过：最低是 22，不是限定区间。 |

### 例子

本机 `node -v` 是 20 → 进 `apps/01-chatgpt-mini` 跑 `yarn dev` → `engines` 失败。正确顺序：

```bash
cd apps
nvm use          # 读 apps/.nvmrc，切到 22（或你已安装的 ≥22）
cd 01-chatgpt-mini
yarn dev
```

换一台新电脑：先装 nvm，再同样在 `apps/` 下 `nvm use`，不要靠「我记得我装过 Node」。

### 我追问过的

- 问了：TypeScript 类型检查不要太严也不要太松，Node 约束在 22 → 答在「是什么 / 取舍」：`strict` + Zod 守门；Node 最低 ≥22。
- 问了：最低是 Node 22，不是限定区间 → 答在「易混点」：不写死 `"22.x"` / 某一个 patch，只拦低于 22 的。

### 取舍

| 方案 | 结果 | 本仓库选 |
|------|------|----------|
| 不写 `engines` | 低版本能装上，跑到一半才爆冷门 API | 不选 |
| 锁死 `22.14.0` | 换机器必踩坑 | 不选 |
| **最低 ≥22 + `.nvmrc` 推荐 22** | 低版本进不来，更高 LTS 能跑 | **选这个** |

### 踩坑

- 错：在仓库根跑 `nvm use` → 读不到 `apps/.nvmrc`，版本没切过去。对：先 `cd apps`。
- 错：本机 Node 低于 22 还在排模型 / Key 的错 → 先看 `engines` 报错。
- 错：把 `engines` 理解成「必须正好 22」→ 22 及以上（含 24）都可以通过。

### 过关自检

- 本仓库最低 Node 22；换机器在 `apps/` 下 `nvm use` 对齐。
- `engines: ">=22"` 只拦低于 22 的，22 以上都能跑，不锁死小版本。
