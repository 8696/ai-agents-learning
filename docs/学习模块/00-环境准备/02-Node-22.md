# **Node ≥22**：最低 22，不锁死小版本；换机器怎么对齐

> 对应模块：[模块 00 · 环境准备](./README.md) · 小节进度第 2 条

- **来源**：本对话（陪跑 Coach）；无外部 URL
- **状态**：已沉淀
- **Demo**：无（会 `nvm use` 即可；跑一段 TS 看不到版本对齐的新信息）

### 是什么

本仓库运行时：**最低 Node 22，不设上限**。各 `apps/` 子文件夹都是 TypeScript 5 + yarn，约定同一条底线，避免「这台电脑能跑、那台不能跑」却去怪模型 Key。

三件东西分工不同，不要揉成一句「必须正好 22」：

| 零件 | 干什么 | 不是什么 |
|------|--------|----------|
| `package.json` 的 `engines: { "node": ">=22" }` | 安装 / 启动时拦住 **低于 22** 的版本 | 不是「只允许 22.x」；22、23、24 都能过 |
| `apps/.nvmrc` 里的 `22` | **推荐**版本，换机器时 `nvm use` 对齐用 | 不是唯一合法 patch（不是锁死 22.14.0） |
| `@types/node` ^22 + `tsconfig` `extends` `apps/tsconfig.base.json` | 类型和编译约定跟运行时同一档 | 不是把所有 ESLint 规则开到最严 |

对齐方式：进入 **`apps/`** 再执行 `nvm use`（它读的是 `apps/.nvmrc`）。仓库根没有这份文件，在根目录 `nvm use` 对不齐。

类型检查要到位：`strict: true`，外部数据（环境变量）用 Zod 在运行时 `parse`。不是「TS 越严越好」，也不是「完全不检查」。

### 为什么（Agent 开发要懂）

后面各 `apps/` 子文件夹共用这条运行时约定。版本飘了会出现两类事故，都像「模型坏了」，其实是环境：

1. 本机还是 Node 17 / 18 / 20 → `yarn app:00-01-mini-server` 被 `engines` 直接拦住。若去改 Key、改 `baseURL`，会浪费一晚上。
2. 锁死某一个小版本（必须 22.14.0）→ 换电脑、CI、以后的你自己，全部卡死。学习摩擦远大于「多锁一个 patch 更安全」。

「最低 22、推荐 22、22/24 都能跑」是为了：**学习环境可预期，又不把更高 LTS 卡死。**

### 易混点

| 容易当成 | 其实是 |
|----------|--------|
| `engines: ">=22"` 只允许 22 | 只拦 **低于** 22；更高版本能过。 |
| 在仓库根执行 `nvm use` | `.nvmrc` 在 `apps/`，根目录读不到，版本没切。 |
| `.nvmrc` 的 22 = 唯一合法版本 | 那是推荐值；硬门槛是 `engines`。 |
| 「约束 Node 22」= `"22.x"` 或 `"22.14.0"` | 当时明确过：最低是 22，不是限定区间。 |
| `engines` 报错 = Key 或 SDK 错了 | 先看 Node 版本，再查模型。 |

### 例子

**1. engines：游乐园身高杆，不是「必须正好 140.0 厘米」**

杆子写「140 以上才能坐」。139 进不去；140、150、160 都能坐。`>=22` 就是这根杆。写成必须 22.14.0，等于要求鞋码正好 42.0，换一双鞋就不能玩。

**2. .nvmrc：出门条上写「推荐穿 42」，不是「只能穿这一双」**

换城市旅游，纸条提醒你带 42 码的鞋，对得上朋友那双备用的。你可以穿 43。推荐和硬门槛不是同一张纸。

**3. 必须在 apps/ 下 nvm use：钥匙在二楼抽屉，一楼门厅翻不到**

`.nvmrc` 放在 `apps/`，像钥匙放在「代码这层」。你在仓库根（大门门厅）喊 `nvm use`，柜子是空的，Node 还是旧的。要先上楼：

```bash
cd apps
nvm use          # 读 apps/.nvmrc，切到 22（或你已安装的 ≥22）
yarn app:00-01-mini-server
```

**4. 换电脑：不要靠记忆，要靠那张推荐条**

新电脑「我记得装过 Node」——可能是 18。正确顺序：先装 nvm，再 `cd apps && nvm use`，再跑 `yarn app:00-01-mini-server`。和「换手机先登 iCloud」一样，对齐的是约定，不是记忆。

**5. 前端：engines 像 browserslist 的最低线**

你写 `>= chrome 90`，不是「只能 Chrome 90.0.1」。Node 22 这条线同一逻辑：拦住太老的，不锁死某一个 patch。

**6. 排错现场**

`node -v` 是 20 → 在 `apps/` 下跑 `yarn app:00-01-mini-server` → `engines` 失败。这时去改 MiniMax Key，是走错科室。先把身高杆过了，再查门票（Key）。

### 我追问过的

- 问了：TypeScript 类型检查不要太严也不要太松，Node 约束在 22 → 答在「是什么 / 取舍」：`strict` + Zod 守门；Node 最低 ≥22。
- 问了：最低是 Node 22，不是限定区间 → 答在「易混点」：不写死 `"22.x"` / 某一个 patch，只拦低于 22 的。

### 取舍

| 方案 | 结果 | 本仓库选 |
|------|------|----------|
| 不写 `engines` | 低版本能装上，跑到一半才爆冷门 API | 不选 |
| 锁死 `22.14.0` | 换机器必踩坑 | 不选 |
| **最低 ≥22 + `.nvmrc` 推荐 22** | 低版本进不来，更高 LTS 能跑 | **选这个** |

### 踩坑

- 错：在仓库根跑 `nvm use` → 读不到 `apps/.nvmrc`。 / 对：先 `cd apps`。
- 错：本机 Node 低于 22 还在排模型 / Key 的错。 / 对：先看 `engines` 报错。
- 错：把 `engines` 理解成「必须正好 22」。 / 对：22 及以上（含 24）都可以通过。

### 过关自检

- 本仓库最低 Node 22；换机器在 `apps/` 下 `nvm use` 对齐。
- `engines: ">=22"` 只拦低于 22 的，22 以上都能跑，不锁死小版本。
