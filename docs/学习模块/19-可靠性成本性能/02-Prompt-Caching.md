### 是什么

**Prompt Caching（前缀缓存）** 是 LLM API 提供商（Anthropic / OpenAI 等）提供的一种**降低重复长前缀费用 + 延迟**的机制——把请求的**前缀部分（prefix）**的处理结果缓存在服务端，下一次相同前缀进来时**复用上一次算过的中间状态**，不必从头重算一遍。

注意三件事：

1. **只缓存前缀**——从消息开头算起的一段**连续**内容。中间或末尾变了不命中。
2. **精确前缀匹配**——一字不差才算同一前缀；改了一个字就 miss。
3. **跨请求复用**——A 用户的请求和 B 用户的请求如果共享同一段前缀（比如同一个 System Prompt），可以**共用同一份缓存**（Anthropic 默认跨用户共享；OpenAI 默认不跨组织）。

价格层面（以 Anthropic Sonnet 为例，2026-10-10 数字会变）：

| 操作 | 相对价格 |
|------|----------|
| Cache miss（首次写入缓存） | 约 **1.25x**（创建缓存的写入略贵） |
| Cache hit（命中后读取） | 约 **0.1x**（命中便宜一个数量级） |
| 普通输入（不参与缓存） | **1x** |

一句话：**前缀缓存不是免费午餐——首次写要加价，但读便宜到几乎是送的**。会用的关键是把**稳定不变的长前缀**集中在消息开头。

### 为什么（Agent 开发要懂）

Agent 调 LLM 是**高频 / 高前缀重复**的场景：

- **System Prompt 稳定**：你给 Agent 的角色说明、行为约束、输出格式——一两次微调后基本不动，几十 KB 到几百 KB。
- **工具定义稳定**：Tool Definitions（每个 Tool 的 name / description / parameters JSON Schema）一旦定下来不再改，几十 KB 到几百 KB。
- **长文档上下文**：RAG 检索到的长文档塞进 messages 开头的 `system` 或单独 `document` 角色；同一会话里后续轮次会重复使用。
- **多轮对话**：历史轮次里前面的对话片段逐步固定（被归档的早期消息）。

具体后果（举三个最常见的）：

1. **没用 Prompt Caching**，Agent 每次调 LLM 都把 System + Tool Definitions 重新算一遍 → 月账单 60% 花在**重复算**上。
2. **缓存放错位置**（用户问题在 System 前面）→ 命中率 0% → 钱白花、延迟没降。
3. **System Prompt 经常改**（每次新会话都生成不同的动态 System Prompt）→ 命中率近 0% → 缓存形同虚设。

Prompt Caching 不懂 = **白白给 API 提供商交两份钱**——一份重复算、一份不命中后重算。

### 易混点

Prompt Caching 常被和它的「邻居机制」混淆。**判错任何一个都会让省钱方案失效**——必须分清。

#### Prompt Caching vs 上下文压缩（Context Compression）

| | Prompt Caching | 上下文压缩 |
|---|---|---|
| **做什么** | 不改语义，只缓存算过的中间状态 | 改语义——把长对话 / 文档摘要成短文本 |
| **省什么** | 省**算力 + 钱**（少走一遍 attention） | 省**输入 Token 数**（下次调用更短） |
| **能不能同时用** | 能——压缩完的短前缀照样可缓存 |

**判错会怎样**：以为压缩就够 → 100K 的上下文压到 10K 是省了输入，但每次还得算那 10K；再叠一层 Prompt Caching 把这 10K 缓存住，**两层一起才是真省**。

#### Prompt Caching vs 传统 KV Cache（Transformer KV Cache）

| | Prompt Caching | KV Cache |
|---|---|---|
| **范围** | **跨请求**（A 用户的请求和 B 用户的请求可共享） | **请求内**（同一次 generation 不同 step 共享 attention 矩阵） |
| **谁做** | API 服务端（你无感） | 模型推理引擎（你无感） |
| **粒度** | 整段前缀按 token 数算 | 每生成一个 token 都维护一份 |

**判错会怎样**：以为「模型本来就缓存了 KV 我没必要再管前缀」——KV Cache 是请求内的；Prompt Caching 是跨请求的。**前者你不用管，后者你得设计前缀结构**。

#### Prompt Caching vs Response Caching（响应缓存）

| | Prompt Caching | Response Caching |
|---|---|---|
| **缓存什么** | 请求的**输入前缀** | 请求的**输出回答** |
| **命中条件** | 前缀一字不差 | 输入完全一致（可加语义模糊匹配） |
| **适合** | System + Tools + 历史对话稳定的 Agent | 同一问题的重复问（如 FAQ） |

**判错会怎样**：用 Response Caching 给 Agent 提速——但用户问题每次都不同，命中率 0；正确做法是 Prompt Caching 缓存稳定前缀。

#### Prompt Caching vs Embedding Cache（向量缓存）

| | Prompt Caching | Embedding Cache |
|---|---|---|
| **在哪一层** | LLM **推理层** | RAG **检索层** |
| **缓存什么** | token 序列的前缀处理结果 | 文本 → 向量的映射 |
| **谁做** | API 提供商 | 你自己的向量库客户端 |

**判错会怎样**：以为「RAG 里有 embedding 缓存就够了」——Embedding Cache 解决「同一段文本别重复 embed」；Prompt Caching 解决「同一段文本别重复送进模型算 attention」。

#### Cache Miss 写入 vs Cache Hit 读取（价格差很多）

| | Cache miss（首次写） | Cache hit（命中读） |
|---|---|---|
| **价格** | **1.25x** | **0.1x** |
| **量级差** | 比普通输入**贵 25%** | 比普通输入**便宜 90%** |
| **持续时长** | 一次性（写入后下次就是 hit） | 整个 TTL 内每次调用都享受 |

**判错会怎样**：以为「反正都是缓存应该便宜」——首次写是**额外**付的钱，要写得值才能赚回来；TTL 短、命中率低、写得频繁反而**更贵**。

### 核心概念（变体 / 分支全扫）

Prompt Caching 不是一个开关——它有 10 个变体。

#### 1. 缓存的是前缀（Prefix），不是任意片段

从消息开头算起的**连续**内容才会被缓存。中间或末尾变了不命中。

**例子**：菜单印在站牌上（System），乘客看自己坐哪趟（User 后缀）。如果菜单印在乘客单据**中间**——不命中，因为不是前缀。

**需求 1（只缓存前缀验证）**：同一长内容放在 System 开头 vs 放在 User 末尾，对比命中率——前者命中，后者为 0。

#### 2. 缓存长度边界（最小 / 最大）

- **最小缓存大小**：Anthropic 1024 tokens，OpenAI 1024 tokens。比这短**不计入缓存**（直接当普通输入）。
- **最大长度上限**：Anthropic 200K tokens 上下文里，缓存前缀本身有上限（具体看版本）。

**例子**：餐厅菜单只印 5 道菜（小内容）→ 不值得做菜单牌，客人直接看小卡片就行——**够长才上缓存**。

**需求 2（最小长度验证）**：构造 < 1024 token 和 ≥ 1024 token 两种 System Prompt，对比命中行为——前者不被缓存。

#### 3. 命中率口径（cache_creation vs cache_read）

API 返回的 usage 字段里有：

| 字段 | 含义 |
|------|------|
| `cache_creation_input_tokens` | 这次写入了多少 tokens 进缓存 |
| `cache_read_input_tokens` | 这次命中读取了多少 tokens |
| 命中率 | `cache_read / (cache_read + cache_creation + 普通输入)` |

**注意**：命中率口径要按**总输入**算，不是按缓存写入量——否则短期内的「写入即 0 命中」会让你误判。

**例子**：电表上的「峰谷电量」——只算「谷段省了多少」不看「峰段用了多少」会得出错误结论。

**需求 3（命中率口径）**：用真实请求拉 100 次，统计 cache_creation vs cache_read；输出（a）总命中率（b）缓存部分命中率（c）账单对比。

#### 4. 失效条件：TTL / 显式 invalidate / 内容变

三种方式让缓存作废：

| 方式 | 怎么触发 | 典型时长 |
|------|----------|----------|
| **TTL**（Anthropic 5 分钟，OpenAI 5~10 分钟） | 自然过期 | 几分钟 |
| **内容变**（精确前缀匹配） | System 加一句 / 改一个字 | 立即 |
| **显式 invalidate**（部分厂商） | 调 API 标记某段缓存失效 | 立即 |

**例子**：超市促销海报贴 5 分钟（TTL）→ 5 分钟后自动撕掉换新；海报内容改了（哪怕只是把「限时 8 折」改成「限时 7 折」）→ 旧版立即作废。

**需求 4（失效验证）**：5 分钟不发请求 → 第 6 分钟发同一前缀 → 验证 cache_creation（重新写入）而非 cache_read。

#### 5. 适合前缀缓存的内容

| 适合 | 例子 |
|------|------|
| **System Prompt** | 角色说明、行为约束、输出格式、Few-shot 示例 |
| **Tool Definitions** | 工具列表的 JSON Schema（稳定不变的部分） |
| **长文档上下文** | RAG 检索到的长文档塞进 messages 开头 |
| **历史对话归档** | 早期轮次被压缩摘要后固定在前面 |

**例子**：公司员工手册印在文件夹最前面，新员工签到表追加在后面——员工手册适合缓存，签到表每次都不一样。

**需求 5（适合场景验证）**：构造「System Prompt 2000 tokens + Tool Definitions 500 tokens」固定场景，连续 10 轮调用同一前缀，验证命中率 ≥ 90%。

#### 6. 不适合前缀缓存的内容

| 不适合 | 为什么 |
|--------|--------|
| **用户问题（每次都不同）** | 每次都变 → 命中率 0 |
| **动态生成的 System Prompt**（如每次会话插入时间戳） | 一字之差就 miss |
| **放在消息中间或末尾的稳定内容** | 不是前缀，不命中 |
| **< 1024 token 的短内容** | 不计入缓存 |

**例子**：客人点的菜（User）每次都不一样，写在黑板（System）前面——黑板上的菜单能缓存，但客人点的菜白纸黑字写一次只能算一次。

**需求 6（不适合场景验证）**：把同一段长文档**放在 User 消息末尾** vs 放在 System 开头——对比命中率，验证位置决定一切。

#### 7. 跨请求复用（多租户共享）

- **Anthropic**：默认跨用户共享同一前缀（按组织隔离）。
- **OpenAI**：默认不跨组织共享；同组织内可手动启用。

**含义**：你的 Agent 用户的 System Prompt 都一样 → 你和隔壁公司的同前缀互不影响；但你和**同组织内**别的应用共享前缀。

**例子**：连锁餐厅的菜单（同一品牌）印一份就行——所有门店共用一份菜单（跨用户缓存）；不同品牌的菜单各印各的（按组织隔离）。

**需求 7（跨用户复用）**：模拟 A 用户和 B 用户共用同一 System Prompt；调用同一前缀；验证 B 用户第一次调用就 cache_read 命中（A 用户之前写过）。

#### 8. 价格模型与回本计算

**回本条件**：单次请求**总成本**（cache_miss 写入 + 普通输入 + 输出）vs 多次请求**累计成本**（缓存命中为主）。回本点是命中次数 ×（单次成本节约）> 单次额外写入成本。

**例子**：写一次菜单 1 元，客人看一眼 0.1 元。如果一桌只来一个客人，写菜单反而亏本；来 10 个客人，菜单写一次大家都看就赚。

**回本简化公式**：

```
总成本(无缓存) = N × (前缀 tokens × 单价)
总成本(有缓存) = 1 × (前缀 × 1.25x) + (N-1) × (前缀 × 0.1x)
回本条件：N 足够大，使 0.1x × N > 1.25x
近似回本点：N > 12.5 次访问同一前缀
```

**需求 8（回本计算）**：自己测算同一前缀 N 次调用的成本曲线；输出「N = 多少时开始省钱」的图表。

#### 9. 实现机制：Vendor-managed vs Client-side

- **Vendor-managed**（Anthropic / OpenAI 自动）：在请求里加 `cache_control: { type: "ephemeral" }` 标记某段为缓存点——服务端自动管。
- **Client-side**：你在客户端**手动拼前缀**——把稳定部分单独存一份，每次请求拼接到 messages 最前面。

**前者主流**——不要自己造轮子。Vendor 已做。

**例子**：大超市的购物车（自动缓存）和自家冰箱手动整理——后者没必要，超市的购物车自动追踪你的购物清单。

**需求 9（Vendor 机制验证）**：构造 Anthropic 风格请求，对同一前缀连续两次调用；第一次 usage 含 `cache_creation_input_tokens`，第二次含 `cache_read_input_tokens`。

#### 10. 观察与调试（usage 字段）

读 API 返回的 usage 是**唯一可信的命中率指标**。常见调试坑：

- **命中率为 0 但前缀一字不差**：可能是 TTL 过期，或跨组织隔离，或前缀长度 < 1024。
- **命中但费用没降**：把 cache_creation 也算进了「缓存成本」——要把 cache_read 单独算。
- **usage 字段缺失**：用了不支持缓存的模型或端点。

**例子**：电表跳数正常，但手机 App 显示「电费 0」——多半是没读对字段或字段没传上来。

**需求 10（usage 调试）**：写一段小工具拉 100 次请求的 usage，统计三个指标（命中率 / 回本点 / 平均成本），并在命中率异常时输出可能原因。

### 例子

#### 报菜名（System + User 顺序）

餐厅菜单 100 道菜固定在前台黑板上（System）→ 客人点单只追加新条目（User）→ 黑板上的菜名不重复算钱。

对应：**System Prompt（2000 tokens 菜单）+ User 问题（动态）→ 缓存命中 System 部分**。

#### 公交站时刻表（稳定 vs 动态）

时刻表印在站牌上（静态前缀）→ 每个人来了只看自己坐哪趟（动态后缀）→ 站牌内容全站共享（跨用户缓存）。

对应：**Anthropic 默认跨用户共享同一前缀**。

#### 前端 long-list（位置决定命中）

列表 1000 项的前 990 项渲染逻辑不变（缓存前缀）→ 最后 10 项随用户滚动变（动态后缀）。

对应：**稳定部分放在 System 开头**才能命中；放在 User 末尾**无效**。

#### 超市促销海报（TTL）

超市促销海报贴 5 分钟（TTL）→ 5 分钟后自动撕掉换新（过期 miss）→ 客人 6 分钟后再来看到的是新版海报（重新写）。

对应：**Anthropic 5 分钟 TTL；过期后下次访问重新 cache_creation**。

#### 复诊病历（适合场景）

医院病历系统：患者历史病历（早期轮次摘要）固定在 System 开头 → 当次问诊（User 问题）追加在后面 → 病历部分命中缓存。

对应：**多轮对话里历史归档部分做前缀**。

#### 错放的菜单（不适合场景）

把菜单（稳定内容）**写在客人点的单据中间**（不是前缀）→ 每次点单时菜单部分**不命中**——必须放在最前面才是前缀。

对应：**位置不对 = 命中率 0**。
