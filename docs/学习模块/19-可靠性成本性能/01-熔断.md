### 是什么

**熔断（Circuit Breaker）** 是一种**调用方主动切断对下游依赖**的保护机制——当下游（外部 LLM、向量库、Tool 后端等）连续出错时，调用方不再真的去敲下游，而是**直接短路返回失败（或降级结果）**；过一段时间后允许**少量探测请求**试水；探测成功就恢复正常调用，失败就再次断开。整套行为用一个**状态机（State Machine）** 描述，三态循环：

| 状态 | 含义 | 调用方怎么做 |
|------|------|---------------|
| **闭合（CLOSED）** | 下游看上去健康 | 请求照常发；窗口里统计失败率 |
| **断开（OPEN）** | 下游明显出问题 | **不再真发请求**，直接返回「电路已断开」或降级结果；等一个冷却时间 |
| **半开（HALF_OPEN）** | 冷却期到了，试试看下游是否恢复 | **放少量探测请求**进入下游；若成功 → 回到 CLOSED；若失败 → 重置冷却计时，回到 OPEN |

```
            连续失败到阈值                      冷却时间到
   ┌──────────────────────────┐         ┌─────────────────┐
   │                          ▼         ▼                 │
 CLOSED ─────────────────► OPEN ─────────────────► HALF_OPEN
   ▲                          │                          │
   │                          │  探测失败                │
   │                          └──────────────────────────┘
   │
   └──────────────  探测全部成功  ◄──────── HALF_OPEN
```

一句话：**熔断不是修下游，是保护调用方不再继续被下游拖死**——让错误**快速失败（fast-fail）**，把线程、Token 预算、用户的等待时间留给还能工作的请求。

### 为什么（Agent 开发要懂）

Agent 在生产里几乎一定面对**外部依赖**——上游 LLM API（Anthropic / OpenAI / 智谱）、向量库、Search API、内部 RAG 微服务、Tool 后端。任何一个出问题，Agent 的特性会让伤害**放大**：

- **重试循环天然存在**：Agent 循环（ReAct / Plan-and-Execute）发现工具失败会自己重试——如果工具背后是 5xx，Agent 会把 1 次失败放大成 5、10、20 次，每一次都烧 Token。
- **同步等待放大延迟**：前端一次 fetch 等 2s 超时还能忍；Agent 一个 step 卡 60s 会**级联**——下一个 step 还没开始，用户的耐心已经没了。
- **失败率传染**：Agent 把 LLM 调用结果再喂给下一个 LLM 调用，一次 5xx 让后续推理全部跑偏；如果不熔断，请求队列里堆的全是注定失败的请求。
- **成本失控**：LLM 调用是按 Token 计费的；连续失败时还在重试 = Token 在白烧。

具体后果（举三个最常见的）：

1. **智谱某区域 API 503**，你的 Agent 没熔断 → 每个请求都重试 3 次再换模型再重试 → 30 分钟里烧掉 ¥800。
2. **向量库主从切换**，查询耗时从 50ms 跳到 8s → Agent 等超时 → 用户的整个对话卡住。
3. **第三方支付 Tool 短暂挂掉**，所有用户同时发起「查询订单」→ 你打爆了那个本来还有救的下游，本来 1 分钟能自愈的故障被你拖成 10 分钟。

熔断器不是「保险」，是**让故障局限在一个时间窗里、不传染**。

### 易混点

熔断常被和它的「邻居机制」混淆。**判错任何一个都会让可靠性反而变差**——必须分清。

#### 熔断 vs 重试（Retry）

| | 重试 | 熔断 |
|---|---|---|
| **目的** | 假设这次失败是临时的，再试一次可能成功 | 假设下游已经病了，**不再试** |
| **触发** | 收到错误立刻重试（1~N 次） | 连续失败到阈值才触发 |
| **对象** | 一次请求内部的多次尝试 | 一段时间内的所有请求 |
| **关系** | 重试前**应该**先查熔断状态——熔断了就别重试了，直接降级 |

**判错会怎样**：把熔断器当重试来用 = 下游挂了还在拼命打，**把可恢复故障打成雪崩**。把重试当熔断来用 = 一次失败就永远断开，**正常抖动都被你干掉**。

#### 熔断 vs 限流（Rate Limit）

| | 限流 | 熔断 |
|---|---|---|
| **保护谁** | **保护下游**别被你打爆 | **保护调用方**别被下游拖死 |
| **触发** | QPS / 并发数到上限 | 失败率到阈值 |
| **方向** | 你方主动减速 | 你方主动断开 |

**判错会怎样**：熔断器保护的是**调用方**自己（线程 / Token / 用户体验）；限流保护的是**被调方**。两者通常**叠在一起用**——上游有限流不让请求太快发，下游有熔断不让请求在出错时还继续打。

#### 熔断 vs 降级（Fallback）

| | 降级 | 熔断 |
|---|---|---|
| **做什么** | 失败时给一个**次等但可用**的结果（缓存 / 默认值 / 简化路径） | 失败时**直接拒**或走预设路径 |
| **触发** | 单次错误 | 累计错误到阈值 |
| **关系** | 熔断 OPEN 之后通常**搭配**降级返回；降级本身可以独立存在 |

**判错会怎样**：以为熔断 = 降级 = 「挂了就报错给用户」。错。熔断是**开关**，降级是开关之后**给什么**——两者要分开设计。

#### 熔断 vs 超时（Timeout）

| | 超时 | 熔断 |
|---|---|---|
| **做什么** | 单次请求的最长等待时间 | 一段时间内的整体策略 |
| **关系** | 超时是熔断的**输入**之一：超时本身算「失败」；超时太长会让熔断器来不及反应 |

**判错会怎样**：超时设 60s → 即使熔断器阈值 = 3 次失败，要 180s 才触发 → 下游真挂时**熔断器基本无效**。熔断要先有「合理的超时」（典型 2~5s）做底。

#### 熔断 vs 缓存

| | 缓存 | 熔断 |
|---|---|---|
| **做什么** | 用旧值替代**没失败**但**慢 / 贵**的下游 | 拒绝**失败**的下游 |
| **触发** | TTL / 命中率 | 失败率 |

**判错会怎样**：把缓存当熔断用——下游真出错时返回**过期脏数据**，反而更糟。**熔断 OPEN 后返回缓存**是可以的（降级策略之一），但熔断本身不是缓存。

### 核心概念（变体 / 分支全扫）

熔断不是「一个开关」——它是一个**有 9 个变体的状态机系统**。

#### 1. 状态机三态 + 状态切换条件

闭合 → 断开：窗口内**判定条件**到达阈值（见变体 2）。断开 → 半开：冷却时间到。半开 → 闭合：探测请求全部成功（或达到成功阈值）。半开 → 断开：探测请求至少一个失败，重置冷却计时。

**例子**：保险丝的「正常 / 烧断 / 试推上去」。

**需求 1（三态状态机）**：实现完整三态状态机；切换条件可配置（失败阈值、冷却时长、半开放探测次数）。

#### 2. 触发判定策略

| 策略 | 怎么算 | 适合 |
|------|--------|------|
| **连续失败计数** | 连续 N 次失败就熔断 | 失败模式集中、突发型故障 |
| **滚动窗口失败率** | 过去 M 个请求里失败 ≥ P% 熔断 | 持续低烈度故障（5% 慢、95% 正常） |
| **时间窗口失败数** | 过去 T 秒内失败数 ≥ K 熔断 | 突发流量型故障 |
| **复合** | 失败率 + 最小样本数（避免样本太少误熔断） | 生产首选 |

**例子**：电表箱的「连续 3 次跳闸就报警」vs「过去 1 分钟掉电 ≥ 5 次就报警」。

**需求 2（两种触发策略）**：至少支持「连续失败计数」+「滚动窗口失败率（Sliding Window）」两种策略可切换。

#### 3. 断开期行为：fast-fail 与 fallback

OPEN 期间不能让线程**空转等待**——必须**立即返回**（fast-fail）。立即返回时给什么？

- **抛异常**：`CircuitOpenError`，调用方决定怎么处理。
- **走 fallback**：返回缓存值、默认值、降级路径、上一会话摘要。
- **异步排队**：放进队列等下游恢复。

**例子**：电梯报警停用时，乘客立刻得到「电梯故障，请走楼梯」的提示，而不是电梯门一直闪着假装在响应。

**需求 3（OPEN 期 fast-fail + fallback）**：OPEN 时 fast-fail，并支持自定义 fallback（默认 fallback / 缓存 fallback / 抛异常三选一可配置）。

#### 4. 半开探测策略

HALF_OPEN 决定「放几个探测请求、怎么判定结果」。

- **单探测**：放 1 个，成功就 CLOSED，失败回 OPEN。
- **批量探测**：放 N 个（如 5 个），成功 ≥ K 个才 CLOSED。
- **比例探测**：按流量比例放少量请求进下游。

**例子**：推上保险丝后先开一盏小灯试一下（小电流），不是直接把家里所有电器都打开。

**需求 4（半开探测）**：HALF_OPEN 放可配置数量的探测请求；探测判定支持「全部成功」或「多数成功」两种策略。

#### 5. 多级作用域：进程内 vs 集中式

- **进程内熔断**：每个实例各自维护自己的状态。简单、快；缺点是 100 个实例各自熔断 = 实际请求量被 100 倍放大。
- **集中式熔断**（Redis / ZooKeeper / 配置中心）：所有实例共享状态。能感知「集群级」失败率；缺点是要多一跳网络、Redis 挂了状态会丢。

**例子**：单家住户各自装漏电保护（进程内）vs 整栋楼的中央配电箱做总保护（集中式）。

**需求 5（集中式 vs 进程内）**：进程内（单实例）熔断器为基线；并提供「集中式」模式开关（共享 Redis 状态），跑同一批请求时两模式指标可对比。

#### 6. 错误分类：哪些算失败、哪些不算

熔断器**必须能区分错误类型**，否则误熔断 / 不熔断：

| 错误 | 进熔断计数？ |
|------|-------------|
| 5xx 服务器错 | ✅ 进 |
| 超时（Timeout） | ✅ 进 |
| 网络错误（连接拒绝、DNS 失败） | ✅ 进 |
| 4xx 业务错（如参数错、库存不足） | ❌ **不进**（你修不好的下游问题熔断了也没用） |
| 401 / 鉴权失败 | ❌ **不进**（你的 Key 错了，熔断了照样 401） |
| 429 限流 | ⚠️ **单独通道**——它是「下游告诉你慢点打」，按限流退避而不是熔断 |

**例子**：4xx 像「地址写错了，信送不到」——这不是邮路坏了，是你自己写错了地址，反复寄也没用。

**需求 6（错误分类）**：错误分类可配置；4xx 默认不计入熔断；鉴权失败 / 限流 单独通道不进熔断；记录每类错误的计数用于排查。

#### 7. 与相邻机制的协同

熔断不是孤岛。常见组合：

| 协同 | 怎么做 |
|------|--------|
| **+ 超时** | 单次 timeout 2~5s；超时也算熔断的「失败」 |
| **+ 重试预算（Retry Budget）** | 整个调用链给一个「重试次数上限」（如 2 次）；熔断触发时直接打 0 次重试 |
| **+ 限流** | 上游限流限速 + 下游熔断断开；两者一起形成「流量整形 + 故障隔离」 |
| **+ 降级（Fallback）** | OPEN 时返回缓存 / 默认值 / 简化结果 |
| **+ 隔离（Bulkhead）** | 不同下游用独立线程池 / Token 预算；一个挂掉不会拖死别的 |

**例子**：厨房有 4 个灶台，其中一个起火时**只关那个灶台的燃气阀**（隔离），而不是关总阀（雪崩）。

**需求 7（四件套协同）**：熔断器可与 timeout / 重试预算 / fallback 三者独立配置；同一调用链路上四者行为可观察（哪一步在等 / 哪一步被短路）。

#### 8. 可观测：状态切换、指标、告警

熔断是个**会切换状态的活系统**，没有观测 = 没人知道它什么时候生效。

要记的：

- **每次状态切换打结构化日志**：`from_state → to_state · 原因 · 失败计数 · 时间`。
- **暴露指标**：当前状态、累计断开次数、本小时断开时长、失败率。
- **触发告警**：断开持续 > X 分钟、断开频率 > Y 次/小时。
- **挂 trace**：每个被短路 / 降级的请求挂一个 trace 标记，方便在 Langfuse / LangSmith 里看到「为什么这一步没真发」。

**例子**：电路总闸跳闸时电表箱会有指示灯；物业要能远程看到这个灯。

**需求 8（可观测）**：每次状态切换输出结构化日志（含原因 + 计数）；暴露「当前状态 / 累计断开次数 / 当前失败率」三项指标；断开持续超阈值告警。

#### 9. 恢复策略：快恢复 vs 慢启动

探测成功之后回到 CLOSED 那一刻，是**立刻全量恢复**还是**慢慢放开**？

- **快恢复**：探测成功立刻全量——简单，但下游刚恢复时可能还脆弱。
- **慢启动（Slow Start）**：探测成功后按比例逐步放流量（如 10% → 30% → 50% → 100%），给下游一个缓冲。

**例子**：保险丝推上去后不要立刻开空调 + 微波炉 + 电热水器，先开一盏灯（小负载），确认没跳闸再逐步开大电器。

**需求 9（恢复策略）**：恢复阶段可选「快恢复」或「慢启动」；慢启动支持配置放流量曲线（如按时间或按成功次数递进）。

### 例子

#### 跳闸（状态机三态）

家里微波炉 + 电热水器 + 空调同时开 → 总闸跳了 → 推上保险丝（**不是立刻全开电器**）→ 先开一盏灯（小电流试一下）→ 没跳闸再逐一开大电器。

对应：**CLOSED**（全开）→ **OPEN**（跳闸断电）→ **HALF_OPEN**（推保险丝试一下）→ **CLOSED**（确认安全全开）。

#### 电梯故障保护（触发判定 + 错误分类）

电梯门连续 3 次关不上（传感器失败）→ 电梯停用报警（OPEN）。但「楼层按钮按错了」（4xx 业务错）**不会让电梯停用**——那是乘客自己的问题，不是电梯的故障。

#### 网约车派单（断开期 fallback + 多实例）

司机连续 5 单都拒（失败率超阈值）→ 平台 30 分钟内不再派给他（OPEN + 冷却 30 分钟）→ 30 分钟后先派一单试试（HALF_OPEN）→ 接了 → 恢复正常派单（CLOSED）；拒了 → 再熔断 30 分钟。

如果只在本机做：100 个城市各自判断——一个城市司机大量拒单**只熔断那个城市**（Bulkhead 隔离），其他城市正常。

#### 前端 fetch：第三方支付 API 5xx（与超时 / 重试协同）

```ts
// 伪代码：每次调用前先查熔断状态
async function pay(orderId) {
  if (breaker.isOpen()) {
    return breaker.fallback(); // 返回「稍后重试」友好提示
  }
  try {
    return await breaker.call(() =>
      fetchPayApi(orderId, { timeout: 3000 }) // 超时 3s
    );
  } catch (e) {
    // 一次失败重试 1 次；重试预算 = 2
    return retryOnce(() => fetchPayApi(orderId, { timeout: 3000 }));
  }
}
```

熔断器在背后：连续 5 次 5xx → OPEN → 30s 内所有请求都直接走 fallback → 30s 后放 1 个探测。
