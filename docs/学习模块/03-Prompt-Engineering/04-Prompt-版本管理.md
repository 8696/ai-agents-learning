# **Prompt 版本管理**：Prompt 也是代码，要 diff、要回归

> 对应模块：[模块 03 · Prompt Engineering ⭐⭐⭐⭐](./README.md) · 小节进度第 4 条
> **来源**：本对话（2026-09-02 首次沉淀）
> **状态**：已沉淀

## 是什么

**一句话：把 Prompt 当代码管 —— 用版本号、变更记录、回归样本、diff/审查，把它从"对话里的一段字符串"变成仓库里的一项资产。**

这件事是 2023 年 LLM 应用走出"玩具阶段"才被正视的工程问题。早期大家以为 Prompt 是"会一点点就行"的小事，产品上线后立刻撞墙：

- 谁改了 "请帮我总结" 这个 Prompt？现在用户报错了，回滚的是哪个版本？
- v3 看着和 v2 只差一个标点，怎么线上崩了？
- 这个 bug 是模型升级导致的，还是 Prompt 改坏了？怎么分清楚？

**Prompt 版本管理**就是回答这三个问题的工程实践。它不是框架、不是 SDK、不是新协议，而是一套**做法**：

| 做法 | 是干什么 | 为什么必做 |
| --- | --- | --- |
| **落文件** | Prompt 不躺在对话/数据库里，写进 `src/prompts.ts` 或 `.prompt.md` | 才有 diff、才有 blame、才能 PR |
| **加元数据** | 文件头注明 version、author、date、changelog | 一眼能看出"现在的线上版本是 v?.?.?" |
| **回归样本集** | 固定一组 ≥5 个输入样例 + 期望要点 | 改 Prompt 后跑同一组，对比行为有没有退化 |
| **diff/审查** | Prompt 当 PR 改，必须有人 review | 一字之差就是线上事故 |
| **绑定模型版本** | 记录这条 Prompt 用的是哪个模型（gpt-4o-mini / MiniMax-M3 / …） | 模型升级是另一条变化的横轴，必须分开记 |

**为什么这件事会引起重视**：代码改一个字符，编译不通过会立刻报错；**Prompt 改一个字符，模型行为可能天翻地覆，而且没有编译错误这种 early signal 提醒你**。这就是把 Prompt 当代码管、要 diff、要回归的根本原因。

## 为什么（Agent 开发要懂）

1. **线上崩了回不去**：客服说"昨天还能正确抽取订单号，今天不行了"——翻 git log，找不到对应的 Prompt commit；改坏的版本已经覆盖了好版本。**丢了就找不回。**
2. **"看起来差不多"骗人**：v2 和 v3 表面只差一句 "Let's think step by step"，但模型行为从 70% → 90%，或者反过来。**人眼看不出来**，必须用回归样本量出来。
3. **多人协作互相踩脚**：A 加了 "请明确引用文档"，B 同时在改同一文件；合并时看 Git conflict 解决得很"对"，但行为全乱了。**没有结构化文件 + 评审 = 事故。**
4. **模型升级悄悄废 Prompt**：上个月某模型还能听懂你的 ReAct 指令，这个月换下一代模型后行为漂了。**不绑模型版本你都不知道这条"漂"是 Prompt 的问题还是模型的问题。**
5. **Agent Loop 调试无证据**：§7 写 ReAct 时，Thought/Action/Observation 不对劲，回滚回到哪一版 Prompt 才能复现？答得上来就 5 分钟，答不上就一整天。

## 易混点

| 组 | 差在哪 | 判错会怎样 |
| --- | --- | --- |
| **Prompt 版本 vs 代码版本** | 都用 git，但 Prompt 改的**频率高**（一次实验一个版本）、**粒度细**（一个词）、**依赖行为而非编译结果** | 用"代码版本"的节奏（每次大改才 commit），Prompt 在并发 PR 中间会被覆盖 |
| **Prompt 版本 vs 模型版本** | 模型升级是**横轴变**（GPT-4o → Claude Sonnet 4），Prompt 改是**纵轴变**。两者各自影响行为，必须**分开绑** | "Prompt 没改怎么就不行了"——其实是模型升级了，把账算在 Prompt 上 |
| **Prompt 版本 vs 配置（temperature / tools 列表）** | Prompt 是**文字内容**；temperature/tools 是**运行时配置**。两者都会影响行为，但要分两份 metadata 记 | 把"我把 temperature 从 0.7 调到 0.3"当成 Prompt 版本变更记一笔，会把"哪些问题来自内容、哪些来自采样"混在一起 |
| **文本 diff vs 行为 diff** | 文本 diff 是肉眼看的；行为 diff 必须在**同一组样本**上跑两版对比才看得出 | "看着差不多" → 不跑回归 → 上线炸。**以行为回归为准**，文本 diff 是辅助 |
| **手动管 vs 用 LangSmith Prompt Hub 等平台** | 手动：文件 + git + 一组样本，门槛低、上限低；平台：自带版本、协作、A/B、评估，与代码仓库双写 | 用了平台之后忘在代码仓库里留一份 — 平台 vendor lock-in，换平台时数据带不出 |
| **回归集 vs 评估集** | 回归集 = 检测"有没有退化"（小、稳定、用上一版跑过作为基线）；评估集 = 衡量"现在到底多准"（大、可扩、可以一次一换） | 把评估集当回归集：评估集每次扩充，回归比较就失去"基线"，看不出退化 |

## 例子（每个核心对象各 1 个能演一遍的）

### 例子 1：Prompt 落文件（机制）

把聊天机器人里"欢迎语"从对话字符串变成仓库里的 `apps/03-Prompt-Engineering/04-Prompt-版本管理/src/prompts/greeting.prompt.md`：

```text
<!-- ── 元数据（每条 Prompt 都有这一段） ── -->
<!-- version: 1.0.0   -->
<!-- author:  longjinwen -->
<!-- date:    2026-09-02 -->
<!-- changelog: -->
<!--   1.0.0 (2026-09-02): 初版，从对话里搬出来 -->
<!-- model:  MiniMax-M3 -->

你是我们公司"星野客服"的虚拟助手。请用中文回复，先问候、再听用户诉求、给到步骤。
```

把 Prompt 从"对话里的字符串"变成"仓库里的、有元数据的一个文件"，就是"Prompt 当代码管"的第一步。

### 例子 2：改动 + diff + 评审

第二天发现"用户上来就投诉，没人看问候"，改一版：

```diff
- <!-- version: 1.0.0 -->
+ <!-- version: 1.1.0 -->
+ <!-- changelog: 1.1.0 — 把问候前置成可选，先听用户诉求 -->

  你是我们公司"星野客服"的虚拟助手。请用中文回复，先问候、再听用户诉求、给到步骤。
+ 如果用户第一句就是投诉/紧急问题，跳过问候，直接进入问题处理。
```

### 例子 3：回归样本集（这是真决断点）

固定一组 5 条样本（这就是 §3 验收里硬要求的"≥5 个样本"）：

| # | 输入 | 期望要点 |
| --- | --- | --- |
| 1 | "我套餐扣错了！" | 直接进入问题处理（不问候） |
| 2 | "在吗？想问个事" | 简短问候 + 问诉求 |
| 3 | "hi" | 友好打招呼，问能帮什么 |
| 4 | "你好，我是新人" | 简短问候 + 自我介绍欢迎 |
| 5 | "我退订一直失败" | 直接进问题处理（紧急） |

跑 v1.0.0 和 v1.1.0**同一组样本**，记每个样本：

- **格式合规率**：v1.0.0 = 5/5；v1.1.0 = 5/5（都没变）
- **诉求回应延迟**：v1.0.0 平均多说 1.2 句问候；v1.1.0 平均 0.3 句（**确实行为变了**——文本 diff 看不出来）
- **投诉识别准确率**：v1.0.0 = 0/3；v1.1.0 = 3/3（**业务指标涨了 3 倍**）

**所以"diff 看起来差不多" ≠ "行为差不多"**。这就是为什么必须以行为回归作为 ship/no-ship 决策依据，文本 diff 只能辅助。

### 例子 4：模型升级导致"Prompt 没动，行为变了"

你同一份 v1.1.0 Prompt，9 月 1 日 MiniMax-M3 上跑得好好的；10 月份服务商升级到 MiniMax-M4，你没改 Prompt，但**回归集全跑一遍**：原本 3/3 投诉识别变成了 1/3。

该怎么排查？先看 metadata：

```text
Prompt version: 1.1.0  (没改)
Model: MiniMax-M3 → MiniMax-M4  (10-01 自动升级)
```

定位是**模型升了**而不是 **Prompt 坏了**。修复路径两条：rollback 模型（更稳），或加 v1.2.0 Prompt 适配新模型（更长期）。**这就是为啥元数据必须分开记"Prompt 版本"和"模型版本"。**

### 例子 5：可编辑 Prompt 对照（最小可操作闭环）

工程上最容易踩的坑：把 Prompt 写死在 `server.ts` 里。改一次 prompt 要发版、要看 git diff、要 review；想做 A/B 测试还得改代码。本条 demo 反过来做：两个 Prompt 字段落到 HTML 编辑框里，每次点「并排对比」就拿刚改的两个版本去调 LLM。

测试对比——同一个追击问题：

| v1.0.0（编辑框里改的） | v1.1.0（默认） |
| --- | --- |
| `只输出数字，不要别的话。` | `请回答下列问题。Let's think step by step, then give the final answer.` |

跑完得到的真实差距：

```text
v1.0.0 长度 403，最终答 "4"  ← 真的只输出一个数字（其余在 <think> 里）
v1.1.0 长度 901，整篇中文三步走 + LaTeX
              顶部黄底：一字之差带来 +498 字符的差距
```

这次"差异"是用户**当场手改**出来的，不是研究员预先配好的。这才能让团队的"Prompt Owner"（产品、运营、内容）直接参与实验，不必绕开发者改代码。

工程含义：
- 生产环境的 Prompt 也应当可编辑、有版本、有审计。这正是 §11（State/Workflow）、§13（Agent Framework 的 Prompt Registry）、§17（Agent Evaluation 的 A/B）等模块的归宿。
- "可编辑" ≠ "任何人都能改"。通常配 **read-only-by-default + 提 PR + 评审 + 自动回归**，而不是放任用户热改。本条 demo 只是把"变量"暴露出来；治理和审计在后面的模块。

## 取舍

### 编辑器 vs 硬编码

| | 哪里 | 用途 | 代价 |
| --- | --- | --- | --- |
| **硬编码** | Prompt 写在 `src/prompts/*.ts` 或 `.prompt.md`（本条沉淀做法） | 生产部署的稳定 Prompt；带版本号、模型绑定、回归脚本；上线要 PR | 改一次要发版；不能动态跑实验 |
| **可编辑** | Prompt 暴露到 UI / 配置中心 / 表单字段（本条 demo 的做法） | 探索期让产品/运营试 prompt；A/B 实验；快速看行为差 | 没有原生版本管理，需要上层审计 |

生产上两者**通常并存**：prod 用硬编码（带版本），experimentation 用可编辑（带审计）。本条 demo 用可编辑是为了让"Prompt Owner"感受行为差，不应当作生产范式照抄。

### 手动 vs 平台

| 方案 | 适合 | 代价 |
| --- | --- | --- |
| **手动 + git**（落文件 + 元数据 + 回归脚本） | 单人 / 小团队 / 1~2 个项目；想避开 vendor lock-in；想用熟悉的 PR 流程 | 自己写回归脚本、自己做 baseline diff |
| **平台**（LangSmith Prompt Hub / Helicone / Arize Phoenix 等） | 多人 / 多产品 / 需要协作评审 + A/B；评估是日常需求 | 与代码仓库双写一份 + 平台账费用 + 迁移成本 |

### 改动的频率与版本节奏

| 风格 | 什么时候用 | 代价 |
| --- | --- | --- |
| **频繁小版本**（每改一句就一个 v ?.?.+1） | 大量实验 / Prompt 还没收敛 / A/B 探索期 | 仓库 commit 数爆炸，要靠 tag 而不是"最新 commit"上线 |
| **偶尔大版 + 小补丁**（一次变动就 minor） | 产品稳了 / Prompt 已收敛 / 改一次就回归一次 | 偶尔大改时回归集可能不够用，需要扩充 |

### 每次改动都跑回归 vs 只跑主版本

- **每次都跑**：回归集是金标准，发现退化立刻知道。
- **只跑主版本**：省时间，但**每次合并都盲发**，"v1.5.0 才回归一次"会让前面几个 v1.4.x 改坏的版本暴露不出去。

**默认原则：每改一次都跑回归**，回归样本集要小（5~10 条足够），否则跑不动。

### 回归集 vs 评估集策略

| 集 | 多大 | 怎么用 |
| --- | --- | --- |
| **回归集（regression set）** | 5~10 条、与生产错误同源、稳定不变 | 每次改 Prompt 跑一次，对比 baseline |
| **评估集（eval set）** | 50~200 条、随时间扩充、反映真实分布 | 衡量"现在到底多准"，不一定每次都跑 |

## 踩坑

1. **把 Prompt 当 `.env` 里一坨字符串**，不写文件 —— 没 diff、没 blame、PR 看不到。
2. **"我看一眼差不多"代替行为回归** —— 文本看着几乎一样，行为已经天差地别。**唯一可信赖的是回归样本量出来的数字。**
3. **用 git commit hash 唯一绑定版本号，不在仓库里存原始文本** —— commit 一旦 garbage collected，Prompt 就找不回。**Prompt 文本必须跟着 commit 一起活在仓库里**（如 `.prompt.md`）。
4. **忘了把模型版本一起记 metadata** —— 模型升级导致回归"莫名失败"，根本分不清谁的责任。
5. **用 LangSmith Prompt Hub 后忘了与代码仓库双写一份** —— 平台被收购 / 涨价 / 关停时所有历史版本外迁困难。
6. **温度 / tools 列表变更塞进同一份 changelog** —— 把"采样变化"和"内容变化"混淆，出 bug 排不下去。
7. **没设"Prompt 失效召回流程"** —— 改坏上线后才发现，没有"一键回滚到上一个已验证版本"的预案；定时炸弹。
8. **把 Prompt 留给 hardcode，没给"产品/编辑"留入口** —— 改一次要发版，diff 又长，谁都不敢动；团队就错过最佳迭代窗口。补的做法 = 至少留一个"评审用编辑器" + 一份"生产用 hardcode"，并按本节"编辑器 vs 硬编码" 的并存策略对齐版本。

## 过关自检

对照本条「要能讲清」——知道改 Prompt 和改代码一样要可追溯：

- 能说清"为什么 Prompt 不能像对话字符串那样随改随丢，而要版本号 + 元数据 + 回归集 + 模型绑定"。
- 能口头复述 5 项核心做法（落文件 / 元数据 / 回归样本 / diff 评审 / 模型绑定）各自是为了解决哪个具体问题。
- 能区分至少 4 组易混：**文本 diff vs 行为 diff**、**Prompt 版本 vs 模型版本**、**Prompt 版本 vs 运行时配置**、**回归集 vs 评估集**。
- 能在团队里推动"改 Prompt 必须走 PR"，并指出**没有回归样本的合并应该被自动拒掉**。
- 能解释模块 03 验收里"≥5 个样本"为什么不是装饰 —— 它就是 ship/no-ship 的判定依据。

## 还没搞懂的（先记住，§5 / §7 / §13 / §17 / §18 会闭环）

- **`tools` 字段算 Prompt 还是算配置**：工具列表变更要不要跟着 Prompt 版本走？§5 Tool Calling 会从协议层面拆这件事。
- **A/B 测试怎么做**：线上同时跑两版 Prompt，用什么指标判断谁赢 —— §17 Agent Evaluation。
- **回放评估（replay evaluation）**：把一次跑过的真实轨迹存下来，下次改 Prompt 后重放，看 Thought/Action 有没有变 —— §7 会引入。
- **观测 / Tracing**：线上每一份真实 Prompt 跑了多少次、成功率多少、出错多少 —— §18 Observability。
- **平台治理**：LangSmith Prompt Hub 如何与 git 双写，如何在团队规模下不"流于形式" —— §13 / §17 会回到这条线。
- **Prompt 优化技术本身**：本条只讲"管理生命周期"，不讲"如何写出更好的 Prompt"（那已由本模块 01~03 节覆盖）。
- **可编辑 Prompt 如何入版本（不存 git 怎么 ship）**：Editor 改完不留 commit，恢复不到 state。这正是 §11（State / Workflow）+ §17（Evaluation 的 A/B）要解决的问题。
- **编辑权限与变更审计**：产品/编辑哪天改了 prompt 没记录，线上炸了找不到谁改的、为什么改。这是 §17 / §20 的内容。
- **编辑历史回放**：把"哪些用户输入在哪些 prompt 版本下产生过什么输出"存下来，方便事后复盘 bug。§18 Observability + §17 Evaluation。

本条**只能**让你"为什么要给 Prompt 加版本、怎么加、加完之后如何当代码评审"；**不会**让你上手 A/B 平台或写评估脚本。§5 / §7 / §17 / §18 写。
