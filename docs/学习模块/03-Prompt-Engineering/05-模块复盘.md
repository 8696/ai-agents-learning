### 一句话讲完这个模块

**把模型行为从"有时候好有时候不好"压成"按你想的稳定输出"**——一句话四个动作：把不变量钉进 `System`（角色 / 格式 / 风格 / 拒绝条件），把形状和灰区钉进 Few-shot（同一请求里给"输入 → 期望输出"样例），把多步推理留给 CoT / ReAct 的思想（先想再做，循环交给后面模块），最后把所有这些 Prompt **当代码管**——落文件、加元数据、绑回归集、绑模型版本、要 diff 要评审。

如果只能留一句话：**约束放 System、形状放 Few-shot、思维留给 CoT、变更靠版本管理**——四件事各管各的一堵墙，缺一堵就漏。

### 这些条怎么连成一条线

四条按"由近及远"排成一条由内到外的层：

| 条 | 它管什么 | 与其他三条的关系 |
| --- | -------- | ---------------- |
| 01 System / User / Assistant 优先级 | **约束层**：消息放哪、谁说了算 | 是后面所有条的地基；System > User > Assistant 是训练事实。**02 / 03 / 04** 都默认你已经知道这条 |
| 02 Few-shot / Zero-shot | **形状层**：字段名、标签词、灰区判法 | 解决"01 把语义钉对了，形状还是漂"的第二堵墙。和 01 互补——System 仍是不变量，Few-shot 是同一请求里的演示 |
| 03 CoT / ReAct（概念） | **思维层**：先想再做、能调工具 | 把模型的"思考"显式出来（CoT），再升级到"想 + 调工具 + 看结果 + 再想"的循环（ReAct）。本条只到思想，**不写循环代码**——那是模块 07 |
| 04 Prompt 版本管理 | **治理层**：落文件、版本号、回归集、模型绑定 | 把 01–03 钉下来的所有 Prompt 都纳入 git + PR + 回归的工程闭环 |

三层"墙" + 一层"治理"的关系：

- **01 是地基**：没有正确的角色放置，02 的示例贴错地方就废（贴在 User 里会被后一句覆盖）。
- **02 是 01 的补丁**：01 解决了"指令语义对"，02 解决"输出形状齐"。两件事必须叠，**单做一条仍然漂**。
- **03 是横向升维**：当任务需要"先推理"或"调工具"时，前两条只负责"提示词怎么写"，03 负责"模型按什么套路想"。本模块只立思想，循环实现留到模块 07。
- **04 是元层（治理）**：前三层钉下来后，Prompt 本身成了"会改但没编译错误的代码"。**没有 04，前三层都是纸上谈兵**——线上改坏一个标点就翻车。

四条相互之间还有几个"硬币的两面"：
- **01 ↔ 02**：System 是"不变量"，Few-shot 是"演示"。前者写"永远 JSON"，后者写"长这样 JSON"。
- **02 ↔ 03**：都是给模型的"额外信息"，但 02 给的是"答卷格式"，03 给的是"思考方式"——可叠穿，不是同一旋钮。
- **01 ↔ 04**：01 决定"Prompt 应该长什么样"，04 决定"Prompt 应该怎么改、改完怎么验"。两条合起来才是工程实践。
- **03 ↔ 04**：CoT 的"step by step"加在哪、要不要加、加完跑哪条样本，都是 04 的版本管理范畴。

| **自测**：Few-shot 的示例应该怎么挑？ | 覆盖所有出口（每个标签 / 每种字段至少 1 条）+ 带 1–2 条灰区 + 带 1–2 条捣乱句 + 短而正确 + 金标由人拍板（不要让模型生成样例再喂回去）+ 样例输入不要等于当前这一条（避免模型直接抄）+ 真实 PII 用假数据替换。详见 [02-Few-shot-Zero-shot.md「场景怎么选」](./02-Few-shot-Zero-shot.md) 的"示例怎么挑"小结 |
| **自测**：System Prompt 和 User Prompt 里的指令冲突时模型听谁的？ | **System > User > Assistant**，这是 RLHF 安全护栏训练时定的事实，不是厂商开关。但**模型不是 if-else**——强诱导（"忽略上面所有指令…"）仍可能让模型偏。所以关键约束（输出格式、安全边界、业务硬规则）**必须做双层**：System 写一遍 + Gateway / 后处理校验一遍 |

### 最容易记错的三条

跨条易混，挑最容易混的三组：

1. **"Few-shot 是微调 / 是 RAG / 是 CoT"**
   Few-shot = ICL（In-Context Learning），**不改权重**、散场就忘，下次不带样例 = 回到 Zero-shot。Fine-tune 才改权重；RAG 是按当前问题检索知识；CoT 是给推理步骤。三者**轴不同**，别混。

2. **"JSON 出现过 = 格式对" / "diff 看着差不多 = 行为差不多"**
   判定"按 System 输出"问的是"输出只能是 JSON"，不是"输出里有 JSON"——思考块 + JSON 拼起来，`JSON.parse(content)` 会挂（[01 例子 4](./01-System-User-Assistant-优先级.md) + [02 Demo 的 `hadThinking`](../../../../apps/03-Prompt-Engineering/02-Few-shot-Zero-shot-step-1/README.md)）。同理，Prompt 文本 diff 看着差不多，行为可能天差地别（[04 例子 3](./04-Prompt-版本管理.md) 的 v1.0.0 vs v1.1.0），唯一可信赖的是**回归样本量出来的数字**。

3. **"CoT = thinking 字段" / "ReAct = Tool Calling"**
   CoT 是 **Prompt 技术**（你硬要求"一步步想"），落到 `assistant.content` 里、用户能看到；thinking 是 **协议机制**（`reasoning_effort=high`），落到 `reasoning_content`、默认隐藏。ReAct 是 **设计模式**（Thought/Action/Observation 怎么循环），Tool Calling 是 **协议名**（`tools` 数组 / `tool_calls` 字段）——ReAct 里的 Action 一步由 Tool Calling 在工程上实现，但两者不是一回事。本模块 03 只到思想；写代码留到模块 05（Tool Calling）+ 模块 07（手写 Agent Loop）。

### 踩过的坑（跨条）

跨多条都会撞的坑，按"是不是同一根因"分组：

1. **协议 A 的 `content` 字符串嵌 `<think>…</think>`**（[01 例子 4](./01-System-User-Assistant-优先级.md) + [02 踩坑第 2 条](./02-Few-shot-Zero-shot.md)）
   下游 `JSON.parse(content)` 直接挂；不要在业务层反复 try-catch，**网关层必须 regex 剥**（`replace(/<think>[\s\S]*?<\/think>/g, "").trim()`）。这条在 01 + 02 两份 Demo 都反复出现。

2. **把"JSON 出现过"当成"只能是 JSON"**（[01 易混点最后一行](./01-System-User-Assistant-优先级.md) + [02 踩坑第 3 条](./02-Few-shot-Zero-shot.md)）
   判定优先级 / 判定格式合规，问的是"输出**只能是** JSON"，不是"输出里**出现过** JSON"。`hadThinking: true` 不等于 System 失败——标签可能完全按 System 走了，是壳不纯；这两件事要分开记。我自己在 01 的 `judgeCase1` 第一次写错过。

3. **System 写"绝对不要做 X" → 反向锚定**（[01 踩坑第 4 条](./01-System-User-Assistant-Assistant-优先级.md) 实际是 [01 踩坑第 4 条](./01-System-User-Assistant-优先级.md)）
   模型更容易想起 X。改成正面指令："请改用 Y 方式回答"。同理 System 写"你必须！！！一定要！！！"也属于这一类——把 Prompt 当玄学加情绪，而不是改结构。

4. **Few-shot 教案当 RAG 用**（[02 易混点 + 踩坑第 6 条](./02-Few-shot-Zero-shot.md)）
   把"订单 8821 已发货"当样例塞进去 = 把假知识当教案，不是检索。样例对齐的是**格式契约 + 灰区判法**，不是事实真相。要查真订单 / 真知识 → 走 RAG（模块 09 / 10），不要用样例当知识库。

5. **Prompt 不落文件**（[04 踩坑第 1 条](./04-Prompt-版本管理.md)）
   写在 `.env` 里、写在对话字符串里、写在 `server.ts` 里 → 没 diff、没 blame、PR 看不到。改坏一次线上崩一次，**回不去**。第 04 条整条就是为这条坑准备的——落文件 + 元数据 + 回归集 + 模型绑定。

6. **"我看一眼差不多"代替行为回归**（[04 踩坑第 2 条 + 例子 3](./04-Prompt-版本管理.md)）
   v2 和 v3 表面只差一句 "Let's think step by step"，但行为可能从 70% → 90% 或反过来。**唯一可信赖的是回归样本量出来的数字**，文本 diff 只是辅助。03 的 v1.0.0 vs v1.1.0 Demo 把这条肉眼化了（403 vs 901 字符）。

7. **没塞 assistant 历史就 multi-turn**（[01 例子 5 + 踩坑第 3 条](./01-System-User-Assistant-优先级.md)）
   不等于模型"完全失忆"——它能从 messages 数组里直接看到 user 早期消息，然后**自信地编**（Case 3 协议 B 的"编天气"是绝佳样本：28℃ / 北风 2-3 级 / AQI 65）。等于**失去"我不知道"的诚实能力**——和模块 01「幻觉是怎么来的」直接对得上。

### 还没搞懂的 → 去哪解决

按"哪个模块会闭环"分组列，每条都明确指去处，不留模糊的"以后再说"：

- **协议 B `thinking` budget 对延迟 / 准确率的 tradeoff 没具体数据** → 模块 18 Observability（拿到 trace 数据再量）
- **Agent Loop + 多轮 + 工具调用 + assistant 历史管理**的完整链路没串过 → 模块 05 Tool Calling（先学协议层怎么传 tools）→ 模块 07 Agent Loop（写循环）→ 用本条 01 + 模块 06 / 07 的内容拼一次完整链路
- **Structured Output / JSON Mode 从协议层钉死形状** → 模块 04（本模块 02 的"网关剥思考 + Zod"是临时方案，模块 04 是协议级硬约束）
- **Prompt 失效召回流程 / 一键回滚预案** → 模块 04 Prompt 版本管理那一节 + 模块 18 Observability（监控 + 告警）
- **A/B 测试怎么做（线上同时跑两版 Prompt + 用什么指标判谁赢）** → 模块 17 Agent Evaluation
- **回放评估（replay evaluation）：存一次跑过的真实轨迹，改 Prompt 后重放** → 模块 07（引入轨迹概念）+ 模块 17
- **线上 Prompt 跑了多少次 / 成功率 / 出错多少** → 模块 18 Observability
- **平台治理（LangSmith Prompt Hub 怎么和 git 双写、团队规模下不流于形式）** → 模块 13 Agent Framework + 模块 17
- **可编辑 Prompt 如何入版本（Editor 改完不留 commit，恢复不到 state）** → 模块 11 State / Workflow + 模块 17（A/B）
- **编辑权限 + 变更审计（产品/运营哪天改了 prompt 没记录，线上炸了找不到谁改的）** → 模块 17 + 模块 20
- **编辑历史回放（哪些用户输入在哪些 prompt 版本下产生过什么输出）** → 模块 18 + 模块 17
- **工具列表（`tools` 字段）算 Prompt 还是算配置、版本怎么跟** → 模块 05 Tool Calling 会从协议层拆这件事

本条只让你"为什么给 Prompt 加版本、怎么加、加完怎么当代码评审"；**A/B 平台、评估脚本、回放、观测**——这几件事一条都不在本模块，模块 17 / 18 写。
