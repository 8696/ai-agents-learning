## 是什么

上一节把约束放进 System、任务放进 User 之后，第二堵墙是：**指令语义对了，形状对不齐**（字段名漂、外套 markdown、先聊天再给 JSON）。Few-shot / Zero-shot 回答的是：要不要在**这一次请求**里塞完整的「输入 → 你要的输出」样例，把形状钉死。

### Zero-shot（k = 0）

这次请求里**没有**完整 I/O 样例，只有指令（通常 System）+ 当前这一条 User。模型靠预训练通识猜形状。人话：只发接口文档，不给调用示例。

### Few-shot（k 条；k = 1 叫 One-shot）

同一次请求里先放若干条「输入 → 期望输出」，再放真正要处理的那一条。模型当场对齐样例的字段、标签词、标点、灰区判法。人话：README 里先贴 3 个 copy-paste 示例再交作业。

两种常见写法（都叫 Few-shot，数据怎么走不同）：

- **写法 A**：样例写成一段 User 文本（「示例1/2/3」）。好 diff、好样例当配置。
- **写法 B**：假对话，`user` / `assistant` 成对出现。协议上更像模型自己说过。这些 assistant **不是真历史**，是你编剧的标准答案。上一节里 assistant 是「把历史回复原样塞回去」；这里是同一角色、教案用途。假对话不要和真多轮混成一锅还不标明。

k 通常 **2～5** 就够钉格式。再堆很多，吃 Context 和钱，中间例子还会被稀释。

### In-context learning（ICL）

**不是**第三种 Prompt 写法，是 Few-shot 为什么生效的机制名：模型**不改权重**，只在这一次 Context 里做模式匹配。请求结束家规就没了。下次不带样例 = 回到 Zero-shot。生产里样例必须写进你的模板代码，不能靠「昨天在 Playground 试过」。

### 同一根尺子，不是三种哲学

| k | 名字 | 机制 |
| - | ---- | ---- |
| 0 | Zero-shot | 只靠指令 + 通识 |
| 1 | One-shot | 仍是 Few-shot 家族，只是只给 1 条 |
| 约 2～5 | Few-shot | 当场抄形状 / 灰区 |
| 几十～几百 | Many-shot | 仍是 ICL，更贵；生产默认不是这条路 |

One-shot / Many-shot 是 **k 的刻度**，不是换了一种学习方式。

## 机制（人话步骤）

1. Tokenizer 把 System、样例、当前输入切成 Token，全部挤进同一次 Context。
2. 预测下一 Token 时，整齐重复的模式权重大：样例三次都是 `{"label":` 开头，就更可能接着吐这个壳，而不是 `情感：好评`。
3. 样例里的标签词表和灰区判例也会被抄。坏样例会**整齐地教坏**。
4. 请求结束，权重不变。

Few-shot 真正稳的是：**格式契约** + **灰区判法**。它不把错误事实变对。堆「订单 8821 已发货」当样例，是把假知识当教案，不是 RAG。

---

## 为什么（Agent 开发要懂）

1. **解析器会炸。** 下游 `JSON.parse` / Zod 认的是壳。形状漂 = 页面 5xx 或空白。模块 04 会从协议再钉一层；现在先会用示例（再加网关）把壳对齐。
2. **灰区会漂。** 「还行吧」「盒子扁了豆子没事」必须按产品定义判，不是模型的文学鉴赏。
3. **每次请求都付钱。** 样例每枪都占 Token。Zero-shot 能稳的任务硬上 Few-shot 是在烧窗口。
4. **坏样例比不加更糟。** 错得更整齐。
5. **和上一节叠：System 仍是不变量**（词表、禁止解释、JSON 壳）。样例是演示，不是替代 System。优先级仍是 System > User > Assistant；示例拧不过 System 硬边界。

## 你的任务上哪种更稳（本条要能讲清）

没有永远赢的一边。先验用四问，裁决用同一批样本的数字：

1. 输出形状是不是自创的（固定枚举 / 固定 JSON / 禁止 markdown）？
2. 有没有产品要拍板的灰区？
3. 下游要不要 parse？（先看**格式合法率**，不要看「读着像人话」。）
4. 样例贵不贵、会不会泄密？

工程对比：固定同一 System、同一模型、同一批 5～10 条真实输入（含灰区 + 捣乱句），跑 Zero 一遍、Few 一遍，比合法率和标签一致率。

| 更稳 | 任务长这样 |
|------|------------|
| Zero-shot | 通识活（翻译、常规摘要、润色）；输出是一段人话；强模型 + 短硬 System；样例会泄露 PII |
| Few-shot | 自创词表 / 自创 JSON 壳；灰区；同一指令三次三次形状不同；要示范转人工 / 拒绝 / 空字段 |

Demo 模拟「豆谷评价分类」：自创三标签 + 固定 JSON + 灰区产品定义（包装差但商品可用 → 中评）。实测协议 A · MiniMax-M3：标签两边都可以是中评，但 Zero-shot 嘴边常夹思考块；Few-shot 嘴边更常是纯 JSON。

## 易混点

| 误读 | 真相 | 判错会怎样 |
|------|------|------------|
| Few-shot = 微调 | ICL 不改权重；Fine-tune 才改 | 下一枪不带样例还怪「模型退化」 |
| Few-shot = RAG | RAG 按当前问题检索；Few-shot 是你手写、几乎固定的教案 | 把知识库当示例塞进去，又贵又不是检索 |
| 示例越多越好 | 过了覆盖出口，收益饱和 | 账单涨、中间例子丢失 |
| 和 CoT 是一回事 | Few-shot 对齐 I/O 形状；CoT 是先写推理再结论（下一节思想）。可叠穿，不是同一个旋钮 | 现在去写 Agent Loop |
| One-shot 是第三种哲学 | 只是 k=1 | 多分类只贴一条，灰区全被吸进那一个标签 |
| Fine-tune / RAG 是第三种 shot | 换轴了：改权重 / 检索 | 该检索的去堆示例，该钉格式的去微调 |
| 有 JSON 出现 = 格式对 | 问的是「输出只能是 JSON」，不是「里面出现过 JSON」 | 思考块 + JSON，前端整段 parse 炸 |
| Few-shot 能消幻觉 | 稳形状和判法，不是事实 | 格式正确的假话更难被看出来 |
| 写法 B 的 assistant = 真历史 | 假对话是教案 | 窗口被教案撑爆，或把示例用户当成当前意图 |

前端对照：Zero-shot ≈ 只有 TypeScript 类型；Few-shot ≈ 再附 Storybook stories；ICL ≈ stories 只活在这次请求里；Fine-tune ≈ 把规范写进组件默认实现并发版。

## 例子（数据怎么走）

### Zero-shot · 客服路由

System：只输出 `order|refund|product|human`。User：「少一袋，能补发吗？」Context 里没有教案 → 通识里既像售后又像订单，标签可能漂。

### Few-shot · 同一路由（覆盖四出口 + 灰区）

四对假对话把四个标签都点亮，并把「少一袋 + 补发或退款」钉成 `refund`。当前句靠近该判例 → 更稳。若把那条错标成 `order`，当前句也会跟着错。

### ICL 散场就忘

今天带 3 条 JSON 样例，输出标准；明天同一 System 不带样例，又开始写 `sentiment: positive`。权重没变，变的是 Context 里还有没有那三页投影。

### 抽取 DTO

Zero-shot 日期在 `2024/3/1` / `三月一日` / ISO 之间漂。Few-shot 三条全示范 `{"date":"2024-03-01","amount":199}`，缺字段示范 `amount: null`（key 还在）。要对齐的是 DTO，不是「更懂财务」。

### Demo 灰区实测（协议 A）

输入：「快递第二天就到了，盒子压扁了但咖啡豆没事。」

Zero-shot 原文常先有思考块再给 JSON；网关剥掉思考后 Zod 能吃到 `中评`。Few-shot 原文常无思考块，直接 `{"label":"中评",...}`。两边标签可一致，**嘴边纯度**不同。

## 场景怎么选（k）

| 场景 | 默认 | k |
|------|------|---|
| 翻译 / 润色 / 普通摘要 | Zero-shot | 0 |
| 自创标签分类、路由 | Few-shot | 每标签 1 + 灰区 1 |
| 字段抽取要对齐 DTO | Few-shot | 齐全 / 缺失 / 怪写法 |
| JSON 壳偶发多余前缀 | 先 Zero，不稳再 Few；**解析端剥思考** | 1～3，样例=最终形态 |
| 转人工 / 拒绝 / 空结果 | Few-shot 示范出口 | ≥1 条出口 |
| 要查真订单 / 真知识 | shot 只管壳 | 不要用样例当知识库 |
| 真实用户数据敏感 | Zero 或假数据 Few | 禁止真 PII |
| 已经又稳又贵 | 往 Zero 收 | 删到合法率不掉 |
| 模型较弱 | 更依赖 Few-shot 钉形状 | 换模型要重跑样本 |

示例怎么挑：覆盖出口、带灰区与捣乱句、短而正确、金标你拍板（不要让模型生成样例再喂回去）、质量 > 数量、样例输入不要等于当前这一条、PII 用假数据。

## 取舍

- **本条 Demo 只跑协议 A**：对照的是 k，不是协议差异。要并排 A/B 是上一节的题，或另开需求。
- **格式合法的两口径**：① 模型嘴边整段是否已是 JSON（Few-shot 更常赢）；② 网关剥思考块之后能否进 Zod（生产解析应走 ②）。Demo 现在用 ② 当 `formatValid`，并用 `hadThinking` 保留 ① 的信息。不要把「剥完能过」说成「Zero-shot 嘴边已经纯了」。
- **写法 A vs B**：要当配置 diff 用 A；发现模型更会续 assistant 用 B。仍是 Few-shot。
- **不要为了对照好看而禁止剥思考**：对照应看见思考块存在，解析应剥掉再 parse。

---

## 踩坑

- 把 Prompt 当成玄学加「你必须！！！」；本条正确动作是改结构、加覆盖出口的样例、加网关校验。
- 前端对**原始字符串** `JSON.parse`，不剥思考块 → MiniMax-M3 协议 A 上 Zero-shot 很容易撞 `<think>`。
- 把「JSON 出现过」当成「只能是 JSON」（上一节 Judge 同类错）。
- One-shot 敷衍多分类。
- Few-shot 只覆盖快乐路径，缺字段时模型省略 key。
- 用真实订单当教案（每次请求都上传 Context）。
- 把思考块当成优先级失败：System 可能已经被听了（标签是中评），失败的是壳。

---

## 过关自检

对照「能对比你的任务上哪种更稳」：

1. Zero-shot = 不给完整 I/O；Few-shot = 同一次请求带着可抄答卷；ICL = 不改权重，散场就忘。
2. 示例对齐的是格式和灰区判法，不是事实真相。
3. 通识 + 宽输出 + 要省 → 偏 Zero-shot；自创词表 / 要 parse 的壳 / 灰区 → 偏 Few-shot。用同一批样本比合法率和一致率。
4. 样例要覆盖出口、带灰区、短而正确；坏样例会教坏。
5. 思考块先剥再 parse 是网关职责；Few-shot 降低「必须靠剥」的概率，不替代网关。
