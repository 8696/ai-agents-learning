# **429 / Rate Limit**：为什么要指数退避；哪些错误不该重试

> 对应模块：[模块 02 · LLM API 开发 ⭐⭐⭐⭐⭐](./README.md) · 小节进度第 4 条
> **来源**：本对话（详解 §4.1~§4.9 全部轮次 + `yarn app:02-04-rate-limit-step-1` 跑通的 5 个场景时间线 + 进入维护模式改 `app:{模块}-{小节}-{短名}` 命名约定 + 真 API burst 撞限的实际结果）
> **状态**：已沉淀

**一句话概括**：LLM API 一定返回 429；第一次上量整个应用就崩——因为没做「分类重试 + 指数退避 + jitter」。这一条把分类表、退避（人话版步骤，不是公式）、jitter 防 thundering herd、重试上限、流式 + 429 怎么接一次讲清。

---

## 429 是什么 + 为什么 LLM 一定有

HTTP 429 = `Too Many Requests`。**语义是「你太快了，触发了我的配额限制，请慢点」**，不是「我出错了」（那是 5xx）。

LLM API 一定有 429 是设计，不是 bug：LLM 推理贵、GPU 资源有限。每个账号都分到按时间窗口算的速率配额：

- **RPM**：每分钟请求数
- **TPM**：每分钟 token 数
- **并发上限**（少数套餐）：同时在线请求数

触发就拒，没商量。

**例子（餐厅）**：去热门餐厅吃饭，门口挂着「今日 200 号已发完」。你不能硬闯（5xx 才是「厨房起火」），服务员递过来一张号：「请 30 分钟后再来取号」。这就是 429 + Retry-After。

**现在做 Agent 会踩什么后果**：

1. **第一次上量就崩**：开发时并发 = 1 没问题；上生产并发 = 10，第一波 429 进来，没处理 → 用户看到一片空白
2. **前端轮询把 Key 打挂**：每 2 秒轮询一次「有没有新结果」很常见，但每次轮询都算请求；1 分钟 30 次就超个人 RPM（按量 Key 通常 60 RPM）
3. **多 worker 同步撞限**：10 个 worker 同时收到任务，各自重试 5 次，每次都失败——服务端被打挂，问题被放大

## 429 vs 5xx：谁负责 vs 谁的问题

| 状态码 | 含义 | 谁负责 | 重试策略 |
|--------|------|--------|----------|
| 429 | 你太快了 | 客户端该慢点 | 听 Retry-After + 指数退避 |
| 5xx | 我出错了 | 服务端该修 | 退避后重试，但别无限 |

429 看着像 503（Service Unavailable），但**含义不同**：
- 503 = 「**我**临时挂了」（维护 / 过载），重试往往能恢复
- 429 = 「**你**太快了」，必须等速率窗口过去

判错会怎样：把 5xx 当 429 死磕 → 持续重试一个真坏的端点，钱白花；把 429 当 5xx → 没尊重速率窗口，被服务端拉黑更久。

## Retry-After 头：服务端给的「请 X 秒后再来」

**是什么**：`Retry-After` 是 HTTP 响应头，值是一个**秒数**或一个**HTTP 日期**（HTTP-date）。服务端告诉客户端：「我现在没法接你的活，请至少等这么久再试。」

**LLM 真实样子**：
- OpenAI：`Retry-After: 0.6`（亚秒级）或 `x-ratelimit-reset-requests` / `x-ratelimit-reset-tokens`（unix 时间戳）
- Anthropic：`retry-after` 头同样是秒数
- 部分代理 / 网关：整数秒 `Retry-After: 30`

**为什么不听它的**：
- 太早回去（< Retry-After）→ 又被拒，再次浪费配额
- 太晚回去（远超 Retry-After）→ 用户白等，体验差

**人话规则**：照 `Retry-After` 等待；它不存在或不可信（有的代理瞎填）时再走自己的指数退避。

**例子**：餐厅给你号「30 分钟后再来」，你不听，1 分钟就回去取号 → 服务员白眼：「说了 30 分钟」。30 分钟准时回去 → 拿到号，开心吃饭。

**判错会怎样**：直接当它不存在，每次固定 3 秒重试 → 服务端还在限速又被你撞，又被拒；或者你已经过了窗口还在干等，用户已经放弃页面。

---

## 指数退避（Exponential Backoff）

**机制**（人话步骤，不是公式）：

```
第 1 次失败 → 等 base 秒
第 2 次失败 → 等 base × 2 秒
第 3 次失败 → 等 base × 4 秒
第 4 次失败 → 等 base × 8 秒
封顶到 maxDelay 秒（一般 30~60）
最多试 maxAttempts 次（一般 3~5）
```

参数推荐（LLM 场景）：

| 参数 | 推荐值 | 为什么 |
|------|--------|--------|
| `base` | 1~2 秒 | LLM 推理慢，2 秒更稳 |
| `maxDelay` | 30~60 秒 | 超过 60 秒用户已经在骂人 |
| `maxAttempts` | 3~5 次 | LLM 一次响应就 5~30 秒，留给重试的预算不多 |

**为什么不能固定间隔（比如每次都等 3 秒）**：固定 = 一波失败后所有客户端在同一个时间点同时回去 → 服务端又被打挂 → 又失败 → 又同时回去 → **雪崩**。指数退避让每个客户端的「回去时间」自然错开（即便没加 jitter，也比固定好）。

**例子（电话占线）**：打电话给客服占线，挂了，1 分钟后再拨 → 还占线，2 分钟后再拨 → 还占线，4 分钟后再拨 → 接通了。客服那头也在「被一群人同时打」——你等得越久，轮到你的概率越大。固定间隔像 100 个人都 3 分钟后再拨——电话那头再次被打爆。

---

## Jitter：防 thundering herd 的那一刀

**是什么**：在指数退避算出来的等待时间上加一段**随机偏移**。两种写法：

- **全抖动（full jitter）**：`wait = random(0, base * 2^attempt)`（更激进）
- **等比抖动（equal jitter）**：`wait = (base * 2^attempt) / 2 + random(0, (base * 2^attempt) / 2)`（更稳，LLM 客户端用得多）

**防的是什么：thundering herd（惊群）**。
即使大家都按指数退避，多个客户端算出来的 `base * 2^attempt` 是**相同**的 → 同时回去重试 → 服务端再次被同一波请求打挂。加 0~1 秒随机偏移 → 大家回去的时间被打散在窗口内 → 服务端瞬间压力降一个量级。

**例子（下课铃响）**：下课铃响，100 个学生同时冲向食堂打饭窗口——窗口挤爆。加 100 个随机数让 100 个学生在 10 秒内错峰去打饭——窗口永远只处理 10 个左右。

**现在做 Agent 会踩什么后果**：多 worker / 多 tab 的 Agent 应用，没加 jitter → 重试雪崩 → 服务端故障扩散到你自己。测试时单机感觉「没事」，上生产 100 并发 → 同一秒退避回来 → 你打挂自己。

## 可重试 vs 不可重试（错误分类表）

### 可重试（重试大概率会成功）

| 状态码 | 含义 | 为什么 |
|--------|------|--------|
| 408 | Request Timeout | 上游慢，下一次可能快 |
| 429 | Too Many Requests | 等过了速率窗口就好 |
| 500 | Internal Server Error | 服务端 bug，下次可能好 |
| 502 | Bad Gateway | 上游网关瞬时挂 |
| 503 | Service Unavailable | 维护 / 过载，下次可能好 |
| 504 | Gateway Timeout | 网关超时，下次可能好 |
| 网络错 | ECONNRESET / ETIMEDOUT / DNS 临时失败 | 网络抖，下次可能好 |

### 不可重试（重试只会得到同一个错）

| 状态码 | 含义 | 为什么 |
|--------|------|--------|
| 400 | Bad Request | 请求格式就坏，下次还坏 |
| 401 | Unauthorized | Key 错 / 过期，重试还是 401 |
| 403 | Forbidden | 权限不足，重试还是 403 |
| 404 | Not Found | 资源不存在，重试还是 404 |
| 422 | Unprocessable Entity | 参数语义对不上 |
| 402 | Payment Required | 余额不足，重试还是没钱 |

### 例外（要单独识别）

- **429 + `insufficient_quota`**（账户欠费）：表面是 429，实际是钱的事——按不可重试处理，立刻报警
- **429 + `rate_limit_exceeded`**：真速率问题，可重试
- **501 Not Implemented**：服务端不支持该功能，重试无意义——按不可重试处理

### 现在做 Agent 会踩什么后果

1. **代码无脑重试所有错**：401（Key 错）重试 10 次，每次扣钱 + 浪费时间，最后还是 401。生产 1000 用户同时 401 → 你收到 10000 次失败报警
2. **代码遇到 422 还重试 5 次**：用户传错的字段根本没改，重试只是把错误信息复制 5 遍，体验差 + 钱白花
3. **正确做法**：拿到错 → 先查表 → 可重试 → 退避 + jitter → 重试；不可重试 → 直接返回错误给上游 / 用户

## 幂等性（Idempotency）：重试安全的前提

**是什么**：HTTP 方法的「重做一次和没重做，状态是否一致」。

- **GET / HEAD / OPTIONS / PUT / DELETE**：理论幂等
- **POST**：**不**幂等（重发 = 创建两份）

**LLM 场景**：
- `chat.completions` 是 POST → **不**天然幂等。重试 = 两次计费 + 两条结果
- `embeddings` 也是 POST，但一般纯计算不写状态，重试只算两次钱，不改业务数据——可接受但浪费
- 多数 LLM API（OpenAI / Anthropic）的 chat 端点**没强校验幂等键**，重试 = 计两次费 + 两条结果。**业务侧要自己处理**

**怎么防**：有副作用的 Tool（写 DB、调外部 API 发请求）必须接受 `idempotency_key` 参数；上游没传就用「tool 名 + 参数 hash + 时间窗口」生成一个。

**例子**：
- **可重试场景**：让 LLM 总结一段文档——重试 3 次得到 3 个略有不同的总结，挑一个最合适的，浪费钱但不坏事
- **不可重试场景**：用 LLM 给用户发一封自动邮件（POST chat.completions 让模型生成邮件正文 + 调 SendGrid 发出去）。没幂等键 → 网络抖一下重试 → **用户收到 2 封一样的邮件**

## 流式（SSE）+ 429：中途才到的 429 怎么办

**问题场景**：上一节学过的 SSE 流式响应，服务端边生成边发。用户在 5 秒内已经收到了 100 个 token，**第 101 个 token 的时候**服务端抛 429（前面没超 TPM，到第 101 个超了）。前端怎么处理？

**两种思路**：

1. **丢弃已发半截 + 重连**：已发到 UI 的 token 全部作废，告诉用户「生成中断，请重试」→ 重新发请求（这次带更少 token / 降并发）→ 从 0 开始
2. **标记未完成 + 保留**：已发的 100 个 token 保留，在 UI 上加个「⚠️ 后半段生成失败，已生成 X / Y」标记，让用户点「续写」按钮重试

**哪种好**：看业务。生成式 UI（聊天、写作）通常选 2（用户已经看了半段，作废体验差）；批量任务（文档总结、代码生成）通常选 1（重做更简单）。

### AbortController vs 退避重试（上一条 vs 本条）

- **AbortController**：**客户端**主动停。用户点了「停止生成」按钮、或者页面卸载、或者超时
- **退避重试**：**客户端**被**服务端**劝停再回。服务端说「我忙」，客户端等一下再回去

两者经常一起用：SSE 流里如果用户点了停 → `controller.abort()` → fetch 取消；如果流里收到 429 → **不** abort，先把已发字节处理掉，再决定是丢弃重连还是标记续写。

## 重试上限与降级：什么时候停、停了之后做什么

**双上限**：

- `maxAttempts`：3~5（OpenAI SDK 默认 3，Anthropic SDK 默认 2）
- `maxTotalTime`：30~60 秒（LLM 一次响应就 5~30 秒，留给重试的预算不多）
- `maxCost`（可选）：按「这次请求预估成本 × maxAttempts」设上限（如 $0.5），超过就停

**降级策略**（按优先级）：

1. **降并发**：把同时跑的请求数从 10 降到 3，等速率窗口过去再拉起
2. **换次级模型**：gpt-5 / claude-opus-4 切到 gpt-5-mini / claude-haiku-4.5，配额更宽松、单价更低
3. **换 Key / 换账户**：多 Key 轮询或主备账户（企业账号常用）
4. **排队 / 队列**：把请求丢到队列里，后台 worker 按速率窗口消费，前端 polling / WebSocket 拿结果
5. **告诉用户失败**：UI 上「服务繁忙，请稍后再试」+ 自动重试按钮

**例子（机场）**：机场办登机柜台前排了 100 个人，地勤说「先别排了」。你做了三件事：① 让一半人先去自动取票机 ② 让商务舱的人去另一柜台 ③ 实在过不去的人给个改签券。**这就是降级**——不是死磕，是换路径。

## 现在做 Agent 会在哪翻车（常见坑汇总）

1. **开发时没模拟过 429**：unit test 全是 happy path，第一次上生产整个应用崩。**防**：写一个 mock server，模拟 429 + Retry-After，验证 client 真的退避了
2. **没加 jitter**：100 个 worker 同时退避回来，服务端被自己打挂。**防**：jitter 加 0~1 秒随机偏移
3. **401 / 422 也重试**：浪费钱 + 浪费配额 + 报警噪音。**防**：分类表 + 白名单只重试「可重试」那批
4. **无限重试 / 没上限**：一个永久失败的请求耗光线程 / 钱。**防**：maxAttempts + maxTotalTime
5. **没听 Retry-After**：1 秒后回去又被拒，循环重试浪费配额。**防**：`Retry-After` 值 × 1（直接用它），没有再走指数退避
6. **流式场景里 429 不处理**：UI 上半截文字卡住，用户不知道发生了什么。**防**：流里捕获错误 → 标记未完成 / 自动重连

## 取舍

- **maxAttempts = 3 vs 5**：3 节省钱（少烧 2 次 token），5 给网络更多机会。OpenAI SDK 默认 3，Anthropic SDK 默认 2。**做 Agent 时**：「省钱」vs「网络容错」之间选；批量任务选 3，实时聊天选 5
- **base = 1s vs 2s**：1 秒响应快，2 秒给服务端更多喘息。LLM 推理慢（5~30 秒/次），**2 秒更稳**
- **jitter = on vs off**：on 防 thundering herd；off 让行为可预测（但撞限就崩）。**默认 on**
- **流式 429 选 1（丢弃）还是 2（标记）**：取决于业务。**批量任务选 1**，用户聊天选 2
- **降级到次级模型 vs 告诉用户失败**：前者用户体验好但成本不可控；后者诚实但需要用户操作。**生产 Agent 默认前者**，且要告警告诉运维
- **真 429 撞限靠什么**：默认 20 并发撞不出，靠 50+ 并发 / 更小模型 / 大 prompt 撞 TPM。**平时练习用 mock 确定性**

## 还没搞懂的

- **Anthropic / 智谱 的 Rate-Limit 行为是否和 OpenAI 完全一致**：429 语义相同，但 Retry-After 头格式、并发计数窗口、429 body 字段可能不同。学到对应模块再补
- **流式场景下 Retry-After 是按已发 token 还是按剩余 token 算**：上游没明说，撞到再补
- **Batch API 的 429 行为**：批量异步接口可能不同（提交一次算一次费？重试怎么去重？）
- **真 API 撞出 429 后 Retry-After 头长什么样**：本次 20 并发没撞出，无法验证。并发调到 50 再跑一次能验

## 过关自检（对照「本条要能讲清」列）

合上笔记，必须能讲清：
