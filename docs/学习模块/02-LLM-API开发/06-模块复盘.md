**三条单独谈不清楚的关系**：

1. **01 是底座**：02、03、04、05 都是「在流式前提上」的扩展；不先懂 SSE 流就算不起来 02 的字段、03 的 abort 时机、04 的「流到第 101 个 token 才来 429」、05 的「thinking 跨多帧要状态机切」。
2. **03 和 04 是同一对兜底，但方向相反**：
   - 03 = **客户端主动停**（用户按停、关页面、超时）→ 关 socket + 关后续读取
   - 04 = **客户端被动停**（服务端说慢点 / 暂时挂）→ 退避 + 重试
   - 它们协同：用户按停立刻 abort（不等退避）；服务端 429 不 abort、把已发字节保留或丢弃、然后退避重试。
3. **05 是 01 × 02 的输出语义**：思考到底在 `delta.content` 里（A 嵌 `<think>` 标记）、还是独立 `content_block_delta.delta.thinking` 字段（B）、还是同层 `delta.reasoning_content`（DeepSeek/GLM）—— 客户端必须跟着「**这一轮响应字段长什么样**」走，不能跟着「协议名」写死。这一条**只在跨条时才看得清**——单看 01 或 02 都只看到一面。
4. **03-adapter-demo 是 02 的收口**：02 讲了协议 A vs B 的所有差异，03-adapter-demo 把那些差异收敛到 `sendMessage` 5 个统一字段 + `sendMessageStream` 的 `UnifiedDelta` 判别联合。**业务层从此不再 `if (protocol === "A")`**。
5. **01 + 03 的灰区**：客户端 abort 后流提前结束，**usage 通常拿不到**（末帧没来），但**已生成的 token 都计入计费**——这是「客户端兜底」碰「服务端照算」的交点，跨条才看得见。

### 最容易记错的三条

跨条易混——只有看完所有外部条 + 跑过所有 Demo 才看得见：

1. **「客户端 abort」≠「服务端停生成」≠「不计费」。**
   - 三件事各自独立：① `controller.abort()` 只关客户端读取 + 底层 socket（HTTP 层） ② 服务端是否立刻停看厂商——OpenAI / Anthropic 关 socket 后多数会停；**自部署（vLLM / TGI / Ollama）最坏情况是跑到自然结束才停** ③ **之前生成的 token 都计入计费**，abort ≠ 免费。
   - 谁来都得记这条——03 单条只讲「客户端怎么实现」，03 demo 「① 全跑 ② 收 N 帧停 ③ 不传 signal」跨 demo 才看全三种行为。
   - 实测数字：`01` 真实模型 11 字 prompt → 47 帧 / 117 token（**带 thinking**），abort 后看不到末帧 usage，但账单上 117 token 已生成。

2. **`delta.content` 是字符串不是 token；流式里没有「这一帧 = N token」的字段；计费唯一看末帧 `usage`。**
   - 三层完全解耦：模型内部 token 数 ≠ SSE 帧数 ≠ 解码后 `content.length`。同一段「Hello world」可能被切成 1 帧 `Hello` + 1 帧 ` world`、也可能 1 帧 `Hello world`（厂商 batching 决定）。
   - 跨条后果：① 不能按帧数算成本 ② 不能按 `content.length / 4` 估 token ③ 流式过程中拿不到 token 数，只有末帧 `usage.completion_tokens`（且需 `stream_options.include_usage: true`）报整段总数。
   - 谁来都得记这条——01 验证「token / frame / content 长度三者解耦」，02 验证「流式 usage 在末帧才出现」，05 验证「thinking 拆出来后整段 token 数还得回到 total 算」。

3. **「协议 A 默认就有 thinking」+「B 默认没 thinking」+「thinking 字段位置三种模式并存」。**
   - A 在 MiniMax-M3 上默认就有思考，**嵌在 `delta.content` 字符串里**（`<think>...</think>` 标记）；B 默认无思考，**显式 `thinking: { type: "enabled", budget_tokens: N }` 才走独立 `type:"thinking"` block**。
   - 但**同一协议换厂商就变脸**：DeepSeek / GLM 的 A 端点把草稿纸放在同层 `delta.reasoning_content` 字段；custom 网关的 MiniMax / Qwen 走 A **不回思考正文**只计 `reasoning_tokens`。
   - 最容易踩的坑：**直接 `textContent += delta.content` → 用户看见思考过程**。客户端必须按响应字段位置解析、不能按协议名写死。`05-思考` 三层表（协议 / 厂商方言 / 这个模型）+ custom 网关四模型实测把这一条砸实。

### 踩过的坑（跨条）

单条 MD 里写过的踩坑不重复；这里只放**跨条才看得到** / **多条都撞到的**：

1. **流式响应中途出错 = 「半截 + 不知发生了什么」。** 跨 01、02、03 三条都撞到：服务端可能不返回 `data: [DONE]` 就关连接（`01-Streaming-SSE` 踩坑第 7 条）；客户端 abort 后 `usage` 经常拿不到（`03-AbortController` 踩坑第 2 条）；流式里收到 429 时已发字节不能简单当「重连重做」（`04-Rate-Limit` 流式章节）。**工程共性**：要把「流提前结束」当一等公民——每帧记录 `chunkIndex`、失败时记 `[aborted at chunk N, Xms in]`、账单对不上时能查到断点。

2. **「开了参数」≠「对方会用」。** 跨 02、05 才看全：`extra_body.thinking.type`（05）/ `stream_options.include_usage`（02）/ `metadata.user_id`（02）—— **兼容网关常只映射 `model/messages/temperature/max_tokens`**，整段 `extra_body` 静默丢掉，200 成功但旋钮是装饰。**校验靠「这次返回」判断，不靠「请求里写了什么」判断**。`05-思考` 例子 4 句话把这点砸实。

3. **MiniMax 兼容端点的「翻译层 quirk」是条「活的跨条」。** 同 `MINIMAX_API_KEY` 走双协议，但字段位置与海外 Anthropic 官方 Claude 行为不一致：
   - A：thinking 拆 `completion_tokens_details.reasoning_tokens`
   - B 一次性：`output_tokens_details.thinking_tokens`（MiniMax 扩展，不是 Anthropic 官方顶层 `reasoning_tokens`）
   - B 流式：**有时报、有时不报**——`02-协议-A-vs-B` 测数学题 223 事件 `output_tokens_details` 没出来，`03-adapter-demo` 测「23 × 47」却有 `thinkingTokens: 41`。**写客户端不能假设「流式一定有 thinkingTokens」**，要做兜底（fallback 到 `output_tokens` 估算）。
   - `signature_delta`：持久化 thinking 时必须保留（Anthropic 验证签名）。

4. **TS strict 是真严格，别绕。** `04-Rate-Limit` index.ts 第 124 行用了 `NodeJS.HttpIncomingMessage["headers"]` 但 Node 22 类型里是 `IncomingMessage`（要 `import { IncomingMessage } from "node:http"`）—— TS 直接不让你糊弄过去。OpenAI v4 SDK 的 `signal` 是 `create(body, { signal })` **第二个参数**（`RequestOptions`），写在 body 里 TS 也直接报错。这条跨 03、04 都有。

5. **「同 Key 换协议」≠「协议相同 Key 也相同」。** 跨 02、adapter demo：MiniMax / 智谱各暴露双协议，**一把 Key 只换 baseURL**（A 走 `/v1`，B 走 `/anthropic`）。但**海外 Anthropic 官方是真单独 Key**——代码里写两套 env 是冗余，但真要写海外 Claude 时 Key 必然不同。**协议 ≠ Key**，别把 Key 当作「协议指纹」。

6. **「协议名」≠「解析路径」。** 跨 05 才看清：A 端点上 MiniMax-M3 想字段嵌在 `delta.content` 里、DeepSeek 想字段在 `delta.reasoning_content`（同层独立）、custom 网关的 MiniMax / Qwen 想字段**根本不在响应里**只计费。**解析必须跟着响应字段位置走**，不能跟着请求里的协议名 / `protocol` 变量走。`05-思考`「解析跟着响应走，不跟着请求走」是这一条的工程收口。

7. **`signal` 没传 = abort 完全无效 = 钱照扣。** `03-AbortController` 第 ③ 端点实证：5 秒后客户端 `res.end()`，但 SDK 没传 `signal` 不知道 → 继续跑完 47 帧 / 117 token。**只调用 `controller.abort()` 不传 signal，相当于「给自己打电话但对方话筒没拿起来」**。这条跨 03、01（用真实模型时也得传）都得记。
