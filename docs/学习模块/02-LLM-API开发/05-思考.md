## 是什么

**思考（thinking / reasoning）**是模型在给出「给用户看的正文」之前，先走的一截内部推理。它可能计费、可能很长、通常不该直接当最终答案渲染。

同一家模型、两套协议，思考落在完全不同的字段里：

| | 协议 A（Chat Completions） | 协议 B（Messages） |
| - | --- | --- |
| 默认 | MiniMax-M3 往往**默认就有思考** | **默认关**；要显式 `thinking: { type: "enabled", budget_tokens: N }` |
| 怎么开 | 原生 Chat Completions 没有 thinking 字段；MiniMax 走 `extra_body`：`thinking: { type: "adaptive" }`，可用 `reasoning_split: true` 把思考拆到独立字段 | 顶层 `thinking`；开启时 `temperature` 必须是 1，且不要同时改 `top_p` / `top_k`；`max_tokens` ≥ `budget_tokens` |
| 流式增量 | `delta.reasoning_content` / `reasoning_details`，或 `delta.content` 里的 think 标记 | `content_block_delta.delta.thinking` vs `delta.text` |
| 非流式位置 | `choices[0].message.content` 里嵌标记，或拆分后的 `reasoning_*` | `content[]` 里 `type: "thinking"` 与 `type: "text"` |

**生活例子**：答题卡分成「草稿纸」和「答案栏」。草稿纸给阅卷老师核对思路（开发者面板），答案栏才贴在成绩单上（用户气泡）。两栏写混 = 用户看见一堆内心独白。

**前端例子**：流式时不能只 `text += chunk.content`。要两块 DOM：思考区追加 thinking 增量，正文区追加 content 增量。本条 Demo 左右栏就是这样。

协议相同只保证「信封长得像」，不保证思考怎么开、从哪回来、你传的字段对方会不会当真。拆成三层，别叠成一层：

| 层 | 是什么 | 谁说了算 |
| -- | ------ | -------- |
| **协议** | URL、SDK、大体字段名（`messages` / `choices[0].delta`） | OpenAI 兼容 vs Anthropic 兼容 |
| **厂商方言** | 思考开关叫什么、响应用哪几个键 | MiniMax / 智谱 / 自定义网关 / 官方 Anthropic |
| **这个模型** | 会不会思考、默认开还是关、能不能关 | M3 vs GLM vs 普通 chat 模型 |

同一套协议 A，请求参数就可以完全不是一套。本条 Demo 写死的是 **MiniMax 方言**：顶层没有 `thinking`，开门靠 `extra_body.thinking.type = "adaptive"`，`reasoning_split: true` 只改思考出现在哪。换一家常常是另一套名字，甚至没有对应旋钮（OpenAI 推理系是 `reasoning` / `reasoning_effort`；DeepSeek Reasoner 往往换模型 id 就带思考；智谱 / 自定义网关上 MiniMax 那套经常当空气）。

同一套协议，返回位置也可以三种都撞上，所以解析必须跟着**这一轮响应**走，不能按协议名写死：

1. **独立字段**：`delta.reasoning_content` / `reasoning_details[].text`（协议 B 则是 `delta.thinking`），`content` / `text` 才是正文。
2. **嵌在正文**：挤在 `delta.content` 里，用 think 标记切开。
3. **看起来像没思考**：模型在想，但网关既不拆字段、也不打标记，全进 `content`。

**生活例子（方言）**：都叫快递面单（协议 A）。圆通要「增值服务码」，顺丰要勾「保价」。拿圆通的码贴到顺丰单上，单子照样能寄，那一栏是废的。

**前端例子（无效参数）**：请求 JSON 里明明有 `extra_body.thinking`，openai SDK 会带出去，网关 200 照回。页面不报「未知参数」，只表现为思考区空、或正文里突然冒出内心独白。兼容 API 的潜规则是：**不认识的字段多半静默丢掉，不 400。**「写了参数」≠「对方会用」。

## 为什么（Agent 开发要懂）

1. **JSON / 结构化输出会被思考污染**：协议 A 把思考嵌进 `content` 字符串时，下游 `JSON.parse` 会挂。工程上要剥思考，或换协议 B 不传 thinking。
2. **计费**：`completion_tokens` 常常含思考 + 正文；思考可能单独计价。看不见拆分字段就会把「贵的那截」当成普通回答。
3. **追问**：下一轮 `messages` 必须告诉模型「你上次说了啥」。协议 A 建议把思考一并回传（标记包住）；协议 B 没有 `signature` 的 thinking block **不能原样塞回去**，本 Demo 只回传正文。
4. **网关 / 厂商方言**：直连 MiniMax 和自定义网关，同一套 `extra_body` 不一定都吐思考增量。请求里开了思考 ≠ 响应里一定有 thinking 帧。换 `LLM_PROVIDER` 不要假设 Demo 里的满参数仍然有效。
5. **无效参数是常态，不是报错**：兼容网关常只映射 `model/messages/temperature/max_tokens`，整段 `extra_body` 或顶层 `thinking` 扔掉。看起来请求成功，旋钮其实是装饰。同一模型 id 换 `baseURL`，行为也可以两套。

## 易混点

| 别混成 | 差在哪 | 判错会怎样 |
| ------ | ------ | ---------- |
| 思考 = CoT Prompt | CoT 是你在 **Prompt 里要求「一步步想」**；thinking 是 **API 字段 / 模型能力** | 只写「请思考」却去协议 A 里找 `thinking` 参数，找不到就以为没思考 |
| `reasoning_split` = 开关思考 | 它只改**思考出现在哪**（独立字段 vs content 里的标记），不负责开/关 | 关思考要 `thinking: { type: "disabled" }`（M3）；M2.x 可能关不掉 |
| 协议 A / B 思考能用同一套解析 | A 是字符串帧 + 可能跨 chunk 的标记；B 是事件流 + 独立 block | 一套 parser 会把 B 的 thinking 当正文，或把 A 的标记渲染给用户 |
| 追问时两边历史可以同一个数组 | A、B 上一轮 assistant 文本不同，必须**分协议各记一份** | 用 A 的回答去当 B 的历史，B 会「记得」它没说过的话 |
| 「协议 A 都有 thinking 参数」 | 那是 MiniMax（以及部分国产）的**扩展**，不是 Chat Completions 标准字段 | 对着 OpenAI 官方文档找 `extra_body.thinking`，找不到就以为模型不会思考 |
| 「参数无效 = 请求失败」 | 无效常常是 **200 成功但没生效** | 你以为开了思考、关了拆分，其实网关当没看见 |
| 「同一模型 id 换 baseURL 行为不变」 | 模型名可以一样，**网关实现可以完全两套** | 官方和自定义网关，思考字段可能一个有一个没有 |

## 例子（数据怎么走）

第一句：「23 × 47 等于多少？」

1. 浏览器并发 `POST /api/a-stream` 和 `POST /api/b-stream`，body 里 `messages` 最后一条是 user。
2. 服务端打满参数并开思考，SSE 先发 `meta`（原始请求），再发 `thinking` / `content` / `raw`。
3. 页面这一轮出现两列：思考区、正文区、原始请求、原始帧。
4. 追问「再乘以 2」：A 的 `messages` = system + 上一轮 user + 带思考的 assistant + 新 user；B 的 assistant 只有正文。
5. `#output` **追加第 2 轮**，不覆盖第 1 轮。
6. 每一列有「思考怎么开 · 从哪回来」：抽出这次请求里真正开门的字段（A 的 `extra_body`，B 的 `thinking`），再按实际 SSE 帧判定：单独字段 / 嵌在正文 / 两种都有 / 没有思考增量。

**无效参数怎么演一遍**：把 `LLM_PROVIDER` 换成 custom / 智谱，仍打 MiniMax 那套 `extra_body`。原始请求栏里键还在，但「这次返回」可能是 `none`，或思考全在正文。那不是页面坏了，是这一跳线路没实现这个方言。

工程收口：解析跟着响应走，不跟着请求走；下游只信拆开后的正文。

## 过关自检

合上笔记能讲清：

1. 思考和正文为什么要分开展示、混在一起会怎样。
2. 协议 A 怎么开思考（`extra_body`），协议 B 怎么开（顶层 `thinking` + budget）。
3. 流式时 A、B 增量各从哪个字段来。
4. 追问时为什么 A 可以回传思考、B 默认只回传正文。
5. 同一协议换厂商，开法 / 返回位置可以不同；请求里写了的思考参数，对方可以静默当无效。
