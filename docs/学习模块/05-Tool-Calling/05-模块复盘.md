### 一句话讲完这个模块

模块 05 = **让模型从「会说话」变成「会动手」的完整握手**——模型开口要调什么工具（协议 + Description 决定「调不调 / 调哪个 / 怎么填」），你后端真的去执行（Registry + Gateway 兜底防乱调），结果塞回对话历史（Protocol 闭环）。**没有这一步，后面所有 Agent / ReAct / 多 Agent / RAG 都建不起来**——Tool Calling 是它们共同的物理前置。

### 这些条怎么连成一条线

四条外部条是一条由「**上游软硬提示 → 下游硬执行兜底**」的**单向收紧链**：

- **[01 Function Calling 协议](./01-Function-Calling-协议.md)**是**骨架**——5 个动作一圈（`model → tool_call → execute → tool_result → model`），并行 / 串行 / 自编排 / 自纠都是这一圈的编排变体。它告诉读者：**模型只开口要，你才真执行**——但它**没讲怎么拦**。
- **[02 Tool Description](./02-Tool-Description.md)**是骨架的**左侧软提示**——模型在「调不调 / 调哪个 / 怎么填」之前，**唯一**能看的就是 description + schema。它告诉读者：**写糊了 = 模型乱调 / 不调 / 瞎填**——但它**不兜底**。
- **[03 Tool Choice](./03-Tool-Choice.md)**是骨架的**上游硬规则**——`auto / none / required / 指定` 决定这一轮「能不能 / 必须 / 禁止调」。它告诉读者：**Description 写得再好也只是软提示，硬约束还得用 Choice**——但它**管不到下游执不执行**。
- **[04 Tool Gateway / 幂等](./04-Tool-Gateway-幂等.md)**是骨架的**下游硬兜底**——模型已经开口了，你的后端要过鉴权 / 配额 / 危险操作 / 幂等 / 委托授权五道钩子才真执行，外加 Tool 业务错误结构化回传。它告诉读者：**模型一定可能幻觉，Gateway 才是工程补救层**。

**一条线**：01 把协议圈画出来 → 02 让模型在该调的时候调对 → 03 用 Choice 强行约束这一轮要不要调 → 04 用 Gateway 拦住模型不该调的东西 + 把副作用做对。**前一条是后一条的前提**，**缺任何一条整套都不稳**——这是它们连成一条线的方式，不是简单并列。

#### 几条值得拎出来的硬约束（贯穿四条）

- **「模型请求了 ≠ 允许执行」**是 01 → 04 的**主线**——01 写「execute 真实副作用」，04 才把 Gateway 钩子拆出来（鉴权 / 配额 / 危险）。
- **「整圈 Tool Calling = 两段字段契约」**是 01 → 04 的**统一抽象**——入参侧（`description` / `schema` / `input_schema`）↔ 出参侧（`tool_result` / `is_error` / `code` / `retryable`）。所有「模型乱调 / 调错参 / 错后乱走」查的都是字段，不是模型「理解力」。
- **「副作用 Tool 必须可重试」**是 01（tool_result 回灌闭环）→ 04（idempotency_key + 同 key 重放结果恒等）的**贯穿概念**——单次工具调用本身没意义，整圈要靠「重放结果恒等」才能在公网 / 模型并发 / 二次确认 UI 重试下不出错。
- **「工具和模型的整个交互 = 两段字段约定（契约）」**——模型不"理解"错误，它只读字段；工具不"理解"模型，它只按 schema 收、按 schema 返。**整圈没有一处是超字段之外的东西**。

### 最容易记错的三条（跨条易混）

| # | 易混 | 真相 |
|---|------|------|
| 1 | 「Function Calling = JSON Mode」 | JSON Mode 只保 `JSON.parse` 不抛；FC 多保「结构化 tool_call + 触发外部执行」。用 JSON Mode 写 Agent → 拿字符串自己解析 + 触发执行，绕一圈 |
| 2 | 「`tool_choice=required` = 模型一定会调」 | 语义上 = 必须调至少 1 个，但 MiniMax-M3（国内网关）**会违约**——`finish_reason=stop` + 空 `tool_calls` 散文回应。生产要做响应侧校验（`required && !hasToolCalls` → 标违约 / 重试 / 换 Provider），不能信 request 字段 |
| 3 | 「Tool Gateway = Tool Choice」 | Choice 管**上游模型要不要产出 tool_call**（请求级字段）；Gateway 管**下游后端要不要真执行**（execute 前钩子）。该 Gateway 兜的让 Choice 兜 → 模型仍可能产出非法 tool_call → 没人拦。Choice 强制调出 ≠ Gateway 放行 |

**对照清单**（每条都能跨 2+ 条）：

- 「**重复执行无害 ≠ 幂等**」跨 01（tool_result 回灌可重发）+ 04（idempotency_key）：无害 = 没出大事；幂等 = 业务结果恒等。没幂等的 3 次调用都 200，但 DB 多了 2 行
- 「**整圈 Tool Calling 都是字段约定**」跨 01 / 02 / 03 / 04：`description` / `schema` / `tool_choice` / `is_error` / `code` / `retryable` / `stop_reason` 全是 JSON 字段 → 模型读 → 决策。**模型不变，只改字段，行为就变**
- 「**理解错误 vs 读字段**」跨 01（tool_result 失败也回灌）+ 04（错误回传分层）：模型读 `code` / `retryable` 字段决策，不"接异常 / 不 try/catch"。让模型 try/catch 工具执行 → 模型被卷进基础设施错误
- 「**鉴权 vs 授权（auth vs authz）**」跨 04：鉴权 = 你是谁（who are you）；授权 = 你能干什么（what can you do）。只鉴权不授权 → 任何人登录就能调删库 Tool
- 「**限流 vs 配额 vs 防抖 vs 幂等**」跨 04：限流 = 频率（每分钟 > 60 次返 429，拒绝重复）；配额 = 总量上限（每月 1 万次）；防抖 = UI（按钮 disabled，只发 1 次）；幂等 = 同 ID 重放结果恒等（接受重复）。三者正交——一个 Tool 既可以有限流也可以有幂等；防抖救不了网络重试 / 并发（请求已离开浏览器），幂等才是后端兜底
