### 是什么

「会话内裁剪」= 当 messages 装不下（context window 上限 / 单次成本超预算 / 延迟超阈值），**怎么裁剪、裁什么、按什么规则**。两条主流策略：

| | 滑动窗口（Sliding Window） | 摘要压缩（Summarization） |
| -- | -------------------------- | -------------------------- |
| **机制** | 保留最近 K 条消息，更早的全部扔掉 | 调 LLM 把旧 N 条浓缩成 1 条 summary，summary 替代原 N 条 |
| **丢什么** | 字面细节（具体名字、数字、专有名词、语气都丢） | 字面细节（同样的丢），但**语义保留**（事实 / 决策结论被浓缩保留） |
| **代价** | 0 额外调用（纯本地 O(K) 操作） | 1 次额外 LLM 调用 ≈ 500ms~3s + summary 本身的 prompt token |
| **实现极简度** | 极简（slice / filter 即可） | 中等（要写 prompt + 处理 summary 失败兜底） |
| **适用长度** | K 越长越占 token；K 短则丢多 | 远期 N 越长 summary 越省 token，但 N 太长摘要 LLM 自己也吃不下 |

**核心对照（一句话）**：滑动窗口**扔字**，摘要压缩**重写**——读过的内容以「更短的形式」留下来，所以「小明住上海」可能被摘要成「用户住上海」保留下来。

### 为什么（Agent 开发要懂）

**控制 token 成本**——这是摘要压缩最根本的动机。不压缩的话，每次请求的 token 数随对话长度**线性增长**；压缩后**有上限**，聊 50 轮和聊 500 轮**成本差不多**（因为远期总是被压成 1 条 summary）。生产级 Chat App 不压 → 用户聊久了账单爆炸 + 模型越来越慢（context 越长首 token 时间越长）。

**两类信息保留的取舍**——滑动窗口硬上限便宜但丢事实；摘要压缩多花一次调用但保留语义。两条线**互补不替代**，生产里几乎都是「**摘要为主保留语义 + 滑动窗口兜底保成本**」混合用：摘要压缩失败时降级到滑动窗口（不报错、不让用户等）。

### 易混点

#### 易混 1：滑动窗口 vs 摘要压缩——「裁剪」不是单一动作

很多教程说「context 太长就裁剪」——但裁剪有两种完全不同的**信息保留策略**：

- 滑动窗口 = **丢弃**（不读，直接扔）
- 摘要压缩 = **重写**（读了再压，保留语义丢细节）

误以为「裁剪 = 截断」会错过摘要这条路径；误以为「压缩就够」会忽视裁断在**实时性 / 成本**上的优势。

#### 易混 2：摘要不是「更好的滑动窗口」——是**互补**不是替代

摘要能保留语义细节，但**代价**（LLM 调用 + 漂移）和**延迟**都不允许它替代滑动窗口。生产里**几乎都是混合用**：

```
messages = [
  system,
  assistant: "【之前对话摘要】用户住上海，喜欢日料，今天想订位...",   ← 摘要（1 条）
  user: "那帮我订 6 点的位子",                                          ← 近 K 条原文
  assistant: "好的，订到了",
  user: "谢谢",
  assistant: "不客气"
]
```

把滑动窗口当「近期原文」用，把摘要当「远期浓缩」用。

#### 易混 3：上下文管理 ≠ 自动 —— **「何时触发」是策略的一部分**

新手以为「messages 越长就越自动该压」——但**触发条件本身就是产品决策**：

- token 阈值？轮数阈值？混合？
- 是**每轮都检查**（性能开销）还是**只在 user 发新消息时检查**？
- 摘要 vs 滑动窗口，**先压哪一种**？还是先压摘要，摘要失败降级到滑动窗口？

这些不是技术细节，**是产品决策**——决定了「用户感受到的体验」。

#### 易混 4：摘要 vs 记忆（容易和模块 10 混淆）

- **摘要**：跨**同一会话内**的轮次压缩，**会话结束就丢**
- **记忆**：跨**会话**持久化，**用户下次开新会话还在**

本条只讲会话内压缩。**记忆 = 另一个模块**（模块 10 Memory），是「把摘要写到长期库里」——但摘要 ≠ 记忆，记忆 ≠ 摘要。

#### 易混 5：「Token Budget」（本条和第 3 条边界）

本条 = **已经决定要裁**之后用哪种策略裁。
第 3 条 = **什么时候决定要裁**（阈值怎么设、各角色分多少 token）。

你不会在「要不要压」还没决定时选「滑动还是摘要」——但反过来，先聊「压的方法」会帮你看清第 3 条的 token 阈值怎么设才有意义。

#### 易混 6：「裁剪对话」 vs 「RAG 检索对话」

- 裁剪 = **决定哪些 message 进 messages**
- RAG 检索对话 = **从历史库里检索相关 message 拼进 messages**（模块 08）

都是「从大的历史里挑一些进 prompt」，但裁剪是**丢 / 重写**，RAG 是**按相关性挑**——本条只讲裁剪，不讲检索。

#### 易混 7：触发阈值 vs 滑动窗口 budget —— 两条独立的线

生产里**实际有两条独立的线**，容易被混为一谈：

| 概念 | 是什么 | 谁来定 | 典型值 |
| ---- | ------ | ------ | ------ |
| **触发阈值**（何时调一次摘要）| total messages token > X 触发压缩 | **硬上限** + 产品可配 | 硬上限 = context window 80%（如 Claude 200K → 阈值 160K） |
| **滑动窗口 budget**（裁剪单位）| 滑动窗口保留多少 token | **用户在配置文件里写** | 如 slidingTokenBudget=500 |

**核心区分**：「什么时候压」是触发阈值；「怎么压」是裁剪单位（包括按条数 / 按 token）。两者不是同一个值，生产里**两条独立的线并存**：

```typescript
// apps/.env 示例
LLM_MODEL=claude-sonnet-5       // 200K context window
SLIDING_TOKEN_BUDGET=500        // 滑动窗口裁剪单位（用户配）
SUMMARIZE_TOKEN_THRESHOLD=160000 // 触发阈值 = context 80%（硬上限）
```

**阈值三种常见做法**：
- **固定比例**（context 80%）：大多数 Chat App 标配
- **用户/管理员可配**：企业 / 自部署（admin 后台配「压缩激进度」滑块）
- **动态阈值**：按模型价格调（GPT-4 贵 → 阈值 60%；GPT-3.5 便宜 → 阈值 90%）

最常见是「**固定比例 + 用户可覆盖**」—— 硬卡 80% 防爆炸，admin 可调。

### 例子

#### 例子 1：滑动窗口（按条数，K=4）

输入历史（messages 已有 8 条）：

```
[system] 你是某助手
[user]   1
[assistant] A1
[user]   2
[assistant] A2
[user]   3
[assistant] A3
[user]   4
[assistant] A4
[user]   5  ← 新轮次
```

策略：保留 system + 最近 4 条（user3/assistant3/user4/assistant4），system pin。

裁剪后发给模型：

```
[system] 你是某助手
[user]   3
[assistant] A3
[user]   4
[assistant] A4
[user]   5
```

数据流：检查 messages.length → 超过 K → 切片 `messages.slice(-K)` → 但要**保留 system**——所以是 `messages = [system, ...rest.slice(-K)]`（注意 rest 是除 system 之外的）。**踩坑**：从最老的非 system 开始扔，不是 `messages.shift()`（那会删 system）。

#### 例子 2：滑动窗口（按 token，B=8000）

用 tokenizer 数 token：

```
totalTokens = sum(tokenizer.encode(m.content) for m in messages)
while totalTokens > 8000:
    messages.pop(N)  ← 从最老的非 system 开始扔
    totalTokens = ...
```

与按条数的差别：单条超长消息（5000 token）按条数也算 1 条、按 token 算就占了一半预算；按 token 更稳。

#### 例子 3：摘要压缩（全量 + 保留近期 5 轮）

输入：50 轮对话。

步骤：
1. 取前 45 轮（待压） + 最近 5 轮（保留原文）
2. 把前 45 轮喂给 LLM，prompt：「你是对话历史总结器。用 200 字以内总结关键事实，重点保留用户告诉过你的事实。」
3. 收到 summary
4. 拼装：
   ```
   messages = [
     system,
     assistant: {role: 'assistant', content: '【历史摘要】' + summary},
     ...最近5轮原文
   ]
   ```

数据流：触发检查（token > 阈值 OR 轮数 > 阈值）→ 切分 [远期 N] + [近期 K] → 调 LLM 生成摘要（**真发网络请求调用**，要写日志）→ 拼装新 messages → 写回存储 → 下一轮就基于这个 messages。

#### 例子 4：摘要失败降级（生产必备）

摘要 LLM 调用超时/失败：

```
try {
  summary = await llm.summarize(oldMessages)
  messages = [system, {summary}, ...recent]
} catch (e) {
  // 降级：直接滑动窗口
  messages = [system, ...recent.slice(-K)]
  logger.warn('摘要失败，降级为滑动窗口', { error: e.message })
}
```

这是生产**必须**的兜底——不能因为摘要失败就让用户等 30 秒或者报错。

#### 例子 5：step-4 兜底降级（数据流 + 字段语义）

step-4 把「摘要失败降级到滑动窗口」做成了可观察的对照实验：跑两次同一份假历史 + 同一问句 + 同一模型，**唯一变量是摘要是否失败**。

**正常模式**（摘要成功）：

```
[full]      msgs=102 hasKey=✅    ← ① 完整
[sliding]   msgs=7   hasKey=❌    ← ② 滑动窗口（key fact 在窗口外）
[summarize] msgs=58  hasKey=✅    ← ③ 摘要压缩（summary 里写了 key fact）
fallback.used=false               ← 没走兜底路径
summary=「用户自我介绍叫 Tina，住上海...」
```

**模拟失败模式**（`simulateSummarizeFail=true`）：

```
[full]      msgs=102 hasKey=✅    ← ① 完整（不受影响）
[sliding]   msgs=7   hasKey=❌    ← ② 滑动窗口（同上）
[summarize] msgs=7   hasKey=❌    ← ③ 答题用的是 messagesSliding（与 ② 同源）
                                      key fact 落窗口外 → 答不出
fallback.used=true                ← 走了兜底路径
fallback.reason="摘要 LLM 模拟超时（教学演示）"
fallback.fallbackMessages.length=7   ← 与 ② messages 长度一致
summary=null                       ← 摘要没成功
```

**关键字段语义**（API 出参）：
- `fallback.used`: `true` = 摘要失败，本次「摘要压缩位」用了滑动窗口 messages 答的（用户不感知）；`false` = 摘要正常
- `fallback.reason`: 摘要失败的错误信息（生产里通常是「限流 / 超时 / 5xx」）
- `fallback.fallbackMessages`: 兜底用的 messages 数组（生产里通常等于 sliding 的 messages）

**对比 step-3**：step-3 摘要失败 → 整个请求 **502**（用户看到红字 ❌）；step-4 摘要失败 → **200 + fallback.used=true**（用户无感知，服务端日志可见）。生产里**让用户感知失败**的代价比「少一点信息」大得多，所以兜底降级是标配。

#### 例子 6：step-5 按 token 算窗口（变体 2 数据流 + 验证对照）

step-5 把「滑动窗口 K = 条数」换成「K = token 数」。从最新往旧累加 token，累加到 ≤ budget 为止；system pin。

**默认参数 (50/500/5000/5/1)**：

```
50 轮假历史（~2679 tokens · 102 条 messages）
       │
       ├─ messagesFull      = 102 条 / 2679 tokens / hasKey=✅     ← ① 完整（基线）
       ├─ messagesSliding   = 20 条 / 605 tokens / hasKey=❌        ← ② 滑动窗口按 token（B=500）
       │   └─ 从最新往旧累加 token，累加到 ≤ 500 为止
       │   └─ 第 1 轮 key fact（自我介绍）在窗口外 → 必丢
       └─ messagesSummarize = 85 条 / 2463 tokens / hasKey=✅       ← ③ 摘要压缩（summary + 近期 5 条原文）
           └─ summary 里有 key fact → 记得
```

**核心可观察**：按 token 滑动窗口（预算 500）丢 key fact；摘要压缩记得 key fact。

**与「按条数」（step-1）的对照**：

| 维度 | 按条数 K=6 | 按 token B=500 |
| ---- | ----------- | ---------------- |
| 窗口大小 | 6 条 | ~20 条（看 token 密度）|
| 单条超长消息（5000 token）| 算 1 条 → 占满窗口 → 其他消息被挤出 | 算 5000 tokens → 超预算 → 整条丢出窗口 |
| token 稳定性 | 不稳定（单条长消息可撑爆）| **稳定**（token 硬上限可控）|
| 适用 | 消息长度均匀 | 消息长度差异大 |

**为什么生产建议「按 token 做硬上限 + 按条数做辅助」**：单条超长消息按 token 算不会撑爆；按条数做辅助防止「极端情况」（如所有消息都是短消息，token 预算远大于条数时仍按条数卡）。

**生产配置示例**（与易混 7 对应）：

```typescript
// apps/.env
LLM_MODEL=claude-sonnet-5       // 200K context window
SLIDING_TOKEN_BUDGET=500        // 滑动窗口裁剪单位（按 token · 变体 2）
SUMMARIZE_TOKEN_THRESHOLD=160000 // 触发摘要的硬上限 = context 80%

// 运行时（每条 user 进来时检查）
const totalTokens = encode(messages).length
if (totalTokens > SUMMARIZE_TOKEN_THRESHOLD) {
  // 触发摘要压缩：远期 → summary + 近期 → 原文
  await summarizeOld(oldMessages)
}
// 不管是否触发摘要，每次发送都过滑动窗口裁剪
const trimmed = tokenWindowTrim(messages, SLIDING_TOKEN_BUDGET)
```

### 我追问过的

| 问题 | 针对什么 | 回答 |
|------|---------|------|

| 「摘要压缩就是压缩成一条摘要，下次再调时一条摘要对应 N 条会话，做到控制 token 成本？」 | 想确认摘要压缩的**根本动机** | 完全对。**核心动机就是控制 token 成本**——不压则每次请求 token 数随对话长度线性涨（聊 50 轮 ~1500 token、聊 500 轮 ~6000 token）；压缩后 token 数有上限（聊 50 轮 ~850 token、聊 500 轮还是 ~900 token，因为远期总被压成 1 条 summary）。这就是摘要压缩是生产 Chat App 标配的原因——不压账单爆炸 + 模型越来越慢。答见上文「**为什么（Agent 开发要懂）**」一节。 |

| 「那也就是说，就算兜底的话，它也有可能回答不出来的情况。因为兜底的就是最近的滑动窗口，它不一定有后面想要的信息。」 | 点出兜底降级的**固有缺陷**——不是 bug，是设计取舍 | 完全对，这是兜底的**固有权衡**：服务不挂 ✅ + 答得动 ✅ ↔ 答得对 ❌ 不能保证。step-4 验证里跑出来的事实：模拟失败模式 `summarize_or_fallback hasKey=False`（兜底用 sliding，key fact 落窗口外 → 答不出）。生产里分三档处理：① 完全无感知直接给（产品流畅但有误导风险）/ ② 响应加 disclaimer「部分早期信息可能遗失」（略繁琐更诚实）/ ③ 把 `fallback.used=true` 暴露给前端让产品决定怎么显示（step-4 走的这档）。**服务端做的是把降级痕迹暴露，不替前端做「是否告知用户」的决策**。答见上文「**踩坑**」节踩坑 4 + 「**取舍**」节「兜底降级策略的工程取舍」三档。 |

### 取舍

| 场景 | 用什么 | 为什么 |
| ---- | ------ | ------ |
| 闲聊 / 短任务 / 不在乎远期 | **滑动窗口** | 0 额外调用，延迟最低 |
| 客服查最近一次工单 | **滑动窗口** | 只关心最近 N 条 |
| 用户会反复引用早前信息（「我之前说的那个方案」= 30 轮前） | **摘要压缩 + 滑动窗口混合** | 单靠滑动窗口 K=6 会丢；单靠摘要成本太高 |
| 多步骤任务（订机票→选座→付款→收据，跨多轮有关联） | **摘要压缩 + 滑动窗口混合** | 决策链不能断 |
| 信息密度高、消息短（用户说的话里有大量关键事实） | **摘要压缩** | 滑动窗口 K=6 容易丢关键事实 |
| 极低成本要求（不想为摘要付额外 LLM 调用费） | **滑动窗口** | 摘要 = 1 次额外调用 ≈ 1~3s + token |
| 极低延迟要求（每轮用户等不了摘要的 1~3 秒） | **滑动窗口** | 摘要 = 同步阻塞 |
| 信息保真度要求极高（法律 / 医疗对话，每个字都要在） | **滑动窗口 K=N 或不压** | 摘要会丢字面细节 |
| 摘要 LLM 失败时的兜底 | **滑动窗口**（不是完整）| 兜底要 ① 不调 LLM（否则套娃）② token 受控（否则降级没意义）；滑动窗口两个都满足 |
| 用户消息长度均匀（如都是短句）| **按条数**（变体 1）| 实现极简，单条不会爆 |
| 用户消息长度差异大（如可能贴 5000 token 文章）| **按 token**（变体 2 · step-5）| 单条不会撑爆窗口，token 硬上限稳定 |
| 生产 Chat App 默认 | **按 token 做硬上限 + 按条数做辅助**（双重限制）| 「怎么压」用 token 算裁剪 + token 预算双卡；防止单条长消息 + 极端情况的组合 |

### 踩坑

#### 踩坑 1：LLM 把整段 user/assistant history 当成「对话上下文」，忽略摘要指令

**现象**：把 45 条 user/assistant 多轮交替直接拼进 messages（system 放「你是摘要器」），模型返回的不是摘要，而是「好的，关于「晚上有什么推荐的电影吗」我先简单回应一下。」——复读了 mock history 里某条 assistant 的原文。

**根因**：模型把 user/assistant 多轮交替看作「对话上下文」，自动进入「该我接着说」的角色，忽略 system 里的「做摘要」指令。模型「角色感」比 system 提示强。

**修复**（已落 step-2）：把 N 条 history 拼成一段带 `[user] (第 N 条)` / `[assistant] (第 N 条)` 标签的**纯文本**，作为**1 条 user message** 发给 LLM。这样模型看到的是「一段待总结文本」，不是「一段对话」。配合更狠的 prompt（明确「你是摘要器不是接着说话的助手」+ 禁止前缀「好的」「明白了」+ 禁止对话延续 + 给示例）才稳定生效。

#### 踩坑 2：system message 没 pin，被滑动窗口一起裁掉

按「最近 K 条」裁可能把 `[system]` 和「小明住在上海」一起丢——模型立刻「失忆」。正确做法是裁剪时** system message 永远保留**（pin），从最老的**非 system** 开始扔，不是 `messages.shift()`。

#### 踩坑 3：增量摘要会「漂移」

增量摘要每次把上一版 summary + 新增 N 条再喂给 LLM 让它「更新 summary」。多次调用后，最早的事实可能被扭曲（用户名字写错、住址从上海漂成北京）。生产里要么定期「全量摘要」重置漂移，要么限制增量次数（每 10 次增量做 1 次全量）。

#### 踩坑 4：兜底后的不准确回答——不是 bug，是设计取舍

**现象**：摘要失败 → 服务端 catch → 自动降级到滑动窗口 → 兜底答得动但**可能答错**（远期信息丢失）。

**根因**：兜底要在两个目标之间权衡 —— ① 服务不挂（用户感知不到失败）✓ ② 答得对（信息准确）✗。**两者不能同时满足**——因为兜底用的是滑动窗口，只留最近 K 条，远期信息已经丢了。

**修复思路**（不是修代码，是修认知）：
- 服务端老老实实把降级痕迹打到 `fallback.used=true`（step-4 走的这档）
- 由前端产品决定「是否告知用户」（这是产品决策，不是技术问题）
- 后端不替前端做这个决策——避免「过度兜底」让用户拿到错误信息还不知道

**为什么是设计取舍**：如果要让兜底既「服务不挂」又「答得对」，唯一办法是**重新调一次 LLM**（用完整 messages）—— 但这等于「兜底本身也可能失败 = 套娃」，且 token 可能爆。所以工程上只能在两者之间取舍。
