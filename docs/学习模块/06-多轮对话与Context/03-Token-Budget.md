### 是什么

**Token Budget = 在每次请求拼装 `messages` 数组之前,先给三块预留硬上限,超了就裁。**

三块预算:

| 块 | 含义 | 能裁吗 |
| -- | ---- | ------ |
| **system 段** | system 消息 + tools 描述 + 知识片段;每轮完全相同 | ❌ |
| **history 段** | 之前 user / assistant / tool 消息 | ✅ **唯一可裁** |
| **output 预留** | `max_tokens` 给模型留的生成空间 | ❌(只能预留) |

核心问题不是「怎么发」,而是「在拼 messages 之前,先算账」。不去算,模型也会算——只不过模型是按它**自己的窗口**算(4096/8192/128k/200k),不是按你的业务**预算**算。窗口是上限,预算通常小得多。

**公式**:

```
total = systemTokens + historyTokens + outputBudget
total ≤ totalBudget? → 不裁
total > totalBudget? → 丢最旧非 system 消息(每次 2 条,user/assistant 对),
                     保留 output/system,直到 total ≤ totalBudget
```

**变体(超预算时"怎么裁")**:

| 变体 | 怎么裁 | 代价 | 何时用 |
| -- | -- | -- | -- |
| **trim**(step-1) | 丢最旧非 system 消息 | 0 额外 LLM | 短对话 / 事实均匀 / 不在乎远期 |
| **summarize**(step-2) | 远期 N 条 → 调 LLM 浓缩成 1 条 summary + 近期 K 条留原文 | + 1 次 LLM 出网 | 长程陪伴 / 整体氛围 / 远期事实重要 |
| **soft+hard 双层**(step-3) | 软阈值先救(trim / summarize)→ 救不回来(超 hardLimit)→ 应急模式 = 只留 system + 末轮 + 提示"请重述" | 同 step-1 / 2 | 50+ 轮真长对话 / **保证服务不崩** |
| **selective inject**(step-4) | **遍历** history 每段,关键词匹配算命中数,取 top-N 命中段塞进 messages(其他不进) | O(N) 遍历 + 关键词 substring | 多话题并行 / history 不长但只 1 段相关 |
| **hard threshold**(已被 step-3 覆盖) | — | — | — |

### 为什么(Agent 开发要懂)

不知道预算,直接踩三个坑:

- **静默截断** — messages 拼好之后才发现超窗口,API 直接 400 / 自动截断最前面,用户感觉"AI 失忆了",其实是你没算账
- **账单爆炸** — 一次对话塞了 5 轮工具调用原文 + 几篇 RAG 片段 + 完整 system,用户单次成本从 ¥0.1 涨到 ¥2,你完全没感知
- **效果下降** — 即使没超窗口,把无关历史塞进去,模型反而被分散注意力,回答质量比精简 history 还差 — 这不是"塞得越多越好"

业务后果:用户问"我们昨天聊的那个方案",AI 答"我不记得了" — 其实是历史被无脑全塞、模型在 50k 历史里**找不回来**那个细节(中段衰退)。Token Budget 的价值**不是"多塞",是"有选择地塞"**。

### 易混点对比

**Token Budget ≠ Context Window**

- Context Window = 模型能接收的**最大物理长度**(例 128k)。硬上限,模型决定的。
- Token Budget = 你**业务上**愿意每次塞多少。**通常远小于**窗口。
- 判错后果:把窗口当预算 → 账单爆炸 + 注意力分散,用户不会主动告诉你"你塞太多了"。

**Token Budget ≠ "保留越多越好"**

- 直觉:历史越长 = 越"全" = 越好。
- 事实:成本线性涨 + 注意力中段衰退 + 输出空间被挤占。**质量峰值在某个"甜点"**,不是"塞满"。
- 判错后果:系统越用越慢、越用越贵,回答质量反而下降。

**output 预留 ≠ "事后能裁"**

- output 是预留(给模型留 token 空间),模型用多用少是它的事。
- 留 800 → 模型可能用 100 / 用 800 / 用 800 被截断,**事前不知道**。
- 留少了 → 模型直接截断(比"丢历史"更糟,用户看不到完整回答);留多了 → 浪费 token。
- **真要"裁"输出**,只能换 stop 序列 / 控制 prompt 引导短答;不能在生成到一半擦掉。

**三块里唯一可裁的是 history**(system 是规则不能动,output 是预留不能事后动)。

### 例子(每个核心对象 ≥1 个)

**三块预算 · 生活例子**

你家有一个行李箱 20kg(类比 context window)。但你**每月只愿意花 ¥100 邮费**——这就是 Budget。配比 = "衣物占 8kg、书占 5kg、礼物占 5kg、缓冲 2kg"。**装满 ≠ 装得多 = 装得值**。

**触发时机 · 前端例子**

滚动加载的列表——用户往下滚,数据不断加。你**不会**每次 setState 都检查总长,而是**滚到 80% 时触发一次加载** + **100% 时强制只保留最近 20 条**。这是"软阈值 + 硬阈值"。

**裁剪策略 · 前端例子**

一个 `<Modal>` 组件显示三种内容——标题、主体、按钮。空间不够时,你**先砍按钮**、再砍主体、**最后才砍标题**。这就是优先级预留——按"业务重要度"而不是"出现顺序"裁。

**三块分账公式 · step-1 实测对照**

```
totalBudget = 2000
output 预留 = 800
system 段   = 29
→ 留给 history 的额度 = 2000 - 800 - 29 = 1171

history 实际 = 2300(50 轮假对话)
→ 2300 > 1171,必须裁
→ 丢到 history = 1150,total = 29 + 1150 + 800 = 1979 ≤ 2000 ✓ 停
→ 一共丢了 50 条(25 对 user/assistant)
```

### step-2 教学点

**触发条件**:同 step-1 — `total = system + history + output > totalBudget`。**不**是"history 长就摘要"。

**双路径对照(同 query / 同模型 / 同 history,唯一变量是裁剪策略)**:

| | 方法一 trim | 方法二 summarize |
| -- | -- | -- |
| **触发** | total > totalBudget | total > totalBudget |
| **怎么裁** | 丢最旧非 system 消息(按 user/assistant 对丢) | 远期 N 条 → 调 LLM 浓缩成 1 条 summary + 近期 K 条留原文 |
| **出网次数** | 1 次问答 | 1 次摘要 + 1 次问答 = 2 次 |
| **默认参数下 3 次出网** | 1 次问答 | + 1 次摘要 + 1 次问答 |
| **何时"忘"** | key fact 在被丢的最旧段 | summary 把关键事实漏掉 / 近期被裁 |
| **典型观察** | key fact 在第 1 轮(默认)→ trim 忘 → ❌ | summary 留住语义 → ✅ |

**KEY_FACT 检测机制**:两路径回答出来后,系统扫回答里有没有"陈述"关键事实(我叫 Tina / 住上海 / 喜欢吃日料):

- 用**肯定句式**(`你叫 Tina` / `你住在上海` / `你喜欢日料`)而不是裸 substring
- 用**否定标记**(`未提及` / `没有` / `不能据此推断` / `无法`)排除反例
- 判定:肯定命中 ≥ 1 且 否定命中 = 0 才算 ✅
- 踩坑:第一版用 substring `["Tina","上海","日料"]` → trim 路径模型答"未提及"时用反例"你常问上海天气"也命中字串 → 误判 ✅;第二版加肯定句式 → trim 路径说"不能据此推断你住在上海"还是命中"住在上海" → 还是误判;第三版加否定标记排除反例 → 准确区分"陈述事实" vs "否认/反例"

**页面 4 张卡**:① 双策略判定小结 ② 方法一:直接丢最旧(预算表 + 完整 messages + 模型回答 + 关键事实判定) ③ 方法二:远期摘要 + 近期原文(同上 + summary 原文) ④ 裁前三块预算(参照基线)

### step-3 教学点(软硬双层)

**核心增量**:相比 step-2,只多了一根**硬阈值**红线 + 应急模式。其它逻辑(trim / summarize / 拼 messages / 调模型)都是从 step-2 搬过来。

**双层防御结构**:

```
层 1 软阈值(救):
  total > totalBudget → trim 或 summarize → 拼 messages → 调模型
  (能救就救;救不回来就丢给层 2)

层 2 硬阈值(兜底):
  total > hardLimit → 应急模式 = 只留 system + 末轮 + 提示"请重述" → 调模型
  (永远 fit,服务不崩)
```

**触发判定**(`beforeBudget.total > hardLimit ? emergency : soft`):
- `beforeBudget.total ≤ hardLimit` → 软路径:按 strategy 选 trim 或 summarize(同 step-2)
- `beforeBudget.total > hardLimit` → 硬路径:应急模式

**应急模式 messages 只剩 3 条**:

| 位置 | 内容 | 为什么 |
| -- | -- | -- |
| system | 原始 system prompt | 规则不能动 |
| 第 2 条 | history 末轮(原 user 或 assistant) | 保留"用户最后说了什么"——模型才知道上下文 |
| 第 3 条(新加) | user 提示:"对话太长,请用一句话重新描述你想做什么" | **让模型知道发生了什么**——不要假装记得 |

**Zod 闸门硬约束**:`hardLimit < outputBudget + 32` → 拒绝(400)。理由:hardLimit 太小 → 要么塞不下 output 预留,要么超模型窗口。**给 output 留够空间,再小就要么超窗口要么没输出**。

**端到端 5 个用例**(实测全过):

| 用例 | 输入 | 走哪条 | 结果 |
| -- | -- | -- | -- |
| 软路径 | 50 轮 / totalBudget=8000 / hardLimit=4000 | `mode: soft` / `soft.mode: trim` | total=3129 < 4000 → trim 不裁,102 条 messages |
| 硬路径(默认参数) | 50 轮 / totalBudget=2000 / hardLimit=1000 | `mode: emergency` | total=3129 > 1000 → 应急 3 条 |
| 硬路径(超长) | 200 轮 / hardLimit=1000 | `mode: emergency` | total=10029 > 1000 → 应急 3 条 |
| 4xx | hardLimit=500 < outputBudget+32=832 | 拒绝 | 400 + Zod issue |
| 5xx | `/api/emergency-force-error` | 立即 502 | 502 + 演示文案 |

**页面 4 张卡**:① 触发说明 + mode 软硬判定(红/绿) ② 软路径(仅 mode=soft 时显示) ③ 硬路径(仅 mode=emergency 时显示,默认展开 messages) ④ 裁前三块预算

**与 step-2 的差别一句话**:step-2 还在教"怎么救"(trim vs summarize 谁好);step-3 才教"救不回来怎么办"(应急模式保命)。拆开两个教学点是**增量最小化**——每步只加一个东西。

**两条线(硬阈值 = 底线 / 软阈值 = 软目标)的精确边界**:

| | 软阈值(soft) | 硬阈值(hard) |
| -- | -- | -- |
| **旋钮** | `totalBudget` | `hardLimit` |
| **触发条件** | `total > totalBudget` | `total > hardLimit` |
| **能不能超** | 可以超(下一步去救) | **不能超**(直接砍) |
| **目的** | 能救就救 | 救不回来就放弃 history,保命 |
| **做法** | trim 或 summarize(选一种去 fit) | 应急模式(只留 3 条 messages) |
| **结果** | 拼 messages → 调模型 | 拼 3 条 messages → 调模型 |
| **边界** | 救到 fit 为止(不会裁过头) | **永远 fit**(3 条 messages < 任何 hardLimit ≥ 256) |
| **类比** | 行李装不下 → 真空袋压一压 | 真空袋也装不下 → 不托运了,只带随身 |

**完整逻辑树**(从拼装 messages 之前的判定开始):

```
调模型前先算账:total = system + history + output 预留
  total ≤ totalBudget  → 不裁,直接发请求
  total ≤ hardLimit    → 软路径:trim 或 summarize(救到 fit)
  total >  hardLimit   → 硬路径:应急模式(只留 system + 末轮 + 提示)
```

**Zod 闸门硬约束(防止 hardLimit 配错)**:`hardLimit < outputBudget + 32` → 拒绝(400)。理由:hardLimit 太小 → 要么塞不下 output 预留,要么超模型窗口。**给 output 留够空间,再小就要么超窗口要么没输出**。这是个**配置安全护栏**——不是业务逻辑,是防止使用者把硬阈值配成"看起来有但永远触发"的值。

### step-4 教学点(选择性注入)

**核心增量**:跟前 3 步**完全不同的问题**。前 3 步处理"history 装不下",step-4 处理"history 不长但只 1 段相关"。

**为什么这个新问题值得单独一步**:多话题并行场景非常常见(用户聊 50 段混合话题,但 query 只跟其中 1 段相关)。前 3 步会**全部塞**(浪费 token)或者**裁掉**(丢信息);step-4 **按 query 内容选**——只塞相关的,其他不进 messages。

**四步流程**:

```
1. 把多话题 history 摊平(5 段 × 10 轮 × 2 角色 = 100 条 messages,每条带 topic 标记)
2. 遍历每段 → 算关键词命中数(score = user 命中 + assistant 命中)
3. 按 score 降序排 → 取 top-N(默认 3;0 分的不选)
4. 把 top-N 段塞进 messages → 调真模型
```

**关键词匹配机制**(最简版本):

| 维度 | 关键词匹配(本步) | embedding 余弦(模块 08) |
| -- | -- | -- |
| **原理** | substring 包含 | 向量空间余弦距离 |
| **能匹配** | 字面一样的词 | 同义 / 语义近(如"寿司" 匹配 "握寿司" / "鱼生") |
| **速度** | 快(O(N) 字面扫) | 中(要算 embedding,但有 ANN 索引) |
| **依赖** | 0 | 需要 embedding 模型 |
| **学习路径** | 入门简单 | 模块 08 RAG 后 |

**完整流程示例**(默认参数):

```
query="上次那个寿司店叫什么?"
keywords=["寿司","拉面","日料","餐厅","美食","上海"]
selectN=3

遍历 100 段 history:
  美食 1-5(寿司/拉面/日料/餐厅/意餐):score=2 → 全命中 → 但只取 top-3
  美食 6-10(火锅):score=1(只命中"美食")→ 不选
  天气 1-10:score=0~1("上海"算)→ 1 分,部分选
  工作 1-10:score=0 → 不选
  电影 1-10:score=0 → 不选
  健身 1-10:score=0 → 不选

取 top-3 = 美食 1-3 → 6 条 messages
+ system + user query = 8 条 messages 调模型
```

**端到端 4 个用例**(实测全过):

| 用例 | 结果 |
| -- | -- |
| 默认(寿司 + 6 关键词 + selectN=3) | 全塞 3385 token / 选择性 341 token(**省 90%**) |
| 4xx(query 为空) | HTTP 400 + Zod issue |
| 5xx(`/api/selective-force-error`) | HTTP 502 + 演示文案 |
| `keywords=""` | 不命中任何段 → selective = full(无省 token) |

**极端场景:query 相关的话题在很早以前**——前 3 步按"时间最近"或"全塞"处理,会**全丢光**或**淹没**;step-4 按"内容相关"选,**反而能找回来**。这是 step-4 相对前 3 步**不可替代**的场景。

**"遍历"的几个事实**(学习者可能想知道):

1. **遍历是同步的** — 简单 for 循环 + Array.sort(),不是流式。100 段几毫秒完。生产几千~几万段时:用倒排索引加速,或用 ANN 向量检索。
2. **关键词粒度 = 一轮** — 1 轮 = 1 user + 1 assistant(2 条 messages);top-N 选的是轮,选中就把 2 条都塞
3. **多话题 history 故意按话题分组(不按时间)** —— 这正是 step-4 的核心("按内容选");按时间就退化成 step-1 了

**5 张卡**:① 触发说明(query + 关键词 + selectN) ② 路径 A 全塞基线(完整 100 条 messages) ③ 路径 B 选择性(只 top-N,默认展开) ④ 对比小结(三行差:段数 / 输入 token / 输出 token) ⑤ 命中明细(5 段 × 10 轮 score 网格,带 ✅ = 被选中)

**与 step-1~3 触发条件的差别**:

| | step-1~3 | step-4 |
| -- | -- | -- |
| **触发** | `total > totalBudget` 或 `total > hardLimit` | query 关键词命中段(无关 total) |
| **处理粒度** | 整段 history 一起裁 | **逐段**判定 |
| **判定依据** | 长度(token 数) | **相关性**(关键词匹配) |
| **跟 step-1~2 配合** | 是 | **可以先用选择性把 history 削薄,再走 trim/summarize** |

### 取舍

**为什么先做"丢最旧"而不是"摘要压缩"?**

- 丢最旧 = 最浅、最快、可观察;不需要额外 LLM 调用,延迟 = 0
- 摘要压缩 = 一次额外 LLM 调用 + 延迟,而且摘要**有损**(专有名词、数字、用户偏好经常被吞);对照 02-step-3 的三方对照能看到这一点
- 选择性注入 = 需要关键词 / embedding 匹配;代码量大,且和"丢最旧"不是替代关系(选择性注入的本质是"挑哪些留",丢最旧的本质是"丢了哪就丢哪"),通常**组合**用而非互斥
- 学习路径上 step-1 先把"算账 + 触发 + 裁最旧"这一刀讲清,step-2/3/4 再换不同裁法

**为什么按 user/assistant 对丢(2 条一次)?**

- 一次丢 1 条 = 留半截对话,模型看到 user 没回答 / 看到 assistant 没问,体验更差
- 一次丢 2 条 = 保持对话轮次完整,模型至少看到成对的"问-答"

**为什么不按 token 算窗口?(留 step-2)**

- 按条数简单、可预测,适合教学"算账 → 触发"这一刀
- 按 token 算 = 真正的"硬上限",生产里最稳(单条超长消息也不会爆),但代码稍多
- step-5 在 02 已经有完整对照,可参照
