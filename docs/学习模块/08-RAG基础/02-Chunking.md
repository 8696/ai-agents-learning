## 是什么

**切块（Chunking）= 把一篇文档切成若干段可以独立被检索的小卡片。** 每张卡片 = 一段文本 + 从加载（Load）传下来的元数据（Metadata）。

它不是一个知识点，是**一个分类**。核心对象有 3 个 + 2 个附属件：

| 核心对象 | 管什么 |
| -------- | ------ |
| **大小（size）** | 一块多长 |
| **重叠（overlap）** | 相邻两块共享多少 |
| **切法（strategy）** | 按什么边界下刀 |
| 附属件 · 每块带什么 | 来源之外还要带章节路径、块序号 |
| 附属件 · 怎么判断切得好不好 | 调参不能靠感觉 |

## 大小（size）：两头都是坑

### 太大丢细节（变体 1）

嵌入（Embedding）会把**一整块**文本压成**一条**向量。一块里写了三个主题，这条向量就是三个主题方向的「折中点」——哪个主题都不特别像。

```text
块 A（3000 字，一整章《售后服务》）
  内容：7 天无理由 + 破损补发 + 保修期 + 偏远运费 + 发票重开
  → 嵌入 → 一条向量（方向 ≈ 五个主题的平均）

用户问「杯子运输途中裂了怎么办」
  问题向量方向 ≈ 纯「破损」
  和块 A 比      → 0.42（被另外四个主题拖下来）
  和别处一句闲话 → 0.55
  → 前 K 条第一名反而是那句闲话

切小之后：
块 A2（180 字，只讲破损补发）
  → 向量方向 ≈ 纯「破损」
  → 同一个问题 → 0.86，稳稳排第一
```

第二个后果：**块大 = 塞进提示词（Prompt）的废话多**。命中 3000 字里只有 180 字有用，剩下 2820 字是噪音，模型可能拿「偏远运费」来答破损问题（= 第 1 条易混点里的「张冠李戴」）。

### 太小丢语义（变体 2）

两种死法。

**死法一 · 句子被腰斩**：

```text
原文：运输过程中造成的破损，可在签收后 48 小时内申请补发或退货。
按 20 字硬切 →
  块1：「运输过程中造成的破损，可在签收后 4」
  块2：「8 小时内申请补发或退货。」
```

块 2 单独拿出来，时限从 48 变成 8。**这不是检索不准，是材料本身就错了**——后面提示词写得再硬也救不回来。

**死法二 · 指代断裂**（更阴，因为每块语法都通顺）：

```text
  ## 保修政策
  本公司所有电器类商品保修期为两年。
  该期限自签收之日起算，不含运输时间。

切成两块：
  块1：「本公司所有电器类商品保修期为两年。」
  块2：「该期限自签收之日起算，不含运输时间。」
```

块 2 的「该期限」指谁，它自己不知道。更糟的是检索层面：用户问「保修从什么时候开始算」，块 2 是正确答案，但它的文字里**根本没有「保修」两个字**，向量方向偏向「期限 / 签收 / 运输」，很可能搜不到。这个坑由变体 15 标题继承来解。

### 大小怎么数：字符、词元、还是汉字（变体 3）

同一个「500」，三种单位差别很大：

| 单位 | 500 大约是多少中文内容 | 谁在用 |
| ---- | ---------------------- | ------ |
| 字符（character） | 500 个汉字 | 你自己写 `text.slice(0, 500)` 时 |
| 词元（Token） | 中文大约 300~500 字（一个汉字常在 1~2 个词元之间） | 嵌入模型和聊天模型的限额都按这个算 |
| 英文单词 | 完全不适用于中文 | 英文教程里的 `chunk_size=500` 默认是这个语境 |

**网上看到的 `chunk_size=512, overlap=50` 几乎都是按英文词元来的**，直接抄到中文文档上会偏小。这不是事故，但它解释了「为什么我照着博客设了 512 还是切得稀碎」。

**还有一条硬约束**：嵌入模型对单次输入有长度上限，超了直接报错。所以切块代码**必须有兜底截断**——第 1 条 step-1 里的「单块 ≤ 3000 字」「每页 6000 字截断」就是这个兜底，不是业务规则。具体上限以各家文档为准，**不要背一个数字当通用值**（和「分数线不能拍脑袋」同一个道理）。

### 大小不是孤立的：和前 K 条、上下文预算连在一起（变体 4）

**调 size，实际上是在调「一次问答喂给模型多少字」。**

```text
喂给模型的材料量 ≈ 块大小 × 前 K 条（Top-K）

块  200 字 × Top-3 =  600 字   ← 精准，但可能漏
块  200 字 × Top-8 = 1600 字   ← 覆盖广，成本上升
块 1000 字 × Top-8 = 8000 字   ← 大概率超预算，且大半是废话
```

所以 size 和 Top-K 要**一起调**：

- 块切小 → Top-K 相应调大（否则一个答案被拆在 3 块里，只取 3 条可能只拿到 1 块）
- 块切大 → Top-K 相应调小（否则撞上下文窗口（Context Window））

这就是模块 06 词元预算（Token Budget）在 RAG 里的落点：**预算先定死（比如材料区最多 2000 词元），size × Top-K 必须落在预算里面。**

## 重叠（overlap）：专门补边界

### 它救的是什么（变体 5）

**重叠（overlap）= 相邻两块共享一段尾巴 / 开头。** 只有一个目的：**答案骑在切口上时，让它至少在某一块里是完整的。**

```text
原文（切口正好落在这里）：
  ……运输过程中造成的破损 | 可在签收后 48 小时内申请补发……
                        ↑ 切口

无重叠：
  块1 =「……运输过程中造成的破损」          ← 有情况，没有办法
  块2 =「可在签收后 48 小时内申请补发……」    ← 有办法，不知道是什么情况
  用户问「破损怎么办」→ 命中块1 → 只能答「是的，破损了」

重叠 50 字：
  块1 =「……运输过程中造成的破损，可在签收后 48 小时内申」
  块2 =「过程中造成的破损，可在签收后 48 小时内申请补发……」  ← 块2 完整
  用户问「破损怎么办」→ 命中块2 → 情况 + 办法都在
```

重点：**重叠不是「让每块都更全」，是「给答案第二次机会」。** 同一段内容出现在两个不同切口位置，总有一个位置能把它包完整。

### 取多少（变体 6）

**经验起点是块长的 10%~20%**：块 500 字 → 重叠 50~100 字。

理由：重叠的作用范围就是「切口附近一句话」。中文一句话通常 20~50 字，50~100 字足够把切口两边各一句包住，再大就是无用功。

**重叠 ≥ 50% 是明显的错误信号**——说明你在用固定长度硬切一份结构很清楚的文档，应该改成按结构切（变体 10），而不是靠加大重叠打补丁。

### 重叠的代价（变体 7）

重叠**不是免费的**，这是「取舍」两个字的重点：

| 代价 | 具体后果 |
| ---- | -------- |
| 库变大 | 重叠 20% ≈ 块数多出约 25%，存储和建库时间跟着涨 |
| 嵌入费用涨 | 多出来的块每块都要调一次嵌入接口 |
| **前 K 条出现重复内容** | 块1 和块2 共享 100 字，用户问的正好是那 100 字 → 两块分数都高 → 3 条材料里 2 条说的是同一件事 |

最后一条影响最大：**你以为拿到 3 条不同材料，实际只有 2 条信息。** 生产做法是检索之后做一次去重 / 合并（相邻块序号合并成一段）。

### 什么时候重叠可以是 0（变体 8）

**每块自己就说得通的时候，重叠是纯浪费。**

- FAQ 文档：一问一答一块，问题本身自带语境
- 条款型文档：一条政策一块（「第三条 破损处理：……」）
- 商品参数表：一行一块

判断标准：**把这一块单独拿给一个没读过原文的人看，他能不能看懂？** 能，就不需要重叠。

按结构切之所以是首选，就是因为它天然让大部分块自洽，重叠可以很小甚至 0。**换句话说：重叠是固定长度硬切的补救措施，不是所有切法的标配。**

## 切法（strategy）：按什么边界下刀

模块验收点名要对比的就是这里：「实现并对比了至少两种 Chunking 策略（固定长度 vs 按结构切分）」。

### 固定长度切（Fixed-size，变体 9）

数够 N 个字就切，不看内容。

```js
for (let i = 0; i < text.length; i += size - overlap) {
  chunks.push(text.slice(i, i + size));
}
```

**优点**：三行代码，任何格式都能切，块大小可预测（对预算友好）。
**缺点**：切口位置纯靠运气，上面两种死法全会遇到，必须靠重叠打补丁。

**什么时候用**：纯文本、没有任何结构的内容（聊天记录导出、连续文本），或者当**兜底**——按结构切之后仍然超长的那一块，用固定长度再切一次。

### 按结构切（Structure-aware，变体 10）

按文档自己的边界切：Markdown 的 `##`、段落空行、句号。第 1 条 step-1 已经在做——`refund.md` 按 `##` 拆、每块带 `section`，那就是按结构切。

**优点**：切口落在语义边界上，块自洽，`section` 天然能填进元数据。
**缺点**：**块大小完全不可控**——一节可能 50 字，另一节可能 5000 字。50 字那块信息太少，5000 字那块会超嵌入上限。

所以实际做法是**递归切分（Recursive Splitting）**：大边界优先，超长就降级。

```text
一段原文进来
  ↓ 先按 "\n## " 切
  还超长吗？ → 是 → 再按 "\n\n"（段落）切
    还超长吗？ → 是 → 再按 "。"（句号）切
      还超长吗？ → 是 → 固定长度硬切（兜底，保证不超嵌入上限）
```

**这是生产里最常用的默认策略**：结构优先、固定长度兜底。它同时解决「切口乱」和「块大小不可控」。

### 按页切（PDF，变体 11）

第 1 条 step-5 已经做了：PDF 按换页符 `\f` 拆，一页 = 一块，带 `page` 字段。

**优点**：页码直接进元数据，回答能点名「第 3 页」。
**缺点**：**跨页段落一定被腰斩**——一个条款从第 2 页末尾延续到第 3 页开头，两块都不完整；而且页面大小差异大（有的页只有一张图 + 两行字）。

这就是 step-1 笔记里写的「凑合解」：按页切是**为了页码这个元数据**付出的代价。改进方向是「按页切之后，再在页内按结构切，同时保留页码」——页码和语义边界可以兼得。

### 语义切块（Semantic Chunking，变体 12）

先按句子拆，给每个句子算向量，**相邻句子相似度突然掉下去的地方 = 话题变了 = 在这里切**。

```text
句1「本公司电器保修两年」        ─┐ 相似 0.82
句2「该期限自签收之日起算」       ─┘
                                  ↕ 掉到 0.31 ← 在这里切
句3「偏远地区运费另行计算」       ─┐ 相似 0.79
句4「新疆西藏加收 20 元」         ─┘
```

**优点**：切口落在真正的话题转折处，不依赖文档有没有标题。
**缺点**：**建库时要给每个句子都调一次嵌入**，成本和耗时成倍涨；而且「相似度掉多少算话题变了」又是一个要调的参数。

**什么时候值得**：文档没有任何结构标记（会议纪要、访谈记录、客服对话），但内容确实分主题。本条只要求能说出它存在、贵在哪，不要求实现。

### 小块检索、大块喂模型（Small-to-Big / 父子切块，变体 13）

这是「小块搜得准 vs 大块读得全」这个两难的**正面解法**——两个都要。

```text
建库时：
  大块（父，800 字，一整节）
    └ 小块1（150 字）→ 嵌入 → 入库，记住 parentId
    └ 小块2（150 字）→ 嵌入 → 入库，记住 parentId
    └ 小块3（150 字）→ 嵌入 → 入库，记住 parentId
  （只有小块进向量库，大块原文另存）

提问时：
  问题向量 → 和小块比 → 命中小块2（准，小块主题单一）
  → 喂给模型的不是小块2，是它的父块（全，上下文完整）
```

**轻量版本叫邻块扩展（Window Expansion）**：不建父子关系，只靠块序号 `chunkIndex`——命中第 7 块，就把第 6、7、8 块一起喂给模型。第 1 条向量库一行要存的四个字段里已经存了 `chunkIndex`，这个字段就是干这个用的。

### 有些东西不能腰斩（变体 14）

不管用什么策略，下面这些切断就废：

| 结构 | 切断后变成什么 |
| ---- | -------------- |
| Markdown 表格 | 表头和数据行分家 → 命中数据行那块，模型不知道每列什么意思 |
| 代码块 | 半个函数，括号不闭合 |
| 编号条款 | 「第三条」和它的内容分家 |
| 有序列表 | 步骤 3、4、5 单独成块，不知道是哪个流程的步骤 |

**处理办法**：切块前先识别这些块级结构，标记成「原子」，宁可超过 size 上限也不切开（超过嵌入上限时再单独处理）。

## 每块带什么：标题继承 + 块序号（变体 15）

「死法二 · 指代断裂」的解法在这里。

**标题继承（Header Inheritance）= 把这一块所在的章节路径拼到块文本开头，再去算向量。**

```text
不继承：
  块文本 =「该期限自签收之日起算，不含运输时间。」
  → 向量里没有「保修」方向 → 问「保修从什么时候开始算」搜不到

继承：
  块文本 =「售后服务 > 保修政策
            该期限自签收之日起算，不含运输时间。」
  → 向量里带上「保修」方向 → 同一个问题能命中
```

**一步解决两件事**：检索时向量方向更准；喂给模型时模型也知道这段属于哪一节。代价是每块多占几十字，而且所有块都带相同标题前缀会让它们之间的区分度略降——一般仍然值得做。

配合第 1 条已有的向量库一行要存的四个字段，切块产出的一行应该是：

```text
{
  id,
  vector,
  text: "售后服务 > 保修政策\n该期限自签收之日起算……",   ← 标题继承
  metadata: {
    source: "manual.md",
    section: "保修政策",
    chunkIndex: 7,     ← 能取前后块（邻块扩展）
    page: 3            ← PDF 才有
  }
}
```

## 怎么判断切得好不好（变体 16）

调 size / overlap **不能靠感觉**，也不能靠「跑一次答对了就行」。可观察的依据有四个：

| 看什么 | 切得不好的表现 | 指向哪个问题 |
| ------ | -------------- | ------------ |
| 命中卡片的**原文** | 开头或结尾是半句话 | 切法太硬 → 改按结构切，或加重叠 |
| 命中卡片的**内容纯度** | 一张卡片里有三个不相干主题 | 块太大 → 调小 size |
| **最高分**的变化 | 同一个问题，换切法后最高分从 0.42 提到 0.86 | 新切法让向量方向更准了 |
| 前 K 条的**重复度** | 3 条里 2 条内容几乎一样 | 重叠太大 → 调小，或加检索后去重 |

**关键原则：只有同一个问题、同一个嵌入模型、只改切块参数，分数才可比。** 换了嵌入模型分数量纲就变了（第 1 条已讲），那时候的对比没有意义。

**不同文档类型不该用同一套参数**（起点，不是答案）：

| 文档类型 | 推荐切法 | size 量级 | 重叠 |
| -------- | -------- | --------- | ---- |
| FAQ / 问答对 | 一问一答一块 | 天然 | 0 |
| 长手册 / 政策 | 按标题 → 段落递归 | 300~800 字 | 10%~15% |
| 法规 / 合同 | 按条款编号，条款不可切断 | 天然 | 0 |
| 会议纪要 / 访谈 | 固定长度 或 语义切块 | 300~500 字 | 15%~20% |
| 扫描 PDF 文本 | 按页 → 页内按段落 | 按页 | 页间少量 |

和阈值一样，最终值要用你自己的文档 + 你自己的嵌入模型测出来。

## 为什么（Agent 开发要懂）

1. **切块是整条流水线里唯一「错了后面全错」的一步。** 嵌入模型换个好的、提示词写硬一点、加个重排（Rerank），都能事后补救；但块本身就是断句，检索再准也只能拿到半句话，模型再听话也只能照着半句话答。**它是唯一的单向不可逆环节。**
2. **改切块策略的代价是全量重建。** 第 1 条维护期频率表写得很清楚：文档更新是行级（按 `source` 先删后建），但**切块策略一改，整库必须重切 + 重嵌入**。所以这个参数是「早期要想清楚」的，不是「上线后慢慢调」的。
3. **它是答不准时最容易被误诊的一环。** 第 1 条「答不准三种修法」里症状 1（前 K 条几乎无关）可能是库里没这类知识，也可能是切块切坏了。分不清就会去换嵌入模型——白花钱还是答不准。
4. **它直接决定成本。** size × Top-K = 每次问答的材料词元数，乘以日请求量就是账单。块大一倍，长期成本大一倍。
5. **它是 RAG「能点名出处」这个独家优势的前提。** 块要足够小，「根据《退货政策》破损一节」才有意义；整章一块的话，点名出处点的是一整章，等于没点。

## 易混点

| 容易混成一句话 | 差在哪 | 判错会怎样 |
| -------------- | ------ | ---------- |
| 切块大小 = 嵌入模型的输入上限 | 上限是**不能超**的红线；合适大小由**检索效果**决定，通常远小于上限 | 一块塞满几千词元，接口不报错，但检索全是「什么都像」 |
| 重叠越大越保险 | 重叠只救切口附近一句话；超过 20% 是在重复入库买噪音 | 库膨胀、前 K 条全是重复内容、账单翻倍 |
| 重叠是每种切法的标配 | 重叠是**固定长度硬切的补救措施**；按结构切、每块自洽时 0 重叠最好 | FAQ 库里每条问答重复三遍 |
| 按结构切就不用管大小 | 按结构切出来的块大小完全不可控，一节可能 5000 字 | 超嵌入上限直接报错；或那一节永远检索不准 |
| 切小了就更准 | 小到句子被腰斩、代词丢主语时，检索准了也没用——材料本身是错的 | 「48 小时」变成「8 小时」，客服照着答，真出事故 |
| 切块参数和 Top-K 无关 | size × Top-K = 喂给模型的材料量，受词元预算约束，必须一起调 | 块调小了 Top-K 没跟着调大，一个答案被拆在 3 块里只拿到 1 块 |
| 中文可以直接抄英文教程的 `chunk_size=512` | 那个 512 通常是英文词元；中文按字符 / 词元 / 汉字三种数法结果都不同 | 照抄之后切得比预期碎，还找不到原因 |
| 切块是嵌入模型帮你做的 | 切块是**本地**纯文本操作；嵌入只吃切好的字符串（第 1 条已讲，这里再钉一次） | 以为换嵌入模型会自动换切法 |
| 改切块策略像改提示词一样便宜 | 改切块 = 整库重切 + **重嵌入**（全量，慢且贵，必须放后台） | 在提问路径上触发全量重建，用户等 30 秒 |
| 语义切块最先进，应该直接上 | 它要给每个句子都调嵌入，建库成本成倍；结构清楚的文档用递归切分效果一样好 | 为一份结构完整的 Markdown 付了 10 倍建库成本 |
| 小块检索大块喂模型 = 把块切大一点 | 它是**两套粒度**：小块进向量库负责搜，大块只在命中后拼进提示词 | 直接把块调大，回到「太大丢细节」 |
| 切坏了可以靠提示词救 | 提示词管的是「模型忠不忠于材料」；材料本身是半句话时，忠于它反而错得更理直气壮 | 在提示词上反复调，问题其实在切块 |
| 分数低就是切块的错 | 也可能是库里根本没这类知识、问法差太远、或分数量纲本来就低（第 1 条修法表症状 4） | 整库重切重嵌入，跑完还是答不准 |
| 标题继承只是为了好看 | 它同时改变**向量方向**——没有标题的块，正确答案可能根本搜不到 | 「该期限自签收之日起算」永远命不中「保修」类问题 |

## 例子

**大小 · 生活**：把一本菜谱做成索引卡。一整章《川菜》抄成一张卡，客人问「宫保鸡丁放不放花生」，你抽出这张卡，上面同时写着回锅肉、麻婆豆腐、水煮鱼——得当场翻半天。改成一菜一卡，抽出来就是答案。反过来，一句话一卡：「花生米下锅」——这是哪道菜的哪一步？没人知道。

**大小 · 前端**：给帮助中心做搜索。用整个 `<article>` 的文本建索引 → 用户搜「退款手续费」，整篇命中，跳过去还得自己找。改成按 `<h2>` 分段建索引 → 直接锚点跳到那一节。再改成按 `<span>` 建索引 → 命中一个「手续」，毫无意义。

**重叠 · 生活**：撕一卷传真纸做归档。正好撕在「保修期为两」和「年」之间，两张都不完整。改成每张多留两行上一张的内容，总有一张能把这句话包完整。

**重叠 · 前端**：无限滚动的 overscan——多渲染上下各 3 条，用户快速滚动不会看到空白。代价也一样：这 3 条被渲染了两次，`key` 要处理好否则会出现重复项。

**切法 · 生活**：整理一份合同。按「第几条」撕（按结构切）最省事；拿尺子每 20 厘米裁一刀（固定长度切）会把条款腰斩；有一条特别长，就在这一条内部按自然段再撕（递归切分）。

**切法 · 前端**：`flex-wrap` 换行。优先在空格处换行（结构边界），单个词超过整行宽度时才 `word-break: break-all`（固定长度兜底）。**优先自然边界、超限才强切**——递归切分就是这个逻辑。另外 `page-break-inside: avoid` 对应的就是变体 14「不能腰斩的结构」：你不希望一张表格被切在两页上。

**标题继承 · 生活**：每张索引卡顶上写清「《员工手册》> 第三章 假期 >」。这样即使卡上写的是「该期限自申请之日起算」，你也知道说的是年假不是病假。

**小块检索大块喂模型 · 生活**：用便利贴在书里标了一句话。别人问起时，你翻到便利贴那页，但念的是**那一整段**。定位用一句，回答用一段。

**质量判断 · 前端**：像调分页大小。你不会凭感觉定 `pageSize=20`，你会看首屏时间、看用户翻页率。切块同理：看命中卡片原文有没有被腰斩、看最高分有没有提上去。

## 需求清单

验收准绳，不是一次搭完整应用的施工单。后面落 Demo 仍按知识一步步加，勾本条时再逐条对。场景都挂在第 1 条同一条业务线「售后助手」上。

1. **同一份文档、两种切法，切块结果并排能看见**
   场景：运营上传 `refund.md`，想知道该按什么切。目标：固定长度切 vs 按结构切，两边切块列表并排展示。知识点：变体 9、10。验收：两侧各自发请求（不是一个接口同时跑多套）；每侧能看到块数、每块字数、每块原文；能一眼看出固定长度那侧有块开头是半句话。

2. **size 可调，太大太小的后果当场可见**
   场景：把块长从 150 调到 3000。目标：看见块数变化和每块内容纯度变化。知识点：变体 1、2。验收：改 size → 切块列表实时重算；块里包含几个 `##` 小节要能标出来（块太大时明显 >1）；块 <100 字时页面能标出「可能被腰斩」。

3. **大小的单位讲清楚，且有兜底截断**
   场景：上传一份单节 8000 字的长文档。目标：按结构切之后仍超长的块能被按字数切兜底，不会把超长文本直接送去嵌入。知识点：变体 3。验收：页面同时显示「字符数」和「估算词元数」；超上限的块显示「已按字数切兜底为 N 块」，不报错、不静默截断。

4. **overlap 可调，且能看见它救了哪一块**
   场景：把重叠从 0 调到 100。目标：看见切口位置移动、看见相邻两块共享的那段文字。知识点：变体 5、6。验收：相邻块共享部分在页面上高亮；overlap=0 和 overlap=100 时，同一个「骑在切口上」的句子在哪一块里是完整的，能对照出来。

5. **overlap 的代价能量化**
   场景：同一份文档，重叠 0 / 10% / 30% 各切一次。目标：看见块数、总字符数、需要调用嵌入的次数怎么涨。知识点：变体 7。验收：页面给出三组数字对照；30% 那组明确标出「库膨胀约 X%」。

6. **重叠命中重复内容能看出来**
   场景：重叠设大（30%）后提问一个正好落在切口上的问题。目标：前 K 条里出现内容几乎相同的两条。知识点：变体 7。验收：命中列表能标出「与上一条重叠 N 字」；能看出 3 条材料其实只有 2 条信息。

7. **重叠 = 0 合理的场景能演示**
   场景：换成一份 FAQ 格式文档（一问一答）。目标：按结构切 + 重叠 0，每块自洽。知识点：变体 8。验收：页面能说明「这份文档为什么不需要重叠」；每块单独展示时是完整问答。

8. **递归切分：结构优先、超长降级**
   场景：一份 Markdown 里，有的小节 50 字、有的 5000 字。目标：短节整块保留，长节自动降级到段落、再到句号。知识点：变体 10。验收：每块能看到它是在**哪一层边界**切出来的（标题 / 段落 / 句号 / 硬切）；块大小分布比纯按结构切均匀。

9. **PDF 按页切的代价能看见**
   场景：上传一份段落跨页的 PDF。目标：看见被腰斩的跨页段落。知识点：变体 11。验收：页尾块和下一页页首块并排展示，能看出是同一段；页码元数据仍然正确保留。

10. **不能腰斩的结构被保护**
    场景：文档里有一张 Markdown 表格和一段编号条款。目标：表格不被切在中间，条款编号和内容不分家。知识点：变体 14。验收：这些块在列表里标为「整块保留」，即使超过 size 也不切；若超过嵌入上限，给出明确处理说明而不是静默切断。

11. **标题继承让指代断裂的块能被搜到**
    场景：搜「保修从什么时候开始算」，正确答案那一块原文里没有「保修」两个字。目标：开继承能命中，关继承搜不到。知识点：变体 15、2。验收：同一个问题、同一个嵌入模型，只切换「标题继承 开 / 关」，两侧最高分和命中排名并排展示，差异明显。

12. **小块检索、大块喂模型**
    场景：问「破损怎么退」。目标：命中的是 150 字小块，喂给模型的是它所在的 800 字父块（或前后邻块）。知识点：变体 13。验收：页面分开展示「检索命中的块」和「实际喂给模型的材料」，两者不同且能对上；靠 `chunkIndex` 取邻块的路径可见。

13. **切块质量可判断，不靠感觉**
    场景：同一个问题，用两套切块参数各跑一次。目标：给出可比较的判断依据。知识点：变体 16。验收：并排显示最高分、命中卡片原文（半句话要标出来）、前 K 条重复度；页面明确写「只有同一嵌入模型、只改切块参数时这个对比才成立」。

14. **size × Top-K 撞上词元预算时能看见**
    场景：块 1000 字 + Top-8。目标：材料区超预算时页面给出提示，而不是静默塞爆。知识点：变体 4。验收：页面显示「材料估算词元 / 预算」；超了给出建议（调小 size 或调小 Top-K），对照模块 06 词元预算。

15. **改切块策略 = 全量重建，不是行级维护**
    场景：改了 size 之后点重建。目标：页面明确告知这次是**整库重切 + 重嵌入**，不是按 `source` 行级更新。知识点：第 1 条维护期频率表在本条的落点。验收：重建提示写清「全量」二字 + 预计耗时 / 嵌入调用次数；与「文档更新 = 行级」区分开。

## 取舍

| 做法 | 什么时候合理 | 代价 |
| ---- | ------------ | ---- |
| 固定长度切 | 纯文本没有任何结构；或作为递归切分的最后兜底 | 切口靠运气，句子腰斩 / 指代断裂，必须靠重叠打补丁 |
| 按结构切 | 文档有清楚的标题 / 条款 / 问答结构 | 块大小完全不可控，短节信息太少、长节超嵌入上限 |
| 递归切分（结构优先 + 按字数切兜底） | 绝大多数真实文档，**推荐默认** | 实现复杂一点；要维护一张「边界优先级」列表 |
| 按页切 PDF | 你需要页码这个元数据来点名出处 | 跨页段落一定被腰斩；页面大小差异大 |
| 语义切块 | 文档完全没有结构标记（纪要 / 访谈 / 对话），但确实分主题 | 每个句子都要调嵌入，建库成本成倍；又多一个阈值要调 |
| 小块检索 + 大块喂模型 | 既要检索准又要上下文全，且愿意多写一层父子 / 邻块逻辑 | 库里要存 parentId 或额外读邻块；提示词变长 |
| 重叠 10%~20% | 固定长度切、或按结构切后仍有长块硬切 | 库膨胀约 25%、嵌入费用涨、前 K 条可能出现重复内容 |
| 重叠 0 | 按结构切且每块自洽（FAQ / 条款 / 参数表） | 万一切口仍然切断了某个答案，没有第二次机会 |
| 标题继承 | 几乎总是值得（尤其文档层级深、正文多代词） | 每块多占几十字；所有块带相同前缀会略微降低区分度 |
| 块调小 + Top-K 调大 | 想提高命中精度 | 材料条数多，要做去重 / 合并；预算要跟着算 |
| 块调大 + Top-K 调小 | 答案通常需要长上下文（流程类、条款串联） | 回到「太大丢细节」，噪音进提示词 |

本条推荐：**递归切分（结构优先、按字数切兜底）+ 标题继承 + 重叠按块长 10%~20%（按结构切且自洽时降到 0）**，参数最终值用自己的文档和嵌入模型测。不要抄英文教程的数字当通用值，也不要靠加大重叠去补救错误的切法。

## 踩坑

1. **照抄英文教程的 `chunk_size=512`。** 那通常是英文词元；中文按字符 / 词元 / 汉字三种数法结果都不同，抄过来会偏小。
2. **没有兜底截断。** 按结构切出来一节 8000 字，直接送嵌入接口 → 超长报错，或被静默截断而你不知道。
3. **靠加大重叠补救错误的切法。** 重叠 ≥ 50% 说明该换成按结构切了，不是该继续加。
4. **重叠之后不做去重。** 前 K 条里两条内容几乎一样，你以为拿到 3 条材料，其实只有 2 条信息。
5. **切块丢了来源 / 章节路径。** 第 1 条已经讲过来源；本条再加一条——**丢了章节路径，带代词的块会永远搜不到。**
6. **把表格 / 代码块 / 编号条款切断。** 表头和数据行分家之后，模型不知道每列是什么意思。
7. **在提问路径上改切块参数触发全量重建。** 改切块 = 整库重切 + 重嵌入，必须放后台任务，用户等不了。
8. **拿不同嵌入模型的分数来比较切块效果。** 分数量纲不一样，这个对比没有意义（第 1 条已讲过量纲问题）。
9. **切块切坏了却去改提示词。** 材料本身是半句话时，模型越忠于材料错得越理直气壮。
10. **一套参数走遍所有文档类型。** FAQ、长手册、法规、扫描 PDF 各有各的合适切法。

## 过关自检

关上文件后还能讲出来能说出口：

- 能说出 **size 的取舍**：太大 → 一块混几个主题，向量被平均掉、检索不准，还把噪音塞进提示词；太小 → 句子被腰斩（材料本身就错）或代词丢主语（搜不到也读不懂）。
- 能说出 **overlap 的取舍**：它只干一件事——答案骑在切口上时给它第二次机会；经验值块长 10%~20%；代价是库膨胀约 25%、嵌入费用涨、前 K 条出现重复内容；按结构切且每块自洽时可以是 0。
- 能说出 **重叠是固定长度硬切的补救措施**，不是所有切法的标配；重叠 ≥ 50% 是「切法选错了」的信号。
- 能对比两种策略：固定长度切（简单、大小可控、切口靠运气）vs 按结构切（切口准、块大小不可控）；生产默认是**递归切分**——结构优先、超长降级、固定长度兜底。
- 能说出还有哪些切法：按页切（为页码付的代价是跨页腰斩）、语义切块（准但每句都要调嵌入）、小块检索大块喂模型（两套粒度）。
- 能说出 **size 不是孤立参数**：size × Top-K = 喂给模型的材料量，受词元预算约束，两个要一起调。
- 能说出 **单位问题**：字符 / 词元 / 汉字三种数法不同，英文教程的数字不能直接抄；切块代码必须有兜底截断防超嵌入上限。
- 能说出 **标题继承**在干什么：把章节路径拼进块文本，同时改善向量方向和模型可读性，救「该期限」这类指代断裂。
- 能说出 **怎么判断切得好不好**：看命中原文有没有半句话、内容纯不纯、最高分变化、前 K 条重复度；且只有同一嵌入模型、只改切块参数时对比才成立。
- 能说出 **代价层级**：改切块策略 = 整库重切 + 重嵌入（全量），不是文档更新那种行级维护。
- 不要求：背某家嵌入模型的具体上限数字、实现语义切块、讲余弦公式（第 3 条）。
