## 是什么

**一句话（进度表要能讲清的）**：知识会改、或必须指出处 → 用检索增强生成（RAG）。口吻和格式要长期稳住、提示词（Prompt）搞不定 → 才考虑微调（Fine-tuning）。多数时候先试提示词 / 少样本（Few-shot）；也可以混合（Hybrid）：知识走检索增强生成，脾气走提示词或微调。

进度表压缩成：「知识常变 / 要引用 → RAG；风格 / 格式稳 → 才考虑微调。」完整决策顺序是：

```text
先问：这是「事实过期 / 要出处」还是「口吻 / 习惯稳不住」？
  ├─ 事实、内部规定、会改、要引用     → 检索增强生成（改文档 + 重新入库，不改模型权重）
  ├─ 口吻、版式、很难用提示词稳住的习惯 → 先提示词 / 少样本；真稳不住再微调
  └─ 两边都要                         → 混合：知识走检索增强生成，脾气走提示词或微调
```

微调在本条里只当「改模型脾气的选项」。怎么训、低秩适配（LoRA）、显卡，本仓库现在不当主线——那些是以后的事。

### 两条路把知识放在完全不同的地方

第 1 条说过：大模型在预测下一个 Token，不是在查你们公司的数据库。训练截止日期之后的售后规则、内部手册，它没有。补知识有两条完全不同的路。

**检索增强生成（RAG，Retrieval-Augmented Generation）**：知识放在模型外面。提问进来 → 找出几段相关切块（Chunk）→ 塞进提示词 → 模型按材料说话。政策改了：改文档、重新切片、重新入库。**权重（Weights）不动。**

**微调（Fine-tuning）**：把「习惯」写进权重。准备一批「用户这么问 → 理想中该这么答」的问答对，跑一次训练任务，改模型权重。改完的是口吻、格式、很难靠一句话提示稳住的习惯。知识如果也被写进权重，它就冻在里面了——手册一改，模型还按旧的说，除非再训一次。

模块 01「预训练 vs 推理」已经讲过：微调贵、要数据、少数情况才做。本条补上它和检索增强生成怎么分工。

**第三条路：提示词 / 少样本。** 不改权重，也不建库。系统提示词里写清口吻，再塞 2～3 条范例。OpenAI / Anthropic 官方对比的共同顺序都是：**先提示词，知识问题再检索增强生成，脾气问题最后才微调。** 很多人把选型做成「检索增强生成或微调二选一」，漏掉这一步。

### 前端类比（整条课共用）

| 前端在干什么 | 对应本条 |
| -- | -- |
| 页面渲染时 `fetch` CMS / 配置中心的最新文案 | **检索增强生成**：运行时去取知识，改内容不用重新打包整个前端 |
| 给组件传 `props` / 主题 token，加 3 个示例 | **提示词 / 少样本**：不改组件库，只改这一次怎么用 |
| fork 组件库，把品牌色、默认文案写进源码，重新发版 | **微调**：改的是「库本身的脾气」；再改要重新构建 |
| 组件库定风格 + 正文仍从 CMS 拉 | **混合**：脾气在库里（或 props 里），事实在 CMS 里 |

把售后手册整本打进 `constants.ts` 再打包上线——那是用微调（或更糟：写死在包里）灌知识。手册每周改，你就每周发版。还几乎说不清「这句话出自第几段」。

生活里：检索增强生成是开卷考试，桌上放最新手册；微调是练答题口吻和卷面格式，不是把会过期的百科背进肌肉。

### 数据怎么走

```text
检索增强生成（知识在库里）
  文档变更 → 加载 → 切块 → 向量化 → 写入向量库
  用户提问 → 提问也变成向量 → 按余弦（第 3 条的尺子）取出 Top-K
           → 带材料的提示词 → 生成（可带来源）

微调（习惯在权重里）
  问答对数据集 → 训练任务 → 得到改过权重的模型
  用户提问 → 直接问这个模型 → 生成（通常没有「第 3 段」这种出处）

提示词 / 少样本（什么都不改，只改这一次输入）
  系统提示词 + 2～3 条范例 + 用户提问 → 生成
```

同一句「我们现在七天无理由退货吗？」：

- **不检索、也不微调**：模型用训练时的常识或过期印象答，可能说「一般是七天」，没有出处，上周改成三天它也不知道。
- **检索增强生成**：库里是 9 月 1 日的公告「改为三天」→ 命中该切块 → 回答「三天」并挂上文件名 / 段落。
- **微调灌过旧政策**：权重里还是「七天」。你改了公告，它仍说七天，除非再准备数据集再训一晚。
- **只加提示词**：「按我们品牌口吻、先结论后依据」。口吻可能立刻像样；事实对不对仍取决于它肚子里有没有这条规定。

## 为什么（Agent 开发要懂）

选错的后果是钱、是错答、是法务风险，不是「架构不够高级」。

1. **政策每周改，你却去微调**  
   每次改规则都要：洗数据 → 排队训练 → 评测 → 换模型。售后改一行，你却重训一晚。期间线上还在用旧权重答。检索增强生成是改一篇 Markdown，重新入库，下一问就按新的说。

2. **法务要出处，你却只微调**  
   权重里吐出的句子指不到「哪篇、哪段」。出了错，客服无法点开依据。检索增强生成的命中列表自带文件名、页码、切块位置（第 1 条的元数据）。

3. **口吻要稳，你却只堆检索**  
   检索只往提示词里塞事实。模型每次仍可能换一种客服腔。品牌要「先道歉、再结论、再依据、禁止夸张」，这是脾气，不是「库里有没有这段话」。

4. **幻觉还在**  
   微调不会把幻觉（Hallucination）关掉。它更像「更像你们的口吻」，不是「变成数据库」。检索增强生成可以在检索太差时弃权（第 1 条已做过「库里没有就说不知道」）。两条都能胡说，但检索增强生成还能指着材料说「这段不够，我不答」。

5. **密钥进了训练集**  
   一段内部薪资、密钥、未公开的人事纪要如果进了微调数据，就写进权重了，删文档也撤不掉。检索增强生成至少还能按来源删行、按角色过滤切块（后面模块会做权限；本条先记住：**能进权重的东西，当它删不掉**）。

## 核心对象

| # | 对象 | 一句话 |
| - | ---- | ------ |
| ① | 检索增强生成（RAG） | 外挂、可更新、可引用的知识 |
| ② | 微调（Fine-tuning） | 改权重里的脾气 / 格式 / 难稳住的习惯 |
| ③ | 提示词 / 少样本（Prompt / Few-shot） | 第三人选：改这一次输入，不改权重、不建库 |
| ④ | 混合（Hybrid） | 知识走检索增强生成，脾气走提示词或微调 |
| ⑤ | 选型口诀 + 决策顺序 | 先分清「事实 / 出处」还是「口吻 / 习惯」，再选路 |

**step-2 在讲的是 ③ 的物理边界**：「口吻差 ≠ 模型差，是 system 差」—— 同份检索材料 + 同模型，左栏 system 空、右栏 system 加品牌口吻约定 + 3 条范例，差异只能来自 system。三刀各管各的事：system + 范例 → 习惯 / 口吻；RAG → 事实 / 出处；微调 → 深度领域反应。官方建议顺序：先 system → 再 RAG → 最后 FT。

第 3 条的余弦相似度（Cosine Similarity）只回答「这两段方向近不近」，**不回答**该不该微调。尺子选对了，选型仍可能错。

## 各变体（是什么 / 为什么 / 例子揉在一起写）

### 变体 1 · 知识常变 → 检索增强生成

售后「七天无理由」上周改成「三天」。FAQ、价格表、库存、版本发布说明，都属这类。

- **生活**：小区电梯检修通知每周换。你不会让全楼重新上「怎么坐电梯」培训班；门口贴新通知即可。
- **前端**：运营在 CMS 改了一条活动规则。你 `fetch` 最新配置，不重新发整个前端包。
- **数据怎么走**：改 `refund.md` → 按来源删旧切块 → 重新切片入库 → 下一问命中新切块。没有训练任务。
- **判错会怎样**：拿上周的模型去答本周的规则 → 客服按错规则答应客户。

### 变体 2 · 要引用 → 检索增强生成

即算法务说「知识两年没改」，只要每句答复必须能点开依据，仍然选检索增强生成。微调给不出「第 2 节第 3 段」。

- **生活**：医生说「说明书第 4 页写了空腹」，你可以翻书核对。医生说「我当年课本好像是这样」——你无法核对。
- **前端**：商品详情页的「材质说明」链到 CMS 那一篇；写死在组件注释里的说明，用户点不开。
- **数据怎么走**：检索结果带 `source` / 页码 / 切块 id → 提示词要求「只根据材料、并列出依据」→ 页面渲染来源列表。
- **判错会怎样**：出了错，你只能说「模型是这么说的」，对质不了文档。

### 变体 3 · 风格 / 格式稳 → 才考虑微调（格式先想结构化输出）

品牌口吻、固定道歉顺序、很难用一句话稳住的书写习惯，才进入「考虑微调」。

**先别上微调的格式问题**：只要 JSON 字段稳，先走模块 04 的结构化输出（Structured Output）。那是协议层约束，不是改权重。

- **生活**：书法课练的是「怎么握笔、怎么落款」，不是把百科背下来。
- **前端**：组件库默认用你们的按钮文案和间距——这是库的脾气。商品名、活动规则仍从接口来。
- **数据怎么走**：微调要的是成百上千条「问 → 理想答」（同一口吻）。检索增强生成要的是手册原文。两份数据长得就不一样。
- **判错会怎样**：为了让客服「先道歉再结论」去训模型，却把本周价格表也塞进训练集——价格一改，口吻还在、事实全错。

### 变体 4 · 第三条路：先试提示词 / 少样本

「听起来像我们品牌」有很大一部分，系统提示词加 3 条好评范例就能稳住。这是官方建议的第一刀，也是最容易漏的变体。

- **生活**：考试前老师在卷子顶上印了三道范例，多数学生格式就齐了，不用集训三个月。
- **前端**：先加 `tone="formal"` 和 3 个示例 props，不要先 fork 组件库。
- **数据怎么走**：请求 = 系统提示词 + 范例 + 用户问题。不入库，不训练。
- **判错会怎样**：提示词一起草就排期微调 → 等一周、花一笔训练费，最后发现 8 行系统提示词就够。

### 变体 5 · 混合：知识走检索增强生成 + 脾气走提示词或微调

生产里最常见的不是二选一。知识会改、口吻要稳：库里放政策，提示词（或以后微调）管「先结论、再依据、禁止夸张」。

- **生活**：律师口吻是练出来的，法条文本是书架上的——开庭既要口吻，也要翻得到条。
- **前端**：组件库定风格，正文仍从 CMS 拉。
- **数据怎么走**：检索命中政策切块 → 与系统提示词拼在一起 → 生成。事实来自切块，口吻来自提示词。
- **判错会怎样**：以为「上了检索增强生成就不用管口吻」，或「微调了就不用建库」。

### 变体 6 · 不该上检索增强生成

闲聊、常识、纯口吻题、模型已经会的通用知识。第 1 条已把检索做成工具（Tool），由循环自己决定要不要查——闲聊硬查会拖进一堆噪音。本条补选型：这类题也**不是**微调场景。

- **例子**：「你好呀」去查退货政策 → 提示词被政策污染，回答变得正式而奇怪。
- **判错会怎样**：用户觉得机器人答非所问；你还以为要微调让它「更会闲聊」。

### 变体 7 · 不该上微调

知识还在改、必须指出处、想靠微调「把文档背进模型」、问答对只有几十条还不稳、预算只够改一篇 Markdown。  
用微调灌新价格表，是本条最典型的反例。

- **例子**：把 200 页手册丢给训练任务，指望以后不用检索。手册第 17 页一改，模型仍背旧的；还指不出第 17 页。
- **判错会怎样**：钱花了，知识仍过期，幻觉还在，出处没有。

### 变体 8 · 幻觉与「库里没有」

- 检索增强生成：分数太低可以弃权（第 1 条已做）。
- 微调：没有「库里没有」这根闸。它仍会编，只是编得更像你们的口吻——**更像，所以更危险**。

客服问一份从未入库、也从未进过训练集的「隐藏折扣」。检索增强生成可以空命中后说不知道；微调模型可能编一个听起来很官方的折扣码。

### 变体 9 · 成本、延迟、运维（对照，不推训练细节）

| | 检索增强生成 | 微调 |
| -- | -- | -- |
| 改一次知识 | 改文档 + 重新入库（分钟级，第 1 条维护期频率表那个量级） | 洗数据 + 训练 + 评测 + 换模型（小时到天；模块 01 给过「单卡几小时、每次几十到几百美元」的量级） |
| 每次提问 | 多一次检索和嵌入 | 少一段长材料时，有可能更短、更便宜 |
| 运维 | 库、切块、嵌入模型、分数线 | 数据集版本、训练任务、模型版本、回滚 |

「微调以后每次请求更便宜」有时成立（提示词变短了）。**知识还在改时，总账通常是检索增强生成更便宜**，因为你比的是「改一百次知识的总成本」，不是单次 Token 单价。按任务选模型（模块 19）是后面的课，这里只记住：选型看**改知识的频率**，不看「微调听起来更高级」。

### 变体 10 · 数据形态：文档 ≠ 问答对

- 检索增强生成要的是手册、FAQ、PDF——**陈述事实的原文**。
- 微调要的是「用户原话 → 理想答复」——**带口吻的输入输出对**。

把手册原文直接当微调数据，模型学到的是「复述手册」，不是「按客服流程答」；把客服聊天记录不经清洗当检索文档，库里会进一堆「好的亲」和过期承诺。

并排看同一条退货规则：左边是 `refund.md` 的一段话（给检索增强生成）；右边是 20 条「用户问 → 理想答」（给微调）。用途一眼不同。

### 变体 11 · 隐私：进权重就当删不掉

误把内部薪资表、未发布的人事纪要拿去微调。文档可以从库里删；权重里的统计痕迹，不能当「删了文件就没了」。检索增强生成至少还能按 `source` 整份删行。

### 变体 12 · 能力边界：检索不教新本事，微调不灌会过期的事实

检索只能往窗口里塞字。模型本来就不会「按你们司审批流程图一步一步追问」，把流程图 PDF 切进去，它仍可能一次问完或跳步。这是**行为 / 流程**，可能要提示词、工作流（后面模块），或以后才考虑微调。  
反过来：模型不是不会「解释退货」，它是不知道**你们现在**几天——这是事实，用检索增强生成。

### 变体 13 · 检索范例当少样本 ≠ 已经微调

从历史好评里找出 3 条最像的答复，塞进提示词当范例——这叫「检索范例 + 少样本」，权重没改。它能改善口吻，也能随库更新范例。**不要把它汇报成「我们微调过了」。**

- **前端**：运行时从「优秀文案库」抽 3 条当参考，不是把文案写进组件库源码。

### 变体 14 · 两者都不够时（点到为止）

转账、删库、改生产配置：这不是检索增强生成或微调能单独收口的，要人点头（后面的人在回路里）。本条只标边界，不展开。

## 易混点

| 容易混成 | 实际差在哪 | 判错会怎样 |
| -- | -- | -- |
| 检索增强生成 = 微调 | 检索增强生成外挂可更新知识；微调改权重里的脾气 | 政策每周改，你却重训模型 |
| 必须二选一 | 可以混合；多数先试提示词 | 排期「上微调项目」，提示词其实够 |
| 微调能消除幻觉 | 微调改的是分布和口吻，不是数据库 | 错答听起来更官方 |
| 用微调灌文档 = 更懂业务 | 灌进去的事实会过期，且难引用 | 手册一改全错，还对质不了 |
| 检索增强生成能教新技能 | 检索只是往提示词里塞字 | 流程题靠切 PDF，模型仍跳步 |
| 要 JSON 稳 → 微调 | 先结构化输出（模块 04） | 为了字段名去训模型 |
| 检索到 3 条好评范例 = 已微调 | 那是少样本，权重没动 | 汇报失真；范例一旧，口吻跟着旧，你还以为「模型版本」坏了 |
| 知识很稳 → 可以不用检索增强生成 | 要出处时仍用检索增强生成 | 法务问依据，你拿不出切块 |
| 微调更高级所以该上 | 高级不高级看问题类型 | 烧训练费，知识仍外挂不了 |
| 长期记忆 = 检索增强生成 = 微调 | 记忆是「这个用户上次说过什么」；检索增强生成是「公司手册」；微调是「模型脾气」 | 把用户隐私写进权重，或把手册当用户记忆 |
| 调口吻 = 调模型 | 调口吻改 system + 几条范例（权重不动）；调模型改权重（永久）。三刀各管各的事：system + 范例 → 习惯；RAG → 事实 / 出处；微调 → 深度领域反应 | 以为「调客服腔 = 上微调项目」 → 实际 8 行系统提示词就能稳住 |
| step-3 = 加了 system 弃权指令 | 弃权指令 step-1 首次沉淀时就在 SYSTEM_TEMPLATE 里了；step-3 只是换了默认 question（从「库里有的题」换成「库里没有的题」）让这条指令第一次被显式触发。**真正的生产原则**：任何 RAG 项目的 system 都该包含「找不到时怎么办」的指令 | 以为「step-3 加了 system 里的弃权指令」 → 实际是 step-1 早就加了，step-3 没改 system，只换了 question |

## 例子

### 例子 1 · 生活：开卷考试 vs 练口吻

开卷：桌上放最新手册（检索增强生成）。练口吻：书法课练落款（微调）。考试前卷子顶上印三道范例（少样本）。既要口吻又要翻得到法条（混合）。

### 例子 2 · 前端：CMS vs fork 组件库

活动规则从 CMS `fetch`（检索增强生成）。`tone` props + 3 个示例（提示词）。fork 组件库把默认文案写进源码再发版（微调）。组件库定风格、正文仍从 CMS 拉（混合）。

### 例子 3 · 售后：七天改三天（本条主对照，前端场景）

页面上同一句「现在还能七天无理由吗？」

1. 点「只靠模型」：不检索，可能仍说七天，没有来源。
2. 点「检索增强生成」：库里已是「改为三天」的公告，回答「三天」并列出文件名 / 段落。
3. 页面写明：本步没有训练任务。

合上文件后必须能指着这次对照说：知识一改，检索增强生成立刻对；微调灌旧政策做不到。

### 例子 4 · 法务要出处（前端场景）

即便政策两年没改，答复旁也要能点开依据。只靠模型的一侧没有可点击出处；检索一侧有 `source` 列表。

### 例子 5 · 先试提示词（前端场景）

同一道投诉，空系统提示词 vs 带 3 条品牌范例，**两侧分请求**。带范例的更接近「先道歉再结论」。页面写明：这不是微调。

### 例子 6 · step-2 客服腔 · system 差异（前端场景）

同一句投诉「我买的鞋子穿了三天开胶了，要退货。」，左栏 `system = 「你是售后客服助手。请按材料回答」`，右栏 `system = 品牌口吻约定 + 3 条范例 + 材料`；两侧都检索命中同一份切块（refund-v2-001 / 002 / 003）。

- 左栏直接进入事实陈述：「您好，根据您描述的『穿了三天开胶』情况，这属于商品质量问题……」
- 右栏按范例「先道歉 + 再结论 + 列依据」：think 块明确参考范例 1（开胶场景），答复开头先承认问题。

→ 同份检索材料 + 同一模型，差异只能来自 system。**口吻差 ≠ 模型差，是 system 差。** 这是「第三条路」（改输入、不改权重），不是微调。

### 例子 7 · step-3 库里没有则弃权 vs 温和型幻觉（前端场景）

同一道「我们公司有没有内部折扣码？」库里（refund-v2-001~004）只讲退货 / 运费 / 退款 / 客服腔 —— 折扣码 = 库里没有。

- **左栏**（system =「你是售后客服助手。请按用户问题回答」，**无弃权指令**）：模型答「您好！关于公司内部折扣码的具体信息，我这边无法查询到。😊建议您通过以下途径获取：1. 咨询 HR 或行政部；2. 查看公司内网/员工手册；3. 询问直接上级……」 —— **温和型幻觉**：没编具体折扣码，但给了一堆无据可查的「你可以这样试试」建议。
- **右栏**（system 含「找不到就说『库里没有这条信息，我不能编』」指令）：模型答「库里没有这条信息，我不能编。依据：无相关材料。」—— **直接弃权**。

→ 选型对照的真正本体：**右栏不只给材料，还给一条「找不到时怎么办」的指令**。模型自带克制但仍会灰色地带游走（给「试试 HR」这种建议）；检索增强生成通过 system 指令显式弃权。

### 例子 8 · step-4 数据形态对照：文档 vs 问答对（前端场景）

左栏 4 段 refund-v2.md 文档：每条 =「来源 / 章节 / 段落全文」结构 —— 陈述事实的原文（退货政策、客服腔、FAQ：发票保修、FAQ：会员等级）。右栏 5 条客服问答对：每条 =「用户原话 + 理想答」结构 —— 带品牌口吻（「非常抱歉您……」开头）+ 处理流程（按订单查条件、发起退换货、解释运费时效）。

- **左栏喂给**：检索增强生成（陈述事实的原文，便于检索命中 + 列出处）
- **右栏喂给**：微调（带口吻 + 处理流程，便于训练模型学会按品牌说话）

→ step-4 立住的两条生产反例：① 把左栏直接当微调数据 → 模型只学到「复述手册」，接到用户投诉时不会道歉 / 不给具体方案；② 把右栏直接当检索文档 → 检索时命中一堆「好的亲」「没问题亲」+ 「上次退过 50 块」单次承诺，模型按材料说话 = 按「亲」说话、承诺成了政策。

→ **step-1~step-4 一以贯之的原则：不同目标用不同方法 + 不同数据**（不是「越高级的方法越好」）。

### 例子 9 · step-6「该不该检索」三种流程（前端场景）

同一道题「现在还能七天无理由退货吗？」进 3 个 sub-page：

- **路由层规则（sub-page 1）**：关键词正则匹配「退」→ 命中 → 走检索分支 → 答「调整为 3 天」+ 依据
- **命中阈值（sub-page 2）**：总是检索，看 top1 score ≈ 0.5 > threshold 0.3 → 走检索 → 同上
- **agent loop（sub-page 3）**：先让模型自己答 yes/no → 模型答 yes（需要检索业务问题）→ 走检索 → 同上

→ 同一道题，三种判断都走检索——但**判断位置**不同（工程师写 / 系统算 / 模型自己答）。

### 例子 10 · step-7 混合 pipeline（前端场景）

同一道题「我买的鞋子穿了三天就开胶了，要退货。」+ 3 种 system 模板 + 改 corpus：

- **默认（brand + 3 天）**：检索命中「调整为 3 天」+ system 是「先道歉 / 再结论 / 列依据」品牌口吻 → 答「非常抱歉……按现行政策……质量问题 3 天内可退……」+ 列出依据 refund-v2-002 / 003
- **改 corpus（brand + 7 天）**：检索命中「调整为 7 天」→ 答「……质量问题 7 天内可退……」→ 事实跟材料变，口吻不变
- **换 system（empty + 7 天）**：检索命中「调整为 7 天」+ system 是「按材料回答」无品牌口吻 → 答「按现行政策……7 天……」无道歉 → 事实不变，口吻跟 system 变

→ 4 个变量（question / corpus / system / 模型）锁死 3 个、改 1 个看 1 个跟变 ——「事实 + 口吻 各管各的」的可观察证据。

## 需求清单

验收准绳，不是一次搭完整应用的施工单。`coach complete` 时逐条对；step 仍按「这一步只看懂一件」往前加。

1. **知识常变（变体 1）**  
   场景：售后政策从「七天」改为「三天」，运营只改了一篇公告。  
   目标：下一问必须按新规则答，禁止为此重训模型。  
   知识点：知识放库里、行级更新、权重不动。  
   验收：同一题，不检索仍说旧的或编；检索增强生成说「三天」。页面能看见「没有训练任务」。

2. **要引用（变体 2）**  
   场景：法务要求每条答复能点开依据；即便政策两年没改。  
   目标：回答旁有来源（文件名 / 段落），不是只有一段光滑的中文。  
   知识点：出处来自切块元数据，不是权重。  
   验收：检索一侧有来源列表；「只靠模型」一侧没有可点击出处。

3. **风格稳、格式先分流（变体 3）**  
   场景：品牌要求「先道歉、再结论、再依据」。  
   目标：看清「只检索事实」挡不住口吻乱飘；要 JSON 字段稳，标注应走结构化输出，不走微调。  
   知识点：脾气 ≠ 知识；格式 ≠ 第一反应微调。  
   验收：同一份材料，两次回答口吻结构仍可能不同；页面有一句「这不是检索增强生成单独能收口的」。

4. **先试提示词（变体 4）**  
   场景：同一道投诉，空系统提示词 vs 带 3 条品牌范例。  
   目标：证明第三人选存在，且往往够用。  
   知识点：改输入，不改权重、不建库。  
   验收：两侧分请求；带范例的一侧更接近规定口吻。禁止做成「已经微调」。  
   **已落 apps/08-RAG基础/04-RAG-vs-Fine-tuning-step-2（端口 50081，🔄 打磨中）** —— 左栏 `system = 「你是售后客服助手。请按材料回答」` + 同份检索材料；右栏 `system = 品牌口吻约定 + 3 条范例 + 材料`。同份检索 + 同模型 + 同问句，差异只能来自 system。

5. **混合（变体 5）**  
   场景：新政策必须对，同时要品牌口吻。  
   目标：政策来自检索，口吻来自系统提示词。  
   知识点：混合（Hybrid）。  
   验收：改公告后事实跟着变；口吻提示不变。来源仍在。

6. **不该检索（变体 6）**  
   场景：用户只说「你好」。  
   目标：选型上既不是微调，也不该硬检索。  
   知识点：闲聊硬查会注入噪音。  
   验收：能看见「本轮未检索」或空命中，回答不被退货政策污染。

7. **不该微调灌事实 + 弃权（变体 7、8）**  
   场景：有人提议「把手册拿去微调，以后就不用检索」。  
   目标：这是反例；库里没有的题，检索能弃权，「只靠模型」仍可能编。  
   知识点：微调灌知识的失败模式；幻觉更像官方更危险。  
   验收：决策卡把该提议标成「不该微调」；无材料题检索侧弃权。  
   **已落 apps/08-RAG基础/04-RAG-vs-Fine-tuning-step-3（端口 50082，🔄 打磨中）** —— 默认题「我们公司有没有内部折扣码？」 = 库里没有；左栏「只靠模型」system 只有「你是售后客服助手」，无弃权指令 → 模型给「问 HR / 看内网 / 问上级」温和型幻觉；右栏 system 含「找不到就说『库里没有』」指令 → 直接弃权。**事实过期 vs 幻觉：step-1 / step-2 演示的是「事实过期」（训练截止后的旧常识），step-3 演示的是「幻觉」（凭空给出看似合理的回答）。**

8. **数据形态（变体 10）**  
   场景：同一条退货规则，一份是手册段落，一份是 20 条客服问答对。  
   目标：分清给检索增强生成的和给微调的不是同一种文件。  
   知识点：文档 vs 问答对。  
   验收：并排能指出「左边入库，右边才是训练样本；不要拿错」。  
   **已落 apps/08-RAG基础/04-RAG-vs-Fine-tuning-step-4（端口 50083，✅ 锁定）** —— 不调 LLM（§5.3.0 例外），左栏 4 段文档 / 右栏 5 条问答对并排对照；立住两条生产反例：① 把手册当微调数据 → 模型只学会复述；② 把聊天记录当检索文档 → 「亲」满天飞 + 单次承诺被检索成政策。

9. **隐私（变体 11）**  
   场景：有人要把内部薪资表拿去微调。  
   目标：标成禁止；对照「从库里删文档」做得到，「从权重里撤回」本条做不到。  
   知识点：进权重当删不掉。  
   验收：该样本被拒，或决策卡明确写「不进训练集」。

10. **检索范例 ≠ 微调（变体 13）**  
    场景：从历史好评抽 3 条当少样本。  
    目标：口吻改善，但页面写明「权重未改」。  
    知识点：少样本检索 ≠ 微调。  
    验收：能看见插入的 3 条范例原文；决策结果是「提示词 / 检索范例」，不是「已微调」。

11. **成本对照（变体 9，偏知识）**  
    场景：本周要改 10 次价格。  
    目标：看见「改 10 次文档」和「训 10 次模型」不在一个量级。  
    知识点：总账看变更频率。  
    验收：对照卡有时间 / 次数，不要求真跑训练。

12. **能力边界（变体 12、14，纯知识）**  
    场景：要按内部审批流程图逐步追问；或转账要人点头。  
    目标：能说「检索手册不够，这是流程 / 人在回路，不是本条用检索增强生成能收口的」。  
    知识点：检索不教新本事；两者都不够时不要硬选。  
    验收：讲得清即可；不在本条真做工作流。

| 「其实没看懂 Step 二的意义在哪里。」 | step-2 与 step-1 的差异没讲清；学习者期望一眼看到「这一步对照演示了什么反直觉点」。 | step-2 在演示「口吻差 ≠ 模型差，是 system 差」—— 同份检索材料 + 同一模型，左栏 system 空、右栏 system 加品牌口吻约定 + 3 条范例，差异只能来自 system。这是 MD 变体 4 的两个反直觉点：（1）调口吻先改 system 加 3 条范例，不要直接排期微调（官方建议第一刀）；（2）这是最容易漏的变体 —— 太多人一上来就排期训练，结果 8 行系统提示词就够。官方建议顺序：先 system → 再 RAG → 最后 FT。 |

| 「其实无非还是说限制模型，不要让它乱说；也就是说，让它知道就知道，不知道就不知道。而不是在灰色地带游走。」 | 弃权策略的本质 + prompt 工程的通用原则。 | 这条原则不只适用于「库里没有」这一场景 —— **任何 prompt 都该给模型边界**。左栏「只靠模型」做的就是「灰色地带游走」：它不知道「公司有没有 HR」，但没收到「不知道时怎么办」的指令，于是按「我是客服」角色自动补全「问 HR / 看内网 / 问上级」 —— 这就是「温和型幻觉」的本体：不是错答，而是滑过「不知道」那条线给一个**看似合理但无据可查**的回答。step-1 / step-2 / step-3 都是在不同场景下演示「怎么画边界」：边界1 =「只按材料」（step-1），边界2 =「口吻要这样」（step-2），边界3 =「找不到就说不知道」（step-3）。prompt 工程的通用原则 = **给模型画边界 + 拆掉它的灰色地带**。 |

## 取舍

- **先提示词，再检索增强生成，最后微调。** 不是「听起来高级的先上」。
- **知识会改或要出处 → 检索增强生成**，即使口吻也要用：口吻用提示词（或以后微调）叠上去，不要为了口吻把事实写进权重。
- **只要 JSON 字段稳 → 结构化输出（模块 04）**，不要为了字段名去微调。
- **闲聊 / 常识 → 不检索也不微调。**
- **知识还在改时，总账通常检索增强生成更便宜**——比的是改一百次知识的成本，不是单次 Token 单价。
- 本条不真训模型：演示「微调要达成的效果」若用系统提示词代替，必须写明「这是代替演示，不是真微调」。
- **step-2 对照设计：同份检索材料 + 不同 system promptVariant。** 检索材料、问句、模型三者全锁死，只让 system（空 / 范例）变 —— 差异才能归因到 system 上。**禁止**用「左栏换模型」或「右栏加额外材料」这类对照，差异混进了别的变量就讲不清「system 影响口吻」这一步。
- **step-3 对照设计：复用 step-1 锁定版本 + 换默认 question。** step-3 几乎不写新代码 —— 复用 lib/flow / lib/rag / routes 全部文件；只改默认 question（从「库里有的题」换成「库里没有的题」）+ 改页面文案。**真正的变化在 question**——因为 system 里的弃权指令首次沉淀 step-1 时就写好了，库里有的题派不上用场，库里没有的题让它第一次显式生效。**禁止**在 step-3 改 lib/flow 的 system 模板，否则就破坏了「step-1 就有弃权指令」这条生产原则的可观察证据。
- **prompt 工程的通用原则 = 给模型画边界 + 拆掉它的灰色地带。** step-1 / step-2 / step-3 三步对应三条边界：「只按材料」/「口吻要这样」/「找不到就说不知道」。任何 prompt 都该给模型明确的边界，而不是依赖模型的「自觉」—— 模型训练时学的是「像人一样说话」，会试探、模糊、礼貌式编；你要的是「像客服 / 像医生 / 像法务」，这些角色要的是「按规矩办」。
- **step-4 对照设计：不调 LLM（§5.3.0 例外「纯 UI 渲染层演示」）。** step-4 不写 `lib/flow/*`，不调真模型；新建 `lib/data-shape/doc-corpus.ts` 与 `qa-corpus.ts` 分别管理（文档 / 问答对是**不同的事**，改一个不该碰另一个）。**禁止**用 `cd apps && yarn typecheck` 之前混入调用模型的组件——保持 step-4 是纯展示。step-4 立住的两条生产原则：**禁止把手册直接当微调数据**（模型只学到复述手册，不会道歉 / 不给处理流程）；**禁止把客服聊天记录当检索文档**（检索时命中一堆「好的亲」+「上次退过 50 块」单次承诺，模型按材料说话 = 按「亲」说话，承诺成了政策）。
- **step-1~step-4 一以贯之的原则：不同目标用不同方法 + 不同数据。** 不是「越高级的方法越好」—— 目标决定方法，方法决定数据。

| 你的目标 | 该用哪种方法 | 该喂什么数据 |
| -- | -- | -- |
| 事实要准（出处 / 最新） | **检索增强生成** | 手册 / FAQ / PDF |
| 知识会改 / 要引用 | **检索增强生成** | 同上 |
| 口吻要稳（客服腔 / 道歉顺序） | **先 system + 几条范例**（不动权重） | 不喂数据 |
| 处理流程 / 行业深度反应（按订单 → 看库存 → 退/换/修；医学/法律专业反应） | **微调** | 真实聊天记录 → 整理成「用户问 → 客服答」问答对 |
| 模型「找不到」怎么办 | **检索增强生成** + system 含弃权指令 | 同 RAG 数据 |
| 闲聊 / 通用知识 | **不检索也不微调** | 不喂数据 |
| 想看「该不该检索」三种判断 | 路由层规则 / 命中阈值 / agent loop（详见 step-6） | — |
| 想看「事实 + 口吻」分层混合 | 同一端点 + 3 种 system 模板 + 改 corpus（详见 step-7） | 手册 + 品牌口吻约定 |

- **step-5 / step-6 / step-7 关系：step-5 是「决策卡 + 反例集」（8 个 sub-page 变体各自一卡）；step-6 是「该不该检索」三种流程（路由层规则 / 命中阈值 / agent loop）；step-7 是「混合 pipeline 综合 demo」（事实 + 口吻各管各的）。三者独立新文件夹 + 各自端口，**不复用** step-1~4 的代码。
- **为什么 step-5/6/7 各开新 step** ——按 §5.3.14「默认每个新教学点 = 新 step-N+1（独立文件夹 + 新端口）」。step-5「一个变体一个 sub-page」+ step-6「三种流程可观察对照」+ step-7「混合 pipeline 4 个变量各管各的」都是新教学点。
- **step-5 mix sub-page 已删 → 需求 5「混合」在 step-7 独立 sub-page**。同样需求 6「不该检索」从 step-5 决策卡挪到 step-6 三种流程独立 sub-page。**禁止**在 step-5 同时演示「混合」和「不该检索」——每个 sub-page 只承担一个变体。

## 踩坑

- 政策每周改，却去重训模型。
- 法务要出处，却只微调，对质不了文档。
- 以为微调能消除幻觉——错答会更像官方。
- 把手册当微调数据灌进去，指望以后不用检索。
- 把客服聊天记录不经清洗当检索文档。
- 要 JSON 稳，第一反应去微调。
- 检索到 3 条好评范例，汇报成「我们已经微调过了」。
- 把用户长期记忆、公司手册、模型脾气当成一件事。
- 密钥 / 薪资表进训练集，以为删文件就没了。
- 用第 3 条的余弦分数代替选型：尺子对了，路仍可能选错。

## 决策卡（需求 3/5/9/11/12/14 · step-5 已用 sub-page 落地）

> step-5/6/7 已开 8 / 3 / 1 个 sub-page 落地（详见「Demo 子节进度」表）：需求 3 风格稳 / 9 检索 ≠ 微调 / 11 隐私 / 12 能力边界 / 13 检索 ≠ 微调 / 变体 9 成本对照 / 14 人在回路 → step-5 决策卡 sub-page；需求 6「不该检索」→ step-6 三种流程 sub-page；需求 5「混合」→ step-7 混合 pipeline sub-page。下面是 MD 文字版的决策卡（与 sub-page 互为补充：sub-page 看对照表 + 反例，文字看原则 + 取舍）。

### 需求 3 · 风格稳 → 才考虑微调（不先上微调）

- **先别上微调的格式问题**：只要 JSON 字段稳，先走**结构化输出**（Structured Output，模块 04）—— 那是协议层约束，不是改权重。
- **JSON 字段稳 + 字段名要改**：结构化输出不达标 → 走微调（但前提是数据量大 + 字段稳定）
- **反例**：为了「让模型返回 `{status: "ok"}`」去训一场微调 → 浪费钱，结构化输出 + Zod 一行搞定

### 需求 5 · 混合：知识走 RAG + 口吻走 system

- **生产里最常见的不是二选一**：政策来自检索 + 口吻来自 system（先道歉、再结论、再依据）
- **step-2 已是混合的最小版**：检索 + 少样本同时用，事实层（检索）+ 口吻层（system + 范例）分开管
- **真正的混合模板**：
  ```text
  system = 品牌口吻约定 + 3 条范例 + 检索命中的切块
  user   = 用户问题
  ```
  → 既能查政策，又能按品牌说话
- **不要为了「混合」硬拆两套** —— 单条 system 拼一起就行

### 需求 9 · 检索范例当少样本 ≠ 已微调

- **检索 3 条好评当少样本**：从历史好评里抽出 3 条塞进 system —— 少样本（few-shot），**权重没改**
- **跟微调的本质区别**：

| | 检索范例当少样本 | 微调 |
| -- | -- | -- |
| 改什么 | 这一次输入的 system | 模型权重（几亿 ~ 浮点数） |
| 持久性 | 调用结束就没了 | 永久 |
| 改的口吻 | 这次会话 | 这次 + 以后所有调用 |

- **反例**：把「检索 3 条好评当少样本」汇报成「我们微调过了」—— 失真；范例一旧，口吻跟着旧，你还以为「模型版本」坏了

### 需求 11 · 隐私：进权重当删不掉

- **禁入训练集的素材**：内部薪资表 / 密钥 / 未发布的人事纪要 / 客户未公开合同
- **删文档 vs 撤回权重**：

| | 检索增强生成的「从库里删文档」 | 微调的「从权重撤回」 |
| -- | -- | -- |
| 能不能做到 | ✅ 一行删 | ❌ 几乎做不到 |
| 留不留统计 | 不留（删除即消失） | 留（权重里统计痕迹删不掉） |

- **生产原则**：选微调前必过一道「这份数据放进去就当撤不回」审查
- **类比**：检索文档 = 借阅室的书，下架即不可借；微调权重 = 在你脑子里的记忆，灌进去就拔不出

### 需求 12 · 能力边界：检索不教新流程，微调不灌会过期的事实

- **检索不教新流程**：模型本来不会「按你们司审批流程图一步一步追问」，把流程图 PDF 切进去，**模型仍可能一次问完或跳步** —— 这是**行为 / 流程**，需要工作流（后续模块）或微调
- **微调不灌会过期的事实**：模型不是不会解释退货，是不知道你们现在几天 —— 这是事实，用 RAG
- **所以**：**行为 / 流程问题** → 微调 或 工作流；**事实 / 政策问题** → RAG
- **不要用 RAG 解决流程问题**（失败模式：模型仍按默认顺序处理）

### 需求 14 · 两者都不够：转账 / 删库 / 改生产配置

- **这些不是检索增强生成或微调能单独收口的**，要**人点头**（人在回路里，Human-in-the-loop）
- **典型场景**：转账（涉及钱）、删数据库（不可恢复）、改生产配置（影响线上）、开权限（涉及安全）
- **RAG / 微调能做的**：提供信息 / 给决策建议；**最终动作仍要人确认**
- **不要做的反例**：把「转账」做成 Tool 让模型自己调 → 模型编一个金额你就转了
- **详细机制**不在本条展开 —— 后面的模块（人在回路 / 工具网关）会讲
