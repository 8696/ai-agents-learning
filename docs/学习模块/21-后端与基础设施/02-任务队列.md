### 是什么

**任务队列（Task Queue）** 是把**「提交任务」和「执行任务」**解耦的异步模式——客户端提交任务后**立刻收到一个 task_id**，任务在**后台 worker 里慢慢执行**，客户端通过 task_id 查进度或拿结果。

#### 为什么不能同步

**HTTP 请求有硬性超时边界**：

| 环节 | 默认超时 | 长任务会发生什么 |
|------|----------|------------------|
| **浏览器 fetch** | 无超时（默认挂着）/ 用户会关 | 用户以为卡死 |
| **Nginx** | `proxy_read_timeout` 60s | 60 秒后断流 |
| **Cloud Run / Lambda** | 平台限制（5~15 分钟） | 超过被强杀 |
| **用户耐心** | 5~10 秒 | 用户刷新页面 |

**同步流程**：客户端发请求 → 服务端跑 10 分钟 → 中间任何环节超时都崩。
**异步流程**：客户端发请求 → 服务端**立刻**返回 task_id → 客户端用 task_id 查进度 → 跑10 分钟不占连接。

#### 任务队列的三件套

```
┌──────────┐       ┌──────────┐       ┌──────────┐
│ Producer │ ─────► │   Queue  │ ─────► │  Worker  │
│ (API)    │ push │  (Redis)  │  pull  │ (后台进程) │
└──────────┘       └──────────┘       └──────────┘
     │                                       │
     ▼                                       ▼
┌──────────┐                          ┌──────────┐
│  Client  │ ◄────── 轮询 / WS ────── │ 存储   │
│ (前端)   │  查 task_id 进度         │ (状态)  │
└──────────┘                          └──────────┘
```

- **Producer**：把任务塞进队列（带 task_id）
- **Queue**：持久化任务（Redis / DB / SQS）
- **Worker**：从队列拉任务执行，更新状态
- **Storage**：任务状态持久化（pending / running / completed / failed）
- **Client**：用 task_id 查进度（轮询 或 WebSocket）

一句话：**任务队列 = 「提交立刻返回 + 后台慢慢做 + 异步拿结果」——把 HTTP 同步请求的时间边界问题彻底解掉**。

### 为什么（Agent 开发要懂）

Agent 时代的任务特别长：

- **多步推理**：Agent Loop跑 5~10 轮 LLM 调用 → 几分钟到几十分钟。
- **代码生成 + 测试**：写代码 → 跑测试 → 修 bug → 再跑 → 几分钟。
- **长文档总结**：100K tokens文档分块总结 → 几分钟。
- **RAG 检索 + 生成**：检索 + 重排 + 生成 → 几十秒。

具体后果（举四个最常见的）：

1. **同步请求超时**：用户发「帮我写一篇文章」→ 服务端跑 5 分钟 → Nginx60s 断流 → 用户看不到结果 → 重新提交 → **重复扣费**。
2. **客户端刷新页面**：用户提交任务后等了 30 秒没动静 → 刷新 → 重新提交 → 服务端跑两份 → **资源翻倍**。
3. **服务器被长任务堵死**：5 个长任务同时跑 → 第 6 个任务连提交都进不来 → **服务雪崩**。
4. **没有重试机制**：worker 临时挂掉 → 任务永远 pending → 用户等不到结果。

Agent 不上任务队列 = **长任务必崩**。

### 易混点

任务队列常被和它的「邻居机制」混淆。**判错任何一个会让异步失效**——必须分清。

#### 任务队列 vs 消息队列（MQ）

| | 任务队列 | 消息队列 |
|---|---|---|
| **目的** | **执行任务**（一、两种任务） | **通信**（多 topic 解耦） |
| **典型工具** | BullMQ / Celery / Sidekiq | RabbitMQ / RocketMQ / Kafka |
| **任务追踪** | **详细**（状态 /进度 / 结果） | 通常**没有**（fire-and-forget） |
| **适合** | Agent 任务 / 后台作业 | 微服务通信 / 事件流 |

**判错会怎样**：用 Kafka 跑 Agent 任务 → 任务追踪要自己造；用 BullMQ 跑微服务通信 → 没有 topic 路由。

#### 任务队列 vs 流式输出（SSE）

| | 任务队列 | SSE 流式 |
|---|---|---|
| **客户端体验** | 提交后等几秒拿到完整结果 | **边生成边推**（用户看着字出来） |
| **延迟** | 高（任务做完才返回） | 低（第一个 chunk 1~3 秒） |
| **HTTP 连接** | 立刻返回 task_id | 长连接挂着 |
| **适合** | 长任务（5 分钟+） | 短任务（1~3 分钟） |

**判错会怎样**：30 秒任务用 SSE 流式 → 不需要任务队列；10 分钟任务用 SSE → HTTP 连接早就断了。

#### 任务队列 vs 定时任务（Cron）

| | 任务队列 | Cron 定时任务 |
|---|---|---|
| **触发** | **用户主动提交**（API / 事件） | **定时触发**（每天 8 点） |
| **关系** | 队列适合「不确定何时触发」 | 定时适合「确定何时触发」 |
| **可以结合** | 队列跑「现在要做」；Cron 跑「每天做」 | — |

**判错会怎样**：用 Cron 跑用户任务 → 用户等 1 小时才执行（因为下次 Cron 才触发）；用队列跑定时任务 → 队列为空时任务卡死（没人触发）。

#### 轮询 vs WebSocket 推送

| | 轮询 | WebSocket 推送 |
|---|---|---|
| **延迟** | 高（按 polling interval） | 低（实时） |
| **资源** | 反复发请求 | 长连接 |
| **适合** | 任务进度（秒级延迟可接受） | 实时通知（毫秒级延迟要求） |
| **实现** | 简单 | 复杂 |

**判错会怎样**：用 WebSocket 推5 秒定长的任务进度 → 过度投入；用轮询推「有新消息」实时通知 → 用户看到通知时已经是几秒前了。

#### BullMQ vs SQS

| | BullMQ | SQS |
|---|---|---|
| **托管** | 自托管（Redis） | AWS 托管服务 |
| **依赖** | Redis | 无（AWS 提供） |
| **特性** | 优先级 / 速率限制 / 重试 | 标准 / FIFO / DLQ |
| **成本** | 服务器 + Redis | 按请求数计费 |
| **适合** | 中小规模 / 自托管 | 大规模 / AWS 生态 |

**判错会怎样**：自托管用 SQS → 离不开 AWS；AWS生态用 BullMQ → 多一层 Redis 维护成本。

### 核心概念（变体 / 分支全扫）

任务队列有 10 个变体。

#### 1. 同步 vs 异步的根因

**HTTP 请求的硬性超时边界**（详「是什么」）：

```
同步流程：
  Client ──request──► Server ──跑 10 分钟──► Client
                        ↑
                   中间任何超时都崩

异步流程：
  Client ──submit──► Server ──立刻返回 task_id──► Client
                       │
                       └─► Queue ──► Worker ──跑 10 分钟
                                  │
                                  └─► 存结果 Client ──轮询 / WS──► Server ──查 task_id──► Client
```

**例子**：餐厅叫号（任务队列）拿号走人，做好叫回来；现场排队（同步）占着位置不走。

**需求 1（同步 vs 异步对比）**：同一长任务分别用同步 / 异步实现；对比客户端体验 + 服务端资源占用。

#### 2. 常见队列选型

| 队列 | 依赖 | 特性 | 适合 |
|------|------|------|------|
| **BullMQ** | Redis | 优先级 / 重试 / 速率限制 | Node.js 中小规模 |
| **Celery** | Redis / RabbitMQ | Python 生态成熟 | Python Agent |
| **Sidekiq** | Redis | Ruby 生态 | Ruby 栈 |
| **SQS** | AWS | 托管服务 | AWS 大规模 |
| **Pub/Sub** | Redis / GCP | 实时推送 | 简单通知 |

**例子**：快递柜（队列）把东西放柜里你下班拿；送货上门（同步）必须等在门口。

**需求 2（队列选型）**：根据技术栈 + 规模 + 运维成本选定一个队列；落地完整任务流。

#### 3. 任务状态机

任务生命周期：

```
 submit start done
pending ──────► running ──────► completed
                    │
                    │ fail
                    ▼
                 failed ──── retry（最多 N 次）──► pending
                    │
                    │ fail N 次
                    ▼
                  dead（进 DLQ）
```

**状态持久化**：任务状态必须**落 Redis / DB**，不能只在内存。

**例子**：外卖订单（任务）状态——已下单 /制作中 / 配送中 / 已送达。

**需求 3（任务状态机）**：实现 5 状态状态机；状态落 Redis；状态变更打日志。

#### 4. 进度轮询

**客户端查进度**：

```http
GET /tasks/{task_id}
→ { "status": "running", "progress": 0.6, "result": null }
```

**轮询策略**：
- 简单轮询：每 1~2 秒查一次
- 指数退避：失败 / 完成后拉长间隔

**需求 4（进度轮询）**：实现 `GET /tasks/{task_id}` 端点；返回状态 + 进度 + 结果。

#### 5. WebSocket 进度推送

**实时推送**：服务端在状态变更时主动推给客户端。

```js
// 服务端
ws.send(JSON.stringify({ task_id, status: "running", progress: 0.6 }));

// 客户端
ws.onmessage = (e) => updateUI(JSON.parse(e.data));
```

**适合**：进度条要动态更新 / 实时通知。

**需求 5（WebSocket 进度推送）**：实现「状态变更 → 推 WebSocket」；客户端实时更新进度条。

#### 6. 幂等性

**任务可能被重复执行**：
- Worker 处理到一半挂掉 → 重启后队列重投
- 队列重试机制 → 同一任务跑多次
- 用户重复点击 → 同一任务提交多次

**幂等要求**：任务**跑多次和跑一次结果一样**。

| 实现 | 例子 |
|------|------|
| **自然幂等** | 读操作 / set 操作 |
| **业务幂等** | 「退款 100 元」带 `idempotency_key`，已退过就不退 |
| **状态机幂等** | 「状态 = A 时才能转 B」，已转过就跳过 |

**需求 6（任务幂等）**：实现「带 idempotency_key」的任务；重复提交不重复执行。

#### 7. 重试策略

**任务失败怎么重试**：

| 策略 | 怎么做 |
|------|--------|
| **指数退避** | 1s → 2s → 4s → 8s → ... |
| **最多 N 次** | 默认3 次；超 N 进死信队列 |
| **可重试错误** | 网络错 / 5xx / 超时 |
| **不可重试错误** | 4xx 业务错 / 数据格式错（直接进 DLQ） |

**需求 7（重试策略）**：实现指数退避 + 最多 3 次 + 可重试 / 不可重试分类。

#### 8. 优先级队列

**不同任务不同优先级**：

| 优先级 | 任务 |
|--------|------|
| **高** | VIP 用户任务 |
| **中** | 普通用户任务 |
| **低** | 后台批处理 / 数据导出 |

**BullMQ 优先级**：1（最高）~ 10（最低）。

**需求 8（优先级队列）**：实现三档优先级；高优先级先消费。

#### 9. 死信队列（DLQ）

**重试 N 次还失败的任务** → 进死信队列 → 人工干预。

**DLQ 不是 run-away**：

```
task ────► retry1 ────► fail retry 2 ────► fail
                       retry 3 ────► fail ▼                         DLQ（人工查）
```

**需求 9（DLQ）**：失败3 次的任务进 DLQ；DLQ 单独端点查；告警通知。

#### 10. 监控与告警

**队列运行指标**：

| 指标 | 怎么算 |
|------|--------|
| **队列长度** | 当前 pending 任务数 |
| **任务延迟** | submit → start 等待时间 |
| **任务时长** | start → done 执行时长 |
| **失败率** | failed / total |
| **DLQ 长度** | 当前 dead任务数 |

**告警规则**：队列长度 > 1000 / 失败率 > 5% / DLQ 长度 > 10。

**需求 10（监控告警）**：实现 5 类指标 + 告警规则；命中时通知（Slack / 邮件）。

### 例子

#### 餐厅叫号 vs 现场排队

餐厅叫号（任务队列）拿号走人，做好叫回来 → 现场排队（同步）占着位置不走。

对应：**任务队列让客户端不用死等**。

#### 快递柜 vs 送货上门

快递柜（队列）把东西放柜里你下班拿 → 送货上门（同步）必须等在门口。

对应：**异步投递 = 投递端和接收端解耦**。

#### 邮件 vs 即时通讯

邮件（队列）发完就走，对方慢慢看 → 即时通讯（同步）等对方在线。

对应：**不同延迟需求选不同机制**。

#### 长 Agent 任务

用户让 Agent 写一篇文章（5 分钟）→ 同步实现：HTTP 5分钟后返回（Nginx 早就断了）→ 异步实现：立刻返回 task_id，后台跑 5 分钟。

对应：**Agent 长任务必须异步化**。

#### Worker 重启

Worker跑到一半挂掉 → 重启 → 队列把任务重新投给另一个 Worker → 任务幂等性保证不重复扣费。

对应：**任务幂等性是基础**。

#### 死信队列人工干预

「退款」任务重试 3 次都失败（支付 API 5xx）→ 进 DLQ → 工程师查日志 → 发现支付 Key 过期 → 换 Key → 重投任务。

对应：**DLQ 是任务的兜底**。
