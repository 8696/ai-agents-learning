### 是什么

本节讲两件事：**对象存储**（文件落哪）+ **RBAC**（谁能调什么）。

#### 对象存储

**对象存储（Object Storage）** 是**专门存海量文件的存储系统**——和传统文件系统 / 数据库二进制字段（BLOB）相比，它有三大特征：

| 特征 | 文件系统 | 数据库 BLOB | 对象存储 |
|------|----------|-------------|----------|
| **容量** | 单机有限 | 受 DB 限制 | **无限**（横向扩展） |
| **成本** | 中 | 高（DB 贵） | **低**（几分钱 / GB / 月） |
| **访问** | OS API | SQL | **HTTP API**（REST） |
| **适合** | 系统文件 | 小文件（< 1MB） | **大文件 / 任意大小** |

**核心**：对象存储用 **HTTP RESTful API**（`PUT /objects/xxx` / `GET /objects/xxx`）访问，不挂载文件系统；天然适合**分布式 / 高可用 / 无限扩展**。

#### RBAC（Role-Based Access Control）

**RBAC** 是**基于角色的访问控制**——用户 → 角色 → 权限：

```
用户（alice）──► 角色（VIP 用户）──► 权限（read:order / write:refund / tool:send_email）
```

**三层模型**（最简也最常用）：

- **用户**：谁能做事的实体
- **角色**：一组权限的集合（命名 + 可复用）
- **权限**：具体能做一件什么事

一句话：**对象存储 = 「文件落哪」的基础设施；RBAC = 「谁能调什么 Tool」的基础设施——两件事一起做 = Agent 生产化的资源 + 权限底盘**。

### 为什么（Agent 开发要懂）

Agent 处理大量**文件** + 处理多个**用户角色**：

- **RAG 文档**：用户上传 PDF / Word → 需要存 +解析 +检索 → **大文件**
- **图片 / 音频生成**：Agent 生成10MB 图片 / 1 分钟音频 → **大文件**
- **代码仓库分析**：导入 Git 仓库 → 几十 MB 到 GB → **大文件**
- **多用户多角色**：VIP 用户能退款，普通用户不能 → **角色差异**

具体后果（举四个最常见的）：

1. **文件落 DB BLOB**：用户上传 100MB PDF → DB 备份文件 100GB → DB 慢到崩 → 必须迁到对象存储。
2. **文件直接放服务器磁盘**：用户上传 1 万个文件 → 服务器磁盘满 → 备份噩梦 → 必须对象存储。
3. **所有人都能退款**：没用 RBAC → 普通用户也能调 refund Tool → **财务崩**。
4. **角色硬编码在代码里**：「if (user.role === 'vip') return refund()」→ 100 个 Tool 要写 100 个 if → 必须 RBAC 中间层。

Agent 上生产 = **文件落对象存储 + Tool走 RBAC**，否则不可扩展。

### 易混点

对象存储 + RBAC 常被和它们的「邻居机制」混淆。**判错任何一个会让资源 / 权限失控**——必须分清。

#### 对象存储 vs 文件系统

| | 对象存储 | 文件系统 |
|---|---|---|
| **访问协议** | HTTP REST | OS API（`open` / `read`） |
| **挂载方式** | 不挂载 | `mount` 到 OS |
| **容量** | **无限**（横向扩展） | 单机有限 |
| **适合** | 海量文件 + Web | 系统文件 + 单机 |

**判错会怎样**：用文件系统存 Agent 上传的文件 → 服务器磁盘满 → 备份难 → 横向扩展困难。

#### 对象存储 vs CDN

| | 对象存储 | CDN |
|---|---|---|
| **角色** | **源**（文件存在这里） | **加速层**（缓存就近分发） |
| **关系** | CDN 通常**回源**到对象存储 | 对象存储 + CDN = 标准组合 |
| **流量** | 存储流量便宜 | CDN 流量稍贵但快 |

**判错会怎样**：把 CDN 当对象存储 → 文件丢了找不回；把对象存储当 CDN → 用户访问慢。

#### 公网桶 vs 私有桶

| | 公网桶 | 私有桶 |
|---|---|---|
| **访问** | **任何人**都能 GET | 需**签名 / 鉴权**才能访问 |
| **适合** | 公开图片 / 静态资源 | 用户文件 / 私密数据 |
| **风险** | 任何人能列桶内容（**永远不要**） | 配置错 = 文件公开 |

**判错会怎样**：默认开公网 → 用户上传的文件被搜索引擎索引 → 隐私泄露。

#### RBAC vs ABAC

| | RBAC（角色） | ABAC（属性） |
|---|---|---|
| **决策依据** | 用户角色 | 用户属性 + 资源属性 + 环境属性 |
| **灵活度** | 中（角色变化要改） | 高（条件组合） |
| **复杂度** | 低（简单三层） | 高（要写策略引擎） |
| **适合** | 大多数场景 |复杂合规场景 |

**判错会怎样**：简单场景用 ABAC → 过度投入；复杂合规场景用 RBAC → 灵活度不够。

#### API 层权限 vs Tool Gateway 权限 vs DB 行级权限

| | API 层 | Tool Gateway | DB 行级 |
|---|---|---|---|
| **粒度** | 粗（按端点） | 中（按 Tool） | 细（按行） |
| **适合** | 「能不能调这个端点」 | 「能不能调这个 Tool」 | 「能不能看这条数据」 |
| **叠加** | 必须**三层叠用** | 单独一层不够安全 | — |

**判错会怎样**：只靠 API 层权限 → 用户能调 Tool 但看不到自己的数据；只靠 DB 行级 → Tool Gateway 鉴权失效 → **越权 Tool 调用**。

### 核心概念（变体 / 分支全扫）

对象存储 + RBAC 有 10 个变体。

#### 1. 文件存储的本质选择

**为什么大文件必须对象存储**：

| 存储 | 单文件大小 | 成本 | 备份 | 横向扩展 |
|------|------------|------|------|----------|
| **DB BLOB** | < 1MB 还好 | **高**（DB 内存贵） | 难（DB 备份巨大） | 难 |
| **本地文件** | < 10GB 还好 | 中 | 中（rsync） | 难（要 NFS） |
| **对象存储** | **任意**（PB 级） | **低** | **易**（服务内置） | **易**（内置分片） |

**例子**：仓库（对象存储）无限大 + 便宜 + 找东西方便；家里衣柜（DB）放太多乱套。

**需求 1（文件存储选型）**：对比 DB BLOB / 本地文件 / 对象存储三种；用100MB 文件做性能 +成本对比。

#### 2. 对象存储落地

| 服务 | 厂商 | 价格 | 适合 |
|------|------|------|------|
| **AWS S3** | AWS | $0.023/GB/月 +流量 | AWS 生态 |
| **阿里云 OSS** | 阿里云 | ¥0.12/GB/月 + 流量 | 国内 / 阿里云生态 |
| **七牛 Kodo** | 七牛 | ¥0.16/GB/月 + 流量 | 国内 / 直播 / 图床 |
| **Cloudflare R2** | Cloudflare | $0.015/GB/月 + **零出口流量** | 全球分发 + 节省流量 |
| **自建 MinIO** | 自托管 | 服务器成本 | 自托管 / 数据主权 |

**需求 2（对象存储落地）**：选定一个对象存储；上传文件 → 拿 URL → 删除文件 完整链路跑通。

#### 3. 文件上传流程（前端直传）

**两种上传方式**：

```
方式 A：前端 ──upload──► 后端 ──upload──► 对象存储
         （占用后端带宽 + CPU）

方式 B：前端 ──presigned URL──► 后端
         ◄──URL──
         ──upload──► 对象存储（不走后端）
```

**方式 B 是主流**——后端只生成签名（轻量），文件直接从浏览器传到对象存储（不占后端）。

**例子**：餐厅厨房（后端）只签菜单（presigned URL），客人直接到食材仓库（对象存储）取货（上传）。

**需求 3（前端直传）**：实现 presigned URL 流程；前端直传对象存储；后端不碰文件流。

#### 4. 访问控制（presigned URL）

**私有桶不能让用户直接 GET**——必须用 **presigned URL**（带临时签名）：

```http
GET /bucket/private.pdf?X-Amz-Signature=xxx&X-Amz-Expires=300
→ 临时 URL，5 分钟内有效
```

**核心参数**：

| 参数 | 含义 |
|------|------|
| `expires` | URL 有效期（默认 15 分钟，可调到 7 天） |
| `method` | GET（下载） / PUT（上传） |
| `path` | 哪个文件 |

**需求 4（presigned URL）**：实现上传 / 下载 presigned URL；验证过期时间生效。

#### 5. CDN 加速 + 签名 URL

**生产架构**：

```
用户 ──CDN──► 对象存储 （CDN 缓存 + 回源）
```

**两种 CDN 策略**：

| 策略 | 做法 |
|------|------|
| **公开桶 + CDN 缓存** | 文件公开 + CDN 缓存 + 长期缓存 |
| **私有桶 + CDN 签名** | CDN 节点也走签名（部分厂商：CloudFront signed URL） |

**例子**：外卖仓库（对象存储）→ 外卖骑手（CDN）就近配送 → 客人（用户）拿到快。

**需求 5（CDN 加速 + 签名）**：配置对象存储 + CDN；验证 CDN 缓存 + 签名 URL 生效。

#### 6. 元数据与检索

**对象存储不只是文件**——还能存**元数据（metadata）**：

```http
PUT /bucket/file.pdf
x-amz-meta-user: alice
x-amz-meta-tags: ["合同", "2024"]
x-amz-meta-source: "agent_upload"
```

**元数据 vs 标签**：
- **元数据**：和文件绑定的自定义键值对
- **标签**：对象存储内部的索引键（部分厂商支持）

**例子**：酒店房间（文件）+ 房间卡（metadata：VIP / 禁烟 / 朝南）。

**需求 6（元数据 + 标签）**：上传时设 metadata；按 metadata 检索文件。

#### 7. RBAC 三层模型

**用户 → 角色 → 权限**：

```
用户 alice ─► 角色 VIP ─► 权限 [read:order, write:refund, tool:send_email]
                 │
                 └────► 权限 [read:report, tool:export_data]
                 
用户 bob ────► 角色 普通用户 ─► 权限 [read:own_order, tool:view_profile]
```

**核心数据表**（最简）：

```sql
users（用户表）
roles（角色表）
permissions（权限表）
user_roles（用户-角色，多对多）
role_permissions（角色-权限，多对多）
```

**例子**：公司门禁卡（角色）能进所有部门；酒店房卡（权限）只能进自己房间。

**需求 7（RBAC 三层模型）**：实现 users / roles / permissions 三张表 + 关联表；可增删改查。

#### 8. RBAC 决策点（API / Gateway / DB）

**三层权限叠加**：

| 层 | 决定 | 例子 |
|------|------|------|
| **API 层** | 端点能不能调 | `/api/refund` 要 VIP 角色 |
| **Tool Gateway** | Tool能不能调 | `refund` Tool 要 `payment.refund` scope |
| **DB 行级** | 数据能不能看 | 用户只能看自己的订单（`WHERE user_id = :current_user`） |

**例子**：小区门禁（API 层）+ 单元门禁（Tool Gateway）+ 自己家锁（DB 行级）——三层都过才进得去。

**需求 8（RBAC 决策点）**：实现三层权限叠加；越权时全部拦截。

#### 9. 多角色权限合并

**用户可能多个角色**——权限要**合并**（union）：

```
alice: VIP + 测试员
权限 → VIP权限 ∪ 测试员权限
```

**关系**：union（取并集）/ intersection（取交集）/ deny优先。

**大多数场景用 union**——任一角色有权限就能调。

**例子**：一个人既是 VIP（公司角色）又是健身教练（兼职角色）→ 能进 VIP 区 + 健身房。

**需求 9（多角色权限合并）**：实现多角色用户；权限 union 合并。

#### 10. 权限审计日志

**每次权限决策留痕**：

| 字段 | 含义 |
|------|------|
| `user_id` | 谁请求的 |
| `role` | 当前角色 |
| `permission` | 申请权限 |
| `granted` | 通过 / 拒绝 |
| `resource_id` | 操作哪个资源 |
| `timestamp` | 时间 |

**例子**：公司门禁刷卡记录——谁几点进的哪个门。

**需求 10（权限审计日志）**：实现权限审计；命中越权时告警。

### 例子

#### 仓库 vs 家里衣柜

仓库（对象存储）无限大 + 便宜 + 找东西方便 → 家里衣柜（DB）放太多乱套。

对应：**大文件必须对象存储**。

#### 公司门禁卡 vs 酒店房卡

公司门禁卡（角色）能进所有部门 → 酒店房卡（权限）只能进自己房间。

对应：**RBAC 是按角色给「能做的事」；不是「能进的所有地方」**。

#### 前端直传 vs 后端中转

前端直传（presigned URL）=客人直接到仓库取货（不经过餐厅厨房）→ 后端中转 = 客人先下单给厨房，厨房再去仓库拿（占用厨房资源）。

对应：**大文件上传走 presigned URL**。

#### CDN 加速 + 签名 URL

外卖仓库（对象存储）→ 外卖骑手（CDN）就近配送 → 客人（用户）拿到快。

对应：**对象存储 + CDN 是标准组合**。

#### 角色合并（VIP + 测试员）

用户既是 VIP 又是测试员 → 权限 = VIP ∪ 测试员。

对应：**多角色权限 union**。

#### 三层权限叠加

小区门禁（API 层）+ 单元门禁（Tool Gateway）+ 自己家锁（DB 行级）——三层都过才进得去。

对应：**任何一层权限失效都越权**。
