### 是什么

大模型每一步生成，是在**词表里挑下一个 token**。挑法不是固定的：模型先算出每个候选 token 的「原始分数」（叫 logits），过一层 softmax 变成概率分布，再从这个分布里**抽样**。`temperature` 和 `top_p` 就是控制「怎么从这个分布里抽样」的两个旋钮。

**Temperature（温度）**：在 logits 进 softmax 之前做一次缩放。`T=1` 不动；`T>1` 把 logits 之间的差距压平，原本「9 分 vs 8 分」会变成「9.1 vs 8.9」，概率分布被拉平、低分 token 也冒头；`T<1` 反过来把差距拉大，最高分 token 几乎垄断。`T=0` 时退化成「每次都选概率最大的」——**贪心解码（greedy decoding）**。

**Top-P（Nucleus Sampling，核采样）**：不直接动 logits，而是改**候选集**。把概率从大到小排，依次累加，累到 ≥ P 就停，剩下的低概率 token 全部丢掉。保留下来的这个「原子核」里，模型仍按**各自剩下的概率**抽（抽完核内会重新归一化），**不是在核里均分、每人 1/N**。P 越小，候选集越小、输出越稳；`P=1` 时等于没过滤。

**Top-K（对照参考，必须会区分）**：固定取概率最高的前 K 个 token。问题是 K 写死了——遇到概率集中的分布，前 K 名之外的好答案被切掉；遇到分布平的分布，前 K 名里又塞了不该留的。所以现在主流推荐 **Top-P 而不是 Top-K**：Top-P 按概率和动态切，更贴合每一步的真实分布。

直觉：**Temperature 改「分布形状」（谁更可能冒头），Top-P 改「候选数量」（让不让冒头）**——两件事各管各的，能各调各的。

多数官方文档（OpenAI *API reference* / Anthropic *sampling parameters* / Hugging Face `generate()`）建议：**默认只动 Temperature，Top-P 留 1**——理由与「何时才动 Top-P」见下方「取舍」节末尾。

### 为什么（Agent 开发要懂）

不懂这两个参数，做 Agent 会在四个地方翻车：

1. **同一个 prompt，调错温度直接翻车**。客服/抽取 JSON 的 Agent 把 Temperature 设为 0.9，模型一会儿返回 `{"status":"ok"}`，一会儿返回 `{"status": "OK"}`（大小写、字段顺序、空格都飘），下游解析全炸。这是稳定性的代价。
2. **抽不到想要的 token ≠ 幻觉**。Temperature 高时模型输出「看起来对但和上一轮不一样」，有人会以为是幻觉。其实不是——幻觉是事实错，温度高只是「换了一种说法」。两件事要分开治。
3. **不能靠「调高 Temperature 让模型更准」**。很多人试「调到 0.3 输出还是不对，再调到 0.7 看看会不会好一点」——错。Temperature 越高输出越花，**准确率不是它的目标**。想要准：换 prompt、换模型、给示例、调工具调用。
4. **可复现性问题**。Temperature=0 常常被当成「完全确定性」的代名词，但浮点累加 + GPU 并行的顺序问题会让两次完全一样的请求返回的 token 顺序在极端边界有微小差异。要「完全可复现」，除了 `temperature=0`，还要把 **seed 也固定**（OpenAI 在部分模型上提供 seed 参数，不是 temperature 的别名）。

### 易混点

| 对比 | 差在哪 | 判错代价 |
| ---- | ------ | -------- |
| **Temperature vs Top-P** | Temperature 改 logits 缩放（**分布形状**）；Top-P 改候选集大小（**采样范围**） | 把两者当成「都能控制随机性，随便挑一个」——同时调到极端会出现「既不稳也不准」的怪现象；多数文档建议**只调一个**，另一个保持默认 |
| **Temperature=0 vs 完全确定性** | T=0 是贪心解码，但**浮点累加**会让极少数边界 case 仍出现微小不一致；要真「完全一致」还要 `seed=固定值` | 以为是 deterministic，做了 1000 次回归测试对账，偶发 1 次不一样就报「线上有 bug」 |
| **Top-P vs Top-K** | Top-P 按概率和动态切；Top-K 写死名次 | Top-K 在分布平的时候丢真候选、在分布集中时硬塞冗余候选；选错的代价是「该出现的好答案没出现」 |
| **温度高 vs 模型更准** | 温度只换「花不花」，**不换「对不对」** | Agent 调温度当准确率旋钮，调来调去准率原地踏步；真正的杠杆是 prompt / few-shot / 工具调用 / 模型选型 |
| **贪心解码 vs 采样** | 贪心永远选概率最大；采样按分布抽样 | 客服场景用贪心（一致即可），生成场景要用采样（贪心会重复字 / 卡句号） |

### 例子

#### Temperature 的生活例子：掷骰子的磁铁

想象模型是「在桌上掷 6 面骰子选数字」：

- **T=0** → 骰子被磁铁吸住，永远 6 朝上（贪心）。
- **T=0.3** → 磁铁比较强，6 朝上的概率 80%，5 占 15%，其他几个加起来 5%。
- **T=1.0** → 没磁铁，纯靠掷，6 个面都是 1/6。
- **T=1.5** → 你手抖了，骰子飞太远偶尔弹回来变成奇怪的姿态——选到了平时选不到的小概率面。

客服场景里你**不想要冒险**，所以磁铁拉满（T 低）；写营销文案你想要「各种花样」，所以松手（T 高）。

#### Top-P 的生活例子：餐厅点菜的「前 N 道招牌」

朋友请你吃饭，菜单 50 道菜：

- **P=0.3** → 餐厅经理说「客人都点前 3 道招牌菜」（概率最高的那 3 道），你只能从这 3 道里挑——很稳，但很无聊。
- **P=0.9** → 「客人 90% 都会点这些」——服务员把「前 90% 概率的菜」圈成一个池子，可能 8 道、可能 15 道，看每道菜的「号召力」。你在里面挑时，招牌菜仍然比边角料更容易被点到（按剩下的概率抽，不是 8 道菜均分）。
- **P=1.0** → 整个菜单 50 道随便点（等于没过滤）——可能踩雷。

这是「按概率和动态切」——**不是写死几道菜**，而是看哪几道「真正有人点」。

#### 同时调两参数的对比例子

同一个 prompt：**「用一句话向 5 岁小孩解释 Transformer」**，跑 5 次：

- **T=0, P=1（贪心）**：5 次一模一样：「Transformer 就像一个会读句子的小机器人……」（一致但可能僵）
- **T=0.7, P=0.9（推荐默认）**：5 次里有 3 种说法，意思都到位，措辞不同（**该有的随机**）
- **T=1.5, P=0.5（又高又窄）**：候选只有 5 个但分布被压平——奇怪说法冒出来，**既不准确也不稳定**（同时调极端的代价）
- **T=0.7, P=0.3（推荐温度 + 严候选）**：候选被砍到 2–3 个 + 温度中等——输出稳，但容易「翻来覆去就那 2 句话」（适合客服，不适合创作）

**结论**：多数场景下**只调一个就够**——抽取场景把 T 拉低（不调 P），创意场景把 T 拉高（不调 P）。同时拉两个还要拉到极端 = 在跟自己过不去。

#### Top-K vs Top-P 的前端例子：名单筛选 vs 投票比例

- **Top-K=40**：固定取前 40 名候选人参加面试。问题：如果这一届候选人普遍都很强（概率集中），前 40 名之外的都很好；下一届候选人普遍很菜，前 40 名之内还混了不少差的。**K 是死的，候选人质量是变的**。
- **Top-P=0.9**：要求「所有能进面试的人加起来，得票要占 90%」。这一届可能只取 12 个，下一届可能取 35 个。**跟着候选人质量走**。

这就是为什么主流推荐 Top-P——它自适应。

#### 追问补例：为什么是「先 T 后 P」——三个类比

学习者追问「多数文档建议只调一个，是调哪个，为什么」之后补的三个生活 / 前端例子，对应「Temperature 是主菜、Top-P 是配菜」这条主线：

**① 做饭：盐 vs 食材种类**
- Temperature = 盐（控味道的本质）。盐加多加少，味道立刻有规律变化。
- Top-P = 食材种类（控可选范围）。选贵的食材还是便宜的，会影响菜品。
- **顺序：先调盐（Temperature）保证味道大致对，再决定食材范围（Top-P）**。盐一乱，再好的食材也救不回来；两边同时乱调，做出来的东西八成不是人吃的。

**② 摄影：曝光 vs 滤镜**
- Temperature = 曝光（影响全局亮度）。曝光对了照片大致能看。
- Top-P = 滤镜（影响风格）。滤镜再花，曝光错了也救不回来。
- **顺序：先调曝光（Temperature）保证画面可看，再决定要不要加滤镜（Top-P）**。

**③ 前端组件库：主题 vs 配色范围**
- Temperature = 主题色系（蓝 / 绿 / 灰——全局风格）。主题定不下来，整个页面飘。
- Top-P = 允许的色相范围（Hue 拉多宽）。范围再花，主题不定也乱。
- **顺序：先定主题（Temperature）保证品牌一致，再决定配色范围（Top-P）是否需要**。

### 我追问过的

- 问了：多数文档建议只调一个，是调哪个，为什么？ → 答在「是什么」节末句（多数官方文档建议默认只动 T）+「取舍」节末尾「什么时候才动 Top-P」块 + 上面「例子」节末尾的 3 例（做饭 / 摄影 / 前端组件库），共同回答「Temperature 是主菜、Top-P 是配菜，先 T 后 P」。OpenAI 官方原话类似 "don't change both temperature and top_p at the same time"——直接点名不要同时改。

### 取舍

| 场景 | 推荐参数 | 为什么 |
| ---- | -------- | ------ |
| **JSON / 抽取 / 分类** | `temperature=0` 或 `0–0.2`，`top_p` 留默认（1）或 0.1 | 下游要稳定解析；任何飘都会让解析器挂 |
| **客服回复 / 模板对话** | `temperature=0.3–0.5`，`top_p=0.9` | 要稳定但又不能完全死板（避免重复） |
| **写文案 / 营销 / brainstorm** | `temperature=0.7–1.0`，`top_p=0.9` | 多样性是产品需求 |
| **SQL 生成 / 代码生成** | `temperature=0–0.2`，`top_p` 默认 | 代码生成错了就跑不起来，稳定优先 |
| **采样任务需要「试试看」** | `temperature=0.7` + **多次采样**，人工/模型挑最好的 | 一次调用解决不了「要多种方案」 |

**结论**：**先用 default**（OpenAI 大模型 `temperature=1, top_p=1`；Anthropic `temperature=1` 且 `top_p` 默认通常关闭）。需要稳 → 把 T 拉低；需要花 → 把 T 拉高。**只在 T 调到极限还不满意时**再碰 Top-P。

#### 什么时候才动 Top-P

只有两种场景会"必须同时调"：

| 场景 | 参数组合 | 为什么 |
| ---- | -------- | ------ |
| **严格锁候选质量**（医疗 / 法律 / 合规）| `T=0` + `P≈0.5` | 等于"只在概率最高的一半里选"，把模型限制在最自信的范围——**宁可少说，别瞎说** |
| **多样但不跑偏**（广告文案 / 博客标题 / 产品命名）| `T=0.7–1.0` + `P=0.9` | 让模型在「前 90% 概率」里自由发挥，**同时**挡掉那 5% 概率的低质 token——创意有了，下限也兜住 |

**一句话总结**：

- **T 调「花不花」**（整体风格）
- **P 调「该不该让某些 token 出现」**（边界控制）
- **顺序：先 T 后 P**——T 是主菜，P 是配菜；主菜先定，配菜再决定加不加。

OpenAI 官方文档原话类似 **"don't change both temperature and top_p at the same time"**——直接点名不要同时改。原因是 Top-P 裁掉低概率 token 后，剩下的会被 softmax 重新归一化，整个分布被重塑，与 Temperature 叠加会引入非线性耦合，工程上很难归因。

### 踩坑

| 错 | 对 | 症状 |
| ---- | ---- | ---- |
| 客服 Agent 把 `temperature=0.9`，理由是「让它答得自然一点」 | 客服/JSON 场景温度低（0–0.3） | 同一问题返回的 JSON 字段顺序、大小写、空格每次都飘，下游解析爆炸 |
| 「幻觉太严重，把 temperature 调到 0.2 看看会不会好」 | 温度高 ≠ 准；想要准 → 改 prompt / 换模型 / 上工具 | 调来调去准率原地踏步，时间浪费 |
| 同时 `temperature=1.5` + `top_p=0.3`，觉得「两边都拉一点」 | 只调一个，另一个留默认；或明确组合意图 | 既不稳也不准，「花得离谱 + 候选少」，比单独调一个还差 |
| 把 `temperature=0` 当成「完全 deterministic」做单元测试 | 要「完全可复现」还得 `seed=固定`（OpenAI 部分模型支持） | 偶发一次对不上 → 报「线上有 bug」 → 实际是浮点累加边界 |
| JSON 抽取场景里只调了 `top_p=0.1`，温度默认 1 | 抽取/JSON 主要靠温度控稳定性，Top-P 是辅助 | 没解决乱序/飘字段的问题 |
