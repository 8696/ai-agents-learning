# **Context Window**：一次请求里输入 + 输出共享的长度上限

> 对应模块：[模块 01 · AI & LLM 基础认知](./README.md) · 小节进度第 3 条

- **来源**：本对话（陪跑 Coach）；现象引用 Liu et al. 2023 *Lost in the Middle*（[arXiv:2307.03172](https://arxiv.org/abs/2307.03172)）。本条对话未打开外部页面。
- **状态**：已沉淀
- **Demo**：伪代码（见机制）（超限后截断/摘要是步骤，不值得为演示去打爆窗口）
- **回填**：无（本模块代码落点是笔记即可）

### 是什么

**Context window = 这一次请求里模型能「看见」的所有内容的总长度上限**，按 token 数算（不是按字数、不是按段落、不是按「页」）。上一条 [Token](./02-Token.md) 讲过——模型读的是一串整数 ID，context window 数的就是这条 ID 序列有多长。

**最关键的一点：输入 + 输出通常共享同一个上限**，不是「输入 100K + 输出无限」。先按「共享总长」估；有的模型会另标很大的 output cap，发出前仍要扣预留输出。教学默认用共享上限。

```text
一次请求 = 系统提示词 + 历史消息 + 用户这一轮的输入 + 工具结果 + 模型要吐出的回复
                                                    ↑
                                            全部加在一起 ≤ context window
```

**前端类比**：`localStorage` 是**源站总配额**（比如 5MB），不是「写 5MB 再另给一份读配额」——prompt 和 completion 挤的是同一条上限。配额满了，浏览器通常是 **`QuotaExceededError` 抛错**，不是默默删别的 key。Chat Completions 一类 API 更接近这个：超了先失败，而不是模型自己偷偷改你的消息。

**和上一条 Token 的关系**：Token 是单位，context window 是上限。链条是：文本 → 切成 token → 序列塞进 window → 模型读这一截，再生成下一截 token。

按 token 算、不要按字估。和 [Token](./02-Token.md) 实测对齐（cl100k 量级，不是精确承诺）：中文大约 1.2 token/字，英文大约 0.26 token/字符 → **128K 大约能塞中文 ~10 万字、英文字符 ~40～50 万**。旧口算「中文 2 token/字 → 5～6 万字、英文 25～30 万」偏紧，不要再用。同一段意思中文切得更碎，同一条 window 里能塞的中文字更少——贵在条数，不是单价。

**一句话总结（向非技术朋友）**：context window 是这一轮能塞进模型的 token 天花板——输入算、输出也算。写 Agent 要自己盯预算；你不管，请求常常直接失败，或者你/产品层先砍了内容你还以为模型读全了。

**生活里怎么理解（再读下面的工程表）**

- **电梯限重**：人和行李一起算。系统提示、历史聊天、工具返回、用户这句、模型还要说的话，全在同一台电梯里。不是「人限重 1000 公斤、行李另外再给 1000」。超重时这栋楼的 Completions 电梯常常**直接拒绝关门**（请求失败），不会自己把你箱子砍一半还装着走。若有人进电梯前把箱子拆了再按按钮，里面的人会以为「电梯运了全部行李」——那是**你先砍的**，不是电梯默默截。
- **会议室只准 8 个人**：注意力是「进来的人可以互相看」；窗口是「门卫只放 8 个」。第 9 个进不来。互看再强也加不出第 9 把椅子。见 [Transformer](./04-Transformer.md)。
- **四种超了还想干活的办法（人话）**：
  - **截断**：书太厚，撕掉后面几章再问「全书讲什么」——快，后半本等于没读。
  - **摘要**：每章先写成半页纪要，再拿纪要开会——主旨还在，细节和数字容易在「调和」里走样。
  - **滑动窗口**：群聊太长，只把最近 20 条带去开会——适合对话流；**不适合**厚合同（前面条款会掉出窗外）。
  - **RAG**：先去书架抽「和这个问题最相关的几页」再开会——适合知识库 / 长合同；**不能**代替「下一句用户还没说出口」的多轮窗口。

下面「是什么」里的 localStorage、四种策略表、Lost in the Middle，是同一套意思的工程版。

### 为什么（Agent 开发要懂）

Agent 不是一次性发个问题等答案。**一次请求里可能包括**：

1. 系统提示词（少则几百、生产里常见几千 token）
2. 历史对话（每轮都加，越聊越长）
3. 工具返回（一个网页 10K、一次查询 50K，**单次就能塞爆**）
4. 当前用户输入（可能附带整份文档）
5. 模型要吐的回复（每生成一个 token 都在挤预算）

**Agent 跑 10 步，每步的 tool 输出都进 context → 涨得飞快**。这是模块 07、模块 11 最痛的工程问题之一。

超了之后**分三层看**，不要混成一句「模型悄悄删」：

| 层 | 常见表现 | 你看到什么 |
|----|----------|------------|
| **Chat Completions 一类 HTTP API**（本路线 MiniMax 协议 A / `openai` SDK） | 服务端先校验：prompt + 预留输出 > 窗口 → **请求失败**（OpenAI 常见 HTTP 400、`context_length_exceeded`；别家文案可能不同） | 「请求失败」，容易当成网络问题 |
| **你自己或产品中间层** | 聊天 UI 丢掉旧消息再发；你 `slice` 了合同再调 API | 用户以为模型读过全文，其实你已经砍过 |
| **训练叙事 / 个别托管能力** | 模型见过超长序列时可能学成某种截断；部分带自动 retrieval 的托管 API 可能在服务端裁内容 | 不要当成 Completions 的默认契约 |

「掐头留尾 / 掐尾留头 / 中间一刀切」描述的是**有人（你或中间层）在砍**之后模型还在流式吐字——吐的是残缺上下文上的续写。Completions **文档会写超长失败**；没写清楚的是各家**聊天产品**怎么丢历史。

**写 Agent 的硬性规矩**：发出前用**对应模型**的 tokenizer 数一遍；预留输出；超了（或预算到 ~80%）就按下面四种策略处理。这是模块 06、模块 11 的种子。

### 易混点

本条四组对比必须搞清；后面模块 06 / 08 / 10 会回来。

#### Context Window vs Memory

| 维度 | Context Window | Memory |
|------|----------------|--------|
| 范围 | 这一次请求 | 跨请求、跨会话 |
| 时长 | 单次请求结束就消失 | 持久化（DB / 文件 / 向量库） |
| 谁管 | 模型侧硬上限（超了 API 常直接失败） | 你自己的代码（写什么、读什么、塞进这次 prompt） |
| 类比 | 函数里的局部变量 | 全局变量 / 数据库 |
| 对应模块 | 本条 | 模块 10 |

**关键区别**：window 是**模型侧物理限制**；memory 是**应用侧设计选择**。模型不知道上次会话——除非你写下来、读出来、塞进这次 context。

#### Context Window vs Output Limit

很多文档同时给两个数字。下面 **4K 是教学假设**，不是 GPT-4o 的真实 output cap（GPT-4o 常见约 **128K 窗口、输出上限约 16K** → 最多大约只能塞 ~112K prompt）。

```text
Context Window:  128K tokens   ← 输入 + 输出共享的总长（教学默认）
Max Output:        4K tokens   ← 单次最多生成多少（这里是假设数字）
```

**Context window** = 共享总上限；**Output limit** = 单次生成上限。估算时**两边都要扣**：

```text
最多能塞的 prompt  ≈  context window − 预留输出（max output）
发出前再检查：      已用 prompt + 预留输出  ≤  context window
还剩多少空位：      context window − 已用 prompt − 预留输出
```

128K 窗口 + 假设 4K 输出 ≠ 能塞 128K prompt，最多约 **124K** prompt。

**本路线 API**：`POST /v1/chat/completions`（及兼容实现）在 prompt + `max_tokens`（或等价字段）超过窗口时，**通常直接报错，不是悄悄截断**。错误码因厂商而异。用户看到的是失败，不是「答错了」。

真正会「悄悄丢」的：你自己拼 prompt 先截了；聊天产品丢掉旧轮次；个别托管 / 自动 retrieval 在服务端裁（Assistants 等已边缘化，细节留模块 02 实测）。

#### 长 Context vs 高质量 Context

| | 长 context | 高质量 context |
|--|----------|----------------|
| 含义 | 塞得多 | 塞得对 |
| 成本 | 贵、慢；中间更难被用上 | 通常更便宜、更快 |
| 准确率 | 中间易被忽略（lost in the middle） | top-K 段更容易被引用 |
| 适用 | 「先把材料都给模型看看」的探索 | 生产、对准确率敏感的 Agent |

工程共识：高质量 context > 长 context。检索 10 段喂入 > 全塞 1M。

#### 截断 vs 摘要 vs 滑动窗口 vs RAG 检索

这四个**不是同一层并列**：

- 截断、摘要、滑动窗口：**已经决定喂这些**，只在 window 里裁
- RAG：**先决定喂什么**，再进 window

RAG 更上游：检索出 10 段，仍可能再摘要或滑动一次控总长。

| 策略 | 实现成本 | 信息保留 | 适用场景 | 对应模块 |
|------|---------|---------|---------|---------|
| 截断 | ★☆☆ | ★★☆ | 暴力应急 | 模块 06 |
| 摘要 | ★★☆ | ★★☆ | 多轮对话 | 模块 06 |
| 滑动窗口 | ★★☆ | ★★★ | 多轮对话 | 模块 06 |
| RAG 检索 | ★★★★ | ★★★★ | 长文档 / 知识库 | 模块 08 |

合同场景见 [例子](#例子)。

**RAG 边界（自测 3）**：不能对**还没发生的下一句用户话**做离线检索——客服这轮说「上周买的鞋」、下轮才给订单号，问题尚未出现。RAG 适合「知识库 → 这一问」；**不要用 RAG 替代多轮窗口管理**。工单、历史会话、退货政策仍可以检索。有公司知识库就对**那部分** RAG；对话流用滑动窗口 + 摘要。

**混搭是常态**，不是「四选一」。见 [取舍](#取舍)。

### 例子

#### 例 0：点外卖把菜单、优惠券、备注一次性塞进对话框

你对店员说的话 = 这一轮请求。菜单全文 + 昨天聊过的口味 + 「不要香菜」+ 店员还要回你的确认短信，全部挤在**同一条字数（Token）上限**里。店员回得越长，你能再贴的菜单越短。群聊软件若在发送前把旧消息删掉，你会以为店员读过三个月前那句「我对花生过敏」，其实那句已经不在这一条短信里——这是 Context ≠ Memory：过敏史要写进档案（模块 10），不能指望窗口自己记得跨天的事。

#### 例 1：10 万字小说塞 128K —— Lost in the Middle

Liu et al. 2023 *Lost in the Middle*：往 context 里塞一堆文档，问模型去引用其中一份。

```text
文档在 context 中的位置     引用准确率
─────────────────────────  ──────────
开头（最前）                ★★★★★  高
中间偏前                    ★★★☆☆  明显降
正中间                      ★★☆☆☆  最低
中间偏后                    ★★★☆☆  回升
结尾（最后）                ★★★★★  高
```

**开头和结尾记得最清，中间容易被忽略**。近年新模型有所缓解，没消失。

全塞一本 10 万字小说时：系统提示在开头较稳；小说中段在正中间最容易被忽略；用户问题在最后、紧邻输出。

**前端类比（避免用 viewport）**：200 个组件**整页都 layout / 算完了**（你付了全部 token、prefill 也慢），只是中间几块用户几乎看不到——不是「没进视口就不 render、可以白嫖」。**全塞进去 ≠ 全用上**；中间那些 token **照样计费、照样算 attention**。

「只检索最相关的 5～10 段再喂」通常优于「全塞 1M」，这是模块 08 的动机。Anthropic *Contextual Retrieval* 讲的是**切块前把上下文写进 chunk、加强检索**，不是同一篇「top-K vs 全塞」实验，不要并成一条证据。

#### 例 2：200K Token 合同 + 128K 窗口

**场景**：合同抽出 200K token；模型按 GPT-4o 量级（窗口 128K）。

**第一步：直接全塞会爆。** `prompt = contract_text + "\n请摘要"` → 200K > 128K。走 Chat Completions：**请求失败**（400 一类），不是模型默默摘要前半段。用户看到的是失败。

**若你方先截断再调用**（例如只留前 128K token）：API 会成功，摘要可能「看起来完整」，后半段条款其实没进模型——**这才是用户不知道漏了的情况**。责任在拼接，不在「GPT-4o 默认悄悄截」。

**第二步：四种策略**

| 策略 | 实现 | 优点 | 缺点 | 适用 |
|------|------|------|------|------|
| **A 截断** | `prompt = contract_text[:能塞进的 token] + "\n请摘要"` | 几行代码 | 后半段全丢 | 不在意完整性 |
| **B 摘要** | 每 ~50K 摘要一次 → 再汇总 | 保留主旨 | 成本高；子摘要矛盾会被「调和」错 | 要主旨不要细节 |
| **C 滑动窗口** | `prompt = contract_text[-能塞进的 token:]` | 一行 | 前面全丢 | **不适用**——单一文档不是对话流 |
| **D RAG** | 切块 + embedding；检索 top 块拼 prompt | 关键片段、不超窗 | 要建库 | **生产默认**（合同不能漏条款） |

**第三步**：生产合同几乎一定 D；早期项目可用 A/B 跑通再升 D。模块 06 管多轮 A/B/C；模块 08 管长文档 D；模块 11 按轮次/长度切换。

#### 例 3：80K 代码库进 128K 找 `parseUser`

**场景**：80K token 的 TS 仓库；窗口 128K。教学上若预留 4K 输出，prompt 预算约 124K，80K 还剩约 44K；按 GPT-4o ~16K 输出则预算约 112K，80K 仍塞得进。

**会不会爆**：不会。**会不会漏调用点**：会，更可能在代码库**正中间**（lost in the middle）。

```text
[开头  ~10K]   import / 常量 / 工具函数
[中间  ~60K]   ★ 业务实现、parseUser 调用集中在这
[结尾  ~10K]   main / export / 框架胶水
```

80K 约占 128K 的 62%，调用点落在中间 60K——模型最弱的引用带。开头/结尾的 import/export 反而记得清。

**全塞 ≠ 全用上（口语 + 机制分开）**：

| | 含义 |
|--|------|
| **口语：注意力被摊薄** | 窗口越长，中间越难被「用上」；不要理解成固定一壶水均分到每个 token |
| **更贴近机制：位置偏置** | 训练里开头/结尾重要更常见，模型沿用 U 型（两端高、中间低） |
| **不是随机 bug** | Lost in the Middle 在多款模型上测到 U 型；新模型缓解但没消失 |

Attention 权重经 softmax 后和为 1，成因留给 [Attention](./05-Attention-Self-Attention.md)。本条记住工程结论即可。

**生产**：按函数/文件切块 → embedding → 问「找 `parseUser`」→ 只喂 top-K 块（模块 08）。

### 取舍

**长 context 的代价**：

| 代价 | 机制 | 影响 |
|------|------|------|
| **贵** | 输入按 token 计费，128K 比 1K 贵约 128 倍 | Agent 多步放大，模块 19 |
| **慢** | prefill 随长度变重；TTFT 上升 | 用户觉得卡 |
| **中间更难被用上** | 系统提示在头、问题在尾，中间很长 | 可能不太听 system；中间引用差 |
| **lost in the middle** | 见例子 | 中间准确率下降 |
| **幻觉风险上升** | 要「调和」互相矛盾的长上下文 | 修法见模块 08 |

四策略：实现成本和信息保留大致同向；应急用截断，生产长文档上 RAG；对应模块 06 / 06 / 06 / 08。

能 1K 解决的事别塞 100K。塞满常常是设计偷懒，不是能力展示。

**实战（自测 3 · 200 轮客服）**：

```text
当前对话历史 ─┐
              ├─→ 滑动窗口（最近 10～20 轮直接保留）
早期对话 ─────┤
              └─→ 摘要（压成 1～2 段 ~500 token）

用户当前输入 ─┐
              ├─→ 拼成 prompt（例如 ≤ 80K，预留 buffer）
公司知识库 ───┘   （有则 RAG top-K；没有就不必）

→ 再设 max output（教学图里写 4K）→ 总长仍留余量
```

- **混搭**：窗口管对话流 + 摘要压早期 + RAG 管知识库（如果有）。不要用 RAG 替代窗口。
- **主动管理**：到约 80% 预算就处理，不要等 400。
- **撞墙**：Completions 常见是失败而不是默默续写；调试别先怪网络。

### 踩坑

- 错：以为 Completions 超了会默默截断再答 / 对：多数会先 **400**；用户看到失败，像网络问题。
- 错：把「训练时可能截断」当成 API 契约 / 对：你或产品层截了，才会「看起来答全了其实漏了」。
- 错：按字数估 token / 对：用对应模型 tokenizer；128K 字数口算跟 [Token](./02-Token.md) 实测对齐。
- 错：塞得进 = 用得好 / 对：中间照样计费，只是更难引用。
- 错：context window = memory / 对：硬上限 vs 你持久化再读回来。
- 错：window 数字大就能干所有事 / 对：要扣输出预留，还要管位置效应。
- 错：对话历史绝对不能 RAG / 对：不能替代多轮窗口；知识库/工单仍可检索。

### 过关自检

对照 README「本条要能讲清」：**能解释超了怎么办（截断 / 摘要）**。能说出口即可勾本条（量级对比是第 10 条「主流模型对比」要能讲清的，本条不强制背 128K / 1M / 2M）。讲解上还要能用人话讲清电梯限重、四种办法各像什么：

- context window = 一次请求里输入 + 输出共享的 token 上限（不要按字数当定义）。
- 超了：Completions 一类常直接失败；要继续干活就自己截断 / 摘要 / 滑动窗口，长文档再上 RAG。
- 能列出四种策略及适用（合同别用滑动窗口当主策略；客服用窗口 + 摘要）。
- lost in the middle：中间引用差，全塞 ≠ 全用上（但中间 token 仍计费）。
- window ≠ memory。

**自测练习**（先自答，再看参考答）

1. **会不会爆、爆了用户看到什么**  
   教学假设：窗口 128K，预留输出 4K（prompt 预算约 124K）。  
   - 历史 100K + 本轮输入 20K，走 Chat Completions，会不会超窗？  
   - 历史涨到 124K、输入仍是 20K 呢？  
   超窗时，更常见的是请求直接失败，还是模型默默截断后继续答？谁先砍了内容，用户才会以为「模型读过全文」？

2. **塞得进 ≠ 用得好**  
   80K token 的代码库丢进 128K 窗口，问「找出所有调用 `parseUser` 的地方」。窗口够不够？如果漏调用点，更可能漏在仓库的开头、正中间，还是结尾？用一句话说明：为什么中间那些 token 仍然在计费？

3. **超了怎么继续干活**  
   200 轮客服：历史约 90K + 用户本轮 5K，相对上面的 124K 预算大概到了哪一档？截断、摘要、滑动窗口、RAG 里，对话流该以哪几个为主、为什么合同场景不该拿滑动窗口当主策略？RAG 能不能替代「还没发生的下一句用户话」的窗口管理？

**参考答**

1. 100K + 20K = 120K，小于 124K **不爆**。历史 124K + 输入 20K = 144K，大于 124K **必爆**。Chat Completions **报错**，不是悄悄截断。用户以为读过全文，多半是你或产品层先砍了 prompt。
2. 80K 塞得进仍可能漏；调用点更可能在**正中间**。中间 token 照样进窗口、照样计费、照样算 attention，只是更难被引用（lost in the middle）。生产用 RAG 喂 top-K。
3. 90K + 5K = 95K，相对 124K 约 77%，下一轮要管。对话流：**滑动窗口**保近轮 + **摘要**压早期。合同是单一长文档，滑动窗口会丢掉前面条款，不当主策略。RAG **不能替代**多轮窗口；有知识库再 RAG 那部分。到 ~80% 就处理。
