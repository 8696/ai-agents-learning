# **Token**：模型读写的计费单位，不是「字」也不是「词」；中文通常更贵

> 对应模块：[模块 01 · AI & LLM 基础认知](./README.md) · 小节进度第 2 条

- **来源**：本对话（陪跑 Coach）；无外部 URL
- **状态**：已沉淀

### 是什么

**01 小节把 LLM 定义为「下一个 Token 预测器」——本条展开 Token 本身。** 这条主线同时串起 LLM 三大局限的根因：**能力边界**（拟合不是查数据库）/ **幻觉**（目标是接得像人话，不是查事实）/ **Context 上限**（序列长度是架构硬约束，下一条 [Context Window](./03-Context-Window.md) 展开）。本条只把 Token 这件事讲清。

人看到的是字和词。模型看见的是 **Token**：词表里的一个**整数 ID**（代号）。读写、计费、Context 长度，全按这条整数序列的长度算。

```text
「你好世界」
    → Tokenizer 切成若干段（不一定按字、也不一定按词）
    → 每段在词表里查成一个整数 ID
    → 模型读的是 [1523, 88, …]，不是汉字本身
```

**Tokenizer = 切 + 查的程序**，和 Token 是「工具 vs 产物」：

> 译名：大陆 NLP 圈常译 **「分词器」** 或 **「子词切分器」**（强调 LLM 这一代按子词切、不是按词切）。日常说「分词器」对方也懂，但严谨点用「子词切分器」，跟传统中文分词（Jieba / THULAC 那种按词典切出完整词的）划清界限。

| 零件 | 干什么 |
|------|--------|
| **词表（vocabulary）** | 所有合法 Token 的名单；每个有一个整数 ID |
| **切分算法** | 常见家族：BPE / WordPiece / SentencePiece。负责「这段文本切成哪几块」 |
| **特殊 Token** | 如开始 / 结束 / 填充，给协议用，不是给你读的词 |

模块 00 打印的 `prompt_tokens` / `completion_tokens`，数的就是这条整数序列有多长，不是「你打了几个汉字」。

**用人话：不是数汉字，是数「打包件」**

快递柜按**件**收费，不按「你写了多少个字的收件人姓名」。Tokenizer 是打包工：把句子拆成词表允许的小块，每块贴一个编号。模型只认编号。中文常被拆得更碎，同样一句话件数更多，所以更贵——单价没给中文单独加价，是件数多。

英文常见词往往整块进箱（`weather` 经常就是 1 件）。中文「天气」不一定享受同样的整词待遇，可能拆成更小的块。像把英文乐高说明书的整块零件，和中文说明书被掰成一粒一粒再数箱。

**输入一次卸货，输出每出一件再开工（所以输出更贵）**

超市进货：一车货开进大门，过一次地磅（输入 / prompt）。收银员每扫出一个商品再响一声、再走一遍流程（输出 / completion）。吐每一个 Token 都要再做一次完整前向，单价表上 completion 往往是 prompt 的大约 3～5 倍。Agent 循环十步，就是十趟「边想边吐」的输出账。

### 为什么（Agent 开发要懂）

模型算力 ≈ 序列长度；输入 + 输出都算钱。后面 Context Window、多轮裁剪、RAG 切片，全是在管 **Token 预算**，不是管「页数」或「字数」。

模块 00 已经能打出 `usage`。本条要把那个数字从「控制台里的三个字段」变成：**你知道它在数什么、为什么同样意思中文更贵、为什么不能拿 A 模型的条数去估 B 模型的账单。**

对账不要拿自己本地的估算当账单，要用 API 回传的 `usage.prompt_tokens`。本地 tokenizer（如 tiktoken）只做两件事：估算「这段还塞得进窗口吗」、做截断决策。

**Agent 多步循环是 Token 预算最痛的一块**：每一步的 reasoning 输出 + tool call 输出都计费，输出通常比输入贵 3–5×（每吐一个 Token 都要重做一次完整前向）。循环 N 步 ≈ N 倍输出成本。设计 Agent 时这是模块 07 / 11 的核心取舍之一——不是「能跑就行」，是「循环步数 × 单步输出 Token × 单价」这条公式算下来能否接受。

### 易混点

| 容易当成 | 其实是 |
|----------|--------|
| Token = 字 | 中文一个字常常是 1～2 个 Token，但不是定义。定义是词表里的 ID。 |
| Token = 词 / 语义 | 语义近不近是 Embedding 那一层的事（后面条）。Token 只负责切成离散符号。 |
| 「中文溢价」= 中文单价更高 | **单价不变，贵在数量。** BPE 一类**训练语料**以英文为主，词表里中文常见词组命中率低，同一段意思要切出更多 Token（常见大约 1.5～2.5 倍）。 |
| 各家模型 Token 数应该一样 | 算法可以同类（都叫 BPE），**词表必然不同**。同一段文本在 gpt-4o / Claude / Gemini 上差 10%～30%，极端 50%+。 |
| 同一个模型名 = 同一个 tokenizer | gpt-4 升 gpt-4o 时词表换过一整套，Token 数可以下降 20%～40%。要锁**模型版本号**。 |
| 每次切都会随机变 | **同模型版本内是确定的**：同一 tokenizer + 同一段输入 → 永远同一条 Token 序列（BPE 是确定性算法）。 |

### 例子

**打包现场（不必真的会写 BPE）**

你在纸上写「你好世界」。眼睛看到 4 个汉字。打包工可能切成 3 件或 5 件——以词表为准，不是以「字」为准。每件换成号码：`[1523, 88, …]`。模型读号码，不读毛笔字。

再写英文 `Hello world`。空格和常见词让它常常更「整块」。所以：**字符少 ≠ 件数少**。验收表里同一意思的中英对照，就是把这件事量出来。

如果跑 `yarn dev "你好"`，终端里 `prompt_tokens` 会是「你好」被 **MiniMax 那套子词切分器**（Tokenizer）切出来的条数；换成更长的中文，这个数字涨得比按「字数」估的更快。（模块 00 验收没强制要求这条具体命令——只要流式跑通过即可。）

**对照实验**（模块 01 验收第 7 条要求；数字已用 `tiktoken` 实测）：

拿**同一段意思**的中英文，分别丢进 `tiktoken` 的两套编码数 Token：

| 句子 | 字数 | cl100k_base（GPT-4 / 4-turbo） | o200k_base（GPT-4o / 4.1） |
|------|----:|---:|---:|
| 中文：「今天天气真好，我想出去散步。」 | 14 | **17** | **11** |
| 英文：「The weather is really nice today, I want to go for a walk.」 | 58 | **15** | **15** |
| 中文：「请把这份合同按条款A和条款B的差异做摘要，输出表格。」 | 26 | **29** | **23** |
| 英文：「Please summarize the differences between clause A and clause B of this contract as a table.」 | 91 | **17** | **17** |

看三件事：

1. **Token 密度差 ~5–6 倍**：第一组中文 14 字 → 17 Token（约 1.21/字），英文 58 字 → 15 Token（约 0.26/字）。这就是「中文通常更贵」的现场，**不是**单价表给中文单独加价。
2. **意思接近 ≠ Token 数接近**：第一组中英文字数比 14 : 58 ≈ 1 : 4.1，但 Token 数比 17 : 15 ≈ 1.13 : 1。**字符少不代表 Token 少**——别按字数估费用。
3. **同模型升级，Token 数会变**：从 cl100k_base 升 o200k_base，中文 Token 数明显下降（17→11、29→23，约 20–35%），英文几乎不变。要锁**模型版本号 + tokenizer 版本号**。

对账场景：本地用 OpenAI 的 tiktoken 去估 MiniMax 的费用 → 数字接近但不会相等。账单以这次请求回传的 `usage` 为准。

**超市小票 vs 心里估的件数**

你进店前用别的店的价目表心算「大概 17 件」。结账以**本店扫描枪**为准。tiktoken 是你口袋里的估算尺，用来出门前判断「这袋还塞不塞得进电梯」（窗口）；扣费以 API 回传的 `usage` 为准。拿 OpenAI 的尺去估 MiniMax 的账，会接近但不会相等。

**换一家店（换模型）件数会变**

同一袋菜，A 超市按个卖、B 超市按两卖。gpt-4 升 gpt-4o 换过词表，中文件数可以少一截。锁**模型版本**，别用 A 的件数乘 B 的单价。

### 我追问过的

- 问了：把前四篇笔记继续按「详细讲透 + 通俗例子」补充 → 答在「是什么」打包件/卸货开工，「例子」打包现场与超市小票。
- 问了：不同模型 Token 数为什么不一样 → 答在「易混点」：词表不同，即使切分算法同类。
- 问了：生产上怎么用这些数字 → 答在「取舍」：对账用 API 的 `usage.prompt_tokens`；本地 tiktoken 只做估算和截断决策；锁模型版本号 + 锁 tiktoken 版本号；不同模型按 model 名选对应 tokenizer。

### 取舍

| 用途 | 用什么 | 为什么 |
|------|--------|--------|
| **对账 / 账单** | 服务端 `usage` | 只有厂商自己的切分才和扣费一致 |
| **决策**（这段还塞得进 Context 吗？该不该摘要？） | 本地 tokenizer 估算 | 请求前就要判断，等 `usage` 回来已经超了 |
| 跨模型比价格 | 分别按各模型 tokenizer 估，或看各厂定价页的量级 | 禁止拿 A 的条数乘 B 的单价 |

### 踩坑

- 错：用错 tokenizer 版本，或拿 A 模型的 Token 数去估 B 模型的账单 → 对：锁模型 + 锁 tokenizer；对账只信 `usage`。
- 错：按「字数 × 某个系数」做生产截断 → 对：用对应模型的 tokenizer 估算，仍留余量给输出。
- 错：以为中文贵是因为控制台给中文设了更高单价 → 对：贵在切得更碎、条数更多。

### 过关自检

- Token 是词表里的整数 ID，不是字也不是词；Tokenizer 是把文本切成这些 ID 的程序。能用「快递按件、不按字数」讲清。
- 按 Token 计费，输入 / 输出分开；中文通常更贵，贵在数量（同样意思要切更多段），不是单价溢价。输出更贵能用「进货过一次地磅 vs 每扫一件再响一声」类比。
- 用 tokenizer 实际数过一段中英文，知道中文字符的 Token 密度大约是英文的 5–6 倍（实测数字见「例子」表）。对账信 `usage`，口袋尺只做估窗。
