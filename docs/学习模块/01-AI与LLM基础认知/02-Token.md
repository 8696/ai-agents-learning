# **Token**：模型读写的计费单位，不是「字」也不是「词」；中文通常更贵

> 对应模块：[模块 01 · AI & LLM 基础认知](./README.md) · 小节进度第 2 条

- **来源**：本对话（陪跑 Coach）；无外部 URL
- **状态**：已沉淀

### 是什么

人看到的是字和词。模型看见的是 **Token**：词表里的一个**整数 ID**（代号）。读写、计费、Context 长度，全按这条整数序列的长度算。

```text
「你好世界」
    → Tokenizer 切成若干段（不一定按字、也不一定按词）
    → 每段在词表里查成一个整数 ID
    → 模型读的是 [1523, 88, …]，不是汉字本身
```

**Tokenizer = 切 + 查的程序**，和 Token 是「工具 vs 产物」：

| 零件 | 干什么 |
|------|--------|
| **词表（vocabulary）** | 所有合法 Token 的名单；每个有一个整数 ID |
| **切分算法** | 常见家族：BPE / WordPiece / SentencePiece。负责「这段文本切成哪几块」 |
| **特殊 Token** | 如开始 / 结束 / 填充，给协议用，不是给你读的词 |

模块 00 打印的 `prompt_tokens` / `completion_tokens`，数的就是这条整数序列有多长，不是「你打了几个汉字」。

**为什么输出通常更贵（大约 3～5 倍）：** 输入可以一次吃进去；生成时每吐一个 Token 都要再做一次完整前向。单价表上 completion 往往明显高于 prompt。

### 为什么（Agent 开发要懂）

模型算力 ≈ 序列长度；输入 + 输出都算钱。后面 Context Window、多轮裁剪、RAG 切片，全是在管 **Token 预算**，不是管「页数」或「字数」。

模块 00 已经能打出 `usage`。本条要把那个数字从「控制台里的三个字段」变成：**你知道它在数什么、为什么同样意思中文更贵、为什么不能拿 A 模型的条数去估 B 模型的账单。**

对账不要拿自己本地的估算当账单，要用 API 回传的 `usage.prompt_tokens`。本地 tokenizer（如 tiktoken）只做两件事：估算「这段还塞得进窗口吗」、做截断决策。

### 易混点

| 容易当成 | 其实是 |
|----------|--------|
| Token = 字 | 中文一个字常常是 1～2 个 Token，但不是定义。定义是词表里的 ID。 |
| Token = 词 / 语义 | 语义近不近是 Embedding 那一层的事（后面条）。Token 只负责切成离散符号。 |
| 「中文溢价」= 中文单价更高 | **单价不变，贵在数量。** BPE 一类词表以英文语料为主，中文常见词组命中率低，同一段意思要切出更多 Token（常见大约 1.5～2.5 倍）。 |
| 各家模型 Token 数应该一样 | 算法可以同类（都叫 BPE），**词表必然不同**。同一段文本在 gpt-4o / Claude / Gemini 上差 10%～30%，极端 50%+。 |
| 同一个模型名 = 同一个 tokenizer | gpt-4 升 gpt-4o 时词表换过一整套，Token 数可以下降 20%～40%。要锁**模型版本号**。 |
| 每次切都会随机变 | **同模型版本内是确定的**：同一 tokenizer + 同一段输入 → 永远同一条 Token 序列（BPE 是确定性算法）。 |

### 例子

模块 00 跑 `yarn dev "你好"` 时，终端里的 `prompt_tokens` 已经是「你好」这句话被 **MiniMax 那套 tokenizer** 切出来的条数。换一句更长的中文，这个数字涨得比你按「字数」估的更快。

对照实验（模块 01 验收还要求亲手做一次）：拿**同一段意思**的中文和英文，丢进在线 tokenizer / tiktoken，看两条数字。中文条数会明显更多——这就是「中文通常更贵」的现场，不是单价表上单独给中文加价。

对账场景：本地用 OpenAI 的 tiktoken 去估 MiniMax 的费用 → 数字接近但不会相等。账单以这次请求回传的 `usage` 为准。

### 我追问过的

- 问了：不同模型 Token 数为什么不一样 → 答在「易混点」：词表不同，即使切分算法同类。
- 问了：生产上怎么用这些数字 → 答在「取舍」：对账用 API 的 `usage.prompt_tokens`；本地 tiktoken 只做估算和截断决策；锁模型版本号 + 锁 tiktoken 版本号；不同模型按 model 名选对应 tokenizer。

### 取舍

| 用途 | 用什么 | 为什么 |
|------|--------|--------|
| **对账 / 账单** | 服务端 `usage` | 只有厂商自己的切分才和扣费一致 |
| **决策**（这段还塞得进 Context 吗？该不该摘要？） | 本地 tokenizer 估算 | 请求前就要判断，等 `usage` 回来已经超了 |
| 跨模型比价格 | 分别按各模型 tokenizer 估，或看各厂定价页的量级 | 禁止拿 A 的条数乘 B 的单价 |

### 踩坑

- 错：用错 tokenizer 版本，或拿 A 模型的 Token 数去估 B 模型的账单 → 对：锁模型 + 锁 tokenizer；对账只信 `usage`。
- 错：按「字数 × 某个系数」做生产截断 → 对：用对应模型的 tokenizer 估算，仍留余量给输出。
- 错：以为中文贵是因为控制台给中文设了更高单价 → 对：贵在切得更碎、条数更多。

### 过关自检

- Token 是词表里的整数 ID，不是字也不是词；Tokenizer 是把文本切成这些 ID 的程序。
- 按 Token 计费，输入 / 输出分开；中文通常更贵，贵在数量（同样意思要切更多段），不是单价溢价。

### 还没搞懂的

还没用 tokenizer **实际数过**一段中英文（模块 01 验收项，本地产出前补上：把两段数字写进本文件或 [本地产出](./11-本地产出.md)）。Context Window 怎么和这条序列的长度绑在一起 → [Context Window](./03-Context-Window.md)。
