## 是什么

两个都会自己循环的 Agent 配合完一次之后，看用户的下一句话进谁的对话。

下一句仍然进原来那个 Agent，中间那个 Agent 只交回一段结果：这是把另一个 Agent 当工具调用（Agents as Tools）。调用方还在。

下一句改由另一个 Agent 接，原来那个不再继续对用户说：这是任务移交（Handoff）。控制权换人。

一句话：下一句还进原来那个，就是当工具调用；下一句换人接，就是任务移交。

上一节的子图（Subgraph）是父图里的一站，跑完把状态交回父图，父图继续。用这一句来看，接用户的还是父图那条线，归到当工具调用。子图字段怎么传，仍看上一小节，这里不重讲。

### 当工具调用：消息列表怎么走

调用方把另一个 Agent 当成一个工具。运行时另开一份消息列表（messages）去跑那个 Agent，等它说出最终结论，再把这段文字放进调用方的消息列表，作为那一次工具调用（Tool Calling）的工具返回值（tool result）。对用户说话的仍是调用方。

用户说：「上周买的耳机右耳没声音，想退款，订单号 A10086。」

```text
总客服的消息列表
  用户：耳机想退款，订单 A10086
  总客服：工具调用 ask_refund_agent（订单号、故障）
  工具返回值：「7 天内、质量问题可全额退，需要用户确认退货地址」
  总客服：可以对用户说的那句「可以退。请确认退货地址。」

退款专员的消息列表（另外一份，通常只有这一次任务）
  系统：你是退款专员，只输出结论
  用户：订单 A10086，右耳没声音
  专员：上面那段结论
        （专员内部还可以再调「查订单」这种普通工具，那一圈仍是模块 05 的工具调用）

用户下一句「用默认地址」→ 仍然追加到总客服的消息列表
```

专员看见的是一次任务。用户看见的是总客服一个人。交回来的是一段结果，不是「下一句由谁接」。

OpenAI Agents SDK 里，把另一个 Agent 包成工具的常见写法是 `as_tool`：子 Agent 跑完，最终文本交回调用方。LangChain 文档把同一种模式叫 agents as tools。

### 同一轮问两个人，仍是当工具调用

总客服同一轮发出两个工具调用：一个问库存专员，一个问物流专员。两段结论都放进总客服的消息列表。总客服拼成一句对用户说。两个专员都没有接过用户的下一句。

这是当工具调用的并行。模块 14 的主管分派，工人侧就是这种：工人交结果，主管还在对用户说话。实现留在模块 14。这里要能归类：工人不接用户的下一句，就不是任务移交。

### 任务移交：当前 Agent 怎么换

当前 Agent 判断接下来不该自己答。运行时把「现在谁在接用户」改成另一个 Agent。新 Agent 直接对用户说话。原来那个 Agent 没有停在「等工具返回值再生成一句」。

```text
当前 Agent：分诊 → 改成退款专员

分诊的消息列表停在这里
  用户：耳机想退款，订单 A10086
  分诊：发出移交（很多框架里这一下仍长得像一次工具调用，名字类似 transfer_to_refund）
  （后面没有「专员结论 → 分诊再生成」）

退款专员成为当前 Agent
  常见做法：带上已经发生的对话，或先滤掉工具调用细节
  各框架滤不滤、滤多少不一样；不变的是下一句谁接
  专员：直接对用户说「我是退款专员。这单可以退，请确认地址。」

用户下一句「用默认地址」→ 追加到退款专员这份对话，不进分诊
```

OpenAI Agents SDK 里，可以移交的名单挂在 `handoffs` 上。跑完谁在接，看当前 Agent；这个 SDK 的运行结果里常用 `last_agent` 表示最后是谁在接。有的图框架用「跳到另一个节点」表达移交：原节点不拿着返回值继续生成，下一个接用户的节点已经换了。

### 移交之后再交给下一个人

退款专员处理完，用户改问「推荐一款替代耳机」。专员再把当前 Agent 改成导购。下一句由导购接。

这是第二次任务移交。导购接到的是更新后的对话，不是专员函数的返回值。专员没有停在同一次请求里，等导购交回一段文字再自己对用户说。

若专员只是内部问了导购「有没有同价位替代」，拿到型号后仍由自己对用户说，那一问是当工具调用。对外说话的人没换。

### 进线第一句就交给专员

用户第一句就是退款。入口直接把当前 Agent 设成退款专员。会话里没有「总客服问完再自己说」。

这不是第三种机制。判据仍是下一句谁接：从第一句起就是专员。它和中途移交的差别只在于，没有一个调用方曾经在等返回值。若入口先等专家结论再汇总，它就变成当工具调用，用户从头到尾只听见入口那一个口吻。

## 为什么（Agent 开发要懂）

只看「有没有再叫一个模型」会选错。选错的后果用户看得见。

**口吻和承诺。** 当工具调用时，人设和承诺都由调用方统一。专员若直接开口，会出现两套说法：总客服说「我帮你申请」，专员说「我不能申请」。任务移交时必须让用户知道换人了，否则用户对着已经下线的人补充地址，新人不在那条上下文里。

**上下文给谁。** 当工具调用时，子 Agent 只该看到这一次任务（订单号、故障）。把调用方的全部历史塞进去，多花 Token（Token），也容易把内部笔记漏给子 Agent。任务移交时，新人要能接着聊，所以要带上已有对话或一份摘要，否则用户得从头说一遍。

**会改数据的动作放在谁手里。** 真退款会改订单。子 Agent 当工具时若自己就把款退了，调用方还没让用户确认，钱已经动了。这种子 Agent 应该只返回「可以退」的判断，执行留在调用方确认之后。移交之后，确认话术和执行权都在新人手里，规则要写进新人的说明，不能还写在已经下线的分诊身上。

**失败了谁改口。** 子 Agent 超时或答非所问时，当工具调用的调用方还能收到一条失败的工具返回值，改口说「我查不到，转人工」。移交之后原调用方已经不在，失败会直接出现在用户面前，新人必须自己有兜底。

**钱和等待。** 当工具调用至少两次模型生成：子 Agent 一圈，调用方再根据返回值说一句。用户每问一次，调用方都在。移交完成之后，后续每句只有新人在跑，原调用方不再为这些句子付钱。模块 14 会算这笔账。这里先记住结构：当工具是每问都双份，移交是换人之后单份。同一轮并行问库存和物流，双份变成多份，接用户的人仍然只有总客服。再交给导购之后，付钱的是导购那一条线，不是停在原请求里的专员。

## 易混点

**两边在模型侧都可以长得像工具调用。** 模块 05 那一圈是：模型发出工具调用，执行，工具返回值放进消息列表，模型继续。当工具调用走完整圈。任务移交常常只借用「模型可以发出一次调用」这个外形，运行时改的是当前 Agent（active agent），不把专员的话放进原列表再让原 Agent 生成。

判错会怎样：日志里看到 `transfer_to_refund`，你以为分诊还会再讲一句，于是把审核和汇总写在分诊后面。实际上用户下一句已经进了退款专员，分诊后面的逻辑没跑。

**把 Agent 当工具，和查数据库那种普通工具不是同一类函数。** 普通工具的输入输出按模式（schema）来，成功或失败比较确定。包进去的 Agent 里面仍是一轮模型循环，会多花 Token，会说错，还会再调别的工具。调用方不能假设「要么按格式返回，要么抛错」。若你需要稳定字段，要在子 Agent 上单独约束结构化输出（Structured Output）。

**再交给下一个人，不是工具返回值。** 「专员做完转回导购或总机」换的是当前 Agent。总机若要在同一次请求里拿到专员的返回值再自己说，专员就不能先对用户把话说完。两种写法，用户看见的人不同。

**等人点头不是任务移交。** 模块 11 的人在回路（Human-in-the-loop）是暂停，等真人确认。任务移交是换成另一个模型继续，没有等人。转人工是等真人。移交是另一个 Agent 接管。

**主管派活不是任务移交。** 工人把结果交回、主管对用户说话，用当工具调用的判据。只有工人直接接用户的下一句，才是任务移交。

**进线分流不是「总客服还在」。** 第一句起当前 Agent 就是专员时，用的是「下一句谁接」。会话里若出现「入口等专家结论再自己说」，那一跳已经变成当工具调用。

## 例子

同一个订单 A10086。下面每一种都把数据走一遍。

### 电话：静音问同事，还是把电话转出去

当工具调用：你按住静音，问退款同事「A10086 能不能退」。同事告诉你「7 天内可退」。你回到原通话，自己对客户说。客户没换人。客户下一句仍是你接。

任务移交：你说「我把您转到退款专员」，然后挂断自己这端。客户下一句是专员接的。你没有拿着耳机等同事的返回值。

再交一次：专员说完退款政策，客户改问选购。专员把电话转到导购。导购接的是这通已经说了一半的电话，不是专员在静音期间问来的一句话。

若专员静音问了导购型号，回到原通话自己告诉客户：客户没换人，那一问是当工具调用。

进线就分流：总机听完第一句直接把线接到退款专员，客户从第一句起就没跟总客服聊过。

同一轮问两个人：你静音打两通内线，一通库存、一通物流，两通都把结论告诉你，你自己对客户说。两通内线都没有接管客户。

### 前端：父组件等结论，还是换掉 activeAgent

当工具调用对应：

```text
const advice = await RefundPanel.consult({ orderId: "A10086", issue: "右耳没声音" })
setBubbles(prev => [...prev, { from: "总客服", text: speakAsHost(advice) }])
```

`RefundPanel` 不替换当前页面。下一轮提交的处理函数仍是总客服这份。`advice` 是工具返回值，气泡的 `from` 是总客服。

同一轮问两个人对应 `Promise.all` 两个 `consult`，两段结果都回到总客服，再渲染一条 `from: "总客服"` 的气泡。

任务移交对应：

```text
setActiveAgent("refund")
```

下一轮 `onSubmit` 读到的是 `refund`。分诊那份处理函数不再等一个 Promise。用户看见的下一条气泡 `from` 是退款专员。再提交一次，请求体里的接收方仍是 `refund`。

再交给导购对应再执行一次 `setActiveAgent("guide")`。下一轮提交进导购。中间没有「专员的函数 return 一段文字、总客服在同一次点击里继续说」。

进线分流对应：第一句分类之后直接 `setActiveAgent("refund")`，页面上不出现总客服的气泡。

## 需求清单

每条对应一种情况。这是验收准绳，不是一次搭完整客服台的施工单。本条不建可运行演示；多个 Agent 真正跑起来留在模块 14。

**需求 1 · 总客服问退款规则，自己回复**（当工具调用）

- 业务场景：用户问订单 A10086 能不能退。
- 目标：专员只交回结论，用户看见的话由总客服说，下一句仍进总客服。
- 涉及：当工具调用、另开一份消息列表、工具返回值放进调用方的消息列表。
- 验收：专员结论出现在总客服的工具返回值里；对用户的那一句由总客服生成；再发一句，接收方仍是总客服。

**需求 2 · 分诊把退款交出去**（任务移交）

- 业务场景：分诊发现整段都该由退款专员接。
- 目标：专员直接对用户说，之后用户的话进专员。
- 涉及：任务移交、当前 Agent 切换、原调用方不等返回值。模型侧即使长得像一次工具调用，运行时仍然换人。
- 验收：用户看见的回复来自退款专员；分诊的消息列表里没有「等结论再生成」；再发一句，接收方是退款专员。

**需求 3 · 专员做完再交给导购**（再移交一次）

- 业务场景：退款说完，用户改问选购。
- 目标：当前 Agent 换成导购，导购接下一句。
- 涉及：再交给下一个人仍是任务移交，不是工具返回值。
- 验收：交出去之后下一句进导购；中间不存在「专员把一段文字 return 给原 Agent，原 Agent 在同一次请求里继续对用户说」。

**需求 4 · 总客服同一轮问库存和物流**（并行的当工具调用）

- 业务场景：用户问「有没有货、几天到」。
- 目标：两段结论都交回总客服，总客服汇总成一句。
- 涉及：同一轮多次当工具调用。主管分派的工人侧用同一判据，实现不在本条。
- 验收：两个专员的文字都在总客服的工具返回值里；对用户说话的是总客服；下一句仍进总客服。

**需求 5 · 进线第一句就是退款**（入口就定当前 Agent）

- 业务场景：入口只做分流。
- 目标：从第一句起由退款专员接。
- 涉及：入口分流用的是「下一句谁接」，没有调用方在等返回值。
- 验收：会话里没有「总客服调用专员再自己说」；第一句回复者就是退款专员。若改成入口等专家结论再汇总，归到需求 1。

## 变体对照

| 情况 | 下一句进谁 | 原调用方还在等返回值吗 | 需求 |
| --- | --- | --- | --- |
| 当工具调用 | 原来那个 Agent | 在等，结论文本放进它的消息列表 | 需求 1 |
| 同一轮问多个 | 原来那个 Agent | 在等，多段结果都放进它的消息列表 | 需求 4 |
| 任务移交 | 新人 | 不在等 | 需求 2 |
| 再交给下一个人 | 再换的那个人 | 不在等；不是函数返回值 | 需求 3 |
| 模型侧长得像工具调用、运行时换人 | 新人 | 不在等。不能用「有没有工具调用」判断 | 需求 2 |
| 进线第一句就交给专员 | 专员 | 从第一句起就没有调用方在等 | 需求 5 |
| 主管派工人、工人不对用户说 | 主管 | 在等工人的结果。归到当工具调用 | 需求 4 的判据；实现在模块 14 |

## 取舍

| 你在意的事 | 当工具调用 | 任务移交 |
| --- | --- | --- |
| 对外只有一个口吻、一个承诺人 | 适合。子 Agent 不直接对用户说 | 要明确告诉用户换人了 |
| 只需要一项结论，后面仍由原 Agent 聊 | 适合 | 不适合。后面每句都让专员接，专员会变成传声筒 |
| 接下来整段都是另一门专业 | 调用方会变成传声筒，多一次生成 | 适合 |
| 这一步会改订单、退钱 | 子 Agent 只给判断，执行留在确认之后 | 确认和执行都归新人 |
| 子步骤失败时要有人改口 | 调用方还在，能接失败的返回值 | 新人必须自己兜底 |

## 踩坑

- 日志里出现一次名字像 `transfer_to_refund` 的调用，就以为原 Agent 还会再生成一句。移交的外形可以是工具调用，运行时改的是当前 Agent。审核和汇总若写在原 Agent 的「工具返回值之后」，用户那边已经换人，那段逻辑不会跑。
- 把「可以退」的判断和「真的退款」放进同一个当工具的子 Agent。用户还没确认，订单已经改了。判断可以交回调用方；会改数据的执行留在确认之后。移交之后则两件事都归新人，说明要写在新人身上。
- 人已经换成专员，补充地址仍追加到分诊的消息列表。专员看不见这句，退款地址对不上。下一句进谁，消息就追加到谁的对话。

## 过关自检

能对着别人讲出这句：下一句还进原来那个 Agent，就是当工具调用，调用方还在；下一句换成另一个 Agent 接，就是任务移交，控制权换人。

再能指着订单 A10086 说出：总客服自己回复时，专员的话在工具返回值里；分诊移交后，再发一句进的是专员；专员转给导购是又一次换人；同时问库存和物流时，接用户的仍是总客服；进线第一句就分流时，从第一句起接的就是专员。
