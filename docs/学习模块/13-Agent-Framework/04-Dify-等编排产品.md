## 是什么

Dify 这一类编排产品（Orchestration Product）是一个网站：你在里面配一段对话，或拖一张流程图，它帮你保存配置、接上模型、跑起来、留下运行记录。你交出去的通常是这个网站里的一份应用，不是仓库里的一个 `server.ts`。

它把两件你已经手写过的事收进自己的服务器：

- 循环（Loop）：还没答完，就再叫一次模型，或再走一个节点。模块 07 里这是你写的 `while`。
- 状态（State）：这一趟任务目前知道的事实，用来决定下一步去哪。模块 11 里这是你声明的那一份类型，加上 `currentNode`。

循环和状态都还在，只是不在你的文件里，你也不能给它们下断点。进度表把这一条标成体验，不当学习主线：原理在模块 07 和模块 11 已经学完。这里要能指出画布上每一个方块，对应你手写过的哪一次转圈、哪一份状态。

同类产品（扣子、FastGPT，或在 n8n 里接一个模型节点）藏法是同一类。下面用 Dify 当名字，因为进度表点名的是它。菜单文案会随版本改。体验时对上「这是在藏循环」还是「这是在藏状态」即可。

和本模块前三节的代码框架不在同一层：

| | 你手里有什么 | 循环和状态在哪 |
| -- | -- | -- |
| 模块 07 / 11 手写 | 你的 `while`、你的状态类型、你的 `step` | 全在你的文件里 |
| 代码框架（上一节及之前） | 你仍写节点函数和状态类型，调度由库来跑 | 仍在仓库里，能提交、能写测试 |
| 编排产品 | 一份画布或一张配置表 | 在产品的服务器里 |

### 同一句热拿铁，三种走法

客人说：「来一杯热拿铁。」

**手写循环（对照，不是产品里的配置）。** 数据这样走：

1. 把这句话放进消息列表（`messages`）。
2. 调用模型。
3. 模型若要查「这杯能不能做」，你执行工具，把结果再放进消息列表。
4. 再调用模型，直到它给出给客人的那一句。

每一圈的入参和返回值都在你的日志里。

**手写状态（对照）。** 另一份对象，不只靠消息列表：

```ts
type OrderState = {
  currentNode: "classify" | "hot" | "iced" | "reply" | "end";
  userText: string;
  drinkName: string | null;
  drinkType: "hot" | "iced" | null;
};
```

走一步：跑当前节点 → 节点只返回自己改的字段 → 调度器合并 → 路由函数读 `drinkType` → 对照边表，不在边表里就拦下 → 写下新的 `currentNode`。这是模块 11 的调度器（Scheduler）。编排产品不把这个函数展示给你。

**智能体应用（Agent App）：循环整段藏进产品。** 界面通常是一段人设、一份工具清单、一个对话框。你选上「查这杯能不能做」。客人的句子进产品。产品内部仍做上面那 4 步。界面上多半只看到一段折叠的思考文字和最后一句「热拿铁可以做」。没有你的 `while`，也没有你拥有的消息数组。

**工作流（Workflow）：节点看得见，调度器和状态类型看不见。** 画布上是这些方块：

```text
开始（收下句子，写入 user_text）
  → 大模型节点（读 user_text，写出 drink_name、drink_type）
  → 条件分支（读 drink_type）
       → 热：回复节点「按热饮出品」
       → 冰：回复节点「按冰饮出品」
  → 结束
```

你看得见节点和连线。一次运行里，`user_text`、`drink_name`、`drink_type` 就是这份状态。它们活在产品的变量面板里，不是你声明的 TypeScript 类型。谁调用「走一步」、失败了停在哪、变量怎么合并，是产品里的调度器。

### 九种情况

#### 1. 智能体应用把整个循环藏起来

界面没有「下一步去哪个节点」。你配人设和工具，产品自己转圈，直到模型不再要工具、吐出给用户的正文。状态主要是产品内部的消息列表，外加它愿意展示的那几行思考文字。你改不了某一圈的工具结果再重放。

#### 2. 工作流画布把节点给你看，把调度器和类型藏起来

方块对应模块 11 的节点。连线对应边。变量对应状态字段。缺的是：一份共享的状态类型、节点只返回自己改的那几项、调度器合并、边表、走一步时先核对边表。店长看得懂方块。仓库里没有 `step(state)`。

#### 3. 聊天流把「这一轮的图」和「跨轮还在的变量」叠在一起

聊天流（Chatflow）仍是一张画布，但这张画布会在同一段对话里跑多轮。会话变量（Conversation Variable）活过单轮。

客人先说「大杯热拿铁」，再说「还是大杯，换成冰的」。第二轮的开始节点能读到会话变量里的杯型。这一份跨轮的状态是产品替你存的，不是你类型文件里的 `size: "large"`。

它和模块 10 的记忆不是同一件事。这里只是一份变量顶着「还记得上一轮」。怎么检索旧对话、怎么摘要，不在这一小节展开。

#### 4. 回边：循环的形状看得见，转圈的代码仍看不见

库存不足时，你从「查库存」拉一条线回到「问客人要不要换一杯」。这条线就是循环的形状。真正执行「再走一次」的仍是产品里的调度器。你没有 `while`。你也没有「最多再问 2 次」这种自己写的上限，除非产品的节点表单里提供了次数，或者你用变量自己记次数。

这和智能体应用不同。智能体应用的圈在界面上不画出来。回边的圈是你画的，执行权仍不在你手里。

#### 5. 一个大模型节点只是调用一次模型

大模型节点（LLM Node）通常是：读入上游变量，调用一次模型，把文本或解析后的字段写到下游变量。这里没有「看工具结果再叫一次」。

循环要么在智能体应用里，要么在你画的回边里，要么在一个专门的智能体节点里。那种节点才是把模块 07 的循环塞进一个方块。单独一个大模型节点默认不是那个方块。

#### 6. 条件分支看得见路由，看不见边表验非法转移

条件分支（Conditional Branch）读变量，选一条出边。这就是条件路由（Conditional Routing）的界面形态：`drink_type` 是 `hot` 就走热饮。

模块 11 还多一步：调度器拿边表核对，下一站不在名单里就写成非法转移，不去。编排产品里有没有同等的核对、有多严，是产品内部的事。讲的时候要承认自己看不见那一层。不能假设它一定拦，也不能假设它一定放行。

#### 7. 代码节点只交出一小段，整次运行仍归产品

代码节点（Code Node）或 HTTP 节点让你写一小段：杯型价格、调用自己的下单接口。这段的输入输出你能看懂。

「会不会走到这个节点」仍由产品的路由决定。这段代码里的局部变量，函数返回就丢，不会自动变成全图那份状态，除非你把它写成节点的输出变量。这和模块 11「节点里的临时变量不进状态」是同一条规矩，只是合并发生在产品里。

#### 8. 代码框架藏调度，编排产品连仓库都没有

LangGraph 那一节：节点、边、状态类型仍是你提交的代码，库负责按图跑。出了问题你能改文件、能写测试、能按你的日志格式把每一步的入参和返回值记全。

编排产品：同样的图存在别人的数据库里。导出的往往是一份产品配置。同事克隆你的 Git 仓库，看不到这张图，除非他也登录那个网站。运行记录是产品的页面，不是你 `logs/` 里按调用记下来的那几条日志。

三条就够划界：代码在不在你的仓库、状态是不是你声明的类型、循环的每一步能不能按你的方式记日志。

#### 9. 有副作用、要人点头、要杀进程再起来：体验交差不够

有的画布上有「等人工输入」这种方块。退款前拖一个方块，人点头才继续，这只说明产品提供了暂停的界面。

它还不等于你拥有检查点（Checkpoint）：进程杀掉之后，从上一份可序列化的状态接着跑。也不等于有副作用的工具按调用编号去重：恢复时不会把「已扣款 / 已发券」再做一次。

这些是模块 11 后面两节已经用代码讲过的。这一小节只要求你认出：方块在，机制仍在产品里。讲不清「不会扣第二次」，就不能把这条业务只放在产品里交差。

## 为什么（Agent 开发要懂）

选型时一定会碰上：「这条客服为什么不直接用 Dify 搭？」答不上循环和状态放在哪，就没法决定什么时候该收回自己的代码。

不当主线，是因为原理已经在模块 07、模块 11 学完。再花很多天拖节点，不会让你更会写 Agent，只会让你更熟一个产品的按钮。这一档的标准是：技术讨论里能讲两分钟，能说清和手写的差别。

漏掉某一种藏法，会在具体的地方翻车：

1. 只看智能体应用的对话框，会以为 Agent 没有循环。回到仓库，就不知道手写版的消息列表是在补产品藏掉的那几圈。
2. 只看画布上的方块，会以为自己已经拥有调度器。非法转移、失败停在哪一站，你都讲不出代码在哪。
3. 聊天流没把杯型放进会话变量，第二轮「还是大杯」会丢。你会去怪模型失忆，而那份状态根本没活过这一轮。
4. 回边画了，却没给「已经问过几次」留变量。产品会一直绕圈，你没有自己的 `while` 上限。
5. 把一次大模型节点说成整段循环，库存查询没人做，回复里却出现「已经查过了」。
6. 把「未付款 → 出品」连上，又用模块 11 的记忆断言产品一定会拦。拦不拦要以你点出来的那次运行为准。
7. 在代码节点里算了价格，却没把价格写成输出变量。下游回复读到的仍是空的。局部变量在函数返回时已经丢了。
8. 用产品交付了一张图，同事只克隆仓库，图不在。出了事故也没有你自己的逐步日志。
9. 退款只拖了一个「等人点头」的方块。进程重启后扣款又跑了一次。暂停的界面没有代替检查点和去重。

另外两条总后果：把产品当主线，模块 07 和模块 11 的验收会空掉；完全不用产品，内部先试一条「问菜单 → 分类 → 回复」也会从零写很久。试通了再决定要不要写成仓库里的状态机。

## 易混点

| 两件东西 | 各自是什么 | 讲错了会怎样 |
| -- | -- | -- |
| 编排产品 vs 代码框架 | 产品把图放在网站里；框架把图留在你的代码里 | 会把「用了 LangGraph」和「用了 Dify」说成同一件事 |
| 智能体应用 vs 工作流 | 前者藏整段循环；后者让你看见节点，藏调度器和类型 | 会把所有方块都说成「里面有一个循环」 |
| 大模型节点 vs 智能体节点 | 前者多半是调用一次；后者才把工具循环塞进一个方块 | 会在一次调用上解释「它自己又转了三圈」 |
| 回边 vs 智能体应用里的循环 | 回边的圈是你画出来的；智能体应用的圈界面上不画 | 会以为「图上没有圈」就等于没有循环，或「图上有圈」就等于循环代码归你 |
| 这一次运行的变量 vs 会话变量 | 前者这次跑完就结束；后者跨轮还在 | 第二轮「还是大杯」会丢，你却去查模型为什么失忆 |
| 环境变量、密钥 vs 这一趟的状态 | 前者是配置；后者是这张单走到哪、杯型是什么 | 会把密钥放进任务状态，或把杯型写成全局配置 |
| 会话变量 vs 模块 10 的记忆 | 会话变量是产品里的一份字段；记忆是另一套检索和摘要 | 拖了一个「还记得上一轮」就以为记忆系统已经做完 |
| 知识库节点 vs 循环 | 知识库节点是检索那一跳 | 拖了一个知识库，就以为 Agent 循环已经学完 |
| 条件分支 vs 边表核对 | 条件分支负责选边；边表核对负责拒绝没画过的下一站 | 会用模块 11 的第 7 步脑补产品一定拦下非法转移 |
| 代码节点的局部变量 vs 全图状态 | 局部变量函数返回就丢；全图状态要写成节点输出 | 下游读不到刚算出来的价格 |
| 人工审核方块 vs 检查点 | 方块表示等人点；检查点表示能序列化、能恢复、副作用不重复 | 会用「点过一次暂停」代替模块 11 的验收 |
| 产品跑通了 vs 原理学完了 | 跑通说明这条业务在产品里能走；原理是你能指出藏起来的循环和状态 | 会把一天的拖拽当成模块 07 / 11 的替代 |

## 例子

### 生活：房间、传送带、台卡、商场收银

**智能体应用。** 新店员被关在房间里，只给他一张可以打的电话清单（库房、收银台）。客人的句子从门缝递进去。他在房间里来回打电话。你只收到他推门递出来的那一句「热拿铁可以做」。房间里的来回就是循环。你没有那张通话记录的所有权。

**工作流画布。** 后厨传送带上贴着「点单 → 做热饮 → 出品」。杯子上的贴纸（大杯、去冰）是状态。传送带的马达是调度器。你能改贴纸和站点牌子，不能把马达拆开看它怎么拒绝「没付款就出品」。

**会话变量。** 台卡上写着「这位大杯、不要香菜」。下一轮服务员还看得到。台卡归餐厅系统，不归你口袋里的笔记本。第二句「还是大杯，换成冰的」读的是台卡，不是服务员的临时记忆。

**回边。** 库房电话回来说没有热拿铁。传送带把杯子送回「再问一句要不要换」。带子绕回去，形状你看得见。马达仍不是你的。台卡上若没有「已经问过 1 次」，这杯会一直转。

**一次加热。** 传送带上的加热箱只加热这一次。它不会自己再去打电话问库房。要再问，得有绕回去的带子，或有一个会自己连续打电话的房间（智能体节点）。

**岔路指错。** 有人把「未付款」的牌子直接指向「出品」。手写后厨的班长会拿允许通行的名单拦住。商场这套传送带拦不拦，要看这次杯子有没有真的过去，不能凭自己店里的班长推断。

**小窗算价。** 传送带中间开了一个小窗。你塞进一张纸条：大杯加 6 元。纸条上的草稿算出门就扔。只有你把「应付 28 元」写到杯子贴纸上，下一站才读得到。整条带子仍不是你的。

**账本和商场屏幕。** 自己的账本每一笔谁记下的、错了改哪一行，你都清楚，也能复印给同事。商场统一收银你只会点「收款 / 退款」。同事拿走你的笔记本，看不到商场屏幕上的那张图。

**退款。** 屏幕上可以弹出「等店长点头」。店长点了，款扣了，然后断电。来电之后系统若把同一次扣款再做一遍，那个弹窗并没有变成你自己的账本，也没有「这一笔记过了」的编号。这种单子要收回自己的本子来记。

### 前端：低代码流程、一次请求、没有 reducer 的面板

前端对照用同一家店的点单小程序。

**智能体应用**像你只调用了 `await chat(text)`。消息数组的追加、工具结果塞回去、什么时候停，都在这个函数私有的实现里。模块 07 是你自己写那个 `while`。

**工作流画布**像低代码流程（飞书自动化、简道云）：你拖「收到句子 → 若是热饮 → 发回复」。流程引擎在人家的服务里转。Redux 的 store 仍是一份，但你没有 `createSlice`。变量面板像一个只能在节点表单里改字段的状态面板。

**会话变量**像状态存在一个你没有源码的会话服务里。第二轮请求还能读到 `cupSize`。它不是你仓库里的 `type OrderState`。刷新规则、活多久，由产品定。这也不是模块 10 那种按话题检索的记忆。

**回边**像流程配置里从节点 B 指回节点 A。圈在配置上看得见。执行这个圈的是流程引擎。次数上限要么是引擎提供的字段，要么是你自己放进变量的计数。

**大模型节点**像按钮处理函数里一次 `fetch`。一次请求不是带重试的 `while`。

**条件分支**像低代码的「如果金额大于 0」。它负责选路。它不是你写的那份「只允许这些下一站」的名单校验。名单校验在不在，要看这次运行。

**代码节点**像塞进流程的一个函数。函数里的 `const price` 返回就丢。流程变量里要出现价格，这个函数得把价格放进返回值，由引擎合并进全图那份状态。

**代码框架**像图的源码在 Git 里：同事拉下来就能跑、能写测试、能在日志里看到每一步。编排产品的图在网站账号里。只拉仓库的人看不到它。

**人工方块和检查点**要分开。页面上的「等待审批」组件表示流程停住。检查点是把当前状态写成可以恢复的数据，并且同一笔扣款有编号，恢复时认这个编号，不扣第二次。组件在，这两件事仍可能没发生。

## 需求清单

这九条是以后验收用的，不是要一次做完的施工单。前八条是同一家咖啡店；最后一条用退款把「必须收回代码」单独站住。

1. **微信自动回复用智能体应用。** 场景：只配人设和「查库存」，客人问热拿铁。目标：得到一句回复，并指出转圈发生在哪。知识点：智能体应用把循环藏在产品里。验收：能指出没有你的 `while`，消息列表你不能当数组去改。
2. **店长要看流程，改成工作流画布。** 场景：开始 → 识别冷热 → 热 / 冰 → 回复。目标：每个方块能对上模块 11 的节点。知识点：画布藏调度器和状态类型。验收：能说出连线是边，变量是状态，调度器不在仓库里。
3. **第二句「还是大杯，换成冰的」。** 场景：同一段聊天的第二轮要读到杯型。目标：用会话变量保住杯型。知识点：聊天流的跨轮状态。验收：能指出这是产品里的字段，不是你声明的 TypeScript 类型，也不是模块 10 那套记忆。
4. **库存不足，线拉回「问要不要换」。** 场景：画布上出现回边，并用一个变量记下已经问过几次。目标：圈看得见，次数有上限。知识点：回边的形状归你画，执行归产品。验收：能讲清没有你的 `while`，没有次数变量就会一直绕。
5. **有人指着单独一个大模型节点说「它会自己循环查库存」。** 场景：该节点只负责从句子里抽出饮品名。目标：把一次调用和循环分开。知识点：大模型节点默认是一次调用。验收：能说明查库存若要再跑，必须是回边或智能体节点。
6. **实习生把「未付款」连到「出品」。** 场景：条件分支的出边画错。目标：对照手写版的边表。知识点：条件分支不等于边表核对。验收：能讲手写版会拦；产品拦不拦必须看这次运行，不能脑补。
7. **杯型价格用代码节点算。** 场景：上游给入杯型，节点返回价格。目标：划清「这一小段归你、走到哪归产品」。知识点：局部变量不自动进全图状态。验收：能说明价格要写成输出变量，下游才读得到；会不会走到这个节点仍由产品决定。
8. **负责人问为什么不写成 LangGraph。** 场景：同一张点单图要进仓库、要测试、要自己的日志。目标：三条划界。知识点：代码框架和编排产品。验收：能说出代码在不在仓库、状态是不是你的类型、每一步的日志归不归你。
9. **退款要人点头，并且进程杀掉后不能再扣一次。** 场景：危险操作。目标：认出产品上的人工方块覆盖不到检查点和去重。知识点：体验交差不够的那一层。验收：能讲这条要回到自己的代码，不能只靠编排产品。

## 踩坑

- 把单独一个大模型节点讲成「里面有整段 Agent 循环」。一次调用不会自己再去查库存。
- 第二轮丢了杯型，却去改提示词。该放进会话变量的字段没放。
- 把会话变量当成模块 10 的记忆系统，不再做检索和摘要。
- 回边没有次数变量，库存不足时一直问。
- 代码节点里算出了价格，没写成输出变量，回复节点读到空。
- 用模块 11 的边表记忆，断言编排产品一定会拦住「未付款 → 出品」。
- 把密钥写成这一趟订单的状态，或把杯型写成全局环境变量。
- 拖了一个知识库节点，就说循环已经学完。知识库节点是检索那一跳。
- 退款只留了一个「等人点头」的方块。重启之后同一笔又扣了一次。
- 同事只克隆仓库来排查事故，图在 Dify 账号里，仓库里没有逐步日志。

## 过关自检

关上文件后还能讲出这三句：

1. 智能体应用藏的是整段循环。你只配人设和工具，转圈在产品里，消息列表不归你。
2. 工作流让你看见节点和变量。藏的是调度器和状态类型。连线是边，变量是状态，仓库里没有 `step(state)`。
3. 有副作用、要人点头、要杀进程再起来的业务，产品上的方块不能代替你自己的检查点，也不能保证同一笔扣款不会再做一次。

再能用热拿铁指认：第二轮杯型在会话变量里；回边的圈看得见但执行不归你；单独一个大模型节点只调用一次；「未付款连到出品」不能脑补产品一定会拦；代码节点的价格要写成输出才进全图状态；和 LangGraph 的差别是代码在不在仓库、类型是不是你的、日志归不归你。

## 还没搞懂的

- 没有打开过 Dify，不知道你手里那个版本的菜单确切文案。体验时对上「藏循环」还是「藏状态」即可，不把某一天的按钮名写死。
- 编排产品运行时有没有模块 11 那种边表核对、核对有多严：没跑过，不编造。以你点出来的那次运行为准。
- 当前版本里「等人工输入」叫什么、进程重启后会不会重放已经扣过款的工具：没实测。讲的时候只坚持「方块不等于检查点，也不等于按调用编号去重」。
