### 一句话讲完这个模块

让 Coding Agent 在仓库里有边界地改文件——**能力块 + 改法 + 约束**，三件配套。能力块决定能做什么（File + Shell + Git + 测试 + 反馈循环）；改法决定怎么动（patch / Search-Replace / 结构化，而不是整文件重写）；约束决定被怎么管（AGENTS.md / SKILL.md 工程级拦截 + HITL）。任何一件配不齐，Coding Agent 都不稳。

### 这些条怎么连成一条线

- **16-01 产品形态** = **能力块**（**做**什么）。给 Agent 五件工具让它能动：File（read / write / list / grep）+ 受限 Shell + Git（diff / status / commit）+ 测试 + 反馈循环。少了一件 Agent 就改不了、验不了、追不动。
- **16-02 精确编辑** = **改法**（**怎么动**）。文件改法选 patch / Search-Replace / 结构化，而不是整文件重写——前者改 N 行只动 N 行周边、diff 干净、review 容易；后者改 N 行整篇重生成、diff 噪声巨大。预算、review、回滚、冲突解决全偏向精确 diff。
- **16-03 AGENTS.md / Skills** = **约束**（**被怎么管**）。用文档约束行为（禁区 + 工作流 + commit 规范），用 HITL（人在环路，Human-in-the-Loop）拦危险动作（删除 / force push / 改全局配置 / 提 PR），用 shell wrapper 工程级拦截；MCP（Model Context Protocol，模型上下文协议）是工具协议——加能力走 MCP，禁止走 AGENTS.md。三件配套。

**三者配套**：能力不齐 = 改不了；改法错 = diff 噪声 / 无关改动；约束不齐 = 危险命令 / 越界。任何一件配不齐 Coding Agent 都不稳。

| 能完成一个真实小任务：「给这个函数加单元测试并跑通」 | **这一步不是这一段能交付的代码，是学习者单独真实项目里要做的事**——讲得清：grep 找到函数定义 → read 同模块测试文件 → patch 加 test case（不要整文件重写测试文件）→ 跑 `vitest run path/to/test.ts` → 失败看 stderr 改 / 成功 git diff 看改动范围合理 → commit 信息含「Add unit test for X」。这一条把 16-01（能力块）+ 16-02（精确编辑）+ 16-03（commit 规范 + 测试通过才提交）三节串了起来。 |
| 有 Sandbox 或工作目录限制，Agent 不能碰工作目录之外的文件 | **能讲**：仓库 + 用户系统之间的硬边界。实现是 shell wrapper + read / write 工具层强制：Agent 试图 `cat /etc/passwd` 或 `rm /tmp` 都被 wrapper 拦下。AGENTS.md 写明，shell wrapper 工程级实施——两层都要。 |
| 危险操作（删除、force push、修改配置）必须人工确认 | **能讲**：HITL 是 Coding Agent 在生产里的最后一道防线。AGENTS.md 写禁区 + shell wrapper 拦截 + 危险动作前 Agent 暂停、请求真人按确认键——这三层独立防护，少一层不稳。 |
| 修改文件前有备份或依赖 Git 保护 | **能讲**：能回滚 = 能精准回到改之前的状态。Git 保护（diff + revert）比手动备份更稳；CI（持续集成） + lint 在改完自动跑（feedback loop 里）。这是 16-02「精确 diff 让 revert 干净」的延伸。 |

**自测问题同步回答（README 4 问）**

1. *Coding Agent 的权限边界怎么设计？* 三层独立防护：①仓库级（AGENTS.md 禁区 + 工作流 + commit 规范）；②工具级（Shell 白名单 + 文件工具沙箱）；③HITL（危险动作真人确认）。三层都不可省——文字约束模型偶尔违反，工程拦截不可越界，真人在环路兜底最后的语义判断。

2. *如何让 Agent 精确编辑文件而不是整文件重写？* AGENTS.md 写「改文件用 patch」+ 工具侧支持 Search-Replace / unified diff（统一格式的修改片段） + 改完跑 `git diff --stat` 验证改动范围。整文件重写的失败方式（无关代码 / 缩进换风格 / 整篇噪声）要在 review 里被看见。

3. *Shell Tool 的安全风险有哪些？* 删（`rm -rf`）、传（force push / 危险配置 / 远程脚本执行）、装（`apt remove`）、写（改全局配置 / 写 token）、改（破坏性命令 / 提 PR 不 review）。底线是白名单 + wrapper 拦截 + 危险动作 HITL。

4. *Skills / AGENTS.md 解决什么问题？* 把团队的「不许做 + 该怎么做」写进 Git，新人新会话都生效——避免每次开会重新对齐。Skills / AGENTS.md ≠ MCP：前者文档，后者工具协议。两者一起决定 Coding Agent 全集。

### 最容易记错的三条（跨条）

1. **规则文件 ≠ MCP**。AGENTS.md 约束行为；MCP 扩展能力。两者一起决定 Coding Agent 全集（能做 + 不许做）。混淆就会出现「我加 DB（数据库）查询写到 AGENTS.md / 我禁 force push 写到 MCP」——两件错位的事。
2. **整文件重写 ≠ 一定错；patch ≠ 一定最优**。新建文件 / 文件 < 100 行 / 大段重写时整文件重写是合法选择（token 更省）。大段改时硬拆 patch 反而累。要按场景选粒度。
3. **跑测试 ≠ 改对了**。测试 pass 只意味着「按规则对得上」，不等于「改的语义对、风格对、改动范围合理」。Review 仍要看 diff、看代码逻辑、看下游影响；不要把 CI 绿当成「我改对了」。

### 跨条踩坑

- **整文件重写丢无关代码**。改 1 行整篇重生成 → diff 全是噪声（16-02）。
- **裸 shell / 没有白名单 / 没有 HITL**。`rm -rf` / force push 一发不可收（16-01 / 16-03）。
- **规则当工具用**——加数据库查询写到 AGENTS.md，毫无作用（16-03）。
- **工具当规则用**——禁 force push 写到 MCP，加不上（16-03）。
- **AGENTS.md 改了但 shell wrapper 没改**——规则与执行脱节（16-03）。
- **不分优先级**——用户一句「这次别管 AGENTS.md」覆盖禁区（16-03）。
- **反馈循环跑一次就提交**——没跑测试 / 没看 stderr（标准错误输出流） / 没比对 diff（16-01）。
- **跑测试通过 ≠ 改对了**——CI 绿不等于语义对（16-01 / 自测）。
- **Skill 当 MCP 错位**（16-03）。
- **禁区写在 Tool Description 里**——模型以为那是工具的能力说明（16-03）。
- **上下文窗口（Context Window）一次塞整个仓库**——大仓库 = 上下文窗口爆（16-01）。
- **改完没跑过 test / lint**（16-02）。
