### 一句话讲完这个模块

让 Agent 上线后**能定位、能算钱、能脱敏**——17 模块给了上线前的门禁（评测 / ship-no-ship），18 模块给上线后的眼睛（trace / span / UI）。**两件配套，缺一件就出事**。

### 这些条怎么连成一条线

- **18-01 Trace / Span** = **概念与协议**（**骨架**）。一次 Agent 调用 = 1 条 Trace；trace 内 N 个 Span。Span 类型（LLM / Tool / Agent / Chain）、父子关系、metadata（input / output / model / token / cost / latency）。**协议层**：OpenTelemetry 是行业标准，Langfuse / LangSmith / Phoenix / Helicone / OpenLLMetry 是具体实现。
- **18-02 轨迹可视化** = **UI 落地**（**界面**）。把 trace 渲染成可点击的视图：树 / 时间轴 / 详情面板 / 过滤搜索 / 统计面板。Langfuse / LangSmith / Phoenix 是主流 UI。**Dataset 联动**（trace 标 bad → 自动进 dataset）让 UI 与 17 模块评测联通。

**两件配套**：没有协议 = UI 没有数据；没有 UI = 协议就是死 log。两者一起：从「上线后无法定位」变成「上线后能查、能算、能跨团队查、能联动评测」。

### 模块验收对答

按模块 18 README「验收」6 条逐条答：

| 验收项 | 我的回答 |
| --- | --- |
| 1. 每次 Agent 执行有唯一 trace id，能串起全链路 | **能讲**：每次 agent 调用由 SDK 生成唯一 trace_id，跨 span 共享。跨服务用 W3C Trace Context（跨服务 trace 传播协议）把 trace_id 透传到下游服务；服务 B 接到 trace_id，作为自己 root span。**没有 trace_id = 跨服务问题定位不可能**。 |
| 2. 每个 LLM Call 和 Tool Call 都是一个 Span，记录输入、输出、耗时、Token | **能讲**：每个独立事件是 Span。LLM span 记 model / prompt / response / input_tokens / output_tokens / latency / cost；Tool span 记 tool_name / args / result / latency / error。**metadata 全是关键**，缺一项等于盲区。 |
| 3. 能在 UI 上可视化看到完整 Agent Trajectory | **能讲**：UI（Langfuse / LangSmith / Phoenix）把 trace 渲染成树 / 时间轴 + 详情面板 + 过滤搜索 + 统计面板。**点开 span 看 input/output 是核心交互**——这跟 console.log 一行行扫难度差 9 倍。 |
| 4. 记录了成本：每次执行花了多少钱 | **能讲**：每 LLM span 算 cost（model 定价 × token 数）。UI 报表聚合一段时间 cost + token；drill-down（逐层下钻，从汇总数据点开看明细）定位某 trace / 某 span。**与计费对得上 = 关键**。 |
| 5. 出错时能定位到具体是哪一步、什么输入导致的 | **能讲**：典型工作流：用户报错 → support 拿 user_id + time → UI 过滤找 trace → 点开 trace → 找到错 span → 看 args / error → 标 bad → 联动 dataset → 17 模块评测查同类问题。**没有这套工作流 = 凭感觉 debug**。 |
| 6. 敏感信息在日志中做了脱敏 | **能讲**：所有 PII（个人可识别信息）字段（密码 / 卡号 / 身份证 / token / 订单详情）在写 trace 前脱敏——hash（哈希，把数据变换成固定长度不可逆值）/ 截断 / 完全不记。**UI 端也得 mask 一次**——后端脱了 UI 仍显示明文 = 泄露。**GDPR / 隐私法遵规**。 |

**自测问题同步回答（README 3 问）**

1. *如何排查一个 Agent 的错误？* **典型工作流**——拿 user_id + time，过滤 UI trace，点开错 span，看 args / error，标 bad；要不要联动 dataset 跑评测看同类问题。
2. *Trace 和 Span 的关系？* **一次 Agent = 1 Trace，N Span**。Trace 是整体，Span 是某一事件；Span 之间有父子关系（root / parent / child）。每个 LLM / Tool Call 是叶子。Trace ID 跨 Span 共享；Span ID 各自唯一。
3. *你会记录哪些指标？* **span 内 metadata**：LLM = model / prompt / response / token / cost / latency；Tool = tool_name / args / result / latency / error。**trace 级 metadata**：user_id / session / env / feature_flag。**配合采样策略**：production ≤10% + 失败 trace 100%。

### 最容易记错的三条（跨条）

1. **Trace ≠ Log**。Trace 是结构化执行轨迹（按 span 组织、有时间区间、父子关系）；Log 是单条消息（一次性、可冲掉）。用 log 当 trace = 还原不了路径。**调试 Agent 出错 = UI 持久化 trace，不靠 console.log**。
2. **UI 也要脱敏**。trace 后端脱了不代表 UI 端也脱——Langfuse / LangSmith / Phoenix 后端都会在 metadata 层 mask；但 UI 的某些二次展示（如 query 字符串、参数预览）可能漏。**两层 mask 都要有**。
3. **Trace / Span 不是性能问题，是事故定位能力**。上线后出事故没有 trace = 看着输出反推不出问题。**事故调查能力 = 留出 trace_id + 能按 user_id 找回**。

### 跨条踩坑

- **不接 trace 只 console.log**（18-01）。
- **trace 落敏感信息**（18-01 / 18-02 UI 端两层都要脱敏）。
- **trace_id 不传到下游服务**——跨服务看不到（18-01）。
- **Span type 不分**（18-01）。
- **LLM span 不记 token / cost**——算不出钱（18-01 + 18-02 cost 报表）。
- **Production 全量 trace**——存储费用崩（18-01）。
- **失败 trace 不保采**——事故现场恰好被采样掉 = 看不到（18-01 + 18-02 dataset 联动）。
- **Trace 没有 user / session 关联**——找不回具体那条（18-01）。
- **Dataset 联动断**——评测与线上脱节（18-02）。
- **UI 过滤维度不全**——找不到那条 trace（18-02）。
- **团队权限没分级**（18-02）。
