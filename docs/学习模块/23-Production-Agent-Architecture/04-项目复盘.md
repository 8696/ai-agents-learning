> 各节写什么、怎么判断归哪一节、达标要求：见仓库根 [AGENTS.md §7.2](../../../AGENTS.md#72-沉淀--小节进度对齐)。

### 是什么

**Demo 复盘**是给每个 `apps/{小节}-step-N/` **写一份经验总结**——**不是讲做了什么**，是讲**卡在哪 / 怎么解的 / 若重做改哪三处**。

#### 复盘 vs 完成

```
完成 = 代码能跑 + README 有
复盘 = 「下次做类似 Demo 速度 +50%」
```

**复盘给谁看**：
- 未来读代码的**自己**（3 个月后忘了细节）
- **同事 / 接手者**（换人维护）
- **未来做类似 Demo 的自己**（下一个 step）

#### 三问模板

每个 Demo 都填三个问题：

| 问 | 答什么 | 例子 |
|----|--------|------|
| **最难的三点** | 卡在哪 | 「异步流式 + 状态管理」 / 「Tool 参数 schema 反复调」 / 「错误态没设计」 |
| **怎么解的** | 怎么想出来 | 「参考 Vercel AI SDK 的 SSE 写法」 /「画了三版 schema 才定」 |
| **若重做改哪三处** | 事后反思 | 「抽象一个流式 hook」 / 「schema 用 Zod 校验」 / 「错误态一开始就设计」 |

**关键**：**三问填满，每个 Demo 至少 3 分钟能讲清**。

一句话：**Demo 复盘 = 「为未来读代码的自己留经验」——三问填完，下次类似 Demo 速度 +50%**。

### 为什么（Agent 开发要懂）

具体后果（举四个最常见的）：

1. **3 个月后看不懂**：当时写得清楚的代码，3 个月后忘了 → 30 分钟白花 → 不写复盘就等于放弃过去的自己。
2. **同事接不住**：换人维护 → 新人完全不懂 → 推倒重来 → **浪费两个人的时间**。
3. **重复踩坑**：下一个 Demo 重新踩同样的坑 → **经验没复利**。
4. **不知道改进了什么**：不知道自己变好了 → 信心问题 → 没动力 → 越做越没劲。

Demo 没复盘 = **过去的工作 80% 浪费**。

### 易混点

Demo 复盘常被和它的「邻居文档」混淆。**判错任何一个会让复盘失去价值**——必须分清。

#### Demo 复盘 vs 入门指南

| | Demo 复盘 | 入门指南 |
|---|---|---|
| **读者** | 未来读代码的自己 / 同事 | 新手（要上手） |
| **重点** | **卡在哪 / 怎么解** | **怎么跑 / 怎么改** |
| **形式** | 经验总结 | 步骤清单 |

**判错会怎样**：把入门指南当复盘 → 半年后看不出哪里哪里翻车。

#### Demo 复盘 vs 选型文档

| | Demo 复盘 | 选型文档 |
|---|---|---|
| **重点** | **过程**（怎么想到这个解） | **结果**（为什么选） |
| **读者** | 维护者 | 评估者 |

**判错会怎样**：把选型文档当复盘 → 看不到「试过的弯路」。

#### Demo 复盘 vs 模块复盘

| | Demo 复盘 | 模块复盘 |
|---|---|---|
| **粒度** | **单条 Demo**（step-N） | **整个模块**（多条小节） |
| **内容** | 这条 Demo 的三问 | 整个模块怎么连成一条线 |
| **位置** | `apps/{小节}-step-N/REVIEW.md` | `docs/学习模块/{模块}/04-模块复盘.md` |

**判错会怎样**：把模块复盘塞进 Demo 文档 → 单条 Demo 看不清。

#### 诚实复盘 vs 自我吹嘘

| | 诚实复盘 | 自我吹嘘 |
|---|---|---|
| **态度** | 承认失败 | 只说成功 |
| **价值** | **避免再踩** | 自我满足 |

**判错会怎样**：只说成功 → 别人接不住 → 自己也学不到教训。

#### 若重做 vs 全部推翻

| | 若重做 | 全部推翻 |
|---|---|---|
| **态度** | 改进（保留好经验） | 否定过去 |
| **关系** | 在已有基础上改 | 从头来 |

**判错会怎样**：每次复盘都「若重做就全推翻」→ 永远从 0 开始 → 没积累。

### 核心概念（变体 / 分支全扫）

Demo 复盘有 10 个变体。

#### 1. 三问模板

**模板**：

```markdown
## 复盘

### 最难的三点
1. [第一个难点]
2. [第二个难点]
3. [第三个难点]

### 怎么解的
1. [第一个怎么解]
2. [第二个怎么解]
3. [第三个怎么解]

### 若重做改哪三处
1. [第一处改进]
2. [第二处改进]
3. [第三处改进]
```

**例子**：工程日志 = 这次哪里翻车了 / 下次怎么避；写完忘翻车等于忘了。

**需求 1（三问模板）**：为 `apps/00-01` 这条 Demo 写完整三问；每个问题填具体内容。

#### 2. 每个 Demo 三问填好

**填三问的步骤**：

1. **最难三点** — 回顾写 Demo 的过程，写下 3 个最卡的地方
2. **怎么解的** — 每个卡点怎么想出来的；什么资料 / 谁帮 / 试错
3. **若重做改哪三处** — 站在现在的角度，重做会改什么

**需求 2（每个 Demo 三问）**：每个 `apps/{小节}-step-N/` 都有三问；至少 10 条 Demo 都填。

#### 3. 横向对比

**对比各 Demo**：

| Demo | 最难点 1 | 最难点 2 | 最难点 3 |
|------|----------|----------|----------|
| `00-01-step-1` | 端口 | 路由 | 流式响应 |
| `05-01-step-1` | Tool schema | 错误态 | Tool 返回解析 |
| `07-02-step-1` | Loop 控制 | 状态机 | Tool 调用 |

**找到模式**：流式响应 / 状态机 / 错误态反复出现。

**需求 3（横向对比）**：10 条 Demo 横向对比表；找出反复出现的难点。

#### 4. 可复用的工程模式

**反复出现的模式**：

| 模式 | 在哪出现 |
|------|----------|
| **流式响应 + chunked** | 00-01 / 01-03 / 22-01 |
| **状态机** | 02-02 / 07-02 / 21-02 |
| **重试 + 退避** | 19-01 / 19-02 / 21-02 |
| **错误态 + fallback** | 19-01 / 20-03 |
| **HITL** | 16-03 / 22-02 |

**需求 4（可复用模式）**：列出 5+ 个反复出现的模式 + 各自的 Demo 出处。

#### 5. 一次性 hack 清单

**不复用的 hack**：

| Hack | 在哪出现 |
|------|----------|
| **特定 Tool 的 schema**（自定义业务） | 05-02 / 12-03 |
| **特殊解析**（PDF / Excel） | 09-03 |
| **业务规则 hardcode**（特定公司） | 16-01 |

**特点**：不复用，但当时绕过了问题。

**需求 5（一次性 hack）**：列出 3+ 个一次性 hack + 出处。

#### 6. 复盘的诚实度自检

**自检清单**：

| 自检问题 | 答 |
|----------|------|
| 是否承认了失败？ | 是 |
| 是否写出了当时**不知道**什么 | 是 |
| 是否给了「若重做改哪」 | 是 |
| 是否避开了「夸大成功」 | 是 |

**判错代价**：不诚实的复盘 = 没人信。

**需求 6（诚实度）**：4 个自检问题全过。

#### 7. 复盘的复利

**每写一个复盘 = 下次 +50%**：

```
复盘第 1 个 Demo：3 小时
复盘第 5 个 Demo：1 小时（-67%）
复盘第 10 个 Demo：30 分钟（-83%）
```

**关键**：复盘的复利 = 经验积累 +模式识别 + 避免重蹈。

**需求 7（复利验证）**：在 10 条 Demo 完成后统计平均耗时变化。

#### 8. 复盘文档结构

**完整复盘文档**：

```markdown
# {Demo 名} 复盘

## 三问
（见 §4.1 模板）

## 关键文件
- lib/flow/xxx.ts
- routes/xxx.ts

## 关键依赖
- koa + tsx + HTM

## 测试结果
- 首 token 时间：1.2s
- 失败率：0%

## 给后来者的提示
- 「Tool schema 用 Zod 校验，不然运行时报错」
- 「错误态一开始就设计，别等挂了在补」
```

**需求 8（复盘文档结构）**：写完整 6 节结构。

#### 9. 复盘时机

**什么时候写**：

| 时机 | 价值 |
|------|------|
| **写完立刻** | 细节最清楚 |
| **3 个月后** | 知道哪些真有用 |
| **交接时** | 给接手者看 |

**最佳**：**写完立刻**（细节最清楚）。

**需求 9（复盘时机）**：写完 Demo 后立刻写复盘；不拖延。

#### 10. 复盘分享

**团队分享**：

- 周会讲一条 Demo 复盘（5 分钟）
- 写团队 wiki（永久沉淀）
- 开 PR 时附带复盘（review 时一起看）

**需求 10（复盘分享）**：把 5+ 条复盘沉淀到团队 wiki。
