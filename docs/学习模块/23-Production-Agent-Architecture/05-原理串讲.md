### 是什么

**原理串讲**是用**自己 `apps/` 里的例子**把前面学的 **5 大原理** 串起来——**不看资料能讲；缺一环能说出会怎样**。

#### 五大原理

| 原理 | 模块 | 一句话 |
|------|------|--------|
| **Token / Context** | 01 / 06 | **Token** 是单位；**Context Window** 是窗口 |
| **Tool Calling** | 05 | LLM **外部调用函数**的协议 |
| **Agent Loop** | 07 | LLM **多步推理 + 调 Tool** 的循环 |
| **RAG** | 08 / 09 | **检索 + 生成**的混合范式 |
| **MCP** | 12 | Tool / Resource / Prompt 的**统一协议** |

#### 串讲链路

```
Token / Context（基础）
   ↓ 提供
Tool Calling（扩展能力）
   ↓ 提供
Agent Loop（多步编排）
   ↓ 配合
RAG（外部知识）
   ↓ 用
MCP（统一协议）
```

**核心**：**任何一环断 = 整个 Agent 不工作**。

一句话：**原理串讲 = 「用自己 `apps/` 里的例子把 5 大原理串起来——缺一环能说出『会怎样』」**。

### 为什么（Agent 开发要懂）

**原理**单独看懂了，**串不起来 = 没真正懂**。

具体后果（举四个最常见的）：

1. **面试讲不清**：面试官问「讲一下 Agent 怎么工作的」→ 答「LLM 调 Tool」→ 面试官追问「Token 怎么算？」→ 答不上 → **挂**。
2. **调试失忆**：Agent 出错不知道是哪层的问题 → **盲目改**。
3. **架构混乱**：做新项目不知道该用哪层 → **每层都用上 = 过度设计**。
4. **团队沟通**：和同事讲「这个 Agent 怎么搭」→ 同事听不懂 → **沟通成本高**。

原理串不起来 = **没真正学懂**。

### 易混点

原理串讲常被和它的「邻居概念」混淆。**判错任何一个会让串讲断掉**——必须分清。

#### 原理 vs 工程

| | 原理 | 工程 |
|---|---|---|
| **是什么** | **抽象**（机制怎么走） | **落地**（用什么实现） |
| **关系** | 原理是工程的**基础** | 工程是原理的**实例** |
| **示例** | 「Tool Calling 是 LLM 调函数的协议」 | 「Anthropic 的 tool_use 字段怎么填」 |

**判错会怎样**：只懂工程不懂原理 → 换框架就懵；只懂原理不懂工程 → 落不了地。

#### Token vs Context

| | Token | Context |
|---|---|---|
| **定义** | **单位**（一个字 / 一段） | **窗口**（一次能装多少） |
| **类比** | 货币单位（元） | 钱包（一次能装多少元） |
| **关系** | Context Window = N 个 Token 的容量 | Token 是 Context 的**度量** |

**判错会怎样**：把 Token 当 Context → 不知道窗口限制；把 Context 当 Token → 不知道计费单位。

#### Tool Calling vs Function Calling

| | Tool Calling | Function Calling |
|---|---|---|
| **定义** | 现在**通用**叫法 | OpenAI 起的旧名 |
| **协议** | function call / tool_use 字段 | — |
| **关系** | **两者**指**同一件事** | — |

**判错会怎样**：以为是两个概念 → 文档互相看不懂。

#### Agent Loop vs ReAct

| | Agent Loop | ReAct |
|---|---|---|
| **定义** | **多步推理 + 调 Tool** 的循环 | **一种实现方式**（思考 → 行动 → 观察） |
| **关系** | Agent Loop 是**框架**；ReAct 是**填充** | — |

**判错会怎样**：把 ReAct 当 Agent Loop 的唯一实现 → 不知道还有其他（Plan-Execute / ReflAct 等）。

#### RAG vs Embedding

| | RAG | Embedding |
|---|---|---|
| **定义** | **检索 + 生成**的混合范式 | 把文本**转成向量**的一步 |
| **类比** | 餐厅 = 厨师 + 食材 + 流程 | 厨师**切菜**这一步 |
| **关系** | RAG 包含 Embedding | Embedding 是 RAG 的**一步** |

**判错会怎样**：把 Embedding 当 RAG → 没做检索；把 RAG 当 Embedding → 只算了向量没生成。

### 核心概念（变体 / 分支全扫）

原理串讲有 10 个变体。

#### 1. 原理串讲的意义

**为什么串**：每个原理单独学只是「点」；串起来才是「面」。

```
懂 Token = 懂一个字
懂 Tool Calling = 懂调一个 Tool
懂 Agent Loop = 懂多步
懂 RAG = 懂检索 + 生成
懂 MCP = 懂协议

串起来 = 懂「Agent 怎么工作」」
```

**例子**：厨师做菜 = 知道食材（Token）+ 切菜（Tool）+ 烹饪（Loop）+ 上菜（RAG）+ 客人点菜（MCP）。

**需求 1（原理串讲）**：用 5 分钟口述 5 大原理怎么串起来。

#### 2. Token / Context 讲清

**核心**：

- **Token = LLM 的「单位」**——一个字 / 一段被切成 Token
- **Context Window = 一次能装多少**——典型 8K / 200K / 1M
- **预算**：输入 + 输出 ≤ 窗口
- **超限**：截断 / 报错

**`apps/` 例子**：`apps/02-01-...` 计费统计能看到 Token；`apps/06-01-...` Context Window 实验。

**例子**：画家画画 = 颜料（Token）+ 画布尺寸（Context）。

**需求 2（Token / Context）**：讲清 Token 是什么 / Context Window 是什么 / 怎么算预算。

#### 3. Tool Calling 协议讲清

**核心**：

- LLM 在 `messages` 里返回 `tool_use` 字段（Anthropic）/ `tool_calls`（OpenAI）
- 客户端解析 → 调 Tool → 把 Tool 返回塞回 `messages` → 再调 LLM
- **Schema 用 JSON Schema**（Anthropic `input_schema` / OpenAI `parameters`）

**`apps/` 例子**：`apps/05-01-...` 真调 Tool；`apps/05-02-...` Tool 参数设计。

**例子**：建筑师盖楼 = 建材（Tool）+ 结构（协议）。

**需求 3（Tool Calling 协议）**：讲清 LLM 返回什么 / 客户端怎么做 / Schema 怎么填。

#### 4. Agent Loop 机制讲清

**核心**：

```
loop:
  思考：LLM(messages + 可用 Tool)
  行动：LLM 决定调 Tool（或直接输出）
  观察：把 Tool 结果塞回 messages
  终止：LLM 输出最终答案
```

**`apps/` 例子**：`apps/07-01-...` Agent Loop；`apps/07-02-...` 状态机控制。

**例子**：建筑师盖楼 = 建材（Token）+ 结构（Tool）+ 设计（Loop）。

**需求 4（Agent Loop）**：讲清 思考 / 行动 / 观察 三步循环。

#### 5. RAG 流程讲清

**核心**：

```
1. load: 加载文档
2. chunk: 切块
3. embed: 转向量
4. retrieve: 检索
5. generate: 生成答案（含引用）
```

**`apps/` 例子**：`apps/08-01-...` RAG 基础；`apps/09-01-...` RAG 进阶。

**例子**：建筑师盖楼 = 建材（Token）+ 结构（Tool）+ 设计（Loop）+ 装修（RAG）。

**需求 5（RAG 流程）**：讲清 5 步 + 每步的常见问题。

#### 6. MCP 规范讲清

**核心**：

- **MCP（Model Context Protocol）** = Anthropic 提出的 Tool / Resource / Prompt 统一协议
- **Tool**（函数）/ **Resource**（数据）/ **Prompt**（模板）
- **OAuth 2.1 + PKCE** 鉴权

**`apps/` 例子**：`apps/12-01-...` MCP 客户端；`apps/12-02-...` MCP 服务端。

**例子**：建筑师盖楼 = 建材（Token）+ 结构（Tool）+ 设计（Loop）+ 装修（RAG）+ 业主需求（MCP）。

**需求 6（MCP 规范）**：讲清 Tool / Resource / Prompt 三件套 + 鉴权。

#### 7. Token → Tool → Loop 链路

**完整链路**：

```
用户问 ──► Token 化 ──► messages
                          ↓
                       LLM 思考（Token 消耗）
                          ↓
                       决定调 Tool
                          ↓
                       客户端调 Tool（Tool Calling 协议）
                          ↓
                       Tool 结果塞回
                          ↓
                       Agent Loop 继续（多步）
                          ↓
                       最终答案 ──► 流式响应
```

**`apps/` 例子**：`apps/07-02-...` 完整循环。

**需求 7（Token → Tool → Loop 链路）**：用 ASCII 画完整链路。

#### 8. RAG → MCP 链路

**完整链路**：

```
用户问 ──► RAG 检索（Vector DB）
          ↓
      检索结果（Resource via MCP）
          ↓
       LLM 生成答案（含引用）
          ↓
       流式响应
```

**`apps/` 例子**：`apps/12-03-...` MCP + RAG 整合。

**需求 8（RAG → MCP 链路）**：用 ASCII 画 RAG 与 MCP 的整合。

#### 9. 缺一环会怎样

**5 个具体后果**：

| 缺哪环 | 会怎样 |
|--------|--------|
| **Token 预算** | Context 超限 → 截断或报错 |
| **Tool Calling 协议** | 解析错 → Tool 没调对 |
| **Agent Loop 控制** | 死循环 → 资源耗尽 |
| **RAG 检索** | 召回低 → 答得不准 |
| **MCP 协议** | Tool 接入混乱 → 不可维护 |

**例子**：建筑师盖楼 = 缺哪一项都盖不起来。
