## 是什么

### 0. 先立地基：模型自己没有记忆

调一次对话补全接口（Chat Completions），把一段文字发过去，模型算一遍，返回一段文字，模型那边什么都不留。模型的权重（Weights）在推理时是只读的,不会因为这一次对话就改变一个数字。下一次请求对模型来说是全新的一次，它不认识你。

ChatGPT 之类产品看起来「记得」，是因为客户端每次都把历史消息重新发了一遍。所以：

> **Agent 的「记忆」在工程上 = 一套决定「这一次请求，往上下文窗口（Context Window）里塞哪些字」的机制，加上它背后的存储。**

由此推出一条铁律：**任何记忆，最终都必须变成上下文窗口里的字，否则等于不存在**。数据库里存了一万条用户偏好，但这次请求没把它拼进 `messages`，模型就是不知道。很多「记忆功能不生效」的故障，查到最后都是这一步断了。

既然记忆是「存什么 + 什么时候拼进去」，不同内容的保存期限、更新方式、召回方式都不一样，混在一起做必然出问题，所以要分类。这套分类借自认知心理学（人的记忆研究），CoALA 论文和 LangGraph 的记忆文档用的是同一套词。

### 1. 工作记忆（Working Memory / Conversation Memory）

当前这一次任务、这一轮会话**正在用**的信息，直接躺在上下文窗口里，模型这一次就能看见，不需要检索。

里面装什么：历史消息列表 `messages`（历史 user / assistant 轮次 + 最新这一问）；本轮工具调用（Function Calling）的调用与 `tool_result`；本轮的中间产物（规划器吐出来的步骤清单、算到一半的中间结论）；模块 06「多轮对话与 Context」做过的摘要（把远期历史压缩成一段话，压缩结果仍留在工作记忆里）。

特点：容量小（受 Token 预算限制）、生命周期短（会话结束或被裁剪就没了）、读写最快（本来就在提示词里，不用检索）。

**跟模块 06 对上**：模块 06 整个模块处理的对象就是工作记忆，当时做的「超预算就丢最旧的几轮、远期喂摘要」，本质是**工作记忆的容量管理**。

**生活例子**：心算「37 乘以 24」。脑子里先记住「37×20 = 740」，再算「37×4 = 148」，最后加起来。中途的 740 就是工作记忆——必须在，不然算不下去；但算完去吃饭回来绝对想不起来这个数。它只需要撑过这一小段过程。

**前端例子**：React 组件的 `useState`。用户在表单里敲的字存在 state 里，组件重渲染时还在，这是工作记忆；页面一刷新，state 归零。不会指望 `useState` 帮你跨会话记住用户偏好——那要写进后端或 localStorage，就是长期记忆的事。

### 2. 情景记忆（Episodic Memory）

**带时间、带场景的「经历」**——某时某刻，发生了什么事，做了什么，结果如何。记的是「一件事」，不是「一个结论」。

里面装什么（通常带时间戳、会话编号、参与者、结果）：第 3 次会话里用户抱怨过发货太慢；上周二 14:30 调用过 `refund` 工具，参数是订单号 A123，返回 403 权限不足；处理「批量改价」任务时先试一次性调接口超时失败，改成分批 50 条成功了。

怎么用：按「相似情境」召回（向量检索：这次任务跟哪次历史经历像），或按时间倒序取最近 N 条。它是 Agent 能说出「上次也遇到过这个，那次的做法是……」的来源，也是从成功/失败经历里挑 few-shot 范例来自我改进的原料。

**生活例子**：记得「去年国庆在南京路那家鞋店买鞋，店员态度特别差，最后没买」。这条记忆有时间（去年国庆）、地点（那家店）、事件经过、结果（没买）。今年路过那家店，「同一家店」这个线索勾起这段经历，于是绕开了——**线索触发召回，召回影响当下决策**。

**前端例子**：客服工单系统的「该用户历史工单列表」。用户问「我那个退款怎么样了」，坐席点开历史工单看到「9 月 2 日 工单 #8821 退款申请 已驳回 原因：超出 7 天」。这一条是情景记忆：具体的事件记录，不是一句关于用户的事实。

### 3. 语义记忆（Semantic Memory，含用户记忆 User Memory）

**脱离具体时间和场景的「事实」**——一句话拎出来就成立的结论。记的是「一个结论」，通常已经不记得这个结论是从哪句话、哪天提炼出来的。

里面装什么：这个用户叫张三，在支付团队；这个用户主用 Vue 3 加 TypeScript，不用 React；这个用户喜欢简短回答；公司退货政策是签收后 7 天内无理由。

结构：通常是一条条短句，或键值对（`framework: Vue 3`），带标签和来源。关键性质是**可更新、可覆盖、可删除**——用户说「我现在改用 React 了」，旧那条必须被改掉，而不是再追加一条让两条打架（怎么判断该不该写、怎么覆盖冲突，是下一小节「写入策略」的内容，这里只要知道语义记忆有这个需求）。

**用户记忆（User Memory）是什么关系**：它是语义记忆里「关于用户本人的那一部分」，是产品里最常见的形态，ChatGPT 的 Memory 功能、各家 Agent 产品的「个性化」基本都是这个。语义记忆比它大一圈，还包括关于世界的、关于公司业务的事实。

**生活例子**：知道「巴黎是法国的首都」，但几乎肯定想不起来这是哪一年、在哪本书、哪节课学到的——**事实留下来了，产生这个事实的经历丢掉了**，这正是语义记忆和情景记忆最直观的分界。人脑很多语义记忆就是从情景记忆反复提炼、场景磨掉形成的；Agent 系统里也一样，是从对话（经历）里抽取事实再落库。

**前端例子**：用户设置页。用户选了「主题=暗色，语言=中文，每页显示 50 条」，存在后端用户表里，换设备、换浏览器、过三个月，一登录就生效。没人关心他是哪天点的这个开关。这就是语义记忆：短、结构化、跨会话、可以随时改。

### 4. 程序性记忆（Procedural Memory）——第四类，进度表标题没写但不能漏

进度表「重点」列只写了三类，只讲三类会导致对号入座时对不上一大块东西，所以补上第四类。业界（CoALA 论文、LangGraph 记忆文档）都是四类并列的。

**「怎么做事」的规则和技能**——不是数据，是做法。

里面装什么：系统提示词里的人设与流程约定（「你是内部前端助手，回答先给结论再给代码」）；工具定义本身（工具名、描述、参数约束）——这就是在告诉模型「你会哪些技能」；沉淀下来的少样本范例（Few-shot）；从踩坑里校正出来的规则（「处理退款前必须先查订单状态」）。

特点：变化最慢；通常**不靠检索，而是常驻**在系统提示词或工具定义里，每次请求都带；改动它等于改 Agent 的行为本身，一般由开发者或离线流程来写，不由某一轮用户对话直接改。

为什么它算记忆：因为同样满足「跨会话保留下来、影响以后行为」。只不过语义记忆存的是「世界是什么样」，程序性记忆存的是「我该怎么做」。

**生活例子**：会骑自行车。说不出「保持平衡的方法是车头向倾倒方向微转」（所以不是语义事实），也不记得是哪个下午在哪条巷子学会的（所以不是情景经历），但跨上车就能骑。**存在身上，一直生效，不需要去回忆它**。

**前端例子**：项目仓库里的 ESLint 配置和组件模板。不是业务数据，没人去「查询」它；但每次写代码它都约束你「引号必须用双引号、组件必须写 props 类型」。新人进组不用背规则，保存文件时自动就被纠正了。Agent 的系统提示词就是它的 ESLint 配置。

### 5. 短期记忆 / 长期记忆这条轴（Short-term / Long-term）

> **短期 / 长期跟上面四类不是并列关系，是两根不同的轴。**

- **四类（工作 / 情景 / 语义 / 程序）回答的是「存的是什么内容」**
- **短期 / 长期回答的是「活多久、存在哪里」**

正确的问法不是「工作记忆和短期记忆有什么区别」（这问法把两根轴混成一根了），而是「工作记忆通常落在短期还是长期这一侧」。

判定口径：把进程杀掉再启动一次，它还在吗？**在 = 长期，不在 = 短期。** 更精确一点：短期活在进程内存或这一次上下文窗口里；长期活在外部存储（关系型数据库、键值库、向量库、文件）里。

| 四类内容 | 通常落在哪一侧 | 说明 |
| --- | --- | --- |
| 工作记忆 | 几乎总是短期 | 长在上下文窗口里，会话一结束或被裁剪就没了 |
| 情景记忆 | **两侧都有** | 「刚才这次工具调用失败了」是本轮内的短期情景；「9 月 2 日那张工单」写进数据库就是长期情景 |
| 语义记忆 | 绝大多数是长期 | 提炼成事实就是为了跨会话复用；刚抽出来还没落库的那一瞬间算短期 |
| 程序性记忆 | 长期 | 写在代码仓库或配置里，比数据库还稳 |

最容易被搞错的是**情景记忆横跨两侧**：很多人以为「情景记忆 = 长期的历史记录」，把本轮的工具失败记录也写进长期库，跑几天库里全是噪音。

### 6. 把四类串成一条链：一次请求的数据怎么走

```text
用户敲下一句话：「帮我把上次那个登录页的表单校验补上」
        │
        ├─① 程序性记忆（全员规则，常驻，不检索）
        │     listRules() → 写入这一次请求的系统设定区（system，即 messages 数组第 1 条）
        │     「你是内部前端助手；先给结论再给代码」
        │
        ├─② 核心用户画像（语义记忆 · 长期，常驻，不按问句筛）
        │     事实库里全部「语义 + 长期」整份写入同一条 system
        │     「主用 Vue 3 + TypeScript」「我是深圳人」
        │     问 B 时不会把问 A 用过的画像从 system 里换掉
        │     （库小、几乎每问都要用：ChatGPT 已保存记忆 / Letta 核心记忆的读法。
        │      条数大到几百条时，长尾才改按问句检索——step-3 单独演示检索，step-4 不走这条。）
        │
        ├─③ 本轮相关经历（情景记忆，按当前问句检索）
        │     只对经历做嵌入 + 余弦 + Top-K=3 + 阈值 0.10；语义画像不进候选池
        │     写入同一条 system 里单独一章：「9 月 10 日为 apps/login 写过 LoginForm.vue」
        │     下一问整章替换，不追加进对话历史；事实库里的经历还在
        │     问候 / 「刚才说了什么」 / 纯算术会跳过这一步，①② 仍带
        │
        ├─④ 工作记忆（对话历史，累积）
        │     不写进 system。接到 messages 数组里 system 那一条的后面
        │     角色（role）是 user / assistant
        │
        ▼
   每一次请求都重新组装完整的 messages（对话补全接口无状态）
        system 整段字符串通常会变（因为 ③ 换了）
        ①② 两章的内容来源不变（除非你改了规则库 / 事实库）
        ──→ 真发网络请求调模型 ──→ 模型返回答复
        │
        ▼
   回写（本小节只点到位置，具体规则是下一小节「写入策略」）
        ├─ 这一轮问答追加进工作记忆
        ├─ 这次会话发生了什么 → 可落一条情景记忆
        └─ 这轮里冒出来的新事实 → 抽取 → 覆盖旧事实 → 落语义记忆
```

四个关键点：

1. **常驻说的是读取策略，不是同一个存储盒子。** 程序性是全员规则，清用户记忆不能动它；语义画像是这个用户的事实，可以改、可以删。两边都写入 system，只是因为这一次请求都要看见。
2. **不是所有长期记忆都按问句做 Top-K。** 条数少、几乎每问都要用的用户事实整份常驻；会无限变长的经历才按问句召回。step-4 改之前把语义也走情景那条检索，问改价时 Vue 会从 system 里消失——那是读错层，不是「规范」。
3. **整段 system 每问都是新拼的，不等于 ①② 被问句筛掉。** 对话补全接口没有一个活在服务器上的 system 对象可打补丁。变的是拼出来的整份文档；前两章从规则库 / 事实库原样拷，第三章按问句换。
4. **最后一步永远是「拼成一段文字」。** 模型只看见这次的 `messages`。system 就是数组第 1 条，不是数组外面另有一个槽。

## 为什么 Agent 开发要懂（不懂会有什么具体后果）

不是「分类清楚显得专业」，每一类混淆都对应一个真实故障。

**后果 1 · 全塞进消息列表 → 成本和效果同时崩。** 把所有历史消息一直往 `messages` 里堆，Token 数会因为每轮都把前面所有轮重发一遍而累积增长，还会触发模块 06 学过的「中间信息被忽略」问题——关键偏好埋在第 40 轮里，模型压根没注意到。

**后果 2 · 全塞进向量库 → 该覆盖的事实覆盖不掉。** 最典型的踩坑。用户三月说「我用 React」，九月说「我改用 Vue 了」。如果把两句话都当文本切块扔进向量库，库里同时存在两条互相矛盾的记录，检索时还可能因为某个词更突出而召回旧那条。**向量库天然是追加式的，而语义记忆需要可覆盖、可删除的更新语义**——这两个需求根本对不上，所以用户事实通常该放关系库或键值库（带稳定的 key，比如 `user:123:framework`），再用向量索引做辅助检索。

**后果 3 · 把经历当事实。** 用户某天随口说「今天有点头疼，先不搞了」。如果抽成一条长期事实「用户经常头疼」，三个月后 Agent 一上来就问候身体，用户会觉得毛骨悚然。经历是一次性的，事实是持续成立的，抽取时必须过这一道判断。

**后果 4 · 把事实当经历。** 反过来，把「用户叫张三」这种铁事实塞进向量检索的经历库，Agent 记不记得名字就取决于这次检索有没有命中，时灵时不灵。用户的感受是「它有时候认识我有时候不认识我」，比完全不认识还糟。

**后果 5 · 不区分短期和长期 → 两个方向都出事。** 一个方向：以为存下来了，进程一重启全没了（存在内存 Map 里）。另一个方向：本来只该活一轮的临时状态被永久写库，跑一周库里几万条垃圾，检索精度直线下降。

**后果 6 · 分不清程序性记忆。** 把「以后回答都先给结论」这种**对所有人都生效的行为规则**，写进了某个用户的用户记忆里。结果这条规则只对他一个人生效，而且下次清理用户记忆时被误删——规则悄无声息地消失。

**后果 7 · 出问题时定位不了是哪一层。** 用户投诉「它没记住我」，这一句背后至少要先问：没记住的是**核心画像**还是**某次经历**。核心画像（技术栈、城市）条数少、几乎每问都要用：故障通常是没写入、没注入这一次 system、或模型看见了却忽略——**不是**「这一问余弦没排进 Top-K」。经历才会走检索：写了但召回没命中、召回了但没写进 system「本轮经历」章、写进去了但被模型忽略。**分类清楚了才能一层层往下切**，否则只能瞎猜。这也是模块验收自测题「如何设计一个记忆系统」真正在考的东西。

## 易混点

### 易混 1 · 记忆 vs 上下文窗口（Context Window）

上下文窗口是**容器**，有物理上限（比如 128K Token），是模型这一次能看见的全部。记忆是**制度**，决定往这个容器里放什么、什么时候放。

判错会怎样：以为「上下文窗口够大就不需要记忆系统了」。哪怕窗口一千万 Token，也不可能每次把用户三年的聊天记录全发过去——成本、延迟、注意力稀释三样都受不了。窗口变大只是让工作记忆宽裕些，不能替代长期记忆的提炼，也不能替代「画像常驻 / 经历按问句召回」这一层读取制度。

### 易混 2 · 记忆 vs 检索增强生成（RAG）

这一组最容易混，因为技术栈长得一模一样（都可能用嵌入 + 向量检索 + 拼进提示词）。差在三条：

1. **数据的主人不同**：RAG 检索的是**外部知识**（产品手册、法规、公司文档），对所有用户是同一份；记忆存的是**这次交互产生的东西**（这个用户的偏好、和他的历史），是一人一份甚至一会话一份。
2. **写入方不同**：RAG 的库是提前灌进去的，Agent 运行时基本只读；记忆是 Agent **自己在运行过程中写出来的**，是读写双向的。
3. **更新语义不同**：RAG 文档更新是「换一版文档」；记忆更新是「这条事实作废了，换成新的」，需要冲突处理。

判错会怎样：把用户记忆直接塞进 RAG 那套只读管线，于是没有覆盖机制（就是后果 2）；或者反过来，把公司产品手册当「记忆」按用户存了 N 份，存储浪费且更新时要改 N 处。

一句话记法：RAG 是「查资料」，记忆是「记住你」。

### 易混 3 · 情景记忆 vs 语义记忆

情景带时间和场景（「9 月 2 日他抱怨过发货慢」），语义不带（「他对物流时效敏感」）。**同一次对话可以同时产出两者**——存一条经历，再从经历里提炼一条事实，不是二选一。

判错会怎样：只存情景 → 每次都要检索长长的历史，慢且不准，模型得自己从流水账里归纳，容易归纳错。只存语义 → 丢掉证据链，用户问「你凭什么说我对物流敏感」，Agent 答不上来，也没法在事实抽错时回溯修正。

实践上：成熟系统两者都存，语义记忆里带一个指回情景记忆的来源标记。

### 易混 4 · 短期记忆 vs 工作记忆（不是同义词）

工作记忆是**内容分类**（当前任务正在用的信息），短期是**生命周期分类**（活得短）。绝大多数工作记忆确实是短期的，很多文章把两个词混着用——但反过来不成立：**短期的不一定是工作记忆**。本轮里「我刚刚调用工具失败了」是短期的情景记忆。

判错会怎样：把「短期」直接等同于「消息列表」，设计里漏掉了「本轮的经历（做过哪些尝试、哪些失败了）」这一块，Agent 在同一次任务里会重复犯同一个错——因为它没有把刚才的失败当成一条可以回看的经历。

### 易混 5 · 记忆 vs 日志（Log）

日志是**给人排查用的原始流水**，怕漏不怕多，要全、要原样。记忆是**给模型用的提炼结果**，怕多不怕少，要短、要准。

判错会怎样：直接把对话日志当记忆库——这就是本模块 README 写的常见坑「把所有历史消息都当作记忆存起来，检索时噪音巨大」。日志里大部分内容（寒暄、重复确认、修正过的错话）对下次决策毫无价值，还会挤掉真正有用的那一小部分。

注意：日志可以是记忆的**原料**（离线跑一遍抽取，把事实提炼出来），但原料不等于成品。

### 易混 6 · 记忆 vs 缓存（Cache）

缓存追求**同样的输入给出同样的输出，只是更快更便宜**，命中不命中只影响速度，不影响答案对错。记忆是**主动改变答案**：有记忆和没记忆，Agent 给的回答本来就该不一样。

判错会怎样：拿缓存的思路做记忆（比如设个短过期时间、容量满了就按最近最少使用淘汰），结果用户的核心偏好被自动淘汰掉。记忆的淘汰必须按「这条事实还成不成立」来判，不是按「最近有没有被用到」。

### 易混 7 · 用户记忆（User Memory） vs 系统提示词里的人设

人设是程序性记忆，**开发者写的、对所有用户一样、用户改不了**；用户记忆是语义记忆，**从对话里抽的、一人一份、用户能改能删**。

判错会怎样：两条都是「写进 system 的一段文字」，代码上很容易混在同一个字符串里。混了之后：用户说「忘掉关于我的一切」，一删把人设也删了；或者做记忆导出功能时，把公司的内部规则一起导给了用户。**存储上必须分开，拼提示词时才合并。**

### 易混 8 · 外部记忆 vs 模型参数里的「记忆」（微调 Fine-tuning）

微调是把知识写进**权重**，属于模型自己的一部分，改一次成本高、不可逐条删除、无法按用户隔离。这一小节讲的全是**外部记忆**：存在模型外面，随时增删改，按用户隔离。

判错会怎样：以为可以「微调一个记得用户的模型」。用户偏好每天在变，不可能每天给每个用户微调一次；用户要求删除个人数据时，也没法从权重里把它「删掉」。**凡是会变的、要隔离的、要能删的，一律走外部记忆。**

### 7. 写入策略：写入侧 3 道把关

光知道怎么分类还不够。**「一句用户原话从模型判类到真正写进事实库」中间必须再过一道把关**——这条把关不是模型给的，是写盘侧自己加的。

判要不要写，按 **3 个独立维度** 联合裁定（任一不过 → 不写）：

**维度 A · 这句话「是不是事实」？**

| 类型 | 写不写 | 例子 |
|------|--------|------|
| **语义记忆**（脱离场景的持续事实） | ✅ 写 | 「我们组用 Vue 3」「我是深圳人」 |
| **情景记忆**（带具体时间的一次性经历） | ⚠ 看场景 | 「2024-03-15 我去客户那签了合同」——业务上需要保留就写；纯流水就丢弃 |
| **工作记忆**（这轮对话的临时状态） | ❌ 不写 | 「刚才算到第 7 步」「下一步要查库存」 |
| **程序性记忆**（全员通用规则） | ❌ 不写 | 「以后表单都用 zod 校验」——这是团队规范，不是用户事实 |

**维度 B · 这句话「跨会话还有用吗」？**

- 跨会话仍然有意义 → **长期**（写）
- 只对本轮有效 → **短期**（不写）
- 判定口径：杀掉进程再启动还在不在？**在 → 长期**

**维度 C · 这句话「值不值得占存储」？**

哪怕是「语义 + 长期」，也不是每条都值得存——存多了召回噪音反而大。常见过滤规则：

| 信号 | 写不写 | 例子 |
|------|--------|------|
| 已有同 key 覆盖更新 | ✅ 写（覆盖） | 「我们组用 Vue 3」→「我们组改用 React」 |
| 跟已有事实完全重复 | ❌ 不写 | 第二次说「我们组用 Vue 3」——同 key 自动覆盖，但内容没变 → 跳过 |
| 「我」开头的随机感慨 | ❌ 不写 | 「我今天心情不错」——除非用户明确要保留 |
| 公开常识 / 检索能查到 | ❌ 不写 | 「北京是首都」——这是 RAG 干的事，不是记忆 |

**三道齐才写**：

```
要不要写？
  → 是不是事实？(维度 A 排除工作记忆 / 程序性)
  → 跨会话还有用吗？(维度 B 排除短期)
  → 值不值得占存储？(维度 C 排除重复 / 公开常识)
三道全过才写。
```

**为什么三道而不是一道？**
- 只看 A → 工作记忆也被存进去，污染长期事实库
- 只看 A+B → 「今天有点累」判成长期就真存了
- 三道齐 → 既能落真的事实，又不会落噪音

### 8. 多轮对话中的读取：画像常驻 + 情景按问句判断

**核心原则**：记忆库、系统设定区（system）、对话历史是三件事。

- **对话历史**（`messages` 里 user / assistant）= 这一次会话说过的话，会越来越长
- **系统设定区**（`messages` 第 1 条，role = system）= 这一次当场组装：① 全员规则 + ② 核心画像 + ③ 本轮经历
- **记忆库** = 跨会话累计的规则 / 事实 / 经历；库本身不随对话变长

每一次请求都重新组装完整的 `messages`（接口无状态）。**核心用户画像每轮整份写入 system**，不按问句筛；**要不要跑情景检索**才按这一问独立判断。不要假设「刚才读过画像所以这轮不用带」——对话历史里通常没有「我们组用 Vue 3」这条跨会话事实。

**对照表（step-4）**：

| 场景 | ① 程序性 | ② 核心画像 | ③ 情景检索 | ④ 对话历史 |
|------|---------|-----------|-----------|-----------|
| 「你好」 | 写入 | 写入 | 跳过（问候） | 看已有轮次 |
| 「写个按钮」再问「我用什么框架？」 | 写入 | 写入（两轮都有 Vue） | 第二问不必靠情景 Top-K 才看见框架 | 两轮问答都在 |
| 「刚才那条记下了吗？」 | 写入 | 写入 | 跳过（问的是本轮对话） | 看这里 |
| 「我叫什么名字？」 | 写入 | 写入（名字在画像里就直接有） | 跳过 | — |
| 「123 × 456 等于多少」 | 写入 | 写入 | 跳过（纯算术） | — |
| 「我处理过哪些批量改价任务？」 | 写入 | 写入（Vue / 深圳仍在） | 跑嵌入，Top-K 整章替换 | — |

**易混**：

- 「刚才你说了什么」→ 看对话历史，不是记忆库，也不是把上一问的情景 Top-K 留在 system 里。
- 「我叫什么名字」→ 看核心画像（语义长期），不是再赌一次余弦。
- 整段 system 字符串每问都可能不同（③ 换了）≠ ①② 被问句筛掉。
- ③ 覆盖的是这一次 system 里「本轮经历」那一章，不是事实库里的经历被删掉。

## 例子

把四类串在一个业务里：**公司内部的前端代码助手 Agent**，服务前端团队十来个人。

第 1 次会话，星期一：

- 张三问：「帮我写个登录表单。」程序性记忆生效：系统提示词写着「先给结论再给代码；组件默认写单文件组件」，回答格式是规范的。
- 张三补一句：「我们组用 Vue 3 加 TypeScript，别给我 React。」这句话触发两种写入：**情景记忆**记下「9 月 14 日会话中，张三指出过要用 Vue 3」；**语义记忆**抽出一条事实「张三：框架 = Vue 3 + TypeScript」。
- 这一整轮对话本身，在会话进行期间都躺在**工作记忆**里。

第 2 次会话，星期四（新开的会话，工作记忆是空的）：

- 张三问：「上次那个表单，帮我补下校验。」工作记忆：空的，这次会话才刚开始。
- 语义记忆画像：事实库里「框架 = Vue 3 + TypeScript」整份写入这一次的 system，不按问句筛。所以 Agent 不会给他 React 代码，哪怕新会话里他一个字没提框架。
- 情景记忆召回：「上次那个表单」这个模糊指代，靠情景检索找到星期一那次会话里写过的 `LoginForm.vue`，写入 system 里「本轮经历」那一章。没有情景记忆，Agent 就只能反问「你说的是哪个表单」。
- 程序性记忆：照旧常驻同一条 system 的开头，回答格式依然规范。

把三类各关掉一个，看会怎样：

| 关掉哪一类 | Agent 会变成什么样 |
| --- | --- |
| 关掉工作记忆 | 同一次会话里，上一句说的下一句就忘了，每句话都像第一句 |
| 关掉情景记忆 | 每次都能记住偏好，但「上次那个」「刚才说的那个方案」一概听不懂，必须重新描述 |
| 关掉语义记忆 | 每开一次新会话都得重新自我介绍：我用 Vue、我要简短回答 |
| 关掉程序性记忆 | 回答风格和流程全乱，该先查订单再退款的直接就退了 |

## 需求清单（贴近业务 · 验收准绳）

业务背景统一设定为上面那个**公司内部前端代码助手 Agent**。这份清单是到 `coach complete` 在进度表打钩那天逐条对照代码演到了没有的验收准绳，**不是**要求一次性把整个应用搭出来。

**需求 1 · 工作记忆：同一次会话内的连续对话**
- 业务场景：张三在一次会话里连问三句：「写个登录表单」→「加上记住密码」→「把它改成暗色主题」，第三句的「它」指前两句的产物。
- 目标：本次会话的消息列表被完整带进每一次请求，模型能理解代词指代；页面上要能看见这次真正发给模型的 `messages`。
- 涉及知识点：工作记忆的定义；躺在上下文窗口里、不需要检索；它是短期的。
- 验收标准：① 页面能逐轮看到消息列表在变长；② 第三轮请求的 `messages` 里确实含前两轮；③ 点「结束会话」后重新开始，消息列表清空，模型不再认识「它」。

**需求 2 · 情景记忆：跨会话的「上次那个」**
- 业务场景：新开一次会话，张三说「上次那个登录表单，帮我补下校验」。
- 目标：系统按这句话去历史经历里召回星期一那次会话的记录，写入这一次 system 里「本轮经历」那一章（下一问整章替换，不追加进对话历史）。
- 涉及知识点：情景记忆带时间和场景；靠相似情境召回；横跨短期和长期两侧。
- 验收标准：① 页面能看见召回了哪几条经历、各自的相似度分数，以及它们写进了 system 的哪一章；② 勾上「跳过本轮情景召回」再问同一句，Agent 表现为「不知道你说的是哪个表单」，核心画像仍在；③ 事实库列表里能把语义画像和情景经历分开展示。

**需求 3 · 语义记忆（用户记忆）：跨会话记住技术栈偏好**
- 业务场景：张三第一次会话里说过「我们组用 Vue 3 加 TypeScript」。第二次全新会话里只说「写个下拉选择组件」，一个字没提框架。
- 目标：核心用户画像（语义记忆 · 长期）整份写入这一次的 system，不按问句筛；产出直接就是 Vue 3 写法。条数少时不要走情景那条「按问句 Top-K」（否则问别的题时 Vue 会从 system 里消失）。
- 涉及知识点：语义记忆是脱离场景的事实；用户记忆是它的子集；小画像常驻是读取策略，和程序性常驻不是同一个存储盒子。
- 验收标准：① 页面能看见语义长期条目整份在 system 里，不是只留跟这一问余弦最高的几条；② 先问无关的题再问框架，两轮的画像里 Vue 都还在；③ 勾上「不注入核心用户画像」再问框架，模型说不出 Vue，两次可对照；④ 事实库里每条都能看到它是一条可覆盖的记录（有稳定的键）。

**需求 4 · 程序性记忆：团队规范常驻生效**
- 业务场景：团队规定「回答先给结论再给代码」「组件一律用单文件组件写法」「涉及删除操作前必须先确认」，对所有人生效，谁也改不了。
- 目标：这些规则以程序性记忆的形式常驻在系统提示词和工具定义里，每次请求都带，不经过检索。
- 涉及知识点：程序性记忆是「怎么做事」；常驻不检索；和用户记忆必须分开存。
- 验收标准：① 页面上程序性记忆和用户记忆是两个独立展示区，能一眼看出哪部分是全员规则、哪部分是这个用户的事实；② 执行「清空这个用户的记忆」后，程序性记忆原封不动，回答风格不变；③ 改一条规则后，所有用户的下一次回答都变。

**需求 5 · 对号入座与短期长期判定：同一句话进了哪个盒子**
- 业务场景：张三在一次会话里说了四句话：「帮我写个表单」「我们组用 Vue 3」「今天有点累先到这」「以后表单校验都用 zod」。这四句该分别进哪类记忆？
- 目标：给出一个可观察的归类结果——每句话被判成哪一类、进短期还是长期、理由是什么。再加一个重启验证：杀掉进程重新启动，长期的还在、短期的没了。
- 涉及知识点：四类的分界；短期长期是另一根轴；判定口径「重启后还在吗」。
- 验收标准：① 页面对每句话展示「归入哪一类 / 短期还是长期 / 一句话理由」；② 「今天有点累」这类一次性内容不进长期语义记忆（页面要能看出它被判为不写入）；③ 重启服务后重新打开页面，长期的那几条还在、工作记忆清空了，页面能对照出差异。

**需求 6 · 写入侧 3 道把关：什么才值得存进事实库**
- 业务场景：张三跟代码助手聊了 10 句。其中「我们组用 Vue 3」值得存；「今天有点累」不值得存；「以后表单都用 zod」是程序性（不属于张三个人）；第二次重复说「我们组用 Vue 3」是同 key 覆盖——写盘侧怎么挡？
- 目标：每一条候选写入都要过 3 道独立维度（是不是事实 / 跨会话还有用吗 / 值不值得占存储），任一不过就不写；页面要能让学习者看见每一条的写入判定过程（写没写 / 为什么 / key）。
- 涉及知识点：写入策略；工作/短期/程序性记忆不写盘；同 key 覆盖更新语义；公开常识/检索能查到的不是记忆。
- 验收标准：① 页面能让学习者对照「候选事实」和「写入决策」（写没写 + 为什么 + key）；② 四类候选（语义长期 / 情景长期 / 短期 / 工作 / 程序性）各显一条，看哪些写哪些不写；③ 同 key 第二次陈述能看见「覆盖」动作；④ 程序性记忆归全员规则不进用户事实库。

**需求 7 · 多轮读取：画像常驻 + 情景按问句判断**
- 业务场景：张三同一个会话连问：「写个按钮」→「我用什么框架？」→「刚才那条记下了吗？」→「我处理过哪些批量改价任务？」→「123×456 等于多少」。
- 目标：程序性 + 核心画像每轮都写入 system；情景检索按问句跳过或重跑，且只替换 system 里「本轮经历」那一章；对话历史只追加。
- 涉及知识点：system 每问重新组装；①② 来源不变；③ 整章替换不是删库；「刚才说了什么」看工作记忆。
- 验收标准：① 连问两句不同的题，画像条数和 Vue 原文保持不变；② 问批量改价时「本轮经历」换成相关经历，画像仍在；③ 「刚才那条」/ 纯算术能看见情景检索跳过，程序性与画像仍在；④ 勾「不注入核心用户画像」再问框架，对照说不出 Vue。

## 取舍

- **用户事实存关系库/键值库，而不是只用向量库**：语义记忆需要「按稳定 key 覆盖」的更新语义，向量库天然是追加式的，两者需求不匹配。取舍是宁可多写一份结构化存储，也不要图省事把用户事实和知识文档混进同一套向量索引。
- **情景记忆要不要分短期/长期两套存储**：本轮内的情景（比如刚才这次工具调用失败）如果也全部写进长期库，噪音会很快堆起来；但完全不落库又会丢掉「上次那个」这种跨会话指代能力。取舍是本轮先留在工作记忆里，会话结束时再判断值不值得沉淀成一条长期情景（判断规则见下一小节「写入策略」）。
- **小画像整份常驻 vs 按问句检索**：事实库只有十几条、几乎每问都要用（技术栈、城市）时，按 ChatGPT 已保存记忆 / Letta 核心记忆的读法整份写入 system。条数大到几百条，长尾才改检索（step-3 演示那一层）。不要把「召回不等于全量注入」用在只有三条画像的时候，否则问改价会把 Vue 从 system 里换掉。
- **情景 Top-K 每问替换 vs 追加进对话历史**：替换这一次 system 里「本轮经历」章，窗口不会被旧召回堆满；经历仍在事实库里。若把每轮召回块追加进对话历史，几轮后又变回全量堆积。

## 踩坑

- 把「今天有点累」这种一次性状态直接抽成长期用户画像，会让 Agent 在完全不相关的场合突然关心起用户身体，体验很诡异——语义记忆的抽取必须先判断这句话是不是「持续成立的事实」，不是随口一说。
- 把程序性记忆（全员规则）和用户记忆拼在同一个字符串里存储，会导致「清空这个用户的记忆」把全员规则一起清掉，或者「导出我的记忆」把公司内部规则一起导给用户。两者必须在存储层就分开，只在拼提示词那一刻合并。
- **把语义画像和情景经历走同一条按问句 Top-K**（step-4 改之前）：问 B 时 system 里只剩跟 B 相关的几条，Vue 从系统设定区消失。这不是「符合规范」，是读错层。核心画像常驻；情景才整章替换。
- **把「整段 system 每问都会变」理解成「画像也被问句筛掉」**：接口无状态，每一次都新组装 `messages[0]`。变的是整份字符串；①② 两章从库原样拷。
- **页面中间写「写入 system」，右边一律写「拼进 messages」**：system 就是 messages 数组第 1 条，但五步共用一句「拼进 messages」会让人以为 ①②③ 写进了对话历史。step-4 终版每一步自己标明：①②③ 写入 system 某一章；④ 接到 system 后面的对话历史。
- **`<details open={...}>` 受控失败**：用 React state 控制 `<details open={showHistory}>` 不会真正展开收起（React 18 不支持受控 details）。修复：用 onClick + 普通 div + 自己管理 visible state。
- **`Array(d.rules)` 是稀疏数组**：`Array([a,b,c])` 返回 `[<3 empty slots>]`（长度 = 元素个数，元素全是空），不是 `[a,b,c]`。修复：用 `Array.isArray(d.rules) ? d.rules : []`。
- **Tailwind CDN integrity hash typo**：复制 step-3 的 `<script integrity="...">` 时把 `2ql948lId...`（小写 L）写成 `2ql948l1Id...`（数字 1），浏览器拒绝加载资源 → 整页 JS 加载失败 → 控制台报错。修复：核对 jsdelivr 给的 sha384 hash 不能差一个字符。
- **babel-standalone 在 head 里跑 inline `<script type="text/babel">` 时 body 还没解析**：`document.getElementById("root")` 返回 null → React error #299 ("Target container is not a DOM element")。修复：把 inline babel script 挪到 body 里 `<div id="root">` 之后（让浏览器先解析完 DOM 再让 babel 跑 inline）。
- **`renderStepXxx` 函数堆在 index.html 导致单页 HTML 超过 400 行硬上限**：把每个步骤的输出渲染拆成独立 `components/renderers.js` 里的 React 组件，让 index.html 只负责装配。
