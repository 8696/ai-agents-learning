## 是什么

死循环防护（Loop Guard）= 给 Agent 的 while 循环套**几道闸门（gates）**，让循环在「该停」的地方停下来，不让它把 token 烧光、把工具调爆、把外部服务打挂。

Agent 循环的本质：

```
while (还没拿到最终答案) {
  1. 问模型：现在该干啥？      ← Reason
  2. 收到模型回答：调工具 X   ← Act
  3. 真去调 X，把结果喂回模型 ← Observe
}
```

如果没闸门，模型可能每轮都说「再调一次」，工具调用又永不失败 → while 就死循环了。必须有几道闸在「不该再跑」的时刻强制 break。

**死循环防护是个分类**，不是单一概念。完整列下来有 **7 个变体**（变体 = 不同维度的闸门）：

| # | 闸门 | 一句话 |
|---|------|--------|
| 1 | **最大步数（max iterations）** | while 跑了几圈硬上限（按 step 计数） |
| 2 | **超时（wall-clock timeout）** | 从开始到现在过了多少毫秒硬上限 |
| 3 | **模型说停（model stop signal）** | 模型自己输出 final_answer / finish_reason=stop |
| 4 | **用户取消（user cancel）** | AbortController.abort() 中途打断 |
| 5 | **工具重试上限（tool retry cap）** | 同一工具连续失败 N 次后降级 |
| 6 | **同工具循环检测（tool call loop）** | 同一个工具、相同参数、连续 N 轮 = 死循环信号 |
| 7 | **Token / 成本预算（token budget）** | 累计 token 超过预算就停 |

7 道闸不是**选一个用**，是**同时叠**。常见最少必备 4 道：max iterations + timeout + model stop + user cancel —— 这正是模块验收第 3 条。

## 为什么（Agent 开发要懂）

不装闸门有 3 种具体后果：

1. **烧钱**：每调一次模型都要钱，每调用一次工具可能也要钱。一次任务从 5 轮拖到 500 轮，账单直接炸。
2. **卡死外部服务**：有些工具是写数据库、调外部 API。500 次写库调用，可能把生产表写满；500 次外部 API 调用，可能把对方服务打挂。
3. **响应永远不返回**：用户在前端点了按钮，30 秒还没动静，最后超时。用户体验崩溃。

所以闸门不是写完后补一个 `max = 10` 那么简单 —— **至少 4 道闸互相配合**，才稳。

## 易混点

**易混 1：max iterations vs timeout**

- `max iterations` 是**轮次**上限（while 跑了几圈）
- `timeout` 是**墙钟时间**上限（从开始到现在过了多少毫秒）

一个任务调一次慢模型（每轮 8 秒）跑 10 轮 = 80 秒；另一个任务调快模型（每轮 0.5 秒）跑 50 轮 = 25 秒。光设 `max=50` 控制不住第一种（80 秒可能把前端超时打断），光设 `timeout=30s` 控制不住第二种（25 秒内能跑 50 轮烧光 budget）。**两个两个都要设**。

**易混 2：「模型说停」 ≠ 模型不调工具了**

模型在 Reason 阶段可能输出「任务完成」字段（`finish_reason = stop` 或 content 里说 final_answer）。但**「模型嘴上说停」不可信**——它可能上一轮也说停，这一轮又说「再调一次试试」。所以「模型说停」只是**软停止信号**，还要叠 `max iterations` 这类**硬闸门**兜底。

**易混 3：用户取消 ≠ 进程 kill**

用户在前端点了「取消」按钮 → 后端不能粗暴 `process.exit()`（这会把整个 Node 进程杀掉，所有别的用户请求也跟着死）。正确做法是 `AbortController.abort()` → 在 while 的条件里检查 `signal.aborted` → 优雅 break。

**易混 4：工具失败 ≠ 整个 Agent 死**

工具调用可能因为网络抖动失败一次。重试 ≠ 失败就 break。**工具层要有自己的重试闸门**（同一调用重试 N 次），全失败才向 Agent 层上报「这条工具不可用」。

**易混 5：闸门是「Agent 框架的活」，不是「模型的活」**

闸门看的是「while 跑了多少圈 / 多少毫秒 / 用户有没有点取消」——这些是 Agent 框架的活，跟模型调不调、调哪家模型无关。理解这一点 → 任何 demo 都可以用 mock 模型演示闸门效果，不需要真调大模型。

## 例子

每个变体都给一个通俗例子 + 数据怎么走。覆盖 7 个变体 ≥1 例。

### 变体 1 · 最大步数（max iterations）

**生活例子**：你跟外卖小哥说「去取餐」，他第一次取错了餐厅。你说「重新去」。他又取错了。第三次你说「算了我取消」—— 这就是 `max=3` 兜底。

**数据怎么走**（TypeScript 写法）：

```
while (state.stepCount < MAX_STEPS) {   // ← 闸门 1
  const decision = await llm(messages);
  state.stepCount++;
  if (decision.toolCall) {
    const result = await runTool(decision.toolCall);
    messages.push(toolResult(result));
  }
}
throw new MaxStepsError(`达到 ${MAX_STEPS} 步上限`);
```

### 变体 2 · 超时（wall-clock timeout）

**生活例子**：你点外卖，APP 上写「预计 30 分钟送达」。40 分钟还没到，你打电话催。这就是 timeout——按**时间**而不是按**次数**设兜底。

**数据怎么走**：

```
const startedAt = Date.now();
const TIMEOUT_MS = 60_000;

while (Date.now() - startedAt < TIMEOUT_MS) {   // ← 闸门 2
  ...
}
throw new TimeoutError(`超过 ${TIMEOUT_MS}ms`);
```

### 变体 3 · 模型说停（model stop signal）

**生活例子**：你问同事「帮我把书架上的书整理一下」。同事整理完跟你说「好了」。你不需要再追问「整完了吗？」—— 他自己说完了。模型也能说：输出 `final_answer` 字段、或 `finish_reason = stop`。

**数据怎么走**：

```
const decision = await llm(messages);
if (decision.finishReason === "stop" || decision.finalAnswer) {
  return decision.finalAnswer;     // ← 闸门 3：模型主动停
}
```

**注意**：这个闸是**软闸**，不能单独用——见易混 2。

### 变体 4 · 用户取消（user cancel）

**生活例子**：你跟外卖小哥说「去取餐」，他说「好」。你说「等等先别去我取消」。他停下来。`AbortController` 就是这个「取消信号」。

**数据怎么走**：

```
const controller = new AbortController();
// 前端用户点「取消」 → controller.abort()

while (!controller.signal.aborted && /* 其他闸 */) {   // ← 闸门 4
  ...
}
throw new UserCancelledError();
```

### 变体 5 · 工具重试上限（tool retry cap）

**生活例子**：你打银行客服电话，第一次占线，第二次还是占线，第三次通了。**重试三次**是常见的。如果重试 10 次还没通，你不会再打了。工具层同理。

**数据怎么走**：

```
async function runToolWithRetry(name, args, maxRetries = 3) {
  for (let i = 0; i < maxRetries; i++) {
    try {
      return await runTool(name, args);
    } catch (e) {
      if (i === maxRetries - 1) throw e;
      await sleep(2 ** i * 100);   // 指数退避
    }
  }
}
```

### 变体 6 · 同工具循环检测（tool call loop）

**生活例子**：你让实习生「查一下客户资料」。他查完说「查不到」。你说「再查」。他又查完说「查不到」。你拦下来：「等等，你两次查的方法一样吗？」—— 同工具同参数连查 3 次 = 死循环信号。

**数据怎么走**：

```
// 记录最近 3 步的工具调用
if (state.lastThreeCalls.every(c => c.name === call.name && JSON.stringify(c.args) === JSON.stringify(call.args))) {
  throw new LoopDetectedError(`工具 ${call.name} 连续 3 次相同参数`);
}
```

### 变体 7 · Token / 成本预算（token budget）

**生活例子**：你给孩子 50 块零花钱，让他自己决定怎么花。30 块花完之前他随便花，30 块花完他必须告诉你。这是 budget。

**数据怎么走**：

```
state.totalTokens += decision.usage.totalTokens;
if (state.totalTokens > TOKEN_BUDGET) {           // ← 闸门 7
  throw new BudgetExceededError(`超 ${TOKEN_BUDGET} tokens`);
}
```

### 闸门组合（最少必备）

| 闸门 | 软/硬 | 必装 |
|------|-------|------|
| max iterations | 硬 | ✅ 必须 |
| wall-clock timeout | 硬 | ✅ 必须 |
| model stop signal | 软 | ✅ 必须 |
| user cancel | 硬 | ✅ 必须（前端交互场景） |
| tool retry cap | 硬 | ✅ 必须 |
| tool call loop detection | 软 | ⭕ 推荐 |
| token budget | 硬 | ⭕ 推荐 |

**最少必备 4 道** = 「达到最大步 / 超时 / 模型说停 / 用户取消」—— 对应模块验收第 3 条。

### 跑出来长什么样（step-2 跑过两次）

[apps/07-手写Agent/03-死循环防护-step-2/](../../../../apps/07-手写Agent/03-死循环防护-step-2/) 用 mock 模型 + mock 工具（latency=80ms/轮）跑了两种 timeout 配置：

**timeout 单闸**（timeout=300ms · latency=80ms/轮 · `latency × 4 ≈ 320ms`）：

| 字段 | 数值 |
|------|------|
| stepCount | 4 |
| tokenEstimate | 642 |
| elapsedMs | 326 ms |
| stoppedReason | timeout |
| 闸门提示 | 「达到 timeout（300ms · 实际 326ms）」 |

**双闸叠加**（max=3 · timeout=300ms · latency=80ms/轮 · `max × 80 = 240ms < 300ms`）：

| 字段 | 数值 |
|------|------|
| stepCount | 3 |
| elapsedMs | 244 ms |
| stoppedReason | max_steps |
| 闸门提示 | 「达到 max iterations（3 步）」 |

→ **双闸叠加谁先到谁说了算**：第一次跑 max=10 + timeout=300ms → timeout 先到（10×80=800ms > 300ms）；把 max 调成 3 → max 先到（3×80=240ms < 300ms）。两闸不冲突，互相补位。

## 取舍

- **变体 1（max iterations）和变体 2（timeout）两个硬闸都要装**，不能二选一：光装 max iterations → 慢模型把响应拖到分钟级；光装 timeout → 快模型 + 高 max 把账单烧光。两者一起装才能互补。
- **变体 3（模型说停）单独装不可靠**：模型上一轮说停这一轮又说「再试一次」很常见。必须叠硬闸（max iterations / timeout）兜底。
- **变体 7（token budget）和变体 1（max iterations）有重合**：max iterations 间接限制了 token（每轮 ≈ 160 tokens）。但 token budget 更精确（直接看 token 总数，不受单轮长度影响）。生产里两者都装：max iterations 是粗闸，token budget 是细闸。

## 踩坑

- **代码写死只许调一次工具就结束**：真正的 Agent 循环必须能连续多轮调用工具直到任务完成——这正是本模块的核心。死循环防护不是禁止多轮，是防止「停不下来」。
- **把 `AbortController.abort()` 当成 `process.exit()` 用**：abort 是给 while 一个「该停」的信号；进程本身继续跑，处理别的请求。`process.exit()` 把整个 Node 进程杀掉，所有别的用户请求也跟着死。
- **闸门失败只 warn 不抛错**：闸门触发必须 throw 一个有名字的 error（如 `MaxStepsError` / `TimeoutError` / `UserCancelledError`）让上层做对应处理。warn + 继续跑 = 闸门没起作用。
- **变体 1 装 max=1000「反正大」**：max=1000 等于没闸。要按任务合理估算（一般 5~50），不能拍脑袋写大数。
- **「mock 模型」当真模型**：mock 模型每轮都说「再查一次」是为了让闸门效果可见。真业务里模型可能自己停（变体 3），所以 mock 演示闸门只是示意，实际部署仍要测真模型行为。

## 还没搞懂的

- 同工具循环检测（变体 6）的「N」应该定多少？业界有 3 次 / 5 次 / 10 次各种说法，没标准答案。要看具体业务场景（搜索工具容忍度高，支付工具容忍度低）。
- Token budget（变体 7）的预算是按「本次任务」算，还是按「用户本月累计」算？前者是单次防护，后者是防滥用。生产系统通常两者都做。
