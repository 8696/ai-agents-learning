## 是什么

死循环防护（Loop Guard）= 给 Agent 的 while 循环套**几道闸门（gates）**，让循环在「该停」的地方停下来，不让它把 token 烧光、把工具调爆、把外部服务打挂。

Agent 循环的本质：

```
while (还没拿到最终答案) {
  1. 问模型：现在该干啥？      ← Reason
  2. 收到模型回答：调工具 X   ← Act
  3. 真去调 X，把结果喂回模型 ← Observe
}
```

如果没闸门，模型可能每轮都说「再调一次」，工具调用又永不失败 → while 就死循环了。必须有几道闸在「不该再跑」的时刻强制 break。

**死循环防护是个分类**，不是单一概念。完整列下来有 **7 个变体**（变体 = 不同维度的闸门）：

| # | 闸门 | 一句话 |
|---|------|--------|
| 1 | **最大步数（max iterations）** | while 跑了几圈硬上限（按 step 计数） |
| 2 | **超时（wall-clock timeout）** | 从开始到现在过了多少毫秒硬上限 |
| 3 | **模型说停（model stop signal）** | 模型自己输出 final_answer / finish_reason=stop |
| 4 | **用户取消（user cancel）** | AbortController.abort() 中途打断 |
| 5 | **工具重试上限（tool retry cap）** | 同一工具连续失败 N 次后降级 |
| 6 | **同工具循环检测（tool call loop）** | 同一个工具、相同参数、连续 N 轮 = 死循环信号 |
| 7 | **Token / 成本预算（token budget）** | 累计 token 超过预算就停 |

7 道闸不是**选一个用**，是**同时叠**。常见最少必备 4 道：max iterations + timeout + model stop + user cancel —— 这正是模块验收第 3 条。

## 为什么（Agent 开发要懂）

不装闸门有 3 种具体后果：

1. **烧钱**：每调一次模型都要钱，每调用一次工具可能也要钱。一次任务从 5 轮拖到 500 轮，账单直接炸。
2. **卡死外部服务**：有些工具是写数据库、调外部 API。500 次写库调用，可能把生产表写满；500 次外部 API 调用，可能把对方服务打挂。
3. **响应永远不返回**：用户在前端点了按钮，30 秒还没动静，最后超时。用户体验崩溃。

所以闸门不是写完后补一个 `max = 10` 那么简单 —— **至少 4 道闸互相配合**，才稳。

## 易混点

**易混 1：max iterations vs timeout**

- `max iterations` 是**轮次**上限（while 跑了几圈）
- `timeout` 是**墙钟时间**上限（从开始到现在过了多少毫秒）

一个任务调一次慢模型（每轮 8 秒）跑 10 轮 = 80 秒；另一个任务调快模型（每轮 0.5 秒）跑 50 轮 = 25 秒。光设 `max=50` 控制不住第一种（80 秒可能把前端超时打断），光设 `timeout=30s` 控制不住第二种（25 秒内能跑 50 轮烧光 budget）。**两个两个都要设**。

**易混 2：「模型说停」 ≠ 模型不调工具了**

模型在 Reason 阶段可能输出「任务完成」字段（`finish_reason = stop` 或 content 里说 final_answer）。但**「模型嘴上说停」不可信**——它可能上一轮也说停，这一轮又说「再调一次试试」。所以「模型说停」只是**软停止信号**，还要叠 `max iterations` 这类**硬闸门**兜底。

**易混 3：用户取消 ≠ 进程 kill**

用户在前端点了「取消」按钮 → 后端不能粗暴 `process.exit()`（这会把整个 Node 进程杀掉，所有别的用户请求也跟着死）。正确做法是 `AbortController.abort()` → 在 while 的条件里检查 `signal.aborted` → 优雅 break。

**易混 4：工具失败 ≠ 整个 Agent 死**

工具调用可能因为网络抖动失败一次。重试 ≠ 失败就 break。**工具层要有自己的重试闸门**（同一调用重试 N 次），全失败才向 Agent 层上报「这条工具不可用」。

**易混 5：闸门是「Agent 框架的活」，不是「模型的活」**

闸门看的是「while 跑了多少圈 / 多少毫秒 / 用户有没有点取消」——这些是 Agent 框架的活，跟模型调不调、调哪家模型无关。理解这一点 → 任何 demo 都可以用 mock 模型演示闸门效果，不需要真调大模型。

**易混 6：同工具循环检测 vs 最大步数**

- **同工具循环检测**（变体 6）= 看「同一个工具、同一个参数」连续 N 轮 = 死循环信号；早一步触发，**针对特定工具**
- **最大步数**（变体 1）= 看「while 总共跑了几圈」；兜底，**对所有轮次**

一个慢循环（模型反复调同一个搜索工具 50 次）→ 同工具循环检测会在第 3 次就 break；最大步数要等 50 次。一个快循环（每次换不同工具）→ 同工具循环检测根本不会触发，靠最大步数兜底。**两个装一起**：同工具循环检测处理「同工具反复调」的早兜底；最大步数处理「任意循环」的总兜底。

## 例子

每个变体都给一个通俗例子 + 数据怎么走。覆盖 7 个变体 ≥1 例。

### 变体 1 · 最大步数（max iterations）

**生活例子**：你跟外卖小哥说「去取餐」，他第一次取错了餐厅。你说「重新去」。他又取错了。第三次你说「算了我取消」—— 这就是 `max=3` 兜底。

**数据怎么走**（TypeScript 写法）：

```
while (state.stepCount < MAX_STEPS) {   // ← 闸门 1
  const decision = await llm(messages);
  state.stepCount++;
  if (decision.toolCall) {
    const result = await runTool(decision.toolCall);
    messages.push(toolResult(result));
  }
}
throw new MaxStepsError(`达到 ${MAX_STEPS} 步上限`);
```

### 变体 2 · 超时（wall-clock timeout）

**生活例子**：你点外卖，APP 上写「预计 30 分钟送达」。40 分钟还没到，你打电话催。这就是 timeout——按**时间**而不是按**次数**设兜底。

**数据怎么走**：

```
const startedAt = Date.now();
const TIMEOUT_MS = 60_000;

while (Date.now() - startedAt < TIMEOUT_MS) {   // ← 闸门 2
  ...
}
throw new TimeoutError(`超过 ${TIMEOUT_MS}ms`);
```

### 变体 3 · 模型说停（model stop signal）

**生活例子**：你问同事「帮我把书架上的书整理一下」。同事整理完跟你说「好了」。你不需要再追问「整完了吗？」—— 他自己说完了。模型也能说：输出 `final_answer` 字段、或 `finish_reason = stop`。

**数据怎么走**：

```
const decision = await llm(messages);
if (decision.finishReason === "stop" || decision.finalAnswer) {
  return decision.finalAnswer;     // ← 闸门 3：模型主动停
}
```

**注意**：这个闸是**软闸**，不能单独用——见易混 2。

### 变体 4 · 用户取消（user cancel）

**生活例子**：你跟外卖小哥说「去取餐」，他说「好」。你说「等等先别去我取消」。他停下来。`AbortController` 就是这个「取消信号」。

**数据怎么走**：

```
const controller = new AbortController();
// 前端用户点「取消」 → controller.abort()

while (!controller.signal.aborted && /* 其他闸 */) {   // ← 闸门 4
  ...
}
throw new UserCancelledError();
```

### 变体 5 · 工具重试上限（tool retry cap）

**生活例子**：你打银行客服电话，第一次占线，第二次还是占线，第三次通了。**重试三次**是常见的。如果重试 10 次还没通，你不会再打了。工具层同理。

**数据怎么走**：

```
async function runToolWithRetry(name, args, maxRetries = 3) {
  for (let i = 0; i < maxRetries; i++) {
    try {
      return await runTool(name, args);
    } catch (e) {
      if (i === maxRetries - 1) throw e;
      await sleep(2 ** i * 100);   // 指数退避
    }
  }
}
```

### 变体 6 · 同工具循环检测（tool call loop）

**生活例子**：你让实习生「查一下客户资料」。他查完说「查不到」。你说「再查」。他又查完说「查不到」。你拦下来：「等等，你两次查的方法一样吗？」—— 同工具同参数连查 3 次 = 死循环信号。

**数据怎么走**：

```
// 记录最近 3 步的工具调用
if (state.lastThreeCalls.every(c => c.name === call.name && JSON.stringify(c.args) === JSON.stringify(call.args))) {
  throw new LoopDetectedError(`工具 ${call.name} 连续 3 次相同参数`);
}
```

### 变体 7 · Token / 成本预算（token budget）

**生活例子**：你给孩子 50 块零花钱，让他自己决定怎么花。30 块花完之前他随便花，30 块花完他必须告诉你。这是 budget。

**数据怎么走**：

```
state.totalTokens += decision.usage.totalTokens;
if (state.totalTokens > TOKEN_BUDGET) {           // ← 闸门 7
  throw new BudgetExceededError(`超 ${TOKEN_BUDGET} tokens`);
}
```

### 闸门组合（最少必备）

| 闸门 | 软/硬 | 必装 | step |
|------|-------|------|------|
| max iterations | 硬 | ✅ 必须 | step-1 |
| wall-clock timeout | 硬 | ✅ 必须 | step-2 |
| model stop signal | 软 | ✅ 必须 | step-3 |
| user cancel | 硬 | ✅ 必须（前端交互场景） | step-4 |
| tool retry cap | 硬 | ✅ 必须（工具层防抖） | step-5 |
| tool call loop detection | 软 | ⭕ 推荐 | step-6 |
| token budget | 硬 | ⭕ 推荐（成本护栏） | step-7 |

**最少必备 4 道** = 「达到最大步 / 超时 / 模型说停 / 用户取消」—— 对应模块验收第 3 条。
**生产标准 7 道** = 上表全装——变体 5 补工具层防抖、变体 6 补模式死循环、变体 7 补成本护栏。

### 跑出来长什么样（step-4 · 用户取消闸）

[apps/07-手写Agent/03-死循环防护-step-4/](../../../../apps/07-手写Agent/03-死循环防护-step-4/) 真调 minimax 模型，latency=800ms/轮（让任务够慢、给取消留时间窗）：

**点完「启动 run」立刻点「中途取消」**（前后相差 < 1 秒）：

| 字段 | 数值 |
|------|------|
| runId | `run_1789030743819_i74gzf`（每次启动随机） |
| 已轮询次数（pollCount） | 3 |
| 最终状态 | `cancelled` |
| stepCount | 1 |
| tokenEstimate | 162 |
| elapsedMs | 2911 ms |
| stoppedReason | `user_cancel` |
| 闸门提示 | 「用户取消（用户取消（点击「取消」按钮 / 页面关闭））」 |

→ **闸门 4 实战可见**：模型只来得及调 1 次工具就被 abort，runLoop 检测到 abortSignal.aborted 立即 break。`process.exit()` 不会做这种「只停当前 run」的细活——它会把整个 Node 进程杀掉，所有别的用户请求也跟着死。

**对照实验**（同 latency、不点取消）：

| 字段 | 数值 |
|------|------|
| 最终状态 | `finished` |
| stepCount | 3 |
| elapsedMs | ~8000 ms |
| stoppedReason | `model_says_stop` |

→ **闸门叠加的真实效果**：用户取消 如果太晚（>3 秒后），模型自己先停 → stoppedReason = `model_says_stop`，取消指令被自然吸收（route 返「已结束，无需取消」）。这印证了「闸门组合谁先到谁说了算」——用户的取消信号和模型的停信号是平行的，谁先到谁 break。

|------|---|
| stepCount | 3（调 3 个 SKU） |
| toolCallCount | 3 |
| toolFailureCount | 1（首轮失败） |

→ **闸门 5 的「按工具层」角色**：max iterations 看不到单次工具失败；tool_retry_cap 把「重试 X/3」这种细活吸在工具层，Agent 不会因为一次 500 / 网络断就死。**重试成功**和**降级**是同一条闸门的两种结果。

## 需求清单（验收准绳 · 每条 = 一个变体或变体组）

> **需求清单定位 = 验收准绳，不是 step 生产的驱动器**——step 生产仍按本节知识本身动态推进（动态 step 引导）；勾本条 `coach complete` 时才按需求逐条对。

| # | 业务场景 | 目标 | 涉及本节哪些变体 | 验收标准 |
|---|---------|-----|-----------------|---------|
| 1 | 「死循环炸账单」演示 | 让学习者亲眼看 token 烧光 / 轮数无限涨（变体 7） | 变体 1 + 变体 7（不带闸 = 反例） | 跑反例：stepCount=200（人为硬上限）· 数字面板显示 tokenEstimate 持续累加（mock 估算每轮 ~160 token，200 步约 32000）。教学目的：让学习者亲眼看到「不装闸会一直涨」，不是「涨到 5 万就停」 |
| 2 | 装上 max iterations + wall-clock timeout | 看两道硬闸怎么把循环截停 | 变体 1 + 变体 2 | step-1 按钮 + step-2 按钮独立触发；≤10 步 或 ≤20 秒时停，结果区显示哪道闸先触发 |
| 3 | 模型说停软闸 | 演示软闸跟硬闸共存 | 变体 3 | 模型输出 `final_answer` 时提前 break，trajectory 显示「模型主动停」 vs 「达到 MAX_STEPS」 |
| 4 | 用户中途取消 | 演示用户取消闸 | 变体 4 | 点「取消」后 while 立即 break；结果区显示 `UserCancelled`；不杀进程 |
| 5 | 工具重试 + 循环检测 | 演示工具层两道闸 | 变体 5 + 变体 6 | trajectory 显示「重试 1/3 → 2/3 → 成功」和「连续 3 次相同参数 → LoopDetected」 |
| 6 | todo 助手端到端 | 端到端验证：业务能跑 + 7 道闸齐 | 变体 1+2+3+4+5+6+7 | 跑真实业务请求（todo 助手「电商购物助手该装哪几闸」）；trajectory 一目了然；任何一道闸触发都能在页面看到。**完整 7 闸齐的端到端 demo 在 [step-8](../../../../apps/07-手写Agent/03-死循环防护-step-8/)**（业务选型面板 7 个 checkbox + 一键「4 道」「7 道」预设）。 |

## 场景选型（7 种方式 × 业务场景怎么选）

需求清单是按变体列（每条 = 一个变体）。**这节是同一个 7 种方式从「业务场景角度」再列一遍**——同一种知识的不同切法，方便按「我现在做的是哪类业务」反向选哪几道必装、哪几道选装。

### 7 种方式 · 一句话 + 适用 + 不适用

| # | 方式 | 一句话 | 适用场景 | 不适用 |
|---|------|--------|---------|--------|
| 1 | **最大步数（max iterations）** | while 跑了几圈的硬上限 | 所有 Agent —— 兜底必须有 | 不适合替代「超时」（轮次 ≠ 时间） |
| 2 | **超时（wall-clock timeout）** | 从开始到现在的毫秒硬上限 | 所有长流程任务、慢模型、外部依赖网络 | 不适合替代「最大步数」（时间 ≠ 轮次） |
| 3 | **模型说停** | 模型自己输出 final_answer | 模型自主性高的研究 / 规划任务 | **不能单独用** —— 模型会反复说停又说「再试一次」 |
| 4 | **用户取消（AbortController）** | 前端点「取消」立即 break | 任何有前端交互的场景（用户能等几十秒） | 无前端 / 后台批处理 |
| 5 | **工具重试上限** | 同一工具失败 N 次后降级 | 调用外部 API / 数据库（网络抖动常见） | 工具本身幂等且已内部重试（避免叠加） |
| 6 | **同工具循环检测** | 同工具同参数连查 N 次 break | 模型可能陷入「再查一次试试」的搜索类任务 | 工具本身就该重复调用（轮询、轮转任务） |
| 7 | **Token 预算** | 累计 token 超预算就停 | 成本敏感（多人共用 / 公开 API）、长会话 | 单次短任务（用不了多少） |

### 关键易混（决定选哪几种）

| 混淆 | 怎么选 |
|------|--------|
| **最大步数 vs 超时** | 慢模型 / 外部 API 慢 → 两个都要；快模型小任务 → 至少 1 道（一般 max） |
| **模型说停 vs 硬条件** | 模型说停必须有，但**必须叠**最大步数 / 超时兜底 —— **永远不要单用** |
| **用户取消 vs 进程 kill** | 有前端 → 必装 AbortController；后台任务 → 不用，但要有外部停止信号（如 SIGTERM） |
| **工具重试 vs 工具层降级** | 工具层已有重试 → Agent 层只设上限兜底；工具层没有 → Agent 层必须装 |
| **同工具循环检测 vs 最大步数** | 慢循环（同工具查 50 轮）→ 同工具检测早一步触发；快循环（每次不同工具）→ 用最大步数就够 |

### 7 类业务的选型清单

**A · 简单单步任务**（一次工具调用就够）
- 典型：问答机器人、单工具查询
- 必装：最大步数（设小，3~5）+ 模型说停
- 不装：超时（同任务最多几秒）、用户取消（无前端）、token 预算（几轮用不了多少）
- 理由：单步任务烧不了多少资源，主要防模型「再调一次」类幻觉

**B · 多步研究任务**（5~20 轮）
- 典型：研究助手、阅读网页总结、多工具协作
- 必装：最大步数（10~20）+ 超时（60~120 秒）+ 模型说停
- 推荐装：工具重试（外部 API 多）+ token 预算（多轮累计不容小觑）
- 选装：同工具循环检测（如果用搜索工具）+ 用户取消（如果有前端）
- 理由：研究任务 = 多步 + 外部依赖多，必须多道互相补位

**C · 长流程生产任务**（几十轮 + 用户可交互）
- 典型：todo 助手、代码生成 Agent、电商购物助手
- 必装：最大步数（30~50）+ 超时（5~10 分钟）+ 模型说停 + **用户取消**（前端必须）+ 工具重试
- 推荐装：同工具循环检测（防「再查一次」）+ token 预算（成本控制）
- 理由：长流程 = 任意一道都可能先到，每道都要装；前端交互必须能中途取消

**D · 用户交互的前端场景**（必装 4 道）
- 典型：聊天界面、Agent IDE 插件、AI 助手面板
- 必装 4 道：最大步数 + 超时 + 模型说停 + 用户取消
- 额外考虑：前端超时（HTTP 层 30 秒兜底）跟后端超时（Agent 内部 5 分钟）是**两道不同超时** —— 都装
- 理由：前端超时是「用户能等多久」，后端超时是「任务能跑多久」

**E · 成本敏感场景**（toC / 公开 API / 多用户共用）
- 典型：toC 聊天产品、API 网关转发
- 必装：最大步数 + token 预算（**这道是核心**）+ 模型说停
- 推荐：超时 + 用户取消
- 理由：token 预算比最大步数精确（每轮 token 数差异大），成本敏感场景必装

**F · 外部 API 容错差的场景**（银行 / 支付 / 写生产库）
- 典型：支付 Agent、生产 DB 写入、风控查询
- 必装：工具重试上限（小，1~2 次）+ 同工具循环检测（N=2 都行）+ 最大步数 + 超时
- 理由：这类工具不能多调（费用高 / 副作用大），同工具循环检测要比一般业务**更早触发**（N=2 而非 N=3）

**G · 后台批处理 / 无人值守**
- 典型：夜间报表生成、定时任务
- 必装：最大步数 + 超时（按任务定）+ 模型说停
- 不装用户取消：没有用户，但必须能响应外部信号（如 SIGTERM / 消息队列的取消消息）
- 额外：落轨迹到文件（出事能事后查）

### 选型决策树（快速判断「该装哪几道」）

```
1. 有前端交互？
   ├─ 是 → 必装 4 道（最大步数 + 超时 + 模型说停 + 用户取消）
   └─ 否 → 走 2
2. 调外部 API / 写数据库？
   ├─ 是 → 加 工具重试上限
   └─ 否 → 不加
3. 工具里有「搜索 / 查询」类可能被反复调的？
   ├─ 是 → 加 同工具循环检测
   └─ 否 → 不加
4. 成本敏感 / 多用户共用 / 长会话？
   ├─ 是 → 加 token 预算
   └─ 否 → 不加
```

**通用底线**：最大步数 + 超时 + 模型说停 这 3 道任何 Agent 必装；用户取消 视前端有无；其余 3 道按业务选装。

### 选装示例（4 个常见业务）

| 业务 | 必装 | 推荐装 | 总计 |
|------|------|--------|------|
| 简单问答机器人 | 1+3 | — | 2 道 |
| 研究助手 | 1+2+3 | 5+7 | 5 道 |
| todo 助手（前端） | 1+2+3+4 | 5+6+7 | 7 道 |
| 后台批处理报表 | 1+2+3 | 7 | 4 道 |
| 支付 Agent | 1+2+3+4+5 | 6 | 6 道 |

### 一句话回到本节

> 7 种方式 = 4 道必装（最大步数 / 超时 / 模型说停 / 用户取消）+ 3 道按业务选装（工具重试 / 同工具循环 / token 预算）。**没有银弹**；按「业务类型 + 是否有前端 + 成本敏感 + 工具副作用」四问决定哪几道必装、哪几道选装。**最常见错误 = 只装 1 道**（典型就是 `max=10` 然后相信它足够）。

## 取舍

- **变体 1（max iterations）和变体 2（timeout）两个硬闸都要装**，不能二选一：光装 max iterations → 慢模型把响应拖到分钟级；光装 timeout → 快模型 + 高 max 把账单烧光。两者一起装才能互补。
- **变体 3（模型说停）单独装不可靠**：模型上一轮说停这一轮又说「再试一次」很常见。必须叠硬闸（max iterations / timeout）兜底。
- **变体 7（token budget）和变体 1（max iterations）有重合**：max iterations 间接限制了 token（每轮 ≈ 160 tokens）。但 token budget 更精确（直接看 token 总数，不受单轮长度影响）。生产里两者都装：max iterations 是粗闸，token budget 是细闸。

## 踩坑

- **代码写死只许调一次工具就结束**：真正的 Agent 循环必须能连续多轮调用工具直到任务完成——这正是本模块的核心。死循环防护不是禁止多轮，是防止「停不下来」。
- **把 `AbortController.abort()` 当成 `process.exit()` 用**：abort 是给 while 一个「该停」的信号；进程本身继续跑，处理别的请求。`process.exit()` 把整个 Node 进程杀掉，所有别的用户请求也跟着死。
- **闸门失败只 warn 不抛错**：闸门触发必须 throw 一个有名字的 error（如 `MaxStepsError` / `TimeoutError` / `UserCancelledError`）让上层做对应处理。warn + 继续跑 = 闸门没起作用。
- **变体 1 装 max=1000「反正大」**：max=1000 等于没闸。要按任务合理估算（一般 5~50），不能拍脑袋写大数。
- **「mock 模型」当真模型**：mock 模型每轮都说「再查一次」是为了让闸门效果可见。真业务里模型可能自己停（变体 3），所以 mock 演示闸门只是示意，实际部署仍要测真模型行为。

## 过关自检

- 能列举至少 3 种停下来的条件（**本条要能讲清**：已超 — 讲了 7 个变体）
- 能讲清 max iterations 和 timeout 的差别（轮次 vs 时间）
- 能讲清为什么「模型说停」单独装不可靠
- 能讲清用户取消为什么不能用 `process.exit()`
- 能讲清闸门为什么至少 4 道叠用、不是选一道
- 给一个新业务（如电商购物助手），能列出本业务需要哪几道闸、按什么顺序装

## 还没搞懂的

- 同工具循环检测（变体 6）的「N」应该定多少？业界有 3 次 / 5 次 / 10 次各种说法，没标准答案。要看具体业务场景（搜索工具容忍度高，支付工具容忍度低）。
- Token budget（变体 7）的预算是按「本次任务」算，还是按「用户本月累计」算？前者是单次防护，后者是防滥用。生产系统通常两者都做。
