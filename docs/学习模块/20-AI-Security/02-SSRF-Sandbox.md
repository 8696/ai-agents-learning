### 是什么

当 Agent 能**真的发网络请求**（调外部 API / 抓网页）和**真的跑代码**（Python / Node 沙箱执行用户生成的代码）时，它就有了传统 Web 应用的两类高危攻击面：

#### SSRF（Server-Side Request Forgery，服务端请求伪造）

**SSRF** 是攻击者让**服务器**（你的 Agent 后端）**替攻击者发请求**——而不是攻击者自己发。服务器代发意味着：

- **绕过网络边界**：你的服务器在内网能访问到的东西，攻击者借你的服务器也能访问。
- **拿到云凭证**：访问 AWS / GCP / Azure 的元数据接口（`169.254.169.254`）拿到 IAM 临时凭证。
- **扫描内网**：内网扫描器伪装成你的服务器流量。
- **读本地文件**：通过 `file://` 协议读 `/etc/passwd` 这类本地资源。

**触发条件**：**让模型决定 URL**——模型拼 URL，Agent 服务器去请求，URL 指向内网 / 元数据接口 / 本地文件。

#### Sandbox（沙箱）

**Sandbox** 是**给用户生成的代码一个受限的执行环境**——防止代码逃逸出去访问不该访问的资源（文件系统 / 网络 / 系统调用 / 其他进程）。

沙箱通常包含：

| 限制 | 防什么 |
|------|--------|
| **文件系统隔离** | 读 / 写沙箱外的路径 |
| **网络隔离** | 访问未授权的网络出口 |
| **资源限制** | CPU / 内存 / 时间 / 磁盘爆掉 |
| **权限降级** | 用非 root 用户跑 |
| **审计日志** | 一切行为可追溯 |

**触发条件**：Agent 跑 `exec()` / `eval()` / Python REPL / Node 子进程——任何让用户代码在服务器上跑的行为。

一句话：**SSRF 防「Agent 服务器被骗去请求不该请求的」；Sandbox 防「Agent 服务器被骗去执行不该执行的」**——两类高危操作要两类防线。

### 为什么（Agent 开发要懂）

Agent 时代的两个标志性能力——**真发网络请求**和**真跑代码**——恰好是 SSRF 和 Sandbox 的两个最大入口：

- **Web Agent**：让模型决定下一个 URL 去抓 → 用户「请帮我看看 `attacker.com/secret`」→ 模型当成合法任务去抓 → SSRF
- **Code Agent**：让模型生成代码并跑 → 用户「请执行 `import os; os.system('rm -rf /')`」→ 跑出来系统崩了 → 沙箱逃逸
- **Tool Agent**：让模型调任意 HTTP Tool → 用户塞 `http://localhost:6379/...`（Redis 未授权访问）→ SSRF 进内网
- **RAG Agent**：抓网页时模型选 URL → 攻击者做一个网页，URL 指向 `http://169.254.169.254/latest/meta-data/` → 拿到 AWS 凭证

具体后果（举四个最常见的）：

1. **AWS 凭证泄露**：Agent 调抓网页 Tool，URL 指向云元数据接口 → 拿到 IAM 临时凭证 → 用凭证访问 S3 / 删数据 / 拉所有资源。
2. **内网 Redis 未授权访问**：Agent 调 HTTP Tool → URL 是 `http://10.x.x.x:6379/` → 攻击者通过 Agent 访问到内网 Redis → 删数据 / 写 SSH 公钥。
3. **代码沙箱逃逸**：Agent 跑 Python → 用户代码 `().__class__.__bases__[0].__subclasses__()` → 找到 `subprocess.Popen` → 跳出沙箱执行任意命令。
4. **DoS**：Agent 跑代码 → 死循环 / fork 炸弹 / 灌满磁盘 → 服务器挂掉，攻击者用你的资源挖矿。

Agent 一旦有「真发请求 + 真跑代码」的能力 = SSRF + Sandbox **两扇大门**必须同时守。

### 易混点

SSRF / Sandbox 常被和它们的「邻居机制」混淆。**判错任何一个会让防御形同虚设**——必须分清。

#### SSRF vs CSRF

| | SSRF | CSRF |
|---|---|---|
| **谁被骗** | **服务器**（你的 Agent 后端）替攻击者发请求 | **用户浏览器**替攻击者发请求 |
| **攻击载体** | 让 Agent / 后端拼 URL | 让用户的浏览器带 Cookie 发请求 |
| **典型场景** | 模型决定 URL → Agent 服务器代发 | 用户点链接 → 浏览器带银行 Cookie 发请求 |
| **防御方向** | URL 校验 / 网络隔离 / 元数据接口保护 | CSRF Token / SameSite Cookie / 双重提交 |

**判错会怎样**：以为防 CSRF 就防 SSRF → 两件事的攻击对象不同。CSRF 防的是「用户浏览器被骗」；SSRF 防的是「服务器被骗」。

#### SSRF vs Open Redirect

| | SSRF | Open Redirect |
|---|---|---|
| **攻击面** | 让服务器发请求给目标 | 让服务器做 302 重定向到目标 |
| **目标** | 服务器**主动**请求 | 服务器**被动**重定向 |
| **关系** | SSRF 是请求被控制；Open Redirect 是重定向被控制 |

**判错会怎样**：把 Open Redirect 防御（验证重定向 URL）当 SSRF 防御 → SSRF 是「服务器主动请求」，和重定向无关。

#### Sandbox vs Container

| | Sandbox | Container |
|---|---|---|
| **关系** | 隔离**策略**的统称 | 沙箱的**一种实现** |
| **常见实现** | chroot / namespaces / cgroups / seccomp / Firecracker | Docker / Podman / containerd |
| **粒度** | 进程级 / 容器级 / VM 级 / gVisor / Firecracker | 容器级 |

**判错会怎样**：以为用了 Docker 就「沙箱化了」→ Docker 默认共享宿主机内核，**容器逃逸**是有名漏洞；高安全场景要 gVisor / Firecracker / VM 级隔离。

#### Sandbox vs VM

| | Sandbox（容器） | VM |
|---|---|---|
| **内核** | 共享宿主内核 | 独立内核 |
| **启动** | 秒级 | 分钟级 |
| **隔离强度** | 中（有逃逸风险） | 高（接近物理隔离） |
| **资源开销** | 小 | 大 |
| **适合** | 多租户、低敏感 | 高敏感、单租户 |

**判错会怎样**：所有场景都上 VM → 启动慢 + 资源浪费；按数据敏感度分级（**用户输入执行 = VM；内部业务代码 = 容器**）。

#### Sandbox vs 权限分层

| | Sandbox | 权限分层 |
|---|---|---|
| **做什么** | **物理隔离**（文件系统 / 网络 / 资源的边界） | **逻辑控制**（按角色决定能调什么） |
| **关系** | 沙箱是「外面进不来」；权限分层是「进了也只能做该做的」 | 两者**叠加**用 |

**判错会怎样**：以为沙箱就够了 → 沙箱内代码可能仍然权限过大；必须**沙箱 + 权限**双层。

### 核心概念（变体 / 分支全扫）

SSRF / Sandbox 有 10 个变体。

#### 1. SSRF 的本质：让模型决定 URL

**核心危险**：模型拼 URL → 服务器代发。攻击者只要能让模型拼出 `http://169.254.169.254/...` 这种 URL，就成功。

**例子**：跑腿代取快递（Agent 替你发请求）→ 跑腿却进你家翻保险柜（SSRF 访问内网）。

**需求 1（SSRF 演示）**：构造 5 个恶意 URL（云元数据 / localhost / 内网 IP / file:// 协议），让 Agent 去请求；验证是否被拦截。

#### 2. URL 白名单 vs 黑名单策略

| 策略 | 怎么做 | 有效性 |
|------|--------|--------|
| **黑名单** | 拦截 `169.254.169.254` / `127.0.0.1` / `localhost` 等 | 弱（绕过方式多：DNS rebinding / IP 编码 / 短链） |
| **白名单** | 只允许已知域名 / 已知 API 端点 | 强（默认拒绝） |
| **混合** | 黑名单 + 白名单双重 | 强（深度防御） |

**例子**：餐厅里黑名单是「禁止进 5 号包厢」（容易被绕过）；白名单是「只允许 1~4 号包厢」（默认安全）。

**需求 2（URL 策略对比）**：实现黑名单 + 白名单；用 10 个攻击 URL 测试，对比拦截率。

#### 3. DNS Rebinding 防御

**DNS Rebinding**：攻击者控制 DNS，返回的 IP 第一次是 `8.8.8.8`（合法），第二次是 `169.254.169.254`（恶意）。URL 检查时是合法 IP，DNS 解析后变内网 IP。

| 防御 | 怎么做 |
|------|--------|
| **解析时绑定 IP** | 解析时拿到 IP 并锁定；后续请求用锁定的 IP |
| **禁用外部 DNS** | Agent 服务器用内部 DNS 或 hosts 文件 |
| **网络层拦截** | 防火墙层禁止访问内网 IP 段 |

**例子**：餐厅菜单上写「送货到 A 餐厅」（合法）→ 送货时司机突然拐进 B 餐厅（投毒）。

**需求 3（DNS Rebinding 防御）**：实现「解析时绑定 IP + 网络层拦截」；用 DNS Rebinding 攻击 URL 测试。

#### 4. 沙箱层次：进程 / 容器 / VM / gVisor / Firecracker

| 层次 | 隔离强度 | 启动速度 | 资源开销 | 适合 |
|------|----------|----------|----------|------|
| **进程级**（chroot / seccomp） | 低 | 即时 | 几乎 0 | 受信任的内部代码 |
| **容器**（Docker） | 中 | 秒级 | 小 | 多租户、低敏感 |
| **gVisor** | 中高 | 秒级 | 小 | 容器逃逸防护 |
| **Firecracker** | 高 | 百 ms | 小 | 高密度多租户 |
| **VM**（KVM / QEMU） | 高 | 分钟级 | 大 | 高敏感 |

**例子**：酒店代订机票（Agent 替你跑代码）→ 酒店却能翻你的护照（沙箱权限过大）→ 必须用 VM 级隔离（Firecracker）。

**需求 4（沙箱层次选择）**：根据数据敏感度选沙箱；高敏感（用户代码执行）走 Firecracker / VM；低敏感（内部业务代码）走容器。

#### 5. 资源限制

| 资源 | 怎么限制 | 防什么 |
|------|----------|--------|
| **CPU** | cgroups / `ulimit` | 死循环 / 计算炸弹 |
| **内存** | cgroups / `ulimit` | 内存炸弹 / OOM |
| **时间** | timeout 命令 / watch dog | 长时间挂起 |
| **磁盘** | 配额 / tmpfs | 灌满磁盘 |
| **文件描述符** | `ulimit -n` | 句柄耗尽 |
| **子进程数** | cgroups / `prlimit` | fork 炸弹 |

**例子**：餐厅里客人只能点 5 道菜（CPU / 时间）+ 桌子只能坐 4 人（内存）+ 套餐不能超过 200 元（磁盘）。

**需求 5（资源限制）**：实现 CPU / 内存 / 时间 / 磁盘四项限制；用死循环 / 内存炸弹 / fork 炸弹测试，验证是否被拦。

#### 6. 文件系统隔离

| 策略 | 怎么做 |
|------|--------|
| **只读白名单** | 只允许读 `/workspace/data/` |
| **可写沙箱目录** | 写操作只能进 `/tmp/sandbox-<uuid>/` |
| **禁读敏感路径** | `/etc/passwd` / `/proc` / `/sys` 黑名单 |
| **chroot** | 沙箱根目录重定向，文件树虚拟化 |

**例子**：酒店代订只能看菜单（只读白名单）；写订单只能写到自己房间的便签本（可写沙箱目录）；不能翻前台账本（禁读敏感路径）。

**需求 6（文件系统隔离）**：实现「只读白名单 + 可写沙箱目录 + 禁读敏感路径」；用路径遍历攻击测试。

#### 7. 网络出口策略

| 策略 | 怎么做 |
|------|--------|
| **允许列表** | 只允许访问 `api.openai.com` / `api.anthropic.com` 等已知 API |
| **拒绝列表** | 拦截内网 IP / 已知恶意域名 |
| **DNS 限制** | 用内部 DNS 解析，禁止外网 DNS |
| **Egress Proxy** | 所有出站流量走代理，由代理做策略控制 |

**例子**：酒店只能叫外卖到特定餐厅（允许列表）；不能叫 7-11（拒绝列表）；外卖地址只能填酒店地址（DNS 限制）。

**需求 7（网络出口策略）**：实现允许列表 + 拒绝列表 + DNS 限制；用 5 个攻击目标测试。

#### 8. 权限降级（不用 root / 单独账号）

| 原则 | 怎么做 |
|------|--------|
| **不用 root** | Agent 跑代码用 `nobody` / `agent` 专门账号 |
| **能力降级** | Linux capabilities 只给必要的（如 `CAP_NET_BIND_SERVICE`） |
| **seccomp** | 系统调用白名单 |
| **AppArmor / SELinux** | MAC 强制访问控制 |

**例子**：酒店服务员（Agent 跑代码）不能拿前台万能钥匙（root），只能拿自己房间的钥匙（专门账号）。

**需求 8（权限降级）**：实现「Agent 用专门账号 + capabilities 降级 + seccomp 白名单」；验证特权操作被拒。

#### 9. 审计与可追溯

沙箱内一切行为**必须**被记录：

| 记录 | 字段 |
|------|------|
| **每次执行** | `request_id` / 用户 / 时间 / 代码 |
| **每次文件访问** | 路径 / 读 / 写 / 大小 / 哈希 |
| **每次网络访问** | 目标 / 端口 / 协议 / 结果 |
| **每次系统调用** | 调用名 / 参数 / 结果 |
| **每次资源使用** | CPU 时间 / 内存峰值 / 磁盘 / 网络流量 |

**例子**：酒店每间房的摄像头 + 门禁记录——客人进了哪间房、拿过什么东西、几点离开。

**需求 9（审计日志）**：实现 5 类审计；结构化日志 + 异常行为自动告警。

#### 10. 异常检测与告警

| 检测 | 触发条件 |
|------|----------|
| **访问云元数据接口** | URL 命中 `169.254.169.254` |
| **访问内网 IP 段** | URL 命中 `10.x` / `172.16-31.x` / `192.168.x` |
| **访问敏感路径** | 文件路径命中 `/etc/` / `/proc/` / `/sys/` |
| **异常资源使用** | CPU / 内存 / 磁盘 / 网络流量超阈值 |
| **逃逸尝试** | 系统调用命中敏感名单（`ptrace` / `mount`） |

**例子**：酒店监控中心看到客人半夜进 5 号包厢（访问敏感路径）→ 立即报警。

**需求 10（异常检测 + 告警）**：实现 5 类检测；命中时结构化日志 + 实时告警（Slack / 邮件）。

### 例子

#### 跑腿代取快递（SSRF 本质）

你让跑腿代取快递（Agent 替你发请求）→ 跑腿却进你家翻保险柜（SSRF 访问内网）。

对应：**让模型决定 URL = 让 Agent 服务器代发**。

#### 酒店代订机票（沙箱权限过大）

你让酒店代订机票（Agent 替你跑代码）→ 酒店却能翻你的护照（沙箱权限过大）。

对应：**沙箱层次不够 / 权限未降级**。

#### AWS 元数据接口（云凭证泄露）

Agent 调抓网页 Tool → URL 指向 `http://169.254.169.254/latest/meta-data/iam/security-credentials/...` → 拿到 IAM 临时凭证。

对应：**SSRF 访问云元数据接口 = 拿到云凭证**。

#### 内网 Redis 未授权访问（内网穿透）

Agent 调 HTTP Tool → URL 是 `http://10.x.x.x:6379/` → 攻击者通过 Agent 访问到内网 Redis。

对应：**SSRF 攻击内网未授权服务**。

#### Python 沙箱逃逸（代码执行）

Agent 跑 Python → 用户代码 `().__class__.__bases__[0].__subclasses__()` → 找到 `subprocess.Popen` → 跳出沙箱执行任意命令。

对应：**沙箱逃逸 = 跳出受限环境执行未授权操作**。

#### Fork 炸弹（资源耗尽）

Agent 跑代码 → 用户代码 `:(){ :|:& };:` → 进程数爆涨 → 服务器挂掉。

对应：**沙箱未做资源限制 = DoS**。
