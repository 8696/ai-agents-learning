### 一句话讲完这个模块

让 Agent 不再靠感觉——从「我看着挺好」变成「跑数字定 ship / no-ship」。四件配套：**答案评测（LLM-as-Judge）+ 过程评测（轨迹）+ 检索 + 答案三段评测（Faithfulness / Relevance / Retrieval Accuracy）+ 落地动作（CI / 门禁 / ship / no-ship 决议）**。任何一件配不齐，Agent 调优就是凭感觉猜。

### 这些条怎么连成一条线

- **17-01 LLM-as-Judge** = **答案评测**。语义题给大模型打分——自动化、相对便宜、有偏差（位置 / 长度 / 自我 / 谄媚 / 顺序）。用 Judge 就要测 Judge。
- **17-02 轨迹评测** = **过程评测**。看 Agent 怎么走的——tool choice / tool argument / step count / loop / token。和 17-01 互补：一个看对没对，一个看怎么对的。同答案不同路径的代价靠这一项。
- **17-03 Faithfulness / Relevance / Retrieval Accuracy** = **检索 + 答案三段评测**。Retrieval Accuracy 评检索；Faithfulness 评生成是否编造；Relevance 评答案是否切题。三项独立报告，不合成综合分——综合分会掩盖分段问题。
- **17-04 CI / ship-no-ship** = **评测的落地动作**。把数字接进 PR / merge / 发布：Golden Set 固定、Baseline 跟合 / 上线更新、Hard fail 拦、Soft warn 提示、Shadow eval 并行、报告能看能报警。

**四件配套**：只有答案没有过程 = 看不到执行质量；只有过程没有答案 = 看不到结果；只有评测没有 CI / 决议 = 数字没用上；只有 CI 没有评测 = 拦错了。任何一件配不齐都是「凭感觉拍板」。

| 维度 | 来源小节 | 关键产出 |
| --- | --- | --- |
| **答案**（对没对） | 17-01 | LLM-as-Judge 评分 + Judge 校对 |
| **过程**（怎么对的） | 17-02 | tool choice / argument / step count / loop / token |
| **检索 + 答案**（哪段坏） | 17-03 | Retrieval Accuracy / Faithfulness / Relevance 三段独立 |
| **落地**（能不能上） | 17-04 | CI + Golden + Baseline + ship 决议 + Shadow |

### 模块验收对答

按模块 17 README「验收」9 条逐条答：

| 验收项 | 我的回答 |
| --- | --- |
| 1. 至少 30 条 Golden Dataset | **能讲**：Golden Set = 标好答案的固定数据集，是 ship / no-ship 的对照件（17-04）。N ≥ 30 是底线，上不封顶——任务越复杂、变体越多就越要大。**这一步不是这一段能交付的代码，是学习者单独真实项目里要做的事**——讲得清：gold 制作流程（同义复述 + 多 gold 命中 + 程序扩）。 |
| 2. LLM-as-Judge 评分 | **能讲**：用大模型当裁判评另一个模型的输出——语义题便宜、自动。**底线**：用 Judge 就要测 Judge（位置 / 长度 / 自我偏好 + 与人工 gold 对齐）。这是 17-01 的核心。 |
| 3. Tool 调用正确率 | **能讲**：轨迹评测里的 tool choice / tool argument 两项（17-02）。调对了工具 + 参数填对 = 双对才算 pass。客服任务调 `get_order(order_id=user_input)` → tool name + argument 都要对。 |
| 4. Trajectory Evaluation | **能讲**：17-02 整篇。**不只是答案，看执行路径**——同答案不同路径的代价（多调无关工具、多花 token）靠这一项。把工具过度选择、循环、step 过大量化。 |
| 5. 一条命令跑报告（`yarn app:17-01-eval`） | **能讲**：评测流水线的入口。能 shell 一行跑：跑数据集 → 模型输出 → Judge 评分 → 出 JSON / Markdown 报告。学到具体一条再加脚本（17-04 的 CI 形态落地）。 |
| 6. 进 CI 或等价过关检查 | **能讲**：17-04 整篇。每次 PR 自动起评测流水线，超阈 fail，sensitivity 阈值调节。**这是评测的落地**：评测出数字没用上 = 没接 CI = 凭感觉拍板。 |
| 7. 至少一次真实 ship / no-ship 记录 | **能讲**：改一段代码 → 跑 baseline + new → Δ → 决策。**改完跑过评测 + 决议就够**，不需要专门「做一次」——日常 CI 拦下 / 放行就是真实记录。**这一步不是这一段能交付的代码，是学习者单独真实项目里要做的事**——讲得清：成功率 / Tool 正确率 / Token 至少两项的 before / after + 决策理由。 |
| 8. 报告能量 Faithfulness / 区分 Relevance vs Retrieval Accuracy | **能讲**：17-03 整篇。Retrieval Accuracy 评检索；Faithfulness 评生成是否编造；Relevance 评答案切题。三项**独立**报告——综合分掩盖分段问题。 |
| 9. 区分 offline 回归 vs online / shadow eval | **能讲**：offline = 跑历史数据集 + Golden；shadow = 上线后并行跑两份版本（旧版本真实流量，新版本同输入不引流量）。**Shadow 的好处**：上线前一天看到真实效果；**风险**：跑两份 = 贵。 |

**自测问题同步回答（README 5 问）**

1. *如何评估一个 Agent 好不好？* **多维度**：答案评测（17-01）+ 过程评测（17-02）+ 检索 + 答案三段（17-03）+ 落地动作（17-04）。单看任何一项都看不全。
2. *什么叫 ship/no-ship？* 拿评测数字与 baseline 对比，**超阈不合并**就是 no-ship，**没超阈可合**就是 ship。决议需要 baseline + 阈值 + 自动拦 / 自动提示。
3. *LLM-as-Judge 的偏差怎么处理？* **先承认有偏差**（位置 / 长度 / 自我偏好 / 谄媚）；再测 Judge（与人工抽检、gold 集对齐）；再加控制（rubric / few-shot / 多 Judge 投票 / 跨家族）。
4. *为什么要评估轨迹而不只是结果？* 同答案不同路径的代价不一样——绕路、循环、tool 错选、参数错填，结果看不到。生产里**过程问题比答案问题更严重**（多花 token、多副作用、可能写邮件 / 删文件）。
5. *Faithfulness 量的是什么？* **回答里的每条事实是否能在检索材料里找到依据**——是「基于检索」不是「绝对正确」。检索材料本身错 = Faithfulness 高但答案错；Faithfulness 高 + 字面也对 = 真可靠。

### 最容易记错的三条（跨条）

1. **综合分掩盖分段问题**。只看 Faithfulness 平均 0.85 不算数——要看哪一类题 Faithfulness 0.5。17-03 三段独立报告是这件事的关键。
2. **Judge 分数不是真理**。位置 / 长度 / 自我 / 谄媚 都在，用 Judge 就要测 Judge——这是 17-01 的核心。同样训诫用 Judge 评 trace 也带偏差（17-02）。
3. **CI 跑 ≠ ship / no-ship**。CI 是自动跑评测，ship-no-ship 是拿数字决议。两个一起才完整。**没决议 = 数字没用上**——17-04 的关键。

### 跨条踩坑

- **没 CI 自动跑 = 评测放着不用**（17-04）。
- **Judge = 真值**（17-01）。
- **Judge 换版看不出**——漂移检测没做（17-04）。
- **Gold 漂了**——baseline 跟着漂（17-04）。
- **单一指标掩盖**——综合分失去信号（17-03）。
- **用 Judge 评检索命中**——这是规则题（17-03）。
- **答对 ≠ 答切题**（17-03 的 Relevance vs Correctness）。
- **答对 ≠ 不编造**（17-03 的 Faithfulness 不等于绝对正确）。
- **改 prompt 不重对齐 baseline**（17-04）。
- **轨迹没 gold = 用 Judge 评**——Judge 看 trace 也有偏差（17-02）。
- **loop 检测没做**——死循环跑 5 分钟才发现（17-02）。
- **CI 跑了但报告没人看** = 数字出 + 决策没做（17-04）。
