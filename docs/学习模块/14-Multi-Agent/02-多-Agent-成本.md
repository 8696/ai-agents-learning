## 是什么

多一次交接，就多一轮模型调用。每一轮的账单只有两截：送进去的全部文字是输入 Token（Input Tokens），模型写出来的全部文字是输出 Token（Output Tokens）。客人从开口到听到取餐号的那段时间，叫墙钟时间（Wall-Clock Time）。耗时不在用量字段里，要自己记时刻。

协议 A（`chat.completions`）把两截写在 `usage.prompt_tokens` 和 `usage.completion_tokens`。协议 B（`messages.create`）写在 `usage.input_tokens` 和 `usage.output_tokens`。每一次返回各加各的。不要用汉字个数估计。输入和输出的单价常常不同，所以两列分开加，最后才换成钱：钱 = 输入 Token × 当天输入单价 + 输出 Token × 当天输出单价。单价以厂商当天价目为准，这里不写死一家的价格。

有的厂商会在用量里另给一列，表示有多少 Token 命中了提示词缓存（Prompt Caching）。那一列的字段名这一轮没有逐家核对，写在「还没搞懂的」。没看到那一列，重复的系统提示词就按全价加。缓存怎么计价，是后面可靠性那一模块的内容。

下面这组数字只为了把加法走通，不是实测，也不是基准。换成真实项目时，用接口返回的用量字段和自己记的时刻重算。

为了能验算，示意里先固定这些计数：

- 任何一个角色的系统提示词：500 Token
- 客人原话：30 Token
- 菜单接口原文：400 Token
- 菜单结论：80 Token
- 杯贴或机器结果：40 Token
- 叫号或驳回：30 到 40 Token
- 每一次「决定下一步」的输出：20 Token
- 每一次模型调用的墙钟：2 秒

公平对照锁住这几件：同一个模型，同一句客人的话，同一份菜单和过敏表原文，同一个温度（Temperature）。两边都读这份固定文字。一边让模型现编菜单、一边真去读接口，差出来的 Token 不能算在「多了几个 Agent」头上。

单 Agent 也会调用好几次。它读菜单、看见结果、再去做杯，消息列表越来越长，每一次都把前面的内容再送一遍。对照不是「1 次对 N 次」。对照是同一杯单上两条完整轨迹的四列：调用次数、输入 Token、输出 Token、墙钟时间。

### 单 Agent：一条消息列表做完

客人说：「来一杯中杯热拿铁。」

调用 1，决定去读菜单。输入 = 500 + 30 = 530。输出 = 20。
调用 2，看见菜单原文后决定做杯。输入 = 530 + 20 + 400 = 950。输出 = 20。这 950 里已经含着菜单原文。做杯这个决定发生在这一跳，模型读得到原文。
调用 3，看见杯贴后告诉客人取餐号。输入 = 950 + 20 + 40 = 1010。输出 = 30。菜单原文还在这条消息列表里。

| 列 | 合计 |
| --- | --- |
| 输入 Token | 530 + 950 + 1010 = 2490 |
| 输出 Token | 20 + 20 + 30 = 70 |
| 调用次数 | 3 |
| 墙钟时间 | 6 秒 |

这就是上一小节说的「读菜单、做杯、对杯贴搅在一起」在账单上的样子：决定做杯时，菜单原文还在输入里。

### 店长一次派一个：每个角色另开一份输入

分工图还是上一小节那张。店长只点名。菜单、吧台、出餐各自干活，干完交回店长。每一个框都要进总账。总账是所有角色的输入 Token、输出 Token、调用次数加在一起。

```mermaid
flowchart LR
  guest[客人一句话] --> s1[店长第1次]
  s1 --> menu[菜单工人自己的调用]
  menu --> s2[店长第2次]
  s2 --> brew[吧台工人自己的调用]
  brew --> s3[店长第3次]
  s3 --> serve[出餐工人]
  serve --> s4[店长告诉客人]
```

菜单工人自己两跳。第一跳输入 500 + 30 = 530，输出 20，决定去读菜单。第二跳输入 530 + 20 + 400 = 950，输出 80，写成结论。这一侧输入 1480，输出 100，墙钟 4 秒。交回店长的那 80 Token 不能代替这一侧的 1480。

吧台工人不读菜单原文，只收那 80 Token 结论。第一跳输入 500 + 80 = 580，输出 20。第二跳输入 580 + 20 + 40 = 640，输出 40。这一侧输入 1220，输出 60，墙钟 4 秒。

出餐工人对照原话和杯贴，一次做完。输入 500 + 30 + 40 = 570，输出 30，墙钟 2 秒。

店长自己四次，每次都带着自己的 500 Token 系统提示词：

| 店长第几次 | 输入怎么来 | 输入 | 输出 |
| --- | --- | --- | --- |
| 1 派菜单 | 500 + 30 | 530 | 20 |
| 2 派吧台 | 530 + 20 + 80 | 630 | 20 |
| 3 派出餐 | 630 + 20 + 40 | 690 | 20 |
| 4 告诉客人 | 690 + 20 + 30 | 740 | 40 |

店长一侧输入 530 + 630 + 690 + 740 = 2590，输出 100，墙钟 8 秒。

四侧相加，再和单 Agent 相减：

| 列 | 多 Agent | 单 Agent | 差（多减单） |
| --- | --- | --- | --- |
| 输入 Token | 1480 + 1220 + 570 + 2590 = 5860 | 2490 | 3370 |
| 输出 Token | 100 + 60 + 30 + 100 = 290 | 70 | 220 |
| 调用次数 | 9 | 3 | 6 |
| 墙钟时间 | 18 秒 | 6 秒 | 12 秒 |

店长一侧的 2590 已经接近单 Agent 的全部输入。多出来的那个人不读菜单、不按咖啡机，他的系统提示词和进度被模型读了四遍。

把吧台「决定做杯」那一跳和单 Agent 的调用 2 放在一起：580 对 950，少 370。370 = 客人原话 30 + 单 Agent 上一轮输出 20 + 菜单原文 400 − 交还结论 80。吧台这一次更短，是因为菜单原文没有进他的输入。总账 5860 仍比 2490 大。上下文隔离省的是某一个工人这一次不用读原文，不是整张账单变少。

店长第二次派吧台时，输入 630 里面有上一跳已经读过的系统提示词、客人原话、菜单结论。重复段要能指出来，并算出它占这一次输入的比例。这一次的 500 Token 系统提示词，占 630 的大约八成。

### 三杯同时问：时间和 Token 分开记

客人改口：「热拿铁、冰美式、燕麦拿铁，今天都能做吗？」三件事互不依赖。编排者先拆一次，三个菜单工人同时做，再汇总一次。每个菜单工人仍按上面那套计：输入 1480，输出 100，自身墙钟 4 秒。上一小节说过，三个工人同时改同一份状态时字段怎么合并，还没有定规则。这一小节只记用量：Token 三份都算，墙钟看最慢的那一份。

编排者拆开：输入 540，输出 60，2 秒。汇总：输入 500 + 80 × 3 = 740，输出 50，2 秒。

三个工人重叠，墙钟只计最慢的那 4 秒。总墙钟 = 2 + 4 + 2 = 8 秒。总输入 = 540 + 1480 × 3 + 740 = 5720。总输出 = 60 + 100 × 3 + 50 = 410。总调用 = 8。

若这三杯排成队，三份工人的 4 秒加成 12 秒，墙钟变成 2 + 12 + 2 = 16 秒。示意里编排者仍是拆一次、汇总一次，Token 仍是 5720 这一量级。客人少等了大约一半时间，输入 Token 没有少。

必须先有菜单结论才能做杯的那一杯，不能用这张同时开工的图。那一杯的墙钟是各跳相加，含店长每一次点名。

### 杯贴打回：整圈入账，后一跳更长

出餐发现杯贴做成了冰美式，交回约 40 Token 的驳回，而不是叫号。店长再派吧台。示意这一圈：

- 店长再派一次，输入约 730，输出 20，2 秒
- 吧台第一跳输入 500 + 80 + 40 = 620，输出 20
- 吧台第二跳输入 680，输出 40，两跳共 4 秒

这一圈输入 730 + 620 + 680 = 2030，输出 80，调用 3 次，墙钟 6 秒。加进原来的 5860，输入变成 7890。最后给客人的那一句仍可能只有几十 Token。漏记这一圈，就会把打回重做看成几乎免费。

后一跳更长，是因为驳回理由写进了下一次的输入。共享状态里的 `menuNotes`、`cupLabel`、驳回原因每多一个字段，后面每一次调用的输入都更长。

### 多一层小组主管

店长只派点单组主管和吧台组主管时，小组主管自己也是模型调用。示意点单组主管收任务、再交回摘要，两次输入各约 580，多出约 1160 输入 Token。店长因此可以不读那 400 Token 菜单原文，店长某一次的输入会变短。总账要把这 1160 加上。层数每加一层，就多一组系统提示词，多一轮「收进来再交上去」。

按层分账：顶层店长一张，小组主管一张，组内工人一张。组内菜单原文不出现在店长那张账的输入里，仍出现在总账里。

### 两种交还，总账范围不一样

共享状态：下一站读字段。菜单原文留在菜单工人自己的调用里，吧台只读 `menuNotes`。那 400 Token 仍要算在菜单工人头上。

当工具调用：工人另开一份消息列表，内部来回默认不进店长的消息列表。店长侧只增长那条工具返回值。总账 = 店长每一次 + 每个工人内部每一次。只加店长消息列表里那一句「今日有热拿铁」，菜单工人读原文的那 950 就丢了。

## 为什么（Agent 开发要懂）

没有这四列，分工图只能回答谁干活，不能回答值不值得拆。模块验收要的是：同一任务，单 Agent 和多 Agent，Token 差多少、耗时差多少，并写出什么场景值得、什么场景是过度设计。

只数调用次数，会漏掉一次超长输入比多次短调用更贵。上面单 Agent 只有 3 次，输入已经 2490。次数和输入 Token 要分开记。

只看并行后的秒数，会把三杯同时查菜单说成更省。8 秒对 16 秒是客人少等了。5720 的输入 Token 还在。时间和钱是两列。

只看隔离之后某一个工人变短，会推出拆开更便宜。吧台那一跳从 950 降到 580，总输入却从 2490 升到 5860。隔离换来的是吧台读不到菜单原文，降低把原文抄进杯贴、或在客人说过牛奶过敏时仍去做奶咖的机会。这笔差是否值得，要另看有没有少做错杯。Token 差本身不是质量分。

只把最终取餐号的几十 Token 当成成本，打回那 2030 输入会全部消失。只加店长看见的工具返回值，菜单工人内部读原文的调用会消失。

## 易混点

**调用次数和输入 Token。** 次数回答模型被叫醒几次。输入 Token 回答每次叫醒时读了多少。店长四次的输入里，系统提示词 500 出现了四遍。只报「多了 6 次调用」，报不出输入差 3370。判错会怎样：一次把整份菜单塞进同一次调用，次数很少，输入却可以超过店长的某一次，账单方向看反。

**最终那句话的 Token 和整条轨迹的 Token。** 客人看见的取餐号可以只有 30 Token。账单是 5860 输入 + 290 输出。判错会怎样：杯贴打回那一圈的 2030 输入不进账，重做看起来几乎免费。

**工人交回的短句和工人内部的调用。** 交回店长的菜单结论是 80 Token。菜单工人自己第二跳的输入是 950，这一侧输入合计 1480。判错会怎样：总账用 80 代替 1480，读菜单的原文从账单里消失。

**并行的墙钟和并行的 Token。** 三杯重叠后墙钟 8 秒，输入仍是 5720。排队则墙钟约 16 秒，输入仍是同一量级。判错会怎样：把「更快」写成「更便宜」，三份系统提示词和三份菜单原文都还在账上。

**某一个工人变短和总账变短。** 吧台决定做杯时输入 580，单 Agent 决定做杯时输入 950。所有角色相加是 5860 对 2490。判错会怎样：用前一个差宣布多 Agent 更省 Token，方向是反的。隔离省的是这一跳的原文，总账通常因为多了点名的人而变大。

**单 Agent 一次调用和单 Agent 一条轨迹。** 单 Agent 读菜单、做杯，消息列表也会变长，调用 2 的输入已经是 950。判错会怎样：用「单 Agent 只调用 1 次、输入只有系统提示词」去减，多 Agent 的差会被放大到失真。

**全价和缓存价。** 重复的系统提示词有时会在用量里单列成缓存 Token，单价可以不同。那一列没出现，500 就要按全价乘以它出现的次数。判错会怎样：看见前缀长得一样就把它从总账里删掉，店长那四遍 500 会少记 2000。

## 例子

### 传单：每一站都把纸条再念一遍

客人说「中杯热拿铁」。单人店员自己看黑板、自己做、自己喊号。黑板上的字他一直看得到，所以做到后面，菜单原文还在他眼前。这就是那条输入 2490 的消息列表。决定做杯时，他眼前仍有那 400 Token 的黑板原文。

换成店长传单。店长把整句再念给菜单。菜单看黑板，把 80 Token 的结论写在纸条上交回。店长再念给吧台。吧台只看纸条，不看黑板原文，所以他决定做杯时只读到 580，而不是单人店员那一跳的 950。出餐再对一次杯贴。每一站都要把到目前为止的纸条再念一遍。念的遍数是输入 Token，纸条上新写的行是输出 Token，客人从开口到听到号的时间是墙钟。吧台少看了黑板，店里被念过的总字数却是 5860，比单人店员的 2490 多。

### 三杯同时看黑板

三杯只问「今天有没有」。三个店员同时看黑板，客人等待看最慢的那个，示意里是 8 秒。三个人的嗓子都算数，输入仍约 5720。排成队则大约 16 秒，字数没有因此减少。

前端里这就是瀑布请求和 `Promise.all`。瀑布图的总时间是各段相加。并行时总时间看最慢的那条。两条路的响应体大小照样相加。网络面板里传输量变少，才会更便宜。只是条带重叠，传输量还在。

### 杯贴做错，整张纸条再走一圈

杯贴做成冰美式。不是只把喊号改一个词。整张纸条再传回吧台，驳回理由写在纸条上，后一跳比第一轮更长。这一圈另计约 2030 输入 Token，加进总账变成 7890。客人最后听见的那一句仍可以很短。

前端里这是失败后再发一轮。新请求体比上一轮多了错误原因字段。只改界面上最后那句成功文案的长度，记不住这一轮请求体。

### 组长多念一遍岗位说明

店长不直接对看黑板的人说话，先对点单组组长说。组长把自己的岗位说明再念一遍，再派组内的人，然后把短结论交回店长。组长这遍岗位说明约 1160 输入 Token，是多出来的一层。店长自己的纸条上可以没有黑板原文。黑板原文仍算在组内那个人头上，总账要加。

前端里这像父函数自己请求几次，每次再等待一个子函数。子函数内部的请求默认不出现在父函数的请求体里，浏览器网络面板里它们都在。总账按网络面板加，不按父函数日志里那一条返回值加。

## 需求清单

这些需求串成同一家咖啡店的用量对照。验收发生在单独的真实项目里：同一杯单、同一个模型、同一份菜单原文，用接口用量字段和自己记的时刻填四列。本仓库不为这一小节新建演示。上一小节留下的两步，菜单和做杯是模型按提示词编出来的字段，不拿来当这组数字的来源。

1. 业务场景：客人点一杯中杯热拿铁。目标：拿出单 Agent 轨迹和「店长一次派一个」轨迹的四列，并写出差。涉及：调用次数、输入 Token、输出 Token、墙钟时间；单 Agent 也有多轮。验收：四列都来自用量字段和时刻相减；差是两列相减。
2. 业务场景：店长第二次派吧台。目标：指出这次输入里哪些 Token 是上一跳已经读过的。涉及：输入被整段重发。验收：能标出重复段（系统提示词、客人原话、上一站结论），并算出它占这一次输入的比例。
3. 业务场景：吧台决定做杯的那一跳，对照单 Agent 看见菜单原文后决定做杯的那一跳。目标：同时写出「这一跳谁更短」和「总账谁更大」。涉及：上下文隔离和总账是两列。验收：两句都引用数字。吧台这一跳更短、总账更大，两句同时成立。
4. 业务场景：热拿铁必须先菜单、再做杯、再出餐。目标：墙钟按各跳相加。涉及：串行交接的等待。验收：客人等待等于各跳墙钟之和，含店长每一次点名。
5. 业务场景：三杯只问今天有没有，同时查。目标：秒和 Token 各一行。涉及：并行时墙钟看最慢的一份，Token 相加。验收：写明时间短了，输入 Token 仍是三份工人加上编排者的拆开和汇总。
6. 业务场景：杯贴做成冰美式，打回重做。目标：这一圈单独成行再加进总账，并看到后一跳因为多了驳回字段而更长。涉及：打回整圈入账；共享状态变长。验收：总账含这一圈的调用次数和输入 Token。最终给客人的那句话的 Token 不能代替这一圈。
7. 业务场景：店长只派点单组主管和吧台组主管。目标：按层分账。涉及：分层多出来的主管调用。验收：顶层、小组主管、组内工人三张账分开。能说出多这一层多了哪些调用。组内菜单原文不出现在店长那张账的输入里，但仍出现在总账里。
8. 业务场景：菜单工人作为店长的一个工具，自己还会读菜单。目标：总账含工人内部每一次模型调用。涉及：当工具调用时的账单范围；共享状态时原文记在产出它的那个工人头上。验收：只加店长消息列表里那条工具返回值，判定为漏账。
9. 业务场景：用上面的差做决定。目标：两句结论都引用自己的数字。涉及：什么时候多出来的 Token 换隔离，什么时候是过度设计。验收：一句写清「菜单、过敏、做杯、对杯贴会互相污染时，多出来的输入 Token 换的是吧台读不到原文」。另一句写清「只问今天有没有热拿铁，却拆成多个工人，多出来的系统提示词没有换到隔离」。

## 这几种做法对照

| 情况 | 数据怎么走 | 需求 |
| --- | --- | --- |
| 四列对照，单 Agent 同样有多轮 | 同一杯单两条轨迹相减 | 需求 1 |
| 下一次调用把上一跳再送一遍 | 重复段占这一次输入的比例 | 需求 2 |
| 单个工人变短，总账变大 | 580 对 950，同时 5860 对 2490 | 需求 3 |
| 串行墙钟相加 | 点名和干活的秒数都算进客人等待 | 需求 4 |
| 并行：时间重叠，Token 相加 | 8 秒对 16 秒，输入仍约 5720 | 需求 5 |
| 打回整圈，后一跳更长 | 这一圈约 2030 输入另计 | 需求 6 |
| 分层多一层主管 | 小组主管那组调用单独成账 | 需求 7 |
| 工人内部调用进总账 | 交回的 80 Token 不能代替工人那 1480 | 需求 8 |
| 用差决定拆不拆 | 隔离值得的一杯，和一步能问完却拆开的一杯 | 需求 9 |

## 取舍

| 你在意的事 | 更合适的做法 |
| --- | --- |
| 菜单、过敏、做杯、对杯贴会互相污染，吧台不该读到菜单原文 | 拆开。接受总账变大，换这一跳的隔离。结论要引用自己的四列差 |
| 客人只问今天有没有热拿铁 | 一个 Agent 问完。拆成多个工人，多出来的是每人一份系统提示词，没有换到隔离 |
| 三杯互不依赖，只问今天有没有 | 同时查。墙钟看最慢的一杯。输入 Token 按三份相加，不要把少等的秒数写成少花的 Token |
| 后一步依赖前一步，例如没有菜单结论就不能做杯 | 一次派一个。墙钟相加。不要为了缩短秒数让吧台和读过敏表同时开工 |
| 工人内部的菜单原文不想留在店长的消息列表里 | 当工具调用。记账时仍把工人内部每一次加进总账 |
| 下一站只该读某个字段 | 放进共享状态。原文记在产出它的那个工人头上。字段变长后，后面每一跳的输入跟着变长 |
| 人很多，店长不该看见组内原文 | 分层。小组主管的调用单独成账，再加进总账 |

## 踩坑

- 用汉字个数代替 `usage` 里的输入 Token 和输出 Token。中文和英文的 Token 数对不上字数。
- 只记客人最后看见的那句取餐号。打回那一圈不在这句话里。
- 只加店长消息列表里的工具返回值。菜单工人自己读原文的那两次没有入账。
- 三杯同时查完，墙钟变短，就写成账单变少。三份输入还在。
- 吧台某一跳比单 Agent 短，就写成多 Agent 更省。总账通常更大。
- 单 Agent 按「只调用一次」去减。单 Agent 的消息列表同样会变长。
- 两边的模型、温度、菜单原文不一致。差出来的 Token 不能算在角色数量上。
- 用量里没有缓存那一列，却把重复的系统提示词从总账里删掉。
- 把本文的 5860、5720、2030 当成自己的实验数据。这些数字只为了把加法走通。
- 把上一小节留下的两步演示的耗时，当成这一小节的单 Agent 对多 Agent。那两步的菜单和做杯是模型按提示词编出来的字段。

## 还没搞懂的

- 各厂商把缓存命中的 Token 写在用量的哪个字段，这一轮没有打开文档逐家核对。没看到单独一列时，重复前缀按全价加。缓存的计价留到后面的可靠性模块。
