## 2.1 浓缩主线

```text
调得动模型 → 让模型调得动工具 → 让模型自己循环把事做完
        → 给它知识（RAG）、记忆（Memory）、状态（Workflow）
        → 用 MCP 和 Framework 把它接入真实世界
        → 用 Evaluation / Observability / Security 证明它靠谱
        → 用你的前端能力把它做成一个人们真的想用的产品
        → 五个项目别人打开能跑、能看懂、你能讲清取舍
```

一句话：**先学会让 LLM 工作 → 再学会让 LLM 调用工具 → 再学会让 LLM 自主循环完成任务 → 再给它知识、记忆和状态 → 再用 MCP 和 Framework 扩展它 → 最后解决评测、稳定性、安全、成本和上线问题。**

1. **原理层**：Agent = LLM + Tools + Loop + State。其余全是它们的工程化。
2. **能力层**：能手写 Agent Loop 的人，学任何框架都是三天的事；只会框架的人，遇到框架不支持的场景就卡死。

每天问自己：当前模块 README 小节进度里**这一条**走完了吗（能讲清楚、链接补了没有、**该条小节 MD 按模板写了没有**；本地代码跑起来了没有、`LEARNING.md` 跟上了没有）？有一个「没有」下次必须补上。

## 2.2 路线图

```text
① LLM 基础（Token / Context / Transformer / Embedding）
        ↓
② LLM Application（API / Prompt / Streaming / Structured Output / Zod）
        ↓
③ Tool Calling（Schema / Execution）
        ↓
④ Agent 核心（Loop / ReAct / Planning / State / Memory）
        ↓
⑤ RAG（Chunking / Vector DB / Retrieval / Rerank）
        ↓
⑥ Workflow / MCP（State Graph / Checkpoint / HITL）
        ↓
⑦ Agent Framework（AI SDK / LangGraph …）
        ↓
⑧ Advanced Agent（Multi-Agent / Browser / Coding）
        ↓
⑨ Production（Evaluation / Observability / Security / Cost）
        ↓
⑩ Full-stack（React/Vue / 部署 / 完整产品 / README·架构图 / 能独立讲清取舍与复盘）
```

每一层都建立在你亲手实现过的上一层之上，而不是并列堆知识点。

### 顺序原则

**MCP 不是基础阶段。** 必须先走通 `LLM → Tool Calling → Agent Loop → Tool Execution`，再学 MCP 如何标准化连接。

1. **能力先于抽象。** 框架 / 协议排在它所抽象的能力之后（MCP 之于 Tool Calling，LangGraph 之于手写状态机）。
2. **单体先于协作。** 单 Agent 没扎实之前，Multi-Agent 只会放大设计缺陷。
3. **可观测先于优化。** Evaluation（17）和 Observability（18）排在可靠性/成本（19）前面。

允许的例外：模块 22 最简流式 UI 可提前到模块 02 之后；模块 13 可提前但必须先完成 07；模块 01 可深挖但不要陷进数学推导；已有后端经验则压缩模块 21。

| Memory / State 与 Framework | 10、11 在 Framework(13) **之前** | 框架实战(6) 在 Memory+State(7) **之前** | **推荐前者**：先手写再看抽象 |
| 安全与多 Agent | Multi-Agent(14) 在 Security(20) **之前** | 安全(9) 在多 Agent(10) **之前** | 两者都行；较早做 Coding Agent 则提前学安全 |

**给 AI 助手**：默认按 2.3 的模块顺序；学习者明确说「按 13 阶段走」才按 2.5。

## 2.6 重点与坑

### 2.6.1 能力分级

系统性学习一定会问：「这么多东西，到底什么最重要？」分成四档。

| 等级 | 能力 | 重要程度 | 原因 |
| ---- | ---- | -------: | ---- |
| S | **LLM API + Token + Context + Streaming** | ⭐⭐⭐⭐⭐ | 所有 AI Application 的基础 |
| S | **Tool Calling** | ⭐⭐⭐⭐⭐ | Agent 的核心能力 |
| S | **手写 Agent Loop** | ⭐⭐⭐⭐⭐ | 真正理解 Agent |
| S | **RAG** | ⭐⭐⭐⭐⭐ | 企业 AI 应用极高频 |
| S | **Context Engineering** | ⭐⭐⭐⭐⭐ | Agent 效果的核心 |
| S | **State / Workflow** | ⭐⭐⭐⭐⭐ | 复杂 Agent 的基础 |
| S | **Evaluation** | ⭐⭐⭐⭐⭐ | 生产上要能做 ship/no-ship，不是「跑过一次评测」 |
| S | **Observability** | ⭐⭐⭐⭐⭐ | Debug Agent 必须具备 |
| S | **Security** | ⭐⭐⭐⭐⭐ | Agent 能执行真实操作 |
| S | **MCP（含生产形态）** | ⭐⭐⭐⭐⭐ | 生产要 HTTP + 鉴权；stdio 玩具不够 |
| S | **Coding Agent** | ⭐⭐⭐⭐⭐ | 程序员背景的差异化：文件 / Shell / 权限 / Sandbox |
| A | Browser / Computer Use | ⭐⭐⭐⭐ | 网页操作是进阶能力，不是 RAG / Workflow 的前置 |
| A | Agent Framework | ⭐⭐⭐⭐ | 实际开发会用，但不能靠框架理解 Agent |
| A | Memory | ⭐⭐⭐⭐ | 很重要，但不应该早于 Agent Loop |
| A | Multi-Agent | ⭐⭐⭐⭐ | 需要知道，但不要过早沉迷；更能讲「何时不该用」 |
| A | Skills / AGENTS.md | ⭐⭐⭐⭐ | 领域知识打包；用文档约束 Agent 行为 |
| B | A2A（Agent 间协议） | ⭐⭐⭐ | 认知即可：MCP=Agent→工具，A2A=Agent→Agent |
| B | Dify 等编排产品 | ⭐⭐ | **只体验**，能讲清和手写的差异，不当主线 |
| B | 能读 Python Agent 代码 | ⭐⭐ | 不转主线；能 `pip` 跑开源评测 / 读懂别人的 Agent |
| B | Transformer 深入原理 | ⭐⭐⭐ | 有帮助，但不用研究级深度 |
| B | Fine-tuning / LoRA / PyTorch | ⭐⭐ | Agent 开发初期不是重点 |
| C | CUDA / 从零训练 LLM | ⭐ | 和目标不是一条路线 |

| 档位 | 投入策略 | 掌握标准 |
|------|---------|---------|
| **S** | 70% 精力 | 能手写 + 能讲清取舍 + 项目里真实用过 |
| **A** | 20% | 能熟练使用 + 能讲清它解决什么问题 |
| **B** | 10% | 技术讨论中不露怯聊两分钟 |
| **C** | 0% | 知道它是什么、和自己无关即可 |

**给 AI 助手**：在 B / C 档停留过久，直接打断，拉回 S 档。五个项目都要达到 [2.7.2 交付标准](#272-项目交付标准五个都要达到)；项目 3+4 是 RAG / MCP / 评测 / HITL 的主战场，项目 5 是权限 / Sandbox / 安全的主战场。不要为「显得全面」平均用力到做不厚。

---

### 2.6.2 不要「框架驱动学习」

看到 LangChain → LangGraph → Mastra → Vercel AI SDK → MCP，很容易变成「今天学框架、明天学新框架」，最后：**会 5 个框架，但是不会写 Agent。**

**第一遍完全手写**（Node + TS + LLM API + Zod）：`LLM → Tool Call → 执行 → Result → LLM → … → Final Answer`。

**第二遍再用框架。** 你会发现 LangGraph 的 State / Node / Edge / Checkpoint，就是你手写过的东西被抽象起来了。这时候才算真正学会。

---

### 2.6.3 另外四个高频坑

| 坑 | 表现 | 破解 |
|----|------|------|
| **教程永动机** | 一直看文档，代码量为零 | 看和写不低于 1:2；有代码的模块必须有 commit（理论模块如 01 写各小节 MD 即可） |
| **Demo 坟场** | 20 个跑一次就废弃的小 Demo | 只维护 [2.7 五个项目](#27-五个项目)，新知识点一律回填 |
| **Prompt 玄学调参** | 效果不好就改 Prompt，凭感觉判断变好 | 提前做模块 17 最小版：哪怕 20 条测试用例 |
| **只做 Happy Path** | 模型一返回意外格式就崩 | 每个模块验收强制包含异常路径 |

### 2.6.4 四个「真的学会了」的信号

1. **能画出来**：不看资料能在白板上画出数据流。
2. **能砍掉**：能说出这个技术在什么场景下**不该用**。
3. **能重建**：把代码删掉，能重新写出核心部分。
4. **能复盘**：能说出这个项目最难的三个点怎么处理的，以及若重做会改哪三处。

## 2.7 五个项目

这个非常重要。**不要做 20 个垃圾 Demo。** 真正应该留下的是这几个项目：

| 项目 | 技术 | 你能学到什么 |
| ---- | ---- | ------------ |
| **项目 1：ChatGPT Mini** | Node + TS + LLM API + React/Vue + SSE | LLM API、Streaming、多轮对话、Context |
| **项目 2：Tool Agent** | Node + TS + Tool Calling + Zod | Tool Calling、Agent Loop、ReAct、错误处理 |
| **项目 3：Knowledge Agent** | RAG + Vector DB + Rerank + Agent | RAG、Embedding、Retrieval、引用 |
| **项目 4：Research Agent** | LangGraph + MCP + Tools + Workflow | State、Workflow、MCP、HITL、Agent Architecture |
| **项目 5：Coding Agent** | Agent + File System + Shell + Git + Browser | Coding Agent、Tool Permission、Sandbox、安全 |

其中真正值得你最后重点打磨的是 **项目 3 + 项目 4 + 项目 5**，因为它们能够把你的能力从：

> 「我会调用大模型」

提升到：

> **「我能够设计和开发 Agent 系统。」**

### 2.7.1 五个项目与模块的对应关系

```text
项目 1  ChatGPT Mini      ← 模块 00 02 03 04 06      （+ 22 的最简版 UI；01 是笔记，不进仓库）
项目 2  Tool Agent        ← 模块 05 07               （+ 10 11 回填）
项目 3  Knowledge Agent   ← 模块 08 09               （+ 17 18 回填）
项目 4  Research Agent    ← 模块 11 12 13 14         （+ 19 21 回填）
项目 5  Coding Agent      ← 模块 15 16 20            （+ 22 23 回填）
```

**关键做法：回填而不是新建。** 学到模块 17（Evaluation）时，不要新建一个「评测 Demo」，而是回到项目 3 给它加评测。这样最终你的项目是**层层加厚**的，而不是一堆浅薄的 Demo。每个项目：`README.md` 始终是**现在怎么跑**（改写，不堆历史验收）；`LEARNING.md` 当前段改成现在的地图、`### 模块 XX` 只追加；每个模块的笔记写在 [docs/学习模块/](./学习模块/README.md) 对应小节 MD，不因回填而改写成「现在的全貌」。助手侧细则 [AGENTS.md §5.1](../AGENTS.md#51-项目只有-readme-与-learning)。

模块 11 拆在两个项目里：先在 **项目 2** 手写状态机 / Checkpoint / HITL；学框架之后，把有状态 Workflow 用框架重写进 **项目 4**。不要为「框架版」再开第 6 个项目。

### 2.7.2 项目交付标准（五个都要达到）

模块级验收看 [docs/学习模块/](./学习模块/README.md) 对应模块 README。五个项目**做厚之后**还要同时达到下面这一条——别人打开仓库能跑、能看懂、你能讲清取舍。勾选落在 [学习总览 · 五个项目](./06-学习总览.md#五个项目)。

- **README**：打开就能看懂做什么、怎么跑、数据流、技术选型与不选另一种方案的理由；按文档能跑通。别人 clone 下来不必再问你。
- **架构图**：图画的模块和仓库里的目录对得上。
- **能讲清**：不看资料能向别人讲完一次真实输入怎么变成最终输出，以及这个项目最难的三个点怎么处理的。
- **能复盘**：每个项目能写出「当时最难的三处、怎么解的、若重做会改哪三处」。
- **学习总览对应格子**：README、架构图；知识库类还要有评测报告；能执行真实操作的还要有安全审计。
- **能不能改完就合进主线**：用模块 17 的数字决定，不凭感觉。

### 2.7.3 每个项目的范围和验收

拆五个项目需求时以本节为准。模块级验收仍看 [docs/学习模块/](./学习模块/README.md) 对应模块 README。

#### 项目 1 · ChatGPT Mini

- **对应模块**：00、02、03、04、06；模块 22 的最简流式 UI 可以提前做。模块 01 是笔记，不进这个项目。
- **第一期必须有**：CLI 或 HTTP 发出一条消息并拿到流式回复；`.env` 不进 git。
- **做厚之后应有**：非流式 + 流式、中途取消、Token / 成本打印、429 / 超时处理、第二家模型、带版本号的 Prompt、Zod 结构化输出、多轮对话 + Token Budget（滑动窗口 vs 摘要）。
- **项目级验收**：能向别人讲清「一次请求实际发给模型的上下文是什么」；异常路径至少测过限流和取消。同时达到 [2.7.2 交付标准](#272-项目交付标准五个都要达到)（README / 架构图）。

#### 项目 2 · Tool Agent

- **对应模块**：05、07；回填 10、11（手写）。
- **第一期必须有**：Tool Registry + 3～4 个 Tool 的完整调用闭环（含参数校验和错误回传）。
- **做厚之后应有**：无框架的 Reason → Act → Observe 循环、停止条件、trajectory 打印、长期记忆、手写 Checkpoint / HITL；至少一个 Tool 幂等；执行前有 Gateway（权限校验，模型请求不等于执行）。
- **项目级验收**：不是「调一次工具就结束」；能画出循环图；完全没有 Agent 框架；杀掉进程能 resume 且不重复有副作用的 Tool。同时达到 [2.7.2 交付标准](#272-项目交付标准五个都要达到)。

#### 项目 3 · Knowledge Agent

- **对应模块**：08、09；回填 17、18。
- **第一期必须有**：Markdown / PDF → Chunk → Embedding → 向量检索 → 注入 Prompt；检索是 Tool，不是每次都检索。
- **做厚之后应有**：Hybrid Search、Rerank、Query Rewrite、引用、≥20 条 RAG 评测集；Golden Dataset + 自动评测（一条命令 + CI 或等价闸门）；Trace；至少一次改动用数字做 ship/no-ship。
- **项目级验收**：知识库里没有答案时说不知道；一次错误回答能归因到切分 / 检索 / 重排 / 生成。学习阶段向量库默认 LanceDB（见 [怎么用 1.2](./02-怎么用.md)）。同时达到 [2.7.2 交付标准](#272-项目交付标准五个都要达到)（含评测报告）。

#### 项目 4 · Research Agent

- **对应模块**：11（框架态）、12、13、14；回填 19、21。
- **第一期必须有**：自己写的 MCP Server（≥2 个 Tool + 1 个 Resource）被 Agent 当 Client 调通；stdio 之外还有 HTTP 形态。
- **做厚之后应有**：HTTP + 最简鉴权；用 Vercel AI SDK / LangGraph.js 重构有状态 Workflow；Researcher + Writer + Reviewer（含单 vs 多 Agent 成本对比）；重试 / 限流 / 缓存 / 成本；部署成可访问服务。Dify 只体验、能讲差异即可。
- **项目级验收**：能列出「手写版 vs 框架版」至少三条具体差异；能论证某任务该不该上多 Agent（含成本和延迟）；能口头区分 MCP 与 A2A。同时达到 [2.7.2 交付标准](#272-项目交付标准五个都要达到)。

#### 项目 5 · Coding Agent

- **对应模块**：15、16、20；回填 22、23。
- **第一期必须有**：Playwright 基础 Tool，用 Accessibility Tree 描述页面，完成一个多步骤网页任务。
- **做厚之后应有**：读 / 改文件、受限 Shell、Git、Sandbox、危险操作 HITL；`AGENTS.md` / `SKILL.md`；完整 Security Audit（含 Tool Gateway）；产品级 Chat UI（Agent Steps 可视化）。能力块对标 Cursor / Claude Code / Codex，不必做成它们的完整产品。
- **项目级验收**：Agent 不能碰到工作目录之外的文件；间接 Prompt Injection 自己打过自己；有架构图和容量 / 成本估算。同时达到 [2.7.2 交付标准](#272-项目交付标准五个都要达到)（含安全审计）。

### 2.8 综合验收（模块 23 收口）

五个项目各自达标之后，还要用下面这一条确认：**整条路线是通的，不是五个孤立 Demo。** 勾选落在 [模块 23](./学习模块/23-Production-Agent-Architecture/README.md) 小节进度；自测题见 [题库 4.8](./04-自测题库.md#48-综合验收模块-23)。

| 验收项 | 要能讲清 |
| ------ | ---------- |
| **仓库能独立跑通** | 五个项目 README 按文档能跑；`.env` 不进 git；架构图和目录一致 |
| **选型能讲清** | 每个关键技术能说出至少两个备选、以及**为什么不选**另一个 |
| **项目能复盘** | 五个项目各自能讲：最难的三个点、怎么处理的、若重做改哪三处 |
| **原理能串讲** | 不看资料，用自己项目里的例子讲清：Token / Context、Tool Calling、Agent Loop、RAG 流水线、MCP 三原语（stdio vs HTTP） |
| **能独立设计** | 给定约束（例如企业内部知识库、要引用、要 HITL、长任务不能占死 HTTP），能画出架构并标出评测 / 观测 / 安全 / 成本各在哪一层 |
