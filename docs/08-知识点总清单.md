## 模块 00 · 环境准备

- 按 Token 计费与两把密钥：账单只认 Token，两种密钥不能混用，流式最后一包可能不带用量。

  - 按 Token 计费：一次请求的账单只有输入和输出两截，不是按「点了几次发送」算。

  - 输入输出分开计价：输出通常比输入贵，Agent 循环多轮的主要开销在输出。

  - 网页订阅密钥与按量接口密钥是两把：前者给网页产品用，后者给代码调接口用，混用会鉴权失败。

  - 国内站与海外站是不同环境：域名不一样，填错会连错环境或直接失败。

  - 用量字段三件：`prompt_tokens`、`completion_tokens`、`total_tokens`，分别对应输入、输出和合计。

  - 流式最后一包不一定带用量：厂商未必支持在流里回传用量，这时要去控制台看账单。

- Node 版本下限：约定「最低 Node 22，不锁死小版本」，换机器靠 `nvm use` 对齐。

  - `engines` 只拦低版本：`>=22` 拦掉 22 以下，22 以上（含更高版本）都放行。

  - `.nvmrc` 里的 22 是推荐值：它是换机器时的对齐目标，不是唯一合法版本。

  - 换机器在 `apps/` 目录执行 `nvm use`：版本文件放在 `apps/`，在仓库根目录执行读不到。

  - 类型检查用严格模式加运行时校验：TypeScript 开启 `strict`，环境变量用 Zod 在启动时解析。

- 密钥安全：真实密钥只放一处，泄露后第一件事是换钥匙。

  - `apps/.env` 放真实密钥：这个文件不进版本库。

  - `apps/.env.example` 只列变量名：让人知道要配哪些名字，不写真实值。

  - 用源文件位置反推配置路径：从 `import.meta.url` 往上找到 `apps/`，不依赖 `process.cwd()`。

  - 泄露后第一件事是轮换：到控制台作废旧密钥、发一把新的、改本地 `.env`；只改 `.gitignore` 不够。

  - 启动时用 Zod 校验环境变量：密钥为空或地址不合法就立刻退出并打印中文错误。

- 模块复盘

  - 三条怎么连成一条线：计费让人看得懂花在哪，版本约束让换机器不掉链子，密钥管理让代码敢推到公开仓库。

  - 最容易记错的三条：订阅密钥当接口密钥用、以为 `engines: ">=22"` 只允许 22、以为改 `.gitignore` 就等于没泄露。

## 模块 01 · AI 与大模型基础认知

- AI / ML / DL 与能力边界：三者是包含关系，神经网络是用数据拟合输入到输出，模型有明确做不好的事。

  - 包含关系 AI ⊃ ML ⊃ DL ⊃ LLM：是套圈不是时间线，规则系统也算人工智能。

  - 神经网络是用数据拟合输入到输出：训练完成后定型，新问题按「像训练里见过的」去续。

  - 查数据库与拟合的区别：前者精确查找，后者统计归纳，训练没覆盖的角落会按「像不像」去编。

  - 能力边界第一类：精确计算与多步大数算术，模型在猜下一个词，不是在做运算。

  - 能力边界第二类：训练截止之后的实时信息，权重里没有「此刻」的世界。

  - 能力边界第三类：没给过的私有知识，模型没有内置可查询的数据库。

  - 同一根因三个切面：能力边界、幻觉、上下文上限都来自「模型在预测下一个词」这一件事，修法各不相同。

- Token：模型读写的计费单位，不是「字」也不是「词」，中文通常更贵。

  - Token 是词表里的一个整数编号：模型读写、计费、上下文长度全按这条整数序列算。

  - Tokenizer 是「切 + 查」的程序：词表、切分算法、特殊 Token 三样零件。

  - 常见切分算法家族：BPE、WordPiece、SentencePiece。

  - 中文更贵的原因是件数多：训练语料以英文为主，同样意思要切出更多段，不是单价更高。

  - 实测量级：中文大约每个字 1.2 个词元，英文大约每个字符 0.26 个词元。

  - 输出比输入贵：每吐一个词元都要重做一次完整前向计算。

  - 不同模型的词表不同：同一段文本在不同模型上的词元数能差 10%～30%。

  - 同一个模型版本内是确定的：同一套切分加同一段输入，永远得到同一条序列。

  - 对账只信接口回传的用量：本地切分器只用来估窗口和决定截断。

- Context Window：一次请求里输入和输出共享的长度上限。

  - 输入加输出共享一个上限：不是「输入能到上限、输出再另算」。

  - 必须预留输出空间：可用输入 = 窗口 − 预留输出。

  - 超限的表现分三层：接口直接失败、自己或产品中间层先裁、模型服务端自己裁。

  - 四种裁剪策略：截断、摘要、滑动窗口、检索增强生成（Retrieval-Augmented Generation，RAG）。

  - 截断与摘要丢的信息不同：截断丢字面细节，摘要丢细节但保留语义。

  - 「中间信息被忽略」现象：开头和结尾记得最清，正中间最容易漏。

  - 上下文窗口不等于记忆：窗口是模型侧物理限制，记忆是你自己设计的制度。

  - 高质量上下文优于长上下文：检索十段喂入通常好过整本塞一百万。

- Transformer：分编码器与解码器两块，自注意力负责「看整句关系」。

  - Transformer 是架构图纸，某个模型是照图纸造出来的车。

  - 编码器负责「读懂」：把一段文本变成内部表示，不负责往外写。

  - 解码器负责「写」：一次定一个词，写出来再拼回输入继续。

  - 自回归生成：刚写出的内容立刻变成下一次预测的输入。

  - 现在的主流是只有解码器的架构：用户提示和系统设定都当成正在写的序列的前缀。

  - 编码器-解码器双塔：用于翻译这类「左边进、右边出」的任务。

  - 掩码自注意力：解码时挡住右边的内容，防止偷看答案。

  - 注意力管「怎么看」，上下文窗口管「能装多少」：两件事。

- Attention / Self-Attention：每个词根据整句其它词算权重。

  - 三个角色 Q / K / V：Q 是「我要找什么」，K 是「我能提供什么标签」，V 是「我的实际内容」。

  - Q / K / V 来自三套不同的可学习变换：同一份输入向量投出三种视角。

  - 算分再归一化：Q 与 K 内积得到分数，过 softmax 变成 0～1 且加总为 1 的权重。

  - 加权求和：按权重把所有 V 混合成这个位置的新向量。

  - 整句同时算：所有位置并行计算，不像循环网络要排队。

  - 软分配而非挑一个：所有词都有份，比例不同。

  - 算力是序列长度的平方：长度翻倍、算力变四倍，这是上下文窗口有上限的根因。

  - 三层结构要分清：内层一次前向内部并行、中层多层堆叠串行、外层解码器自回归串行。

  - 位置编码补的是顺序：注意力本身不区分词序，靠位置编码提供「谁在前」。

  - 键值缓存（KV cache）省的是重复计算：重开一轮时键值复用，只有查询要重算。

- Embedding：文本变成向量，语义近的距离近，和词元不是同一层。

  - Embedding 是语义坐标：词元的编号是「索书号」，Embedding 是「经纬度」。

  - 词元解决「哪两个字不一样」，Embedding 解决「哪个词跟哪个词意思近」。

  - 训练机制是填空题：为了让模型猜对被遮住的词，常一起出现的词在向量里靠近。

  - 余弦相似度（Cosine Similarity）是主要度量：只看方向，不受长度干扰。

  - Embedding 不是位置编码：前者是「含义」，后者是「顺序」，两者互不重叠。

  - 静态与上下文相关两派：静态便宜可缓存，上下文相关能区分歧义词。

  - 大模型的输入层也是固定查表：真正上下文相关的是经过多层注意力之后的表示。

  - 三个用途：检索增强生成的召回、语义记忆、工具匹配。

- Temperature / Top-P：控制随机性，抽取任务和创意任务要调不同的旋钮。

  - Temperature 缩放对数概率：`T=0` 退化成贪心解码，永远选概率最大的。

  - Top-P 是核采样：按概率累加到 P 为止，保留这一批候选再按概率抽。

  - Top-K 与 Top-P 的差别：Top-K 名次写死，Top-P 按概率分布动态定。

  - 温度控制「花不花」，不控制「对不对」：调温度治不了幻觉。

  - 贪心解码与采样的取舍：客服要一致用贪心，创作要多样用采样。

  - 完全可复现还要固定随机种子：温度为 0 时，浮点累加顺序仍可能带来边界差异。

- Hallucination：模型在预测下一个词，不是在查数据库。

  - 成因一句话：模型没有事实核查这一步，只关心接得通不通。

  - 五种形态：编造引用、编造人物、虚构数据、混淆相似概念、时间穿越。

  - 与故意撒谎的区别：模型没有意图也没有道德开关，加道德提示词没用。

  - 与能力差、能力强弱的区别：换成更大的模型也不能根治幻觉。

  - 与温度的区别：温度只影响措辞，幻觉是事实错。

  - 与能力边界的区别：能力边界是架构就不会，幻觉是本可以做对却编了，蒙对也算幻觉。

  - 治法：检索增强生成、工具调用、结构化输出，三条一起才是完整解法。

- 预训练 vs 推理：训练你不做，调接口做的是推理。

  - 四个阶段：预训练、指令微调与人类反馈对齐、可选微调、推理。

  - 阶段边界是「改不改权重」：只有改权重才叫训练。

  - 基础模型与聊天模型：只会接龙的是基础模型，会听指令的是对齐后的模型。

  - 监督微调与人类反馈对齐是两件事：一个学「理想回复」，一个学「哪种回复更好」。

  - 什么时候才做微调：提示词怎么写都稳不住时才考虑；准备好数据和钱。

  - 蒸馏是用大模型的输出训小模型，能力有上限。

  - 你的工作边界：推理每天做，微调偶尔做，预训练和对齐永远不做。

- 主流模型对比：至少四家，每家记强项、价格档、上下文上限。

  - 三层标签要分清：供应商是卖推理的，模型族是产品线，模型标识是请求里真正写的字符串。

  - 价格档怎么读：分输入价与输出价，输出通常贵几倍；每家都有旗舰、主力、便宜三档。

  - 上下文上限要分广告数字、价目里的长文溢价档、聊天网页产品的额度。

  - 协议与端点：一套通用接口形状能接多家，但价、上下文、能力不复制。

  - 选型流程：先看任务，再看窗口够不够，再在够的里面选最便宜能过关的。

  - 「兼容某家」不等于「就是那家」：换家必须重建知识库。

  - 输出上限和上下文上限是两件事：上下文还剩很多也可能因为单次输出上限被截。

  - 模型标识写错的三种后果：找不到模型、鉴权失败、悄悄降到别的模型。

- 模块复盘

  - 十条怎么连成一条线：先给大模型在学科地图里定位，再进内部结构，最后落到运行时行为和选型。

  - 跨条最容易混的三组：词元与 Embedding、幻觉与上下文上限、温度与 Top-P。

## 模块 02 · 大模型接口开发

- 流式输出与服务端事件（Server-Sent Events，SSE）：为什么逐字返回，而不是等全部生成完。

  - 一次性返回：攒齐再给，前几秒屏幕空白，体验像卡死。

  - SSE 帧的形状：`Content-Type: text/event-stream`，一行一个字段，空行收帧。

  - 结束标记：约定用 `data: [DONE]\n\n`。

  - 增量字段是字符串不是词元计数：一帧可能含一个或多个词元，也可能厂商攒批。

  - 三个层级要分清：模型内部词元数、SSE 帧数、帧里字符串长度，完全解耦。

  - 思考内容与正文可能同字段也可能分字段：写客户端必须同时认三种形状。

  - 思考词元单独计费：完整用量里有一项专门报思考部分。

  - 流式不等于实时：显著降低首字延迟，总耗时可能差不多。

  - 断流处理：服务端可能不送结束帧就断开，客户端要处理残余数据。

- 协议 A 与协议 B：两套调用形状，字段名、角色位置、用量字段都不同。

  - 协议 A 是通用对话补全形状：`messages` 里三种角色，流式用布尔开关打开。

  - 协议 B 是消息式形状：`messages` 里只放用户与助手两种角色，系统设定单独提到顶层。

  - 协议 B 的单次输出上限必填：不填直接报错。

  - 用量字段命名不同：一边是输入/输出/合计，另一边只有输入和输出。

  - 流式文本字段位置不同：一边在增量字段里，另一边在块增量事件里。

  - 流式结束标志不同：一边是结束帧，另一边是消息停止事件。

  - 字段名映射表：写适配层最容易写错的五处。

  - 适配层收敛：业务只调一个统一入口，协议差异全在适配层翻译。

  - 流式版本的适配层：统一增量类型用可辨识联合，业务按类型分支。

- 取消请求（AbortController）：客户端停写，服务端可能还在生成。

  - 取消信号三件：实例、触发方法、挂在异步操作上的信号。

  - 取消同时做三件事：标记已取消、触发回调、让请求立刻失败并关掉连接。

  - 客户端取消不等于服务端停止：服务端可能继续生成，已生成的词元照常计费。

  - 两种能让服务端真正停：断开底层连接、用服务端原生的取消接口。

  - 厂商差异：所有厂商都支持客户端取消；服务端能否立刻停看实现，自部署最差。

  - 与 `EventSource` 的差别：取消支持任意方法、能带任意请求头。

  - 超时取消：Node 17 以上有内置的「到点自动取消」，但别把超时设太短。

  - 两种异常都要接：接口层抛的取消错误和 SDK 包过的取消错误。

- 限流与重试（Rate Limit / Retry）：为什么要指数退避，哪些错误不该重试。

  - 429 的语义：是你太快了，不是服务端出错。

  - 为什么一定会有：推理贵、显卡有限，账号按时间窗口分配额。

  - 三种配额：每分钟请求数、每分钟词元数、并发数。

  - 429 与 5xx 的区别：一个是「你太快」，一个是「我坏了」。

  - 重试等待头：服务端告诉客户端「至少等这么久再试」，优先听它。

  - 指数退避：第 1 次等 1 份基准、第 2 次 2 份、第 3 次 4 份，上限封顶。

  - 抖动（jitter）：加一段随机偏移，避免所有人同一时刻一起回去把服务端再打挂。

  - 可重试与不可重试的错误分类表：4xx 业务错、鉴权失败不该重试。

  - 额度不足型 429 是特例：表面像限流，实际是钱的问题，要立刻报警。

  - 幂等性是重试的前提：写操作重试可能做两次，要有幂等键。

  - 流式中途才来 429 怎么办：两种选择——丢弃已发内容重连，或保留已发内容标记未完成让人续。

  - 取消与退避的分工：用户主动停走取消，服务端劝退走退避。

  - 重试上限与降级：次数上限、总时长上限、然后降级到备用方案。

- 思考内容（Thinking / Reasoning）：协议里思考和正文怎么分、怎么开、追问时怎么回传。

  - 思考是什么：给用户看的正文之前先走的一截内部推理。

  - 同一套协议两个厂商三种方言：开关名字、返回位置、默认开都不统一。

  - 思考的两种返回形态：嵌在正文里用标记包住，或放在独立字段/独立块。

  - 客户端要处理三种形状，不能假设某一种。

  - 思考预算：告诉模型「最多用这么多词元思考」，是软上限不是硬截断。

  - 思考预算与单次输出上限的关系：预算不得大于输出上限。

  - 不传思考参数不代表模型不思考，只是没有单独暴露出来。

  - 追问历史怎么拼：协议 A 建议把思考一起回传，协议 B 的带签名思考块不能原样塞回去。

  - 追问的例外：官方思考模式在思考块里会带校验签名，持久化时必须保留。

- 模块复盘

  - 五条怎么连成一条线：流式是底座，协议差异靠适配层收敛，取消管客户端，限流管服务端，思考管输出语义。

  - 跨条最容易混的三条：客户端取消不等于服务端停止、帧数不等于词元数、思考默认形态不能假设。

## 模块 03 · 提示词工程（Prompt Engineering）

- 消息角色与优先级：冲突时谁说了算、系统设定该放什么。

  - 三种角色：系统设定是全局规则，用户消息是这一轮输入，助手消息是多轮里的历史回复。

  - 优先级是训练出来的事实：系统 > 用户 > 助手，不是厂商开关。

  - 但模型不是严格执行 if-else：遇到强诱导仍可能偏，关键约束要做双层（提示词 + 网关校验）。

  - 系统设定该放什么：身份、输出格式、风格、拒绝条件、工具约束、长期偏好。

  - 系统设定不该放什么：临时任务、当前文档、业务规则全量。

  - 系统设定太长会注意力稀释：越到中后段越不敏感，所以要短而密。

  - 角色与「系统消息」不是一回事：系统消息只指某一种角色字段。

  - 写「绝对不要做 X」会反向锚定：改成正面指令「请改用 Y 方式回答」。

  - 助手历史必须原样塞回去：不塞模型会从用户消息里直接看到信息，然后自信地编。

  - 判定标准要看「输出只能是 JSON」：不是「输出里出现过 JSON」。

- 少样本与零样本（Few-shot / Zero-shot）：示例怎么帮模型对齐格式。

  - 零样本：这次请求不给完整样例，只给指令。

  - 少样本：同一次请求里先放若干条「输入 → 期望输出」。

  - 两种写法：写在一条用户文本里，或者写成假的多轮对话。

  - 假对话里的助手消息是「标准答案」，不是真历史，不要和真多轮混在一起。

  - 上下文学习（In-context Learning）不是第三种写法：它是少样本生效的机制名，不改权重。

  - 一个样本叫「单样本」，几十个叫「多样本」，都是同一根尺子上的刻度。

  - 少样本真正稳的是格式契约和边界判法，不保证事实正确。

  - 怎么挑示例：每种结果都有样例、带上边界不好判的例子、简短正确、标准答案由人拍板。

  - 样例数通常 2～5 条就够：再多吃上下文、还会被稀释。

  - 坏样例比没样例更糟：会教出整齐的错误。

  - 少样本 ≠ 微调、≠ 检索增强生成：三个改的是不同东西。

- 思维链与推理-行动模式（Chain of Thought / ReAct）：先知道思想，循环到模块 07 再写。

  - 思维链：让模型把推理过程显式写出来再给答案。

  - 零样本思维链：提示词末尾加一句「一步步想」。

  - 少样本思维链：示例里带完整推理步骤。

  - 推理-行动模式：思考 → 调工具 → 看结果 → 再思考的循环。

  - 它解决的是「模型不知道的事」：比如明天的天气，模型只能编。

  - 轨迹长什么样：思考、行动、观察三类标签反复出现，结束是行动的一种。

  - 思维链和「思考字段」不是一回事：前者是提示词技巧，后者是接口机制。

  - 推理-行动模式和任务规划不同：规划一次列完，推理-行动边走边看。

  - 什么时候不用：单步简单任务、前置数据已备好、还没实现工具调用的循环。

- 提示词版本管理：提示词也是代码，要能比对、能回归。

  - 五件核心做法：落文件、加元数据、备回归样本、走代码评审、绑定模型版本。

  - 元数据里有什么：版本号、作者、日期、变更记录、绑定的模型。

  - 为什么要落文件：才能有版本差异、能追责、能走合并请求。

  - 为什么要回归样本：改一个标点可能让效果天翻地覆，肉眼看不出来。

  - 文本差异与行为差异是两件事：真正决定能不能合的是行为差异。

  - 一定要把模型版本一起记：模型升级是另一条变化线，混在一起分不清是谁的锅。

  - 回归集与评估集不是一回事：回归集小而固定，评估集大而会扩。

  - 改一次跑一次回归：样本集小到十几条才跑得动。

  - 手动管与用平台：手动门槛低但上限低，平台协作强但数据在别人家。

  - 可编辑与硬编码并存：生产用带版本的硬编码，探索用可编辑的界面。

- 模块复盘

  - 四条怎么连成一条线：约束层、形状层、思维层、治理层，一层管一堵墙。

  - 跨条最容易混的三条：少样本不是微调、JSON 出现不等于格式对、文本差异不等于行为差异。

## 模块 04 · 结构化输出（Structured Output）

- JSON Schema：类型、可选、枚举，以及它和 Zod 的关系。

  - JSON Schema 是一份 JSON 形态的数据结构说明书，描述另一段 JSON 该长什么样。

  - 当前主流版本是 2020-12 版，除非工具明确要求旧版。

  - 四个核心概念：类型、必填清单、枚举、可空。

  - 必填的默认极性相反：JSON Schema 默认全可选，Zod 默认全必填。

  - 枚举与常量不同：枚举是若干选一，常量是钉死一个值。

  - 可空的两种写法：JSON Schema 用类型数组，Zod 用可空修饰。

  - Zod 一份定义给三件事：运行时校验、编译期类型推导、错误信息生成。

  - `parse` 与 `safeParse`：前者失败抛错，后者永不抛、返回「成功与否」的两分支。

  - 类型推导出来的结果：可选字段带问号，默认值字段是必有的。

  - `transform` 会改类型推导出来的结果：输出形状不再等于输入形状。

  - 两边极性相反，抄错一边就会判错。

  - 怎么把一份定义喂给模型：从 Zod 派生成 JSON Schema，避免两份定义漂移。

- JSON 模式与结构化输出：前者保证是合法 JSON，后者保证符合你给的形状。

  - 六档全景：两种协议各三档（只靠提示词、只保证 JSON 语法、保证符合结构）。

  - 只靠提示词：模型自由发挥，格式完全没有保证。

  - JSON 模式：保证能解析，但不保证字段名、必填项、枚举值。

  - 结构化输出（严格模式）：额外保证符合形状，各家实现程度不同。

  - 物理拦截与软约束的差别：严格模式在采样时屏蔽不合规的词元，别的做法只是提示。

  - 「写了结构化输出但没写严格开关」是最常见的错：等于退回了 JSON 模式。

  - 各家厂商对严格模式的实现不同：有的真做屏蔽，有的直接忽略。

  - 忽略比报错更危险：请求成功返回，但根本没校验。

  - 两种协议的形状不同：一种响应永远是字符串要自己解析，另一种是对象数组，按类型分支。

  - 严格模式的写法限制：不能用联合类型或引用，每个对象要声明禁止额外字段并列出必填项。

  - 工具调用是另一种强制形状的路径。

  - 推理模型会夹带思考标记：解析前必须先剥壳。

  - 同一份清洗逻辑必须所有路径共用：不然会出现「校验通过但字段缺失」的矛盾。

  - 生产五层防御：选档、字段写对、剥壳、后置校验、失败重试或降级。

  - 单一事实来源：从一份定义派生出各家要用的形状。

- 模块复盘

  - 两条怎么连成一条线：先学会读和写形状，再学会在不同档位之间选，并守住最后一道兜底。

  - 跨条最容易混的三条：JSON 模式不等于结构化输出、清洗逻辑必须共用、剥壳要在解析之前。

## 模块 05 · 工具调用（Tool Calling / Function Calling）

- 工具调用协议：模型说「我要调哪个、参数是什么」，代码执行，再把结果塞回对话。

  - 完整一圈五个动作：模型要调 → 执行 → 结果回填 → 模型再生成。

  - 工具定义里有什么：名字、描述、参数结构（JSON Schema）。

  - 「决定调用」和「真的执行」是两件事：模型只开口，执行权在你。

  - 增量字段是 JSON 字符串：拿到要先解析再喂给处理函数。

  - 执行三步走：解析参数 → 校验参数 → 真正执行。

  - 结果回填：成功和失败都要回填，失败信息也塞进对话，模型才能换一种方式重试。

  - 结束判定：结束标志是「模型要调工具」还是「模型给出最终回复」。

  - 两种协议的字段对照：定义方式、要调位置、结果回填位置、强制调用的写法、输出上限是否必填。

  - 并行与串行怎么选：主轴是「后面那一个需不需要前面那一个的结果」。

  - 同圈多个调用要并发执行：串行会让模型不耐烦，甚至编造结果。

  - 串行依赖的写法：先执行再把结果传进下一步参数，放进并发里会拿到空值。

  - 模型自编排链：用一个循环反复问模型，由模型自己决定要不要继续调。

  - 循环要有上限：超过就报错，别让模型永远转。

  - 三种编排方式：路由层写死、模型自由编排、混合（路由层定硬约束，模型决定要不要进）。

  - 链越深越贵：上下文更长、单圈更慢、词元更多。

- 工具描述：描述和参数结构决定模型「什么时候」调。

  - 描述有两个字段：自然语言说明（何时调、何时别调、字段语义）和参数结构。

  - 描述是写给模型读的提示词，不是给程序员看的注释。

  - 描述太短或太模糊：模型不调（明明接了工具）。

  - 描述没写不适用场景：模型乱调（问退款却调了查订单）。

  - 字段没有描述：模型填错值（城市名当订单号、日期差两天）。

  - 字段描述漏了别名映射：模型靠语义硬救，思考变长，换厂商就不稳。

  - 工具太多会「选择性雪崩」：原本调用率高的工具掉到很低。

  - 参数结构不写枚举：模型填出枚举外的值，校验直接拒。

  - 六个变体：触发条件、参数语义、反例、示例、枚举约束、跨厂商兼容。

  - 反例有双向价值：既拦不该调的，也加速该调的（思考更短）。

  - 示例的真正作用是「稳定格式、不瞎填」，不是「抽数字」。

  - 判定方法：期望工具要按问句内容动态判定，不能写死。

- 工具选择参数（Tool Choice）：这一轮「可以调 / 必须调 / 禁止调 / 必须调某一个」。

  - 四种语义：自动、禁止、必须调任意一个、必须调指定某一个。

  - 禁止调时仍可以保留工具定义：这样模型还记得工具长什么样。

  - 必须调任意一个 ≠ 必须调某一个：多工具场景前者会选错兄弟工具。

  - 「必须调」在实现上不一定守约：需要响应侧校验。

  - 思考模式与强制调用会冲突：某些厂商直接报错。

  - 关掉思考或换模型是绕开冲突的三条路。

  - 这个开关是服务端写死的：模型改不了，用户界面上的开关最终也是改这个字段。

  - 一个变体：按问句偏置该用哪个强制策略。

- 工具网关与幂等：请求不等于执行，有副作用的工具必须可重试。

  - 网关是执行前的钩子层：参数二次校验、鉴权、配额、危险操作确认。

  - 危险操作走二次确认：返回「需要确认」，界面弹窗，人点头后再调一次。

  - 幂等的确切定义：同一组输入执行任意次，业务结果和执行一次一致。

  - 「重复执行没报错」不等于幂等：三次都成功、钱扣三次，不是幂等。

  - 两种落地：客户端传幂等键 + 服务端缓存命中返旧结果；服务端按业务键做去重写入。

  - 幂等键是「意图指纹」不是「请求指纹」：同一意图同键，不同意图不同键，必须由发起方生成。

  - 「业务结果恒等」不等于「调用次数等于一」：技术上也可能真调了多次，对外副作用只有一次。

  - 有副作用的工具必须幂等：没有幂等就等于把业务交给运气。

  - 幂等、限流、防抖三者正交：幂等接受重复、限流拒绝重复、防抖只是界面不重复发。

  - 用户委托授权：调第三方服务要用用户自己的身份，不能用平台的一把万能钥匙。

  - 令牌三种生命周期：授权码一次性、刷新令牌长期存、访问令牌短期现换。

  - 最小权限：每个工具配一个范围；删数据这种根本不该有范围，必须人点头。

  - 错误回传：工具的业务错误要结构化塞回对话，不能抛到最外层变成 500。

  - 分层：工具只抛业务语义错，中间件翻译成模型能读的元数据，路由层做协议适配，模型读字段决策。

  - 整圈都是契约：描述、参数结构、选择开关、错误标记、是否可重试、停止原因，全是模型读了就行动的字段。

- 模块复盘

  - 四条怎么连成一条线：协议是骨架，描述决定模型调不调，强制开关决定这一轮怎么调，网关和幂等决定敢不敢真调。

  - 跨条最容易混的三条：函数调用不等于 JSON 模式、模型请求不等于允许执行、跳过已做的和幂等是两件事。

## 模块 06 · 多轮对话与上下文工程（Context Engineering）

- 上下文与记忆：这一次请求塞进消息列表的，和跨会话存起来的。

  - 上下文是「这一桌的菜」，记忆是「上次给你写的小卡片」。

  - 上下文是容器，记忆是决定往容器里放什么的制度。

  - 会话、上下文、历史、状态四个词的关系与判断标准。

  - 检索增强生成是往上下文添砖，不是记忆：外部知识是共享的，记忆是这一位用户的。

  - 记忆是用户的，微调是厂商的：能变、要隔离、要能删的一律走外部记忆。

  - 上下文分四类：系统段、多轮消息、工具结果、附件与检索段落。

  - 记忆分五类：事实、偏好、技能与工作方式、当前工作状态、历史检索。

  - 记忆的四个操作：写入、读取注入、更新覆盖、删除遗忘。

  - 三类翻车：长期信息塞上下文、临时数据塞记忆、把会话历史整段当记忆。

  - 记忆注入的六种位置：系统设定末尾、开头、中间插入、多模态、工具返回值、按需读不注入。

  - 最稳是「按需读」：模型自己有工具能力时自己决定要不要取。

  - 写入侧三道把关：是不是事实、跨会话还有用吗、值不值得占存储。

- 压缩、摘要与滑动窗口：两种裁剪各丢哪类信息。

  - 滑动窗口：只留最近若干条，早的全扔；零额外调用，纯本地。

  - 摘要压缩：把远期若干条压成一条摘要；多一次模型调用，保留语义。

  - 核心对照：滑动窗口是「扔」，摘要是「重写」。

  - 滑动窗口适合对话流，摘要适合多步骤任务。

  - 摘要的有损代价：会丢细节、会漂移，所以摘要要从原始素材重新生成，不要拿上一版摘要再压。

  - 失败兜底：摘要失败时降级到滑动窗口，不报错、不让用户干等。

  - 降级也有代价：答得动但可能答不准，这是取舍不是 bug。

  - 摘要和记忆不同：摘要是会话内压缩，记忆是跨会话。

  - 触发阈值和裁剪单位是两条独立的线：什么时候压、按什么单位裁。

  - 常见阈值做法：按窗口的固定比例、用户可配、按模型价格动态调。

- 词元预算（Token Budget）：给历史、给系统、给本轮各留多少。

  - 三块预算：系统段（不可裁）、输出预留（只能预留）、历史段（唯一可裁）。

  - 总公式：总长度 = 系统段 + 历史段 + 输出预留。

  - 裁剪策略四种：丢最旧、摘要、软硬双层、选择性注入。

  - 软阈值是「尽量救」，硬阈值是「救不了就保服务不崩」。

  - 硬阈值兜底的做法：只留系统段、末轮、和一句提示模型重述。

  - 硬阈值配得太小会有配置安全问题：得给输出预留留够空间。

  - 选择性注入：按问句挑相关段落进上下文，不相关的整段不进。

  - 关键事实检测要用肯定句式加否定标记，否则「不能据此推断」也会被当成命中。

  - 三个坑：以为丢历史就是失忆的全部原因、跳过置信度直接做语义判定、以为检索命中多就是浪费。

- 模块复盘

  - 三条怎么连成一条线：先分清什么进上下文什么进记忆，再学怎么裁，最后学怎么分配预算。

  - 跨条最容易混的三条：上下文不等于记忆、裁剪不等于压缩、预算不等于窗口。

## 模块 07 · 手写 Agent

- Agent 循环与推理-行动模式：想 → 做 → 看，以及什么时候停。

  - 三个阶段：想是调一次模型，做是执行工具，看是把结果变成模型能读的东西。

  - 一次只调一次工具、然后就返回的是「带工具的一次问答」，不是 Agent。

  - 想的输出只有两类：要调工具，或者给最终答案。

  - 想有两种形态：显式写出思考过程，或只回工具请求（后者仍是推理-行动模式）。

  - 零工具直接答是合法的停止方式。

  - 做的变体：同圈一个（依赖串行，多圈呈现）、同圈多个（无依赖，并发执行）。

  - 并行和串行的决定权不在循环代码：代码永远并发执行当前圈，串行是模型自己「这圈只返一个」的效果。

  - 做的副作用必须看得见：跑之前拍一张快照、跑完再拍一张，比对出改了哪几行。

  - 看的变体：成功观察、失败观察后继续。

  - 失败观察：工具返回结构化错误而不是抛异常，错误进对话，下一圈模型自己改参数。

  - 失败观察和请求级失败是两件事：后者是请求根本没进循环或中途被截断。

  - 循环的变体：多圈直到完成、一圈就停（合法）。

  - 四种停止条件：最终答案、最大轮次、超时、用户取消。

  - 用户取消靠取消信号打断，不靠杀掉进程。

  - 状态要放在圈外：轮次、已调工具、累计词元、轨迹。

  - 消息类型必须用官方原生的：自定义字段名会被序列化丢掉，工具结果引用会断。

  - 工具结果的正文必须是字符串：要展示给人看时先解析再格式化。

- 先规划再执行 vs 一步步走：两种策略的代价。

  - 一步步走：每圈看完观察再决定下一步，没有事先写完的清单。

  - 先规划再执行：先产出完整步骤清单，再按清单执行，清单在第一次执行前就存在。

  - 先规划不是取消循环：执行阶段仍然可能转圈，多出来的只是「动手前那一次规划」。

  - 规划有三种形态：自然语言步骤、工具调用序列、加上可选的简单依赖说明。

  - 重规划改的是「剩下整份清单」，比一步步走的「下一个动作」粒度更粗。

  - 代价对照表：模型调用次数、第一次行动前的等待、适应性、清单过期、能不能先给人看、能不能拆模型档。

  - 什么时候值得：步骤结构事先说得清、步骤之间稳定或可独立、要给人看或先拦一下、执行能变便宜、清单不容易过期。

  - 什么时候不值得：一两步就完、下一步强依赖上一步的未知结果、世界变得快、用户必须马上看到第一个动作。

  - 策略放哪是控制流分支，不是工具调用：由代码按任务类型、用户开关或配置分流。

  - 让模型自己决定要不要规划不可靠：模型倾向固定策略，还会多一次不稳定调用。

  - 计划写出来了不等于计划对：规划器也会编不存在的工具、编还没查到的编号。

- 死循环防护：最大步数、超时、模型说停。

  - 防护是分类不是单开关：七个变体。

  - 最大步数：按圈数封顶。

  - 超时：按墙钟时间封顶，管「一次工具卡死」。

  - 模型说停：软信号，模型可能这轮说停、下轮又说再试一次。

  - 用户取消：靠取消信号打断。

  - 工具重试上限：同一工具连续失败若干次后降级。

  - 同工具循环检测：同一个工具、同一组参数连续若干轮就断。

  - 词元预算：按累计成本封顶。

  - 两种上限不能互相替代：慢模型跑十轮会超时，快模型跑五十轮会烧光预算。

  - 同工具检测针对特定工具、最大步数兜住所有循环：两个一起装。

  - 少必备的四道：最大步数、超时、模型说停、用户取消。

  - 拦截触发必须抛有名字的错误：只警告不抛等于拦截没生效。

  - 按业务类型选：简单问答装两道、研究任务装三到五道、长流程交互装全套。

  - 决策树：有没有前端交互、要不要调外部接口、有没有可能反复调的搜索类工具、是不是成本敏感。

- 模块复盘

  - 三条怎么连成一条线：先会画圈和停，再选决策节奏，最后给圈加停止条件。

  - 跨条最容易混的三条：Agent 循环不等于带工具的一次问答、并发与串行的决定权不在代码、模型说停不等于可以只靠它。

## 模块 08 · 检索增强生成基础（RAG 基础）

- 检索增强生成流水线：加载 → 切块 → 向量化 → 检索 → 生成。

  - 五步各自进出什么数据：加载拿到原文和元数据，切块拿到卡片，向量化拿到向量，检索拿到前 K 条，生成拿到带出处的答案。

  - 建库时三步（加载、切块、向量化）和提问时三步（问题向量化、检索、生成）是分开的。

  - 提问时不会重新加载和切块整库。

  - RAG 存在的根因：模型没有你那些知识，训练截止之后的和公司私有的都必须主动喂。

  - 「省词元、变快、变准」是副产品，不是选它的理由。

  - RAG 相对长上下文真正独有的优势：能点名出处，可追责、可更新、能拒绝编造。

  - 加载要处理两种格式：文本按标记分段，PDF 要抽文本并带页码。

  - 加载失败要单独通道：空文件、坏文件、不支持的格式、扫描件抽出来是空或乱码。

  - 扫描件最阴：解析器报成功但正文是空的，不能当成入库成功。

  - 切块要带着来源：来源字段给运营删旧用，章节路径给检索用，位置编号给取邻块用。

  - 向量化在流水线里出现两次：建库时每张卡片一条，提问时问题一条，必须同一个嵌入模型、同一套前缀约定。

  - 聊天模型和嵌入模型是两个产品两个标识：把聊天模型填进嵌入槽位会建库失败。

  - 各家嵌入接口的方言不同：有的走自有 HTTP 加字段，有的走通用兼容形状。

  - 通用兼容 SDK 的默认编码要显式指定：否则小数字数组会被当成字节解码，库里全是零。

  - 检索返回的是带分数、带来源的卡片列表，不是一句答案。

  - 提问时嵌入只返回一条向量；库里的行是已经存好的。

  - 检索的实现是全表读出来在进程里打分取前 K，库大了才换近似最近邻。

  - 检索做成工具还是写死：写死会让闲聊也去搜，做成工具由模型自己决定。

  - 库里没有就该弃权：材料区替换成「无可用材料」，系统提示强制说不知道，模型仍要把这句话生成出来。

  - 检索质量要量化：命中数、最高分、阈值、是否弃权、原因。

  - 四种弃权判定：只看第一名、逐条过滤、按平均分、最严的那条也要够。

  - 选只看第一名的理由：判定最简单、不浪费一次加法、给模型多一点上下文没坏处。

  - 两种失败通道要分开：加载失败是入库时的事，弃权是提问时的事。

  - 阈值不是通用及格线：换嵌入模型要重标定。

  - 维护频率表：文档变更走行级（按来源整份删旧再写入）、切块策略或嵌入模型变了才全量。

  - 只写入不删除是真实事故源：库里新旧并存，模型挑到过期的。

  - 答不准时的三种修法：行级、全量、不动库；先按症状选，不要一律重跑整库。

  - 四种「换」重建范围完全不同：换聊天模型不动库、换嵌入模型要整库重嵌入、改切块策略要整库重切加重嵌入、微调只动权重。

- 切块（Chunking）：太大丢细节、太小丢语义，重叠补边界。

  - 太大丢细节：一块塞三个主题，向量被平均掉，什么都像。

  - 太大还有第二个代价：塞进提示词的噪音多，模型可能抄错段落。

  - 太小丢语义之一：句子被腰斩，时限从四十八小时变成八小时。

  - 太小丢语义之二：指代断裂，「该期限自签收之日起算」单独成块后不知道指谁。

  - 大小的三种数法：字符、词元、汉字；英文教程里的数字按英文词元算，不能照抄到中文。

  - 大小要服从嵌入模型的单次输入上限：超了要兜底截断。

  - 大小和前 K 条乘起来才是材料量：受词元预算约束，两个要一起调。

  - 重叠的唯一目的：答案骑在切口上时给它第二次机会。

  - 重叠的经验值：块长的 10%～20%。

  - 重叠过大是信号：说明切法选错了，应该改成按结构切。

  - 重叠的代价：库变大、嵌入费用涨、前 K 条出现重复内容。

  - 重叠为零的合理场景：每块自己就说得通（问答对、一条政策一块、参数表一行）。

  - 固定长度切：简单、大小可控，但切口纯靠运气。

  - 按结构切：切口准、块自洽，但块大小完全不可控。

  - 递归切分是生产默认：结构优先，超长再降级，最后按字数兜底。

  - 按页切：为了页码这个元数据，代价是跨页段落被腰斩。

  - 语义切块：按相邻句子相似度掉落处切，代价是每个句子都要调一次嵌入。

  - 小块检索大块喂模型：两套粒度，小块负责搜得准、大块负责读得全。

  - 邻块扩展是便宜版：靠块编号取上下邻居，但邻居可能是别的主题。

  - 有些结构不能腰斩：表格、代码块、编号条款、有序列表；识别成原子块，宁可超长也不切开。

  - 标题继承救指代断裂：把章节路径拼到块文本开头，同时改善向量方向和可读性。

  - 判断切得好不好的四个维度：命中原文有没有半句话、内容纯不纯、最高分有没有提上去、前 K 条重不重复。

  - 只有同一个嵌入模型、只改切块参数时对比才成立。

  - 不同文档类型用不同策略：问答对、手册、法规、会议记录、扫描件各有一套。

- 余弦相似度：比的是方向，不是向量长度。

  - 公式：点积除以两个向量的长度。

  - 三种度量：余弦（看方向）、点积（不除长度）、欧氏距离（看落点距离）。

  - 同向不同长是核心对照：余弦并列第一，点积让长的赢，欧氏让长的最远。

  - 点积被长度收买：等于把「写得长」当成「更相关」。

  - 归一化：每个向量除以自己长度变成单位向量，之后点积等于余弦。

  - 归一化有两种：向量层归一化（除长度）和分数层归一化（min-max 或标准分），层不一样别混。

  - 语义近就是夹角小：同向接近 1，正交接近 0。

  - 反向很少到 -1：真实嵌入里「可以退」和「一律不退」是同一主题下的两种结论，不是 180 度。

  - 前 K 条是按余弦降序取的：不是等值查询。

  - 阈值弃权：最高分还很低说明几何上库里没有。

  - 分数不是概率、不能跨模型比：0.82 不是 82% 正确。

  - 近似最近邻只加速「找谁来比」，不改变「近等于夹角小」。

- 检索增强生成 vs 微调：知识常变或要引用就用前者，风格格式稳才考虑后者。

  - 选型一句话：事实和出处交给检索，口吻和习惯交给提示词或微调。

  - 三件事各管各的：系统提示加样例管习惯，检索管事实和出处，微调管深层领域反应。

  - 微调不能消幻觉，而且编得更像官方。

  - 微调灌知识的后果：手册一改模型还背旧的，还指不出出处。

  - 微调不能教新流程：把流程图切进去，模型仍会一次问完或跳步。

  - 进权重的东西当它删不掉：私密的不能往里放。

  - 数据形态不同：检索要陈述事实的原文，微调要「用户原话 → 理想答」。

  - 手册当微调数据，模型只学会复述手册；聊天记录当检索文档，检索会命中「好的亲」和一次性承诺。

  - 检索范例当样例不等于已微调：权重没动。

  - 聊天流程和闲聊不该硬检索：硬检索会把政策塞进闲聊。

  - 「该不该检索」有三种判断位置：工程师写规则、系统按分数算、模型自己回答要不要。

  - 混合：事实层和口吻层各管各的，改语料事实跟着变，换提示词口吻跟着变。

- 模块复盘

  - 四条怎么连成一条线：流水线是骨架，切块是取舍，余弦是尺子，选型是决定要不要用这条流水线。

  - 跨条最容易混的三条：RAG 不是长上下文优化版、前 K 条不是「有答案」、四种「换」的重建范围不同。

## 模块 09 · 检索增强生成进阶（RAG 进阶）

- 关键词检索与混合检索（BM25 / Hybrid Search）：关键词能补纯向量的短板。

  - 纯向量擅长换词，弱在编号、专名、必须逐字命中的字段。

  - BM25 是更聪明的查找：问三件事——这个词有没有、出现几次、这个词有多稀有、这篇有多长。

  - 词频会饱和：出现 50 次不会比 5 次强十倍。

  - 稀有度决定排序：常见词几乎不加分，罕见编号一配上就猛拉分。

  - 长文要打折：不然全文永远压过那一条规定。

  - 稠密检索与稀疏检索：前者每个维度都非零，后者只有出现的词有重量。

  - 混合检索是两边各自出榜再融合，不是先过滤一边再算另一边。

  - 加权融合要先拉齐刻度：余弦 0～1，BM25 十几到几十，硬加等于只听 BM25。

  - 倒数排名融合（Reciprocal Rank Fusion，RRF）：只看名次，`1 / (k + 名次)`，不用对齐刻度。

  - RRF 的代价：强度信息被抹平（第一名 0.92 和 0.51 对它一样）。

  - RRF 不是重排序：它合成两份粗名单，重排序是对一份名单再打更贵的分。

  - 按问句偏置：带货号的问句降低向量比重，日常说法提高。

  - 中文切词决定召回：连字符保留还是拆成单字，排名可以完全不同。

  - 切词只砸关键词通道：向量侧不受影响，但前提是没有「先关键词过滤再向量」。

  - 自己写三步 vs 接现成检索：小库自己写看得见分数，大库换的是倒排索引不是思想。

- 重排序（Rerank）：先粗召回再精排，不是一次前 K 条定生死。

  - 两阶段：粗召回从整库捞一批候选，精排只给这批重新打分排序。

  - 精排改顺序不换库不改问句：桌上没有的变不出来。

  - 双塔编码器（Bi-encoder）：问句和切块分开编码，比余弦，快但看不见「这一对」。

  - 交叉编码器（Cross-encoder）：问句和切块拼在一起跑，直接出相关分，准但慢。

  - 通用政策排第一的原因：双塔只看「两个方向近不近」，看不见「没拆」加「超过七天」这个组合。

  - 候选窗是天花板：正确切块不在桌上，精排再贵也没有它。

  - 两种失败要分开：没捞到，和捞到了但排错了。

  - 多塞二十条给生成 vs 先精排再塞五条：前者词元和噪音一起涨，模型仍抱着通用政策不放。

  - 三种分数不是同一把尺子：余弦、BM25、精排分不能硬加。

  - 三种打分形状：逐条打分、成对比较、整份名单重排。

  - 成对比较是相对判断：问「A 和 B 哪个更该回答这句」，不是再出两个分数。

  - 成对比较只解决「两条怎么比」，不解决「哪两条拿出来比」。

  - 选哪两条来比的三种策略：争议分数挑、前几名两两配对、冠军候选制。

  - 整份名单重排一次出新顺序：省调用次数，但吃上下文，而且模型可能编编号。

  - 整份名单重排必须校验编号：否则静默引用不存在的切块。

  - 什么时候可以不做精排：库很小、召回已经准、延迟或钱不够、评过发现没提升。

  - 精排叠在混合之后，不替代混合，也不替代查询改写。

- 查询改写（Query Rewrite）：用户口语往往不是好检索词。

  - 词汇鸿沟是根因：用户用词和库里用词不是一套，不是模型没读懂。

  - 改写发生在检索之前：把送进检索器的那串字对齐到库词。

  - 改写是整句换词，扩展是原句加补丁，两者都还是一条查询。

  - 假想文档嵌入（HyDE，Hypothetical Document Embeddings）：先让模型写一段「如果库里有答案，那段大概长这样」，再拿这段去做向量检索。

  - HyDE 补的是「形态」：问句是疑问句口语，库里是陈述段条款口吻，形态不对齐就靠不上。

  - HyDE 用余弦不用字面：假想段是模型编的，字面和真实切块不重合。

  - HyDE 产出是假的：只能当检索探针，不能展示给用户、不能当答案。

  - 多轮指代补全：残句要先补成独立问句再搜。

  - 谁负责什么：开发者负责准备输入（拼接、截断、格式、兜底），模型负责实际消解指代。

  - 模型是在猜：用最近原则、句法角色、主题连贯三条启发式猜。

  - 减少猜错的四个手段：历史截断、显式摘要、多候选带置信度、失败兜底。

  - 一句里两个问题要先拆成子问题：拆是检索前的改写，生成仍然只调一次模型。

  - 锚点问题句不要改写：货号、条款编号已经是检索锚点，改写会把主键改丢。

  - 锚点判定用规则不用模型：本地正则命中就跳过改写，主键不会丢。

  - 判定要集中在一个函数里：业务加新主键只改这一处。

  - 改写改偏是意图漂移：原句和改写句两份名单要并排看，能一键回退到原句。

  - 改偏怎么发现：靠对照、靠粗信号、靠多模型投票、靠离线命中率差，程序判不出语义漂移。

  - 人工介入的位置：最关键的是客服在检索后自查，能一键用原句重搜。

  - 检索用改写句，生成和界面用原句：内部探针不要冒充用户原话。

  - 改写失败要兜底：先尝试调改写，失败才回退原句检索。

- 切块与查询变体：四种手段各补哪类失败。

  - 父子切块：检索单位不是生成单位，小块搜得准、父块读得全。

  - 父块不进向量库：进去会被多主题平均掉，污染检索信号。

  - 同父去重：多个子块命中同一父块，父块只喂一次。

  - 邻块扩展是便宜版：靠编号取邻居，邻居可能是另一主题。

  - 情境检索：切块离开全文后丢了「这段在讲谁」，建库时让模型读全文写定位句拼在块前。

  - 情境嵌入和情境关键词索引是两回事：定位句也要进关键词索引，专名才对得上。

  - 标题继承和情境检索的差别：前者是程序拼路径，补不了封面里的公司名、季度。

  - 情境检索改的是库，不改用户问句：提问时照常。

  - 情境检索的成本在建库：每块调一次模型。

  - 多路查询：一条问句只打中一个语义邻域时，生成多条问句分别搜再合并。

  - 多路查询不是多次生成：一次模型调用返回多行，再多次本地检索、一次生成答复。

  - 一次调用返回多行更可能是同义改写：提示词按角度明确写会更稳。

  - 真不同角度要多次独立调用，成本成倍，多数场景不划算。

  - 多路查询和拆子问题不同：一个换说法覆盖邻域，一个切开两个独立意图。

  - 扩展救不了多邻域：一条查询补再多词还是一次打分。

  - 四种手段的适用边界：父子、情境、多路、扩展各对应一类失败。

  - 一次只加一个变量：同时开四个，变好了不知道谁起作用。

- 模块复盘

  - 四条怎么连成一条线：从底层粒度、入口改写、检索通道、名单顺序四层各补一刀。

  - 跨条最容易混的三条：精排补不了检索失败、改写不是给模型改问句、多路查询不是多次生成。

## 模块 10 · 记忆（Memory）

- 记忆分类：工作记忆、情景记忆、语义记忆、程序性记忆，外加短期与长期这根轴。

  - 铁律：任何记忆最终都必须变成上下文窗口里的字，否则等于不存在。

  - 模型自己没有记忆：权重推理时只读，「记得」是产品每次重发历史造成的。

  - 工作记忆：当前任务正在用的信息，容量小、生命周期短、读起来最快。

  - 情景记忆：带时间和场景的经历，记的是「一件事」不是「一个结论」。

  - 语义记忆：脱离场景也成立的事实，可更新、可覆盖、可删除。

  - 用户记忆是语义记忆的子集：关于用户本人的那部分事实。

  - 程序性记忆：怎么做事的方法和规则，通常常驻，不靠检索。

  - 短期与长期不是第五类：它们是另一根轴，回答「活多久、存在哪」。

  - 判定口径：杀掉进程再起来还在不在；在就是长期。

  - 情景记忆横跨两侧：本轮工具失败是短期情景，写进长期库的那条工单是长期情景。

  - 四类串成一次请求：程序性常驻、核心画像常驻、本轮经历按问句召回、对话历史累积。

  - 常驻说的是读取策略，不是同一个存储盒子：程序性和用户记忆必须分开存。

  - 不是所有长期记忆都按问句取前 K 条：条数少、几乎每问都要用的事实整份常驻。

  - 三类翻车：全塞进消息列表、全塞进向量库、把经历当事实、把事实当经历。

  - 记忆和检索增强生成的区别：数据主人、写入方、更新语义三条都不同。

  - 记忆和缓存的区别：缓存不改变答案，记忆改变答案。

  - 记忆和日志的区别：日志是原始流水，记忆是提炼结果；日志可以是记忆的原料。

  - 记忆和微调的区别：能变的、要隔离的、要能删的一律走外部记忆。

  - 写入侧三道把关：是不是事实、跨会话还有用吗、值不值得占存储。

- 写入策略：不是每句都存，要提取、要去重、要有过期。

  - 八关流水线：写入时机、提取、把关、去重、冲突更新、过期、压缩合并、安全审计。

  - 写入时机五种：每轮实时、后台异步、会话结束整段处理、离线批量、用户显式或模型自己调工具。

  - 后台异步的代价：有一个不一致窗口，刚说的话下一句召不到。

  - 提取两种做法：规则匹配和模型按固定形状输出。

  - 候选事实六个字段：稳定的键、事实正文、记忆类型、置信度、来源、有效期。

  - 没有稳定的键，覆盖就无从谈起：同一件事被起了三个键名就永远覆盖不掉。

  - 提取结果必须是数组且允许空：说「你好」抽零条是正常结果。

  - 同一段话可以同时产出语义事实和情景经历：两者后面的关卡完全不同。

  - 抽取粒度按「能不能独立变化」拆。

  - 把关五道：置信度阈值、内容维度三道、敏感信息过滤、人工确认。

  - 判定顺序是先置信度再内容维度：省一次模型调用，也避免对没把握的候选做不准判定。

  - 两道判定是独立的：置信度高不等于该写，置信度低不等于不该写。

  - 一次模型调用同时判三道内容维度：省词元、判据不漂。

  - 敏感信息过滤是独立的第四道：身份证、银行卡、健康状况即使是真长期事实也可能不该存。

  - 人工确认是三件事：置信度是输入、分档是机制、用户主动点是输出。

  - 三档分档是灰度区间：高的自动过、中的攒起来等人点、低的直接拦。

  - 去重四种：字面完全相同、同键不同值、措辞不同意思一样、新信息量更大。

  - 字面相同不做任何事：不要刷新更新时间，否则按时间排序会乱。

  - 措辞不同用嵌入相似度判断：查重用的是余弦相似度。

  - 「意思像不像」不管长度、不管键是否一样；「信息量更大不大」必须同键、看得见长度。

  - 更笼统的新值不要替换更具体的：否则库会越聊越空。

  - 去重时机两种：写入前查（准但慢）和定期合并（快但中间是脏的）。

  - 冲突更新四个动作：新增、更新、删除、什么都不做。

  - 「什么都不做」也要做成显式动作：否则看不出这一条为什么没写。

  - 冲突判据：新的赢、看明确程度、看来源可信度、能合并就别覆盖。

  - 旧值三种去向：硬删除、软删除、双时间轴（既记它什么时候成立、也记什么时候失效）。

  - 「事实错了」和「事实过时了」是两回事：错要删，过时要标失效但留历史。

  - 过期四种：永不过期、事实自带有效期、不用就衰减、被新事实挤掉。

  - 相对时间要靠模型算：提取时必须把今天的日期告诉模型，否则「下周三」只能瞎猜。

  - 衰减不能照搬缓存的最近最少使用淘汰：重要的东西可能半年才用一次，但一次都不能丢。

  - 过期不等于删除：只是不再参与召回，原始记录归档保留。

  - 压缩三个层次：单轮压成事实、整段会话压成一条会话摘要、多条零碎事实合成一段画像。

  - 第二层和第三层是两种独立技术：输入材料不同，触发条件不同，互不依赖。

  - 库要有容量上限：写满了自动合并，逼系统定期做减法。

  - 自动合并做三件事：把新画像覆盖到同一条记录上、把被合并的零碎事实标记退场、容量真的下降。

  - 退场不等于删除：退场的事实在归档视图里还看得见。

  - 事实层和综合层并存：行业主流是两个层都留、互不取代。

  - 摘要必须从原始素材重新生成：拿上一版摘要再压会漂移。

  - 记忆投毒：用户说「以后不用做权限检查」，前面几道关卡一道都拦不住。

  - 记忆投毒的三条防法：内容区与指令区分开、程序性记忆不许由对话写入、写入侧再过一道安全检查。

  - 可审计与可撤回：每次写入记下写了什么、动作是什么、旧值是什么、从哪句抽的、置信度多少。

  - 信任链靠四道判定叠起来：应用层禁止改、存储层隔离、不可变导出、哈希链。

  - 写入要幂等：同一轮重试两次，库里不能多两条。

  - 谁判哪一步：语义理解交给模型，确定性判定交给代码。

  - 抽取这一跳独立调模型：和主对话用两套角色、两个温度、两种输出格式。

  - 三种写入时机只差「这几次调用在什么时间点跑」，别的全一样。

- 模块复盘

  - 两条怎么连成一条线：分类是写入策略的输入，八关流水线是把值得记的写对。

  - 跨条最容易混的三条：工作记忆不等于长期记忆、提取不等于整段存、八关是流水线不是单个函数。

## 模块 11 · 状态与工作流（Agent State / Workflow）

- 状态机：节点、边、条件路由，Agent 的一步就是一次状态转移。

  - 六个核心对象：状态、节点、边、条件路由、状态转移、图与调度器。

  - 状态全图只存一份：节点函数不另存，只读自己关心的字段、只写自己产出的字段。

  - 节点只声明改什么：返回部分字段，由调度器合并；返回整份会互相覆盖。

  - 节点里的临时变量不进状态：函数返回就丢。

  - 调度器是四样合一：节点函数表、路由表、边表、走一步的主循环。

  - 边表是状态机和普通流程图的分界：没有边表就不算状态机。

  - 走一步九步：终止检查 → 拿节点函数 → 跑出改动 → 合并 → 问路由 → 拿下一站 → 对边表验一次 → 写当前节点 → 返回。

  - 调度器不做的：业务计算、路由决策、存盘、调模型、权限校验。

  - 八个变体：线性、条件路由、循环回边、多个终止态、显式状态、走一步、并行分叉、节点失败走边。

  - 条件路由要互斥也要穷尽：漏一种状态就掉进洞。

  - 循环回边要在状态里记次数：不记就是死循环。

  - 多个终止态：成功和失败都要画，漏画会发出两段打架的话。

  - 显式状态优于散落变量：散落的当下就对不齐，也存不住。

  - 走一步才算一步：一个按钮跑完全程就看不见转移。

  - 并行分叉：两个互不依赖的节点同时跑，都结束后进汇合节点。

  - 并行节点只写自己改的字段：都写整份会互相盖。

  - 有数据依赖的两站不能画成并行。

  - 图上的并行和同一圈多个工具调用不是一回事。

  - 节点失败是一条边不是把图摔死：写错误字段、走失败边、进程还活着。

  - 节点失败走边和业务回边再试不同：一个是这一站坏了，一个是结果为空再来。

  - 画法九步：写一句话任务 → 列站点（用动词） → 每站写清读什么写什么 → 有依赖的画先后 → 分叉写条件并查互斥穷尽 → 标终止 → 有环必须画退出 → 标入口和初始状态 → 用一张表验收。

  - 多能力 Agent 的三种编排：外层是大模型、外层是状态机、单 Agent 多工具。

  - 强依赖不能靠外层大模型自觉：必须画在状态机的边上。

  - 子图之间要有一份对外可见的总状态：否则子图互相读不到产出。

- 检查点与持久恢复（Checkpoint / Durable Resume）：状态要能序列化，恢复时不重复有副作用的调用。

  - 检查点是一次任务运行的完整快照：状态全文加当前节点。

  - 持久恢复是新进程用同一个任务运行编号读回最近一份完整快照继续走。

  - 可序列化的要求：只有纯数据能进检查点，函数、连接、数据流都不行。

  - 序列化的四种陷阱：函数被静默丢掉、空值字段被丢掉、日期变字符串、映射和集合变空对象。

  - 「序列化没报错」不等于「能安全恢复」。

  - 进程内映射不算持久恢复：名字里带记忆的检查点器也一样，杀进程就丢。

  - 恢复和从头再跑不同：恢复是从当前节点继续，从头再跑会重做副作用。

  - 写检查点的时机决定窗口：默认一整步完成后才写。

  - 四种杀进程时机：钱没扣、钱扣了检查点没写、检查点写完下一站没开始、写到一半。

  - 第二种最危险：恢复会再进那个节点。

  - 副作用不重做的三道保护：调度器跳过已做的、按工具调用编号去重、工具自身幂等。

  - 三道不是替代关系：只做第一道第二种时机扣两次钱。

  - 只读节点可以重跑：不必给只读工具也套一套幂等。

  - 一件任务运行一个编号：用户、会话、任务运行、HTTP 请求是四个不同的编号。

  - 会话内简化规则：新业务就是新编号，但有三个边界要警觉。

  - 三个边界：同一句话里有条件结构、上一件已经结束、长流程跨多次输入。

  - 终态之后开新业务三档做法：默认新编号、新编号加父引用、同编号暂停恢复。

  - 引擎只认最新一份完整快照：历史给人看，回滚有副作用风险。

  - 快照恢复和事件重放不同：重放会把副作用事件再执行一遍。

  - 半份文件必须当没写过：写临时文件再改名，或用事务。

  - 图改了旧检查点可能对不上：版本不一致要明确失败，不要猜着改名继续。

  - 检查点、记忆、上下文回答三个不同问题：这一趟到哪一站、跨会话还想用的事实、这一次请求里有哪些字。

  - 纯计算可重跑、有副作用的不能随便重跑。

- 人在回路（Human-in-the-loop）：哪些操作必须人点头才能继续。

  - 人机回圈不是弹个确认框：是把提议摊开，人承担决定，然后才执行。

  - 六个对象：人机回圈、待审批操作、等待人的节点、人的决定、危险操作策略、超时默认。

  - 必须停的判定只问一句：对外发生之后能不能收回，代价由谁承担。

  - 转账、删数据、发通知、改生产配置必须停；只读查询、内部草稿、可逆低代价不必停。

  - 灰色地带按「不可逆乘影响面」往必须停靠。

  - 「模型很有把握」不能当通行证：把握是生成质量，不是授权。

  - 停在执行前是唯一合法位置：先执行再弹确认是通知不是人机回圈。

  - 人的三种回法：通过、拒绝、改完再通过。

  - 改参数不等于批准：改和盖章是两下。

  - 谁决定要停：写死名单优先，阈值是加码，不能靠模型自觉。

  - 阈值能被拆成多笔绕过：要按同一单累计算。

  - 等人期间靠检查点活着：人和页面可能离开再回来。

  - 通过之后执行仍要走幂等三道保护。

  - 人通过不等于执行成功：渠道失败是节点失败，不是人拒绝。

  - 超时默认拒绝：「没人反对」不是同意。

  - 只在危险边停：每一步都问会让人对真正危险的那一下麻木。

  - 复核要发出去的内容仍然停在发送前：那是两个节点。

  - 人机回圈和检查点是两件事：检查点管「进程死了单还在」，人机回圈管「人没点头不能往下做」。

- 模块复盘

  - 三条怎么连成一条线：骨架（画图）、肌肉（持久恢复）、刹车（人点头）。

  - 跨条最容易混的三条：下一步去哪由模型还是由代码说了算、检查点存住不等于有人机回圈、杀进程不等于节点失败。

## 模块 12 · 模型上下文协议（Model Context Protocol，MCP）

- 协议架构：客户端与服务端，三种原语。

  - 两层：数据层管「说什么」，传输层管「走哪条路」。

  - 底层是 JSON-RPC 2.0：带编号的请求，配同一个编号的响应。

  - 三个角色：宿主、客户端、服务端；一个宿主对每个服务端各建一个客户端。

  - 客户端和服务端是一对一专线，不是一个客户端连很多家。

  - 大模型不直连服务端：模型只跟宿主说话，宿主按工具名路由。

  - 用户也不直连服务端：管子在宿主内部。

  - 三种原语按「谁有权决定用」分：工具由模型决定、资源由应用决定、提示词模板由用户决定。

  - 三种原语的方法：列清单再按类型调用。

  - 列表会变：服务端可以通知客户端再拉一次。

  - 服务端反过来问用户也是一种能力：方向仍是「服务端请求、宿主找用户」。

  - 「采样」这个能力在较新规范里已过时：需要调模型的那一方自己调。

  - MCP 不是另一种工具调用写法：模型侧仍然是模块 05 那一圈。

  - MCP 多解决的是工具从哪来、谁维护、换宿主还能不能用。

- 标准输入输出 vs 可流式 HTTP：本地玩具 vs 远程生产加按用户鉴权。

  - 标准输入输出：客户端把服务端当本机子进程拉起来，协议从标准输入进、标准输出出，日志走标准错误。

  - 标准输入输出不能往标准输出打日志：客户端会把日志当成坏掉的协议消息。

  - 客户端退出子进程一起结束：一根输入输出流对一。

  - 可流式 HTTP：服务端是独立进程对外一个 MCP 端点，每次 JSON-RPC 打一次 HTTP POST。

  - 可流式 HTTP 可以回 JSON，也可以回只属于这次请求的服务器事件流。

  - 本机用 HTTP 管子要只绑回环地址并校验来源头，防域名重绑定。

  - 远程必须鉴权：没令牌用 401，不要做成业务报错。

  - 过时的「HTTP 加服务器事件流」双端点写法不要再用：已被可流式 HTTP 取代。

  - 三种身份形态：环境变量、接口令牌、OAuth 2.1 加令牌受众校验。

  - 接口令牌能证明你知道密码，但一把共享令牌不等于按用户隔离。

  - 生产为什么不能停在标准输入输出：服务端不能住在员工笔记本里、进程生命周期不能绑在某个客户端、一根输入输出流接不了全公司、身份不能只靠环境变量、运维是 HTTP 服务那一套。

  - 这一节的演示必须成对：提供端和调用端都要有，否则讲不清「谁在提供、谁在用」。

- Skills 与规则文件 vs MCP：一个连工具，一个打包做法。

  - 一句话划界：MCP 给人「能访问什么」，技能和规则文件给人「按你们的店规怎么做」。

  - 技能是什么：一个文件夹，至少一份说明书，可带参考资料、模板、可选脚本。

  - 技能目录先给短目录：宿主先只看见有哪些技能、各干什么。

  - 规则文件和技能是同一层的两种打包形态：加载时机不同。

  - 规则文件常驻（每次打开项目就在），技能按需加载（任务相关才读进上下文）。

  - MCP 连上就常占上下文，技能按需加载省词元。

  - 官方对比：两者都要；一个技能可以编排多台服务端，一台服务端可以被多个技能用。

  - 三种「提示词」入口不同：服务端提示词模板、技能、这一轮的系统设定。

  - 工具描述只写「怎么正确调用这个接口」，店规写技能里。

  - 技能里的可选脚本不是 MCP 工具：没有发现协议、没有按用户鉴权、不能当标准接口复用。

  - 资源不是技能：资源是事实数据，技能是怎么用这些事实。

  - 做法知识做成假工具是最常见的错：模型以为执行了店规，其实什么都没发生。

  - 说明书不该整本塞进系统设定：问菜单也背着出杯全文。

- 模块复盘

  - 三条怎么连成一条线：协议结构 → 传输与鉴权 → 做法知识分桶。

  - 跨条最容易混的三条：MCP 不是工具调用升级版、接上工具不等于按店规做、系统设定不是制度库。

## 模块 13 · Agent 框架（Agent Framework）

- 框架解决什么：对照自己手写的循环和状态机，看它省了什么、藏了什么。

  - 三个词要拆开：省了、藏了、多了。

  - 省了：样板从仓库消失，改成一行配置或一个 Hook。

  - 藏了：物理事实还在，但默认不出现在你的业务文件里。

  - 多了：为了换运行时，要接受新词汇、新文件布局、升级绑定。

  - 框架不是新原理：想、调用、观察、状态转移还是那套。

  - 要对标的成熟产品：Vercel AI SDK 对偏对话和工具循环接前端，LangGraph 对偏有状态工作流加检查点。

  - 九个变体：循环样板、流式接前端、工具协议编排、状态调度和检查点、藏起来的默认策略、多出来的概念、锁定与升级、抽象不合适、框架解决不了的。

  - 藏起来的默认策略最危险：默认最大步数是 1 就会变成「带工具的一次问答」。

  - 工具失败被默默重试就会重复扣款：手写版要求幂等键，框架未必传得下去。

  - 抽象不合适时框架成为负担：简单问答硬套一套图等于用状态管理一个开关。

  - 框架挡你改循环：需要「失败就直接告诉用户不要喂回模型」就得关掉它的循环。

  - 框架解决不了的：产品判断、权限、人点头、过敏改推这些仍在你的代码里。

  - 两协议在同一出口下的差异：路径后缀、请求头、文本字段位置、思考字段位置、输出上限是否必填、思考怎么触发。

  - 各家思考的放法不同：有的写在正文里用标记包，有的单独放一个字段。

  - 通用 SDK 默认不读各家自加的思考字段：换 SDK 才能拆出来。

  - 换 SDK 要按厂商分流：一种 SDK 读标记，另一种读独立字段。

  - 端点拼接规则：通用形状的 SDK 自己带版本段，另一种要你手动补。

  - 浏览器侧可以完全一样：同一份拆帧和事件处理，差别只在上游。

- 状态图（State Graph）：用图表达工作流，和手写条件分支的差别。

  - 状态图就是模块 11 那四样换成框架的链式声明接口。

  - 节点函数一行都不用改：被换掉的是装配和调度。

  - 状态标注要显式声明每个字段的合并规则：因为要支持并行。

  - 边和条件边：固定一条路 vs 读状态临时挑。

  - 条件边的路径映射里没有这个键就报错——从「业务级拦截」变成「接口级报错」。

  - 编译是声明期和运行期的分界：静态检查节点重名、边指向不存在的节点、走不到的节点。

  - 运行与超级步：一次调用跑到结束，或每走一步吐一个事件。

  - 超级步可以同时跑多个节点：手写的「走一步」严格一站一站。

  - 检查点存储器和线程编号：每走完一个超级步写一次快照，同编号再调就接着走。

  - 副作用不重做仍是你自己的事：写盘发生在超级步之后，节点内部已扣款但这步没写完时恢复会重进。

  - 中断与恢复：节点里调中断，图当场停住并存快照；恢复时中断所在的节点会从头再跑一遍。

  - 递归上限：数的是超级步不是模型轮次，一个不调模型的节点也算一步。

  - 十个变体：线性、条件分流、回边循环、并行扇出扇入与归约函数、非法转移、检查点与恢复、中断与恢复、递归上限、子图、不该上图。

  - 并行不写归约函数会报错：手写版更糟，是静默丢一份。

  - 非法转移从「运行时拦」变成「压根画不出来」：但要业务级优雅收场得自己兜。

  - 子图：编译好的图当一个节点挂上去，同名字段自动传、不同名要自己翻译。

  - 不该上图的口诀：步骤和分支能提前画出来才上图，下一步只有模型临场才知道就留给模型循环。

- 当工具调用 vs 任务移交：调用方还在 vs 控制权换人。

  - 判据只有一句：用户的下一句进谁的对话。

  - 下一句仍进原来那个 = 当工具调用；下一句换人接 = 任务移交。

  - 当工具调用：另开一份消息列表跑子 Agent，交回一段结果，作为一次工具调用的返回值。

  - 用户和所有用户都只跟调用方说话。

  - 同一轮问两个专员还是当工具调用：并行版当工具调用。

  - 任务移交：当前 Agent 改成另一个，它直接对用户说话，原来那个不等返回值。

  - 模型侧长得像工具调用也可能是移交：运行时改的是「当前 Agent」。

  - 移交之后再交给下一个人：换的是当前 Agent，不是函数返回值。

  - 进线第一句就交给专员：还是用「下一句进谁」判定。

  - 移交和人在回路不同：移交是换成另一个模型继续，人在回路是等真人。

  - 主管派工人不是移交：工人交结果、主管对用户说话，属于当工具调用。

  - 六个变体：单次调用、并行多问、再移交一次、模型侧像调用运行时换人、进线分流、主管派活。

  - 选型对照：对外只要一个口吻用当工具调用、后面整段是另一门专业用移交、这一步会改数据时执行留在确认之后、子步骤失败要有人改口用当工具调用。

- Dify 等编排产品：体验即可，不当学习主线。

  - 编排产品是一个网站：配对话或拖流程图，帮你保存配置、接模型、跑起来、留运行记录。

  - 它把循环和状态收进自己的服务器：你交出去的是一份应用配置。

  - 三层对照：手写全在你文件里、代码框架仍在仓库里、编排产品在产品服务器里。

  - 九种藏法：智能体应用藏整段循环、工作流画布藏调度器和状态类型、聊天流把跨轮变量和当轮图叠在一起、回边画得见但执行不归你、大模型节点只调一次、条件分支只选边不做边表核对、代码节点只交一段、代码框架与产品在仓库边界上、人工方块不等于检查点。

  - 智能体应用：配人设和工具，产品自己转圈。

  - 工作流画布：节点看得见，变量看得见，调度器和状态类型看不见。

  - 聊天流：同一张画布跑多轮，会话变量活过单轮。

  - 回边：圈是你画的，执行权还在产品；次数上限要么用产品给的字段，要么你自己写变量。

  - 大模型节点只调一次模型：循环要么在智能体应用里，要么在你画的回边里，要么在专门的智能体节点里。

  - 条件分支和边表核对是两件事：产品拦不拦，要看这次运行。

  - 代码节点的局部变量函数返回就丢：要写进输出变量下游才读得到。

  - 这一趟的字段归这一趟：别写进全局配置，密钥也混进配置。

  - 有副作用、要人点头、要杀进程再起来：产品上的方块不能代替你自己的检查点和去重。

  - 拖一个知识库节点不等于 Agent 循环：知识库节点是检索那一跳。

- 模块复盘

  - 四条怎么连成一条线：同一条主线「编排产品替你藏了什么、你写的部分是什么」的不同切片。

  - 跨条最容易混的三条：画了不等于暴露、等点头不等于检查点、脑补产品会拦等于错。

## 模块 14 · 多 Agent（Multi-Agent）

- 主管模式（Supervisor）：谁分派、谁执行、怎么交还。

  - 星形分工图：中间的主管只负责分派，工人负责干活，干完交回主管。

  - 三句话对上：谁分派是主管、谁执行是工人、怎么交还就是工人把产出交回主管。

  - 客人的下一句仍然进主管：工人不接过「现在由我对客人说话」。

  - 主管的输出应该是下一个名字或者结束：不能一次回复里把所有产出都生成了。

  - 一次只派一个：用在后一步依赖前一步的时候。

  - 先拆开、能同时做的并行、再汇总一次：用在一批互不依赖的事情上。

  - 两种图不能混：先做菜单再做杯的那一杯不能走并行那张图。

  - 分层主管：主管只派小组主管，组内再派人。

  - 分层的原因是让主管的上下文里不堆组内原文。

  - 交还进共享状态：下一站读字段，原文留在产出它的那个工人那里。

  - 交还进工具返回值：工人另开一份消息列表，只交回一段文字。

  - 两种交还的差别在「下一站输入从哪来」，下一句都进主管。

  - 结束是主管的一个合法选择，和「选某个工人」并列。

  - 工人失败也走同一条交还边：对客人说话的人始终是主管。

  - 还要有最大轮次：主管每次都能找到工人时图会一直转。

  - 六个变体：一次只派一个、编排者-工人、分层主管、共享状态、工具返回值、结束与失败后再分派。

- 多 Agent 成本：多一次交接就多一轮词元，要有自己量出来的数字。

  - 账单只有两截：输入词元和输出词元；墙钟时间不在用量字段里，要自己记时刻。

  - 两套协议的用量字段名不同，但都是各加各的。

  - 有些厂商会另给一列表示命中了提示词缓存；没看到那列时，重复前缀按全价算。

  - 公平对照要锁住：同一个模型、同一句客人的话、同一份原始材料、同一个温度。

  - 对照不是「一次调用对多次调用」：单 Agent 也会调好几次，消息列表越来越长。

  - 四列对照：调用次数、输入词元、输出词元、墙钟时间。

  - 主管一次派一个的算法：每个角色各算各的，再全部相加。

  - 一个工人变短不等于总账变少：隔离省的是这一跳的原文，总账因为多了点名的人而变大。

  - 并行省的是时间不省钱：墙钟看最慢的一份，输入词元照样三份相加。

  - 打回重做是整圈入账：后一跳因为多了驳回字段而更长。

  - 分层多一层多一组系统提示词：那层也要进总账。

  - 两种交还的总账范围不同：工具返回值模式下，工人内部每一次仍要加进总账。

  - 三个最容易记错的：某一跳变短就当总账变少、主管模式就等于代理对代理协议、一次工具调用也升成一个代理。

  - 值得拆的两类理由：上下文要隔开、对方不在你进程里。

  - 过度设计的两种：客人只问一句今天有没有、那个能力只是一次调用。

- 代理对代理协议（Agent2Agent，A2A）：连工具 vs 连另一个代理。

  - 模型上下文协议连的是工具：给参数、拿结果。

  - 代理对代理协议连的是另一个代理：先发现它、再委派、再盯任务生命周期。

  - 客户端和远程代理两个角色：角色名里的「用户」常常是那个客户端代理。

  - 代理卡片：对方是谁、会什么、怎么连的一份 JSON 说明。

  - 卡片里有什么：名字说明版本、技能、支持的接口、能力、媒体类型、认证方式、签名。

  - 公开卡片和扩展卡片：登录后才看得到更多技能；公开卡片只写能公开的。

  - 三种找卡片的方式：约定网址、目录、事先写好的地址。

  - 约定网址是 1.0.0 版的那个后缀：旧文章里的那个后缀已经不对。

  - 两种合法回法：一条消息就结束，或者建一个有状态的任务。

  - 任务标识由服务端生成：客户端不能自己编一个去创建。

  - 上下文标识把相关任务归成一次办事：对方生成的要原样带回，别拆开猜。

  - 只带上下文标识不带任务标识：在已有上下文里新开一份任务。

  - 消息和制品是两件事：结果应该放在制品里，不是放在某条消息里。

  - 四种内容块：文字、结构化数据、文件网址、文件字节；一块里只能放一种。

  - 任务状态三类：进行中、被打断、终态；终态不能再收消息。

  - 两种被打断：需要输入等的是业务内容，需要授权等的是身份。

  - 需要授权时凭据走带外通道，不写进内容块。

  - 凭据到位后对方可以不再等消息就继续做，所以要订阅、推送或自己查。

  - 三种知道进展的办法：一直等到停、流式、推送通知；后两种要卡片先声明。

  - 推送可能重复到达：要认得出是自己发出去的那份。

  - 四种终态不能合成一句：完成是有成品，失败是没做成，取消是自己叫停，拒绝是对方不做。

  - 三个最容易错的：模型上下文协议和代理对代理协议是同一层、主管模式就是代理对代理协议、用了代理对代理协议就等于任务移交。

  - 边界：问一句就能做完的留在模型上下文协议；会自己循环、会反问、会交文件、又不在你进程里的才用代理对代理协议。

- 模块复盘

  - 三条怎么连成一条线：分工图、这本图的账、协议边界。

  - 跨条最容易混的三条：某一跳变短不等于总账变小、主管模式不等于代理对代理协议、一次调用也升成代理是过度设计。

## 模块 15 · 浏览器与桌面 Agent（Browser / Computer Agent）

- 无障碍树（Accessibility Tree）：给模型的页面摘要，通常比整页标记短、噪音少。

  - 浏览器里同时有三份东西：整页标记、文档对象模型、无障碍树。

  - 无障碍树是浏览器为读屏软件另算的一棵树：角色、可访问名称、状态、层级关系。

  - 很多节点不进这棵树：没有语义的包裹层、脚本、样式、隐藏的内容。

  - 无障碍快照是再收过一次的文本：缩进表示层级，一行一个节点。

  - 快照格式：角色、可访问名称、方括号里的状态。

  - 状态有哪些：已勾选、禁用、已展开、校验失败、层级、已按下、已选中。

  - 可访问名称的查找顺序：先找指向别处的标签引用，再是标签本身，再是关联的标签元素、按钮内文字、图片替代文字，最后才退到标题属性。

  - 占位符不可靠：字一填进去，占位符消失，这份名字也没了。

  - 测试用的快照模板和给模型的快照不是一回事：模板可以只写「这里有个按钮」。

  - 旧的页面无障碍快照接口已经删了：现在用新的无障碍快照接口。

  - 优先无障碍树的理由：词元省一个数量级、角色和名字稳定、不随样式变。

  - 影子树：组件暴露了角色就能按角色和名字点；没暴露就变不出来。

  - 只抽可见文字会丢角色：状态徽章和筛选芯片可以同名，一个该读一个该点。

  - 状态决定下一步：禁用、折叠、校验失败都要出现在当次快照里。

  - 同名控件要带定位信息：订单号或序号。

  - 点完必须重取快照：加载更多、弹窗、虚拟列表都让旧快照过期。

  - 取整页还是只取当前区域：对话框打开时只取对话框。

  - 内嵌框架是另一份文档：跨来源时父页面读不到。

  - 画布里的文字树上没有：旁边有表格就读表格。

  - 没有名字的图标按钮：树上就是三个没名字的按钮，分不清。

  - 截图只是补充通道：补树上没有的画面。

- Computer Use：比「只开浏览器」范围大，权限和风险更高。

  - 两个含义：具体的能力名，和一类产品形态；本条讲后者。

  - 和浏览器 Agent 的差别：范围、操作信号、精度、风险面、隔离方式、失败路径、可观测。

  - 浏览器截图只覆盖当前标签页，桌面截的是整桌或指定窗口。

  - 精度变了：按角色和名字点稳定，按坐标点脆。

  - 风险面完全不同：能读桌面所有文件、能改系统设置、能在已登录会话里代为签批。

  - 桌面无障碍接口和直接看像素是两条路：前者拿到的「是控件」，后者「是颜色块」。

  - 和机器人流程自动化（Robotic Process Automation，RPA）的差别：脚本化按步骤点 vs 模型每步自己决定。

  - 和视觉语言模型（Vision-Language Model，VLM）的差别：VLM 是看得懂的脑子，Computer Use 是加上手脚的整套系统。

  - 键入和文本编辑工具不是截图工具：拿到的结构化文本和命令输出。

  - 十个变体：范围、操作信号、隔离权限、点空、弹窗遮挡、敏感操作、上下文堆满、登录验证码、多显示器、审计打码。

  - 截图前后对比：用文字识别加视觉语言模型做差异比对，不靠「我看着差不多」。

  - 动作要幂等：点空后重定位再点，不重复点五次。

  - 上下文堆满：最近几张保留全图，更早的压成「关键状态」摘要。

  - 隔离：跑在虚拟机里，宿主桌面不暴露给 Agent，可以整体重置。

  - 敏感数据不进提示词和日志：密码、验证码、卡号。

  - 不代真人登录和代签批：只整理素材。

  - 审计三件：动作、时间、截图加描述，敏感字段打码。

- 模块复盘

  - 两条怎么连成一条线：同一条「看得见 → 操作信号 → 失败兜底 → 隔离与可观测」在两个范围的应用。

  - 跨条最容易混的三条：无障碍树不等于截图、网页不等于桌面、虚拟机不等于裸跑在自己的机器上。

## 模块 16 · 编码 Agent（Coding Agent）

- 产品形态：文件工具、命令行、版本控制加测试组成编码循环。

  - 五个能力块：文件工具、命令行工具、版本控制工具、测试运行、反馈循环。

  - 至少要有前三件：少了命令行改完没法验，少了版本控制改完没法回退，少了文件工具没法动手。

  - 后端产物是一圈工具配合推理跑下来的实际改动，不是一段话。

  - 反馈循环不是「生成 → 提一次交」，是「生成 → 跑测试 → 看错 → 改 → 再跑」。

  - 编码任务对上下文窗口不友好：几百行文件一次压进去，看完再改。

  - 命令行工具是双刃剑：必要（跑测试、装依赖）和危险（删库、强推、改全局配置）。

  - 底线是白名单加人在环路，不是把根权限给模型。

  - 规则文件不是模型上下文协议：一个用文档约束行为，一个给模型新工具。

  - 精准读和精准编辑是一对：读用查找定位再局部读，改用补丁只改几行。

  - 十个变体：产品形态、上下文注入、修改方式、反馈循环、命令行隔离、版本控制整合、规则文件与工具协议、工作区与沙箱、可回滚、人在环路。

  - 常见任务流：加单测、修安全漏洞、跨多文件重构。

  - 修复依赖漏洞不是盲目安装：要找齐所有引用点、替换、跑构建和测试、看差异、提合并请求。

  - 上线前要补一句：说了改了不等于仓库里真改了。

- 精确编辑 vs 整文件重写：为什么生产里要用补丁。

  - 精确编辑是粒度到「指定位置改成什么」；整文件重写是给一份全新的文件。

  - 关键差别：改 N 行只动 N 行周边 vs 改 N 行整篇重生成。

  - 整文件重写最大的代价不是错，是噪声：两百行改一行，差异里两百行都变了。

  - 成本和改动量不成正比：改一行加重写，等于两百行重新生成一遍。

  - 对上下文窗口双向不友好：先读整份再写整份。

  - 评审可读性：补丁六行一眼看出，差异两百行要先对比旧版。

  - 模型自己重写整个文件常顺手换风格：命名、错误处理写法、变量声明方式。

  - 整文件重写不是不能用：新建文件、文件很短、大段重写、配置文件。

  - 三种精确编辑形式：统一格式的修改片段、查找替换、按符号或类型的结构化操作。

  - 查找替换不等于统一格式片段：前者靠字面匹配，后者带上下文锚点。

  - 文件类型影响修法选择：JSON 和 YAML 对缩进敏感，Markdown 的列表有序无序，SQL 关键词大小写，类型声明不能丢。

  - 小模型更适合整文件重写、大模型相对稳。

  - 补丁和版本控制的配合：能直接应用、能精准回滚、冲突解决看上下文。

  - 精确编辑不等于结构感知：重命名符号是按抽象语法树做的，补丁多半按字面。

  - 工具能力有边界：有些模型只支持整份写入，不支持补丁。

  - 十个变体：修法选择、文件类型、改动量、验证方式、回滚能力、模型能力、符号重命名、合法场景、评审影响、工具支持。

- AGENTS.md 与技能：用文档约束行为，不是再写一套工具协议。

  - 规则文件是文档：告诉模型怎么干、能干什么、不能干什么。

  - 常见文件名：AGENTS.md、SKILL.md、.cursorrules、CONVENTIONS.md。

  - 规则文件和工具协议是分工：前者约束行为，后者扩展能力。

  - 规则文件能做：禁、规范格式、给工作目录、给文件改法、给提交信息规范；不能接工具、加新能力。

  - 规则文件与单次提示词：前者跟着仓库走，后者跟着会话走。

  - 没有规则文件等于每次开会重新对齐。

  - 加载时机：启动一次加载或按需触发。

  - 优先级：系统设定最高，仓库规则其次，用户消息最低。

  - 不分层的话，用户一句「这次别管规则文件」就直接覆盖禁区。

  - 三层叠加：仓库根、模块子目录、某个任务。

  - 典型规则文件里写什么：工作目录、修改文件、命令行禁区、版本控制规范、禁区。

  - 典型技能文件里写什么：某个任务的标准步骤。

  - 技能是任务说明书，不能当工具调用。

  - 规则文件里写命令行示例不等于真拦住了：那是模型自律，工程拦截要在包装层做。

  - 禁区写在工具描述里会被当成工具能力说明。

  - 规则改了但工程拦截没改，就脱节了。

  - 十个变体：文件名差异、作用范围、加载时机、优先级、内容形态、与工具协议分工、工程级与自律级、常见误区。

- 模块复盘

  - 三条怎么连成一条线：能力块决定能做什么、修改方式决定怎么动、约束决定被怎么管。

  - 跨条最容易混的三条：规则文件不等于工具协议、整文件重写不一定错而补丁不一定最优、跑测试通过不等于改对了。

## 模块 17 · Agent 评测（Agent Evaluation）

- 用模型当裁判（LLM-as-Judge）：用模型打分方便，但裁判自己也有偏差。

  - 三种形式：单模型打分、成对比较、多维度分别评。

  - 评测流水线的核心组件：跑数据集 → 模型输出 → 裁判评分 → 出数字报告。

  - 人工评贵、规则评只适合客观题、裁判评是中间形态。

  - 五种偏差：位置偏好、长度偏好、自我偏好、谄媚、顺序偏好。

  - 把裁判分数当客观真理 = 把这些偏差当真理。

  - 用裁判就要测裁判：人工抽检、标准答案集对齐。

  - 位置偏好怎么测：同一对随机换位置跑两次，看胜出比例差多少。

  - 标准答案集对齐：手标一批，算裁判分数与人工分数的相关性。

  - 多维度比压成单分更能看出哪儿变好哪儿变坏。

  - 成对比较适合难定绝对分、也适合判定「升级有没有真的升级」。

  - 规则题就别用裁判：检索命中、完全一致、关键字这些用规则更准。

  - 裁判模型的选择：用同家族模型评自己家族会偏，换不同家族。

  - 评分准则和少样本裁判让结果更稳：不然每次评分都飘。

  - 裁判不必等于标准答案的字面：让裁判严格字面匹配又贵又断。

  - 十个变体：打分方式、评分维度、偏差种类、校对方式、输入结构、规则与裁判的分工、裁判选择、评分准则、多维度、抽样成本。

- 轨迹评测（Trajectory Evaluation）：工具调对了没有、步骤是否跑偏，不只看最终答案。

  - 轨迹包含：调了哪些工具、填了什么参数、看完返回怎么决定下一步、走了多少步、有没有重复、每步的词元和耗时。

  - 和答案评测互补：一个看对没对，一个看怎么对的。

  - 同样答案可以走完全不同的路径。

  - 改提示词让答案对了，轨迹可能变差：答案对、过程贵。

  - 过程问题在生产里常常比答案问题更严重：多花词元、多花时间、可能调了不该调的副作用工具。

  - 五个过程指标：工具选择准确率、参数准确率、步数分布、循环检测、词元总成本。

  - 步数不是越少越好：复杂任务步数少可能跳过了关键验证。

  - 不同任务该调的工具不同：模板化的工具列表不通用。

  - 工具参数对才算过：工具名对但参数填的是原始用户文本，不算过。

  - 步数分布里尾巴那批要看：复杂还是绕路。

  - 循环检测：同一调用重复三次就是死循环信号。

  - 工具过度选择：任务只要查订单，多调了搜索、总结、翻译就是浪费。

  - 词元总成本：涨两个点准确率但词元涨三成，这升级不划算。

  - 有标准轨迹时用规则比：没标准轨迹时只能用裁判，而裁判看轨迹也有偏差。

  - 十条变体：评估维度、评估方式、轨迹来源、是否有标准答案、离线在线、轨迹类型、循环专项、词元预算、轨迹差异、裁判评测。

- 检索与答案三段评测：检索对了吗、回答是否只基于材料、答得切不切题。

  - 检索准确率评检索器；忠实度评生成有没有编；相关性评答案切不切题。

  - 检索准确率常用的量：命中率、召回率、平均倒数排名、归一化折损累积增益。

  - 忠实度是「每条事实能不能在材料里找到」，不是「事实对不对」。

  - 材料本身就错的时候，忠实度高但答案还是错的。

  - 相关性问「答得切题吗」，正确性问「答案字面对不对」：字面对但答偏，正确性高、相关性低。

  - 三类常见问题对应三项指标：召回差、编造、答非所问。

  - 只报一个分数就分不清是哪一段坏。

  - 检索增强生成评测的三项通常就是这三个。

  - 忠实度和上下文精确度不同：前者看用没用材料，后者看用得准不准。

  - 检索召回和嵌入质量不同：后者是检索器的一个零件。

  - 多跳检索：单一前一名不够，要更大的 K 和多个标准答案。

  - 三项独立报告，不合成综合分。

  - 十条变体：检索阶段指标、忠实度算法、相关性算法、多跳多模态、三项一起、标准答案集太小、升级前后对比、跨语种、指标与工具选型。

- 持续集成与上不上线决议：用同一份标准答案集出数字，再决定能不能上。

  - 持续集成在每次改动后自动跑评测流水线；上不上线决议拿数字决定合不合。

  - 关键件五样：标准答案集、基线数字、门禁、报告、上不上线决议。

  - 标准答案集必须固定：改了数据集基准就漂了。

  - 基线必须随每次合和上线更新：否则跟当前生产脱节。

  - 自动跑防止「忘了跑评测」：手动跑一定会忘。

  - 只跑评测不做决议等于数字没用上。

  - 硬拦下和软提示是两种门禁：硬拦下用错会把不重要的指标也挡下来。

  - 回归检测是「同一份数据集、同一个裁判、同一个脚本对比」。

  - 影子评测：新版本和线上版本并行跑，新版本不引流量。

  - 影子评测的好处是上线前一天看到真实效果，代价是跑两份很贵。

  - 裁判漂移：裁判换版后同一份数据集分数全变，要重新对齐基线。

  - 基线漂移和标准答案漂移是两回事：前者一段时间更新一次，后者不该动。

  - 多评测集分档：冒烟集快、回归集全、黄金集标答案。

  - 评测耗时长就要分层跑：合并请求阶段跑冒烟，合并后跑回归，上线前跑全量。

  - 十条变体：持续集成形态、门禁种类、标准答案集设计、报告输出、离线和影子、多评测集、基线更新、裁判漂移检测、评测集版本管理、失败处理。

- 模块复盘

  - 四条怎么连成一条线：答案评测、过程评测、检索答案三段评测、评测落地动作。

  - 跨条最容易混的三条：综合分掩盖分段问题、裁判分数不是真理、跑了持续集成不等于做了上不上线决议。

## 模块 18 · 可观测性（Observability）

- 追踪与跨度（Trace / Span）：一次 Agent 执行就是一条追踪，每步模型调用和工具调用是一个跨度。

  - 追踪是一次执行的完整轨迹，跨度是轨迹里的一个独立事件。

  - 一次 Agent 调用等于一条追踪；追踪里有 N 个跨度；跨度之间有父子关系。

  - 根跨度是整次调用，中间层是子 Agent 或链，叶子是模型调用和工具调用。

  - OpenTelemetry 是行业标准的追踪跨度协议；各家工具要么兼容要么自有，但语义一致。

  - 追踪编号在同一条追踪里共享，跨度编号各自唯一。

  - 跨度类型：模型调用、工具调用、链、检索、子 Agent。

  - 模型跨度记什么：模型、提示、回答、输入词元、输出词元、成本、耗时。

  - 工具跨度记什么：工具名、参数、结果、错误、耗时。

  - 追踪级别的元数据：用户、会话、环境、功能开关。

  - 追踪和日志不是一回事：追踪是结构化、有时间区间、有父子；日志是一条消息。

  - 成本记在元数据里：漏记词元就算不出钱。

  - 敏感信息必须脱敏：密码、卡号、身份证、令牌全暴露在追踪里就是数据泄露。

  - 脱敏三种手法：哈希、截断、完全不记。

  - 异常和追踪失败不是一回事：一个跨度出错不等于整条追踪失败，Agent 可能自纠。

  - 追踪编号串起来不等于时间戳对齐：用追踪编号串，不要用时间戳猜。

  - 生产环境要采样：全量追踪存储成本会爆。

  - 失败追踪要保采：事故现场恰好被采样掉就看不出问题。

  - 追踪要落库：只实时不持久化，事后复盘没数据。

  - 跨服务要传递追踪编号：传递标准是 W3C Trace Context。

  - 子 Agent 是嵌套跨度：整条追踪的词元和成本是所有跨度之和。

  - 十条变体：追踪协议、跨度层级、跨度类型、追踪关联、词元成本记录、脱敏、生产采样、跨服务、错误定位、持久化与实时流。

- 轨迹可视化：在工具里点到失败的那一步。

  - 主流工具：Langfuse、LangSmith、Phoenix、Helicone、OpenLLMetry，各自定位不同。

  - 四个关键件：层级视图、详情面板、过滤搜索、统计面板。

  - 比一行行扫日志快一个数量级：扫日志要靠时间对应，界面能直接点。

  - 生产端日志会被冲掉：界面持久化才能找回。

  - 跨会话和跨用户关联：界面是过滤和分组的事，日志难做。

  - 团队协作：产品看成本报表、开发看失败轨迹、支持看单个用户，各看各的视图。

  - 评测数据集联动：轨迹上标好或坏，自动进数据集，跑评测。

  - 评测和可观测不是两套系统，是一套。

  - 视图选择：树看父子关系，时间轴看并发和顺序。

  - 权限分级：支持人员只能看自己负责的用户。

  - 界面也要脱敏：后端脱了，界面里某些二次展示仍可能显示原文。

  - 十条变体：视图、过滤、聚合、实时与历史、数据集联动、团队权限、报警、脱敏、自建与商用、跨服务追踪。

- 模块复盘

  - 两条怎么连成一条线：协议是骨架，界面是界面；两件配套。

  - 跨条最容易混的三条：追踪不等于日志、界面也要脱敏、追踪跨度是事故定位能力不是性能问题。

## 模块 19 · 可靠性、成本与性能

- 熔断（Circuit Breaker）：连续失败就断开，半开探测，恢复后再接上。

  - 熔断是调用方主动切断对下游依赖：连续出错就不再真发请求，直接短路返回失败或降级结果。

  - 三个状态：闭合（正常发、统计失败率）、断开（不再真发、等冷却）、半开（放少量探测请求试水）。

  - 状态切换条件：失败到阈值进断开、冷却到期进半开、探测全成功回闭合、探测有失败重置冷却并回断开。

  - 一句话：熔断不是修下游，是保护调用方不再被拖死，让错误快速失败。

  - Agent 放大伤害的三条：重试循环天然存在、同步等待放大延迟、失败率传染、成本失控。

  - 和重试的区别：重试假设这次失败是临时的、马上再试；熔断假设下游已经病了、不再试。

  - 和限流的区别：限流保护下游不被打爆，熔断保护调用方不被拖死。

  - 和降级的区别：降级是失败时给一个次等但可用的结果，熔断是直接拒或走预设路径；熔断断开后通常搭配降级。

  - 和超时的区别：超时是单次请求的最长等待，熔断是一段时间内的整体策略；超时本身算失败，也是熔断的输入。

  - 和缓存的区别：缓存用旧值替代没失败但慢或贵的下游，熔断拒绝失败的下游。

  - 十条变体：状态机三态、触发判定策略、断开期快速失败与降级、半开探测策略、多级作用域、错误分类、与相邻机制协同、可观测、恢复策略、限流与配额。

  - 触发判定四种：连续失败计数、滚动窗口失败率、时间窗口失败数、复合（失败率加最小样本数，生产首选）。

  - 断开期必须立即返回：抛专门的错误、走降级、异步排队三选一。

  - 半开探测三种：单探测、批量探测、比例探测。

  - 进程内还是集中式：进程内简单快，100 个实例各自熔断等于请求量放大 100 倍；集中式能感知集群级失败率。

  - 错误分类：5xx、超时、网络错进计数；4xx 业务错、鉴权失败不进；429 单独通道按限流退避。

  - 协同四件套：超时、重试预算、降级、隔离。

  - 可观测：每次状态切换打结构化日志、暴露状态和次数和失败率三项指标、超阈值告警、给被短路的请求挂追踪标记。

  - 恢复策略：快恢复还是慢启动（按比例逐步放流量）。

- 提示词缓存（Prompt Caching）：重复的长前缀可以少花钱。

  - 缓存的是请求前缀的处理结果：下次相同前缀进来时复用中间状态。

  - 三条前提：只缓存前缀、一字不差才算命中、可以跨请求复用。

  - 价格三档：首次写入约 1.25 倍，命中读取约 0.1 倍，普通输入 1 倍。

  - 一句话：不是免费午餐，首次写要加价，读便宜到几乎是送的。

  - Agent 是高频高前缀重复的场景：系统提示稳定、工具定义稳定、长文档前缀、多轮归档。

  - 三个最常见的失败：没用缓存、缓存放错位置、系统提示每次都变。

  - 和上下文压缩的区别：缓存不改语义只省算力，压缩改语义省输入词元；两层一起才真省。

  - 和传统键值缓存的区别：键值缓存是请求内的，前缀缓存是跨请求的。

  - 和响应缓存的区别：前缀缓存缓存输入，响应缓存缓存输出；用户问题每次不同，响应缓存命中率低。

  - 和嵌入缓存的区别：嵌入缓存在检索层，前缀缓存在推理层。

  - 十条变体：只缓存前缀、长度边界、命中率口径、失效条件、适合内容、不适合内容、跨请求复用、价格模型与回本、实现机制、观察调试。

  - 长度边界：低于一千零二十四词元不计入缓存；上限另算。

  - 命中率口径：按总输入算，不是按写入量算。

  - 失效三种：自然过期、内容变、显式作废。

  - 适合放前面的：系统提示、工具定义、长文档开头、归档后的历史。

  - 不适合：用户问题、每次都变的系统提示、放在中间或末尾的稳定内容、太短的内容。

  - 跨用户复用各家不同：一家默认跨用户共享，一家默认不跨组织。

  - 回本点：同一前缀访问超过约十二五次才划算。

  - 实现方式：厂商托管（在请求里标缓存点）主流，不要自己造轮子。

  - 调试靠用量字段：命中率为零可能是过期、跨组织隔离、长度不够。

- 模型路由（Model Routing）：简单题走小模型，按任务总成本而不是单次单价算账。

  - 路由是按任务难度和预算给请求挑模型，由路由器决定。

  - 路由器三种：规则（关键词、长度、用户等级）、分类器（小模型先分类）、另一个大模型决策。

  - 模型分档：便宜档、主力档、旗舰档，价格差几十到几百倍。

  - 按任务总成本算：路由器成本加主调用成本加重试成本加降级成本。

  - 小模型重试五次可能比大模型一次答对更贵。

  - 和降级的区别：路由按难度选（省钱主动），降级按主模型挂了换（保命被动）。

  - 和级联的区别：路由是跑之前定好走哪个，级联是先跑小的看置信度再决定升不升。

  - 和模型集成的区别：路由只跑一个模型，集成跑多个投票。

  - 和上下文压缩的区别：路由换模型（省单价），压缩改输入（省词元）。

  - 和对比测试的区别：路由是生产决策，对比测试是找更好方案。

  - 十条变体：路由判定输入、路由策略、模型分档、降级边界、级联、任务总成本、延迟敏感场景、质量风险控制、可观测、动态调整。

  - 判定输入五种：任务分类、输入长度、用户等级、历史轮次、上一轮失败次数。

  - 三种策略的成本和准确度不同：规则零成本但会漏、分类器一次小模型调用、路由器一次大模型调用。

  - 质量风险两类代价：难题走小模型会答错，简单题走大模型是浪费，还有路由抖动让体验不稳。

  - 可观测字段：请求编号、路由策略、选了哪个模型、为什么选、路由器成本、主调用成本、总成本、是否降级。

  - 动态调整三种：灰度上线、对比测试、紧急流量切换。

- 模块复盘

  - 三条怎么连成一条线：熔断是底盘、缓存是输入侧省钱、路由是输出侧省钱。

  - 跨条最容易混的三条：路由不等于降级、缓存的是前缀不是中间段、成本按任务总成本算。

## 模块 20 · 人工智能安全（AI Security）

- 提示注入（Prompt Injection）：用户直接注入，检索到的文档里的间接注入。

  - 定义：让模型把「数据」当成「指令」执行的攻击。

  - 两种形态：直接注入（用户在输入里塞）、间接注入（第三方内容里塞）。

  - 核心机制：模型不像传统程序那样区分数据和指令。

  - 一句话：不是提示词写得不够好，是架构上把两者混在一起了，光改提示词防不了。

  - Agent 里外部内容进入上下文的四个口子：检索内容、工具返回、多模态输入、多轮历史。

  - 四个具体后果：客服工单里塞退款指令、知识库被投毒、邮件里塞转发指令、图片里藏指令。

  - 和越狱的区别：越狱是突破模型内置安全策略（内部），注入是外部内容变指令（外部）。

  - 和 SQL 注入的区别：注入对象和根因都不同，模型没有「参数化提示词」这回事。

  - 直接注入和间接注入的防御难度不同：间接注入是 Agent 时代的主要威胁。

  - 和提示泄露的关系：泄露是注入的子集或副作用。

  - 提示词防御和架构防御：架构防御才可靠，提示词只是门上贴张纸。

  - 十条变体：直接注入、间接注入、工具注入、越狱与注入的边界、攻击向量分类、数据流敏感点、缓解策略层次、输入清洗与输出校验、工具白名单与权限分层、检测告警。

  - 攻击向量六类：用户输入、检索内容、工具返回、多模态、第三方插件、文件内容。

  - 数据流敏感点：系统提示和工具定义可信；用户消息中等；检索内容、工具返回、多模态低。

  - 缓解策略四种：数据与指令通道分离、不可信内容包标记、多层系统提示夹住、工具调用走单独策略层。

  - 输入清洗五种：关键词黑名单、语义检测、输出校验、工具白名单、参数校验。

  - 工具调三层：模型决定调什么、策略层校验能不能调、执行层真调。

  - 检测告警四类：直接注入、间接注入、异常工具调用、异常输出。

- 服务端请求伪造与沙箱（SSRF / Sandbox）：能真发请求、能跑代码时的边界。

  - 服务端请求伪造是攻击者让服务器替自己发请求：绕过网络边界、拿云凭证、扫内网、读本地文件。

  - 触发条件是让模型决定地址：模型拼地址、服务器去请求、地址指向内网或元数据接口。

  - 沙箱是给用户生成的代码一个受限执行环境：文件系统隔离、网络隔离、资源限制、权限降级、审计日志。

  - 一句话：服务端请求伪造防「服务器被骗去请求」，沙箱防「服务器被骗去执行」。

  - 四个具体后果：云凭证泄露、内网未授权访问、沙箱逃逸、资源耗尽。

  - 和跨站请求伪造的区别：一个骗服务器，一个骗用户浏览器。

  - 和开放重定向的区别：一个是主动请求，一个是被动重定向。

  - 和容器的区别：沙箱是策略统称，容器是一种实现；容器默认共享宿主内核，逃逸是有名漏洞。

  - 和虚拟机的区别：内核独立、启动慢、隔离强、开销大；按敏感度分级。

  - 和权限分层的区别：沙箱是物理隔离，权限分层是逻辑控制，两者叠加。

  - 十条变体：本质是让模型决定地址、地址黑白名单、域名重绑定防御、沙箱层次选择、资源限制、文件系统隔离、网络出口策略、权限降级、审计追溯、异常检测告警。

  - 地址策略：黑名单弱、白名单强、混合最好。

  - 域名重绑定：解析时绑定地址、用内部域名解析、网络层禁止内网段。

  - 沙箱层次：进程级、容器、gVisor、Firecracker、虚拟机，五档按敏感度选。

  - 资源限制六项：CPU、内存、时间、磁盘、文件描述符、子进程数。

  - 文件系统隔离四种：只读白名单、可写沙箱目录、禁读敏感路径、根目录重定向。

  - 网络出口四种：允许列表、拒绝列表、域名限制、出站代理。

  - 权限降级四种：不用 root、能力降级、系统调用白名单、强制访问控制。

  - 审计五类：每次执行、每次文件访问、每次网络访问、每次系统调用、每次资源使用。

  - 异常检测五类：访问云元数据、访问内网段、访问敏感路径、资源使用异常、逃逸尝试。

- 工具网关与 OAuth 委托授权：执行前的策略层；用户身份不等于上帝钥匙。

  - 上帝钥匙陷阱：用一把长期有效的全权限密钥调所有下游工具。

  - 三个风险：全权限失守、用户身份无法隔离、撤销成本高。

  - 工具网关是在 Agent 和下游之间插一层策略网关：身份验证、权限校验、令牌转换、审计日志、限流配额、参数校验。

  - 委托授权流程：用户授权 → Agent 拿到用户访问令牌 → Agent 用自己身份加用户授权换出新令牌 → 用新令牌调下游。

  - 核心：用户令牌不直接给下游。

  - 一句话：工具网关是「调用前加一道策略层」，委托授权是「让用户身份和 Agent 身份正确分离」，两件一起才是身份基础。

  - Agent 与传统应用的差别：它代用户调下游。

  - 四个具体后果：上帝钥匙泄露、用户身份混淆、令牌长期有效、令牌直接转发。

  - 用户身份与 Agent 身份的区别：令牌类型、用途、在委托授权流里同时用不互换。

  - OAuth 令牌与接口密钥的区别：短期可撤销有范围 vs 长期全权限难撤销。

  - 工具网关与通用 API 网关的区别：后者不管「Agent 在代表谁」。

  - OAuth 2.0 与 2.1：推荐授权码加 PKCE，隐式流程弃用。

  - 令牌转发与委托授权的区别：转发是用户能调的 Agent 也能调（越权）。

  - 十条变体：上帝钥匙陷阱、工具网关拦截层、身份分离、委托授权流、令牌范围最小化、权限分层、审计追溯、令牌存储轮换撤销、跨服务身份联邦、模型上下文协议授权规范对接。

  - 范围最小化：发邮件一个范围、读订单一个范围、退款一个范围、删数据不该有范围。

  - 权限分层四档：普通用户、付费用户、管理员、Agent 自身没有独立权限。

  - 审计八字段：请求编号、哪个 Agent、哪个用户授权的、哪个工具、什么参数、什么范围、结果、花了多少钱。

  - 令牌生命周期：存在密钥管理服务、定期轮换、泄露立即撤销、必须有过期时间。

  - 跨服务身份联邦：每个下游有自己的授权服务器，Agent 在中间做转换。

  - 模型上下文协议的授权规范：OAuth 2.1 加 PKCE、范围声明、资源指示符、令牌轮换。

- 模块复盘

  - 三条怎么连成一条线：一根根因、两条危险面、一道统一防线。

  - 跨条最容易混的三条：注入和越狱、令牌转发和委托授权、沙箱和容器。

## 模块 21 · 后端与基础设施

- 流式被网关缓冲：默认可能攒满再发，流式会「卡住再一次性喷出」。

  - 服务器事件流是服务端主动推送的长连接协议，是模型流式输出的事实标准。

  - 问题是反向代理、网关、内容分发网络、平台默认缓冲响应。

  - 后果：三十秒没动静然后整段喷出，流式完全失去意义。

  - 触发条件：服务前有网关且默认开了缓冲。

  - 一句话：不是「长连接」就有用，是「边到边」才有用。

  - 四个具体后果：反向代理、内容分发网络、平台网关、内网代理。

  - 各平台默认值不一样：有的默认关、有的默认开。

  - 和双向通信的区别：服务器事件流是单向、普通 HTTP 协议、对代理友好。

  - 和长轮询的区别：长轮询要反复发请求，延迟高。

  - 响应缓冲开关和缓存开关是两个独立开关：只关缓存流式照样卡。

  - 加速标头和缓存标头管的是不同人：加速标头只对某个反代，缓存标头对所有代理但管的是缓存不是缓冲。

  - 内容分发网络缓冲要逐节点关，每个边缘节点默认值还不一样。

  - 十条变体：协议本质、网关默认缓冲、关缓冲的配置、边缘节点缓冲、平台缓冲、响应头约定、健康检查、长连接超时、断流监控、跨代理链路。

  - 响应头三件：内容类型、缓存控制、加速标头。

  - 健康检查四种：命令行加不缓冲参数看分块到达时间、浏览器开发者工具看是不是分块响应、服务端打时间戳、统计首字延迟。

  - 判断标准：第一个分块应该在 1～3 秒到，不是 30 秒。

  - 长连接超时：默认六十秒读超时，长任务会中途断；三个超时都要调到一小时以上。

  - 监控四项：首字延迟、平均分块间隔、流式成功率、断流位置分布。

  - 跨代理链路：浏览器、内容分发网络、反向代理、应用，每一层都可能缓冲，漏一层就卡。

- 任务队列（Task Queue）：长 Agent 不要占着 HTTP 请求不放。

  - 任务队列把「提交任务」和「执行任务」解耦：提交后立刻拿到任务编号，后台慢慢做，客户端按编号查进度。

  - 为什么不能同步：浏览器可能无限等、反向代理六十秒断、平台限时强杀、用户耐心只有几秒。

  - 五件：生产者、队列、工人、状态存储、客户端。

  - 四个具体后果：同步超时、客户端刷新导致重复提交、服务器被长任务堵死、没有重试机制。

  - 和消息队列的区别：任务队列是执行任务、追踪详细；消息队列是通信、多主题解耦、通常不追踪。

  - 和流式输出的区别：任务队列延迟高但适合长任务；流式首字快但适合短任务。

  - 和定时任务的区别：定时是定时触发，队列是不确定何时触发。

  - 轮询和推送的区别：轮询简单、延迟高；推送实时但实现复杂。

  - 自托管队列和托管队列的差别：要不要多维护一层存储。

  - 十条变体：同步异步根因、队列选型、任务状态机、进度轮询、推送、幂等性、重试策略、优先级队列、死信队列、监控告警。

  - 选型五种：BullMQ、Celery、Sidekiq、SQS、发布订阅。

  - 状态机五态：待处理、执行中、完成、失败、重试后仍失败进死信。

  - 状态必须存到磁盘，不能只在内存。

  - 进度轮询两种节奏：固定间隔和指数退避。

  - 幂等三种：天然幂等、业务幂等（带幂等键）、状态机幂等（只能从某状态转到某状态）。

  - 重试策略四项：指数退避、最多次数、可重试错误、不可重试错误。

  - 优先级三档：高（付费用户）、中、低（后台批处理）。

  - 死信队列是兜底不是垃圾桶：需要人工查。

  - 监控五项：队列长度、任务延迟、任务时长、失败率、死信队列长度。

- 对象存储与基于角色的访问控制（Object Storage / RBAC）：上传文件不进数据库大字段；角色决定能调哪些工具。

  - 对象存储是专门存海量文件的系统：容量无限横向扩展、成本低、访问走 HTTP 接口、不挂载文件系统。

  - 和文件系统、数据库大字段、缓存分发网络的对比。

  - 基于角色的访问控制是用户到角色到权限三层。

  - 四个具体后果：文件落数据库大字段把备份撑爆、文件放服务器磁盘把盘占满、所有人能退款、角色写死在代码里。

  - 和文件系统的区别：接口协议、挂载方式、容量、适用场景。

  - 和缓存分发网络的区别：源站和加速层，组合是标准做法。

  - 公网桶和私有桶的区别：私有桶必须用签名地址。

  - 基于角色和基于属性（RBAC / ABAC）的区别：简单场景用角色，复杂合规用属性。

  - 接口层、工具网关、数据库行级三层权限必须叠用。

  - 十条变体：文件存储本质选择、对象存储落地、前端直传、访问控制、加速加签名、元数据与检索、三层模型、决策点、多角色合并、审计日志。

  - 三种存储对比：数据库大字段适合很小、对象存储适合任意大小。

  - 落地选型：S3、OSS、七牛、Cloudflare R2、自建 MinIO。

  - 前端直传主流：后端只生成签名地址，文件直接从浏览器到对象存储。

  - 签名地址三个参数：有效期、方法、路径。

  - 元数据与标签的区别：元数据是自定义键值对，标签是存储系统内部的索引键。

  - 三层模型核心表：用户、角色、权限，加两张多对多关联表。

  - 决策点三层：接口层决定端点能不能调、工具网关决定工具能不能调、数据库行级决定数据能不能看。

  - 多角色权限合并：多数场景取并集，也可以取交集或拒绝优先。

  - 审计六字段：谁请求的、当前角色、申请什么权限、通过还是拒绝、操作哪个资源、时间。

- 模块复盘

  - 三条怎么连成一条线：响应层、异步层、资源层加权限层，三道边界防线。

  - 跨条最容易混的三条：缓冲开关和缓存开关、任务队列和流式输出、对象存储和文件系统。

## 模块 22 · 全栈产品化

- 流式 Markdown：边到边渲染会闪，标题和列表会跳动。

  - 核心问题是不完整语法导致解析抖动：模型一个字一个字吐，每次来都可能改变 Markdown 的语义。

  - 标题、列表、加粗、代码块、链接五种典型闪烁。

  - 性能问题：每个分块都全量重新解析并重新渲染，复杂度是平方级。

  - 四个优化方向：增量对比渲染、不完整语法用占位符、缓冲若干字符再渲染、只在换行时重新解析块。

  - 和流式纯文本的区别：前者会闪、解析和渲染两步。

  - 和一次性渲染的区别：首字延迟。

  - 和朴素重渲染的区别：平方级对线性级。

  - 和 HTML 解析器的区别：Markdown 是上下文敏感的、不闭合难处理。

  - 和流式 JSON 的区别：JSON 必须成对才合法。

  - 十条变体：根本问题、朴素重渲染代价、五种闪烁场景、占位符、缓冲、换行触发、库选型、增量对比渲染、虚拟滚动、性能指标。

  - 库选型：专门为流式设计的库对流式最友好，通用库要自己包装。

  - 虚拟滚动：几千字不全部渲染在页面里，只渲染可视窗口。

  - 性能指标五项：首字延迟、首屏渲染、闪烁次数、帧率、CPU 占用。

- Agent 步骤界面：思考中、正在调工具、完成，要让人看懂 Agent 在干什么。

  - 把执行轨迹结构化展示给用户，核心是三状态：思考中、调工具中、完成。

  - 三个层次：思考完成、调工具中、未开始，加上流式输出。

  - 四个具体后果：Agent 卡住被误判、Agent 答错无法解释、开发调试困难、用户不信任。

  - 和流式界面的区别：离散步骤对连续文本。

  - 思考中的界面做法：转圈加文案、流式未完成文本、动态短语。

  - 调工具中的界面：工具名、输入参数、等待提示。

  - 完成的界面：最终结果加元信息（耗时、词元、成本、工具调用次数）。

  - 折叠和隐藏的区别：折叠保留内容，隐藏丢掉内容。

  - 轨迹可视化和日志的区别：一个给用户和客服看，一个给开发排查。

  - 十条变体：三状态可视化、思考中界面、调工具中界面、完成界面、步骤折叠、错误态、流式与步骤并存、轨迹可视化、可交互步骤、无障碍。

  - 步骤区显示过程，流式区显示结果，两区分开。

  - 错误态：错误码、错误描述、重试按钮。

  - 可交互步骤四种：展开参数、重试此步、从此步继续、编辑后重跑。

  - 无障碍：屏幕阅读器实时区域、所有步骤可键盘聚焦、回车展开或重试、颜色对比度达标。

- 模块复盘

  - 两条怎么连成一条线：过程层和结果层两个层。

  - 跨条最容易混的三条：流式 Markdown 不等于流式纯文本、步骤界面不等于流式界面、折叠不等于隐藏。

## 模块 23 · 生产级 Agent 架构（Production Agent Architecture）

- Agent 运行时（Agent Runtime）：网关、鉴权、循环、工具、队列、观测、评测怎么叠在一起。

  - 是把前面所有模块的能力叠成一条完整链路，不是某一个工具。

  - 六层链路：接口网关、异步层、Agent 循环层、工具网关层、下游服务、观测层。

  - 每层做什么不做什么、关键取舍是什么。

  - 四个具体后果：能力凑不齐、观测缺失、评测脱节、架构混乱。

  - 和框架的区别：运行时是把能力叠起来（部署加集成），框架是帮你写 Agent（开发）。

  - 同步与异步链路的选择：按预期时长超过六十秒切异步。

  - 鉴权与用户身份传递：用户编号从网关到 Agent 再到工具，丢了就是跨用户泄露。

  - Agent 循环五维控制：最大轮次、单步超时、总超时、词元上限、重复检测。

  - 工具网关集成：五维校验。

  - 多模型路由集成：按难度选模型，主挂了自动降级。

  - 三类缓存集成：前缀缓存、嵌入缓存、键值缓存。

  - 观测三件：追踪跨度、指标、结构化日志。

  - 评测门禁：改动代码就跑标准答案集，不达标拒绝合并。

  - 全链路压测四个场景：百并发、千长任务、流量突发、工具慢返回。

  - 十条变体：完整链路架构、同步异步边界判定、鉴权与身份传递、循环控制、工具网关集成、多模型路由集成、缓存集成、观测层、评测门禁、全链路压测。

- 容量与成本估算：用自己项目的词元数外推一千日活。

  - 意义是把「现在能跑一百次」外推到「一千日活时一个月多少钱」。

  - 三块成本：模型接口占六到八成、服务器占一到两成、存储加观测占半成到一成。

  - 外推公式：月成本等于单次任务成本乘每人每日调用次数乘日活乘三十。

  - 单次任务成本包括输入词元价、输出词元价、工具调用成本、重试降级额外成本。

  - 四个具体后果：融不到资、定价错误、算错容量、算错成本。

  - 每秒请求数与并发数的区别和换算关系。

  - 单次成本与总成本的区别：真实生产有重试降级重投，总成本约是单次的一点五到两倍。

  - 日活、月活、同时在线的用途与关系。

  - 平均与峰值的倍数关系：峰值是平均的三到五倍。

  - 毛利率与净利率的差别。

  - 十条变体：单次任务词元模型、日活到每秒请求数推导、成本外推公式、三大成本项拆分、高峰冗余、按用户分摊、毛利率估算、不确定性区间、规模上限触发器、成本看板。

  - 区间估算：用乐观中性悲观三档给决策者留弹性。

  - 触发器四项：每秒请求数超七成容量、延迟九分位超三秒、成本超预算八成、失败率超百分之五。

  - 看板五项：每日模型成本、每日调用次数、单次平均成本、按用户分摊、毛利率。

- 应用交付标准：说明文档、架构图、数据流、选型取舍。

  - 把每个子文件夹当作一个完整可交付的小项目：打开说明文档就能跑，不看资料能讲清一次请求怎么走。

  - 说明文档十个必备字段：名字、端口、启动命令、数据流图、选型理由、环境变量、依赖关系、常见故障、日志位置、健康检查。

  - 一句话：打开说明文档就能跑，不看资料能讲清。

  - 四个具体后果：找不到入口、跑不起来、讲不清设计、交接失忆。

  - 和小节文档的区别：读者、重点、形式。

  - 数据流图和架构图的区别：粒度和焦点不同。

  - 选型理由和优缺点的区别：选型理由是可执行的取舍。

  - 环境变量和配置文件的区别：密钥不能写进配置文件。

  - 依赖、端口、启动各回答一个问题。

  - 十条变体：说明文档必备字段、数据流图模板、选型理由模板、环境变量清单、启动命令三步、日志位置与健康检查、常见故障排查、依赖关系图、选型对比表、交付清单。

  - 选型理由模板：每个选型至少两个备选加取舍。

  - 启动三步：装依赖、类型检查、启动。

  - 故障排查五种：端口占用、密钥错、数据库连不上、依赖装不上、类型检查错。

  - 交付清单十条。

- 项目复盘：每个项目最难的三点、怎么解的、若重做改哪三处。

  - 复盘不是讲做了什么，是讲卡在哪、怎么解的、若重做改哪三处。

  - 完整等于代码能跑加说明文档有；复盘等于下次做类似项目快一半。

  - 三问模板：最难的三点、怎么解的、若重做改哪三处。

  - 四个具体后果：三个月后看不懂、同事接不住、重复踩坑、不知道自己进步了。

  - 和入门指南、选型文档、模块复盘的区别。

  - 诚实复盘和自我吹嘘的区别。

  - 若重做和全部推翻的区别。

  - 十条变体：三问模板、每个项目都填、横向对比、可复用模式、一次性做法清单、诚实度自检、复利、文档结构、写作时机、团队分享。

  - 横向对比能找出反复出现的难点。

  - 可复用模式：流式响应、状态机、重试退避、错误态降级、人在环路。

  - 一次性做法清单：特定工具的结构、特殊解析、硬编码的业务规则。

  - 复盘文档六节结构。

  - 复盘的复利：第一个项目三小时、第五个一小时、第十个半小时。

- 原理串讲：用自己项目里的例子讲清词元与上下文、工具调用、Agent 循环、检索增强生成、模型上下文协议。

  - 五大原理各自对应哪个模块和一句话定义。

  - 串讲链路：词元上下文提供基础、工具调用扩展能力、Agent 循环做多步编排、检索增强生成配合外部知识、模型上下文协议提供统一协议。

  - 核心：任何一环断，整条链路就不工作。

  - 四个具体后果：面试讲不清、调试失忆、架构混乱、团队沟通成本高。

  - 十条变体：串讲意义、词元与上下文、工具调用协议、Agent 循环机制、检索增强生成流程、模型上下文协议规范、词元到工具到循环的链路、检索到协议的链路、缺一环的后果、原理与工程双视角。

  - 五组易混：原理与工程、词元与上下文、工具调用与函数调用、Agent 循环与推理-行动模式、检索增强生成与嵌入。

  - 缺一环的五个后果：上下文超限、工具调错、循环失控、召回低、接入混乱。

  - 原理和工程两个视角都要：机制怎么走加用什么实现。

- 独立系统设计：给定约束能画出架构，并标出评测、观测、安全、成本。

  - 约束四要素：业务目标、用户量级、预算上限、上线时间。

  - 缺这四样等于没开始设计。

  - 四个具体后果：面试压顶、创业失败、团队协作困难、技术债。

  - 十条变体：约束四要素、约束到选型到架构的流程、七大关键决策、架构图模板、风险标注、成本估算、可观测设计、评测设计、方案对比、完整设计文档模板。

  - 七大关键决策：同步异步、单模型多模型、单租户多租户、直连工具还是网关、没有检索增强生成、没有模型上下文协议、自建还是用现成服务。

  - 风险标注四类：可靠性、安全、性能、成本。

  - 可观测七个记录位置：接口网关、Agent 循环、工具网关、模型接口、异步队列、数据库、观测层。

  - 评测设计五类：标准答案集、模型裁判、轨迹评测、检索增强生成时加忠实度、持续集成拦截。

  - 方案对比至少两套备选加取舍。

  - 完整设计文档十节结构。

  - 架构设计与详细设计的区别、风险标注与测试用例的区别、方案对比与直接选的区别、生产级与演示级的区别。

- 模块复盘

  - 六条怎么连成一条线：骨架、数字、工程落地、经验、认知、应用，缺一层整体就不完整。

  - 跨条最容易混的三条：运行时不等于框架、路由不等于降级、项目复盘不等于模块复盘。

  - 二十四模块的完整路径：基础、能力、扩展、协作、质量、生产六段。

## 附：全课程贯穿的主线（总结）

- 词元是单位，上下文窗口是容器：所有计费、截断、预算、裁剪都建立在这两个词上。

- 工具调用是 Agent 能力的起点：没有它，Agent 只会说话；有了它，才谈得上多步编排。

- Agent 循环是多步的骨架：想、做、看三阶段加上停止条件，构成了「会自己往前走的程序」。

- 检索增强生成解决「模型没见过」：外部知识外挂进来，改文档就改库，不改权重。

- 记忆解决「跨会话」：上下文窗口一关就没了的东西，要靠外部存储记住，并讲清写入、读取、更新、过期四件事。

- 状态机与工作流解决「业务规定的步骤」：下一步去哪由代码说了算，不是模型即兴。

- 模型上下文协议解决「怎么接外部能力」：工具、资源、模板三种原语加标准发现和鉴权。

- 评测解决「上线前能不能上」：答案、过程、检索三段分开评，数字接进门禁。

- 可观测解决「上线后出了事怎么查」：追踪和跨度给出定位能力，脱敏给出安全底线。

- 可靠性成本性能解决「上线后撑不撑得住」：熔断兜住失败、缓存和路由压住成本。

- 安全解决「能代用户做事之后的安全底线」：数据与指令分离、请求与执行有边界、身份与权限不混。

- 后端基础设施解决「别人能访问到」：流式不被缓冲、长任务不占死连接、文件不进数据库大字段。

- 全栈产品化解决「用户看懂」：过程透明加结果稳定。

- 生产架构解决「整体能扛事」：把前面所有能力叠成一条链路，并给出数字、风险、观测、评测。
